# Аудит качества проекта Mega CRM

**Дата:** 2026-07-27
**Объект:** Mega CRM v1.0 MVP
**Источник:** внешний аудит (ChatGPT Sol), предоставлен владельцем проекта
**Статус:** первоисточник требований для milestone production hardening

**Области проверки:** архитектура, backend, worker, PostgreSQL, Redis/BullMQ, SendGrid, multi-tenancy, безопасность, аналитика, frontend, тестирование и эксплуатационная готовность.

---

## 1. Итоговая оценка

Общее качество реализации: **7,5/10**
Функциональная готовность MVP: **8,5/10**
Готовность к production-нагрузке: **6/10**

Проект написан заметно лучше среднего AI-generated MVP. Архитектура в целом последовательная, код разделён на модули, используется строгая типизация, реализована большая часть заявленной функциональности, присутствуют RLS, очереди, шифрование ключей и значительное количество тестов.

Полная переработка проекта не требуется. Нужен отдельный этап production hardening.

Главный вывод: проект функционально готов, но пока недостаточно устойчив к сбоям SendGrid, конкурентной работе нескольких тенантов, росту базы, смене партиций и production-инцидентам.

## 2. Проверенные положительные стороны

### Архитектура

- Монорепозиторий разделён на API, worker, web и общие packages.
- Fastify, Drizzle, BullMQ и React применены по назначению.
- Triggered- и broadcast-письма находятся в отдельных очередях.
- Большая часть межпроцессных данных описана общими TypeScript/Zod-схемами.
- Delivery pipeline не смешан напрямую с HTTP API.
- Tenant ID присутствует в основных предметных таблицах.

### Multi-tenancy

- Для 22 таблиц включены PostgreSQL RLS и `FORCE ROW LEVEL SECURITY`.
- Tenant context устанавливается внутри транзакций.
- Большинство запросов дополнительно ограничивается workspace ID.
- SendGrid-ключи хранятся в зашифрованном виде.

### Безопасность

- Реализовано envelope encryption для SendGrid API keys.
- SendGrid webhook проверяется по исходному телу запроса.
- Используются Helmet, CORS и API rate limiting.
- Ключи не возвращаются пользователю в открытом виде.
- Основные входные данные валидируются через Zod/Fastify schemas.

### Тестирование

На момент проверки:

- сборка проходит;
- 91 тестовый файл;
- 526 тестов проходят;
- отсутствуют падающие тесты;
- покрыты основные API-модули, очереди, аналитика и tenant context.

### Документация и GSD

- Milestone v1.0 содержит 7 завершённых фаз и 96 исполненных планов.
- 49 из 49 требований MVP отмечены как реализованные.
- Присутствуют phase verification, security, validation, review и UAT-артефакты.
- `SPECIFICATION.md` подробно описывает фактическое состояние системы.

## 3. Блокирующие production-риски

### 3.1. Один тенант может затормозить отправку остальных

В обоих email workers вызывается глобальный механизм BullMQ:

- `apps/worker/src/queues/email-broadcast.worker.ts:27`
- `apps/worker/src/queues/email-triggered.worker.ts:24`

`worker.rateLimit(...)` ограничивает worker целиком, а не конкретного тенанта. Если tenant A исчерпал лимит своего SendGrid-ключа, обработка заданий других тенантов также может остановиться.

Это противоречит заявленной архитектуре tenant-scoped throttling.

Требуемое исправление: откладывать только конкретное задание или задания конкретного workspace, не применяя глобальный BullMQ rate limit.

Приоритет: **High, блокирует production**.

### 3.2. Неоднозначный результат SendGrid записывается как достоверная ошибка

После перевода отправки в `dispatching` сетевой сбой или падение процесса может произойти уже после того, как SendGrid принял письмо, но до сохранения результата в PostgreSQL.

Обработка прерванных отправок находится в:

- `apps/worker/src/queues/send-dispatch.ts:224`
- `apps/worker/src/queues/flows/flow-send.ts:158`

Сейчас такое состояние сводится к `failed`, хотя настоящий результат неизвестен. Повторная отправка может создать дубль, а отсутствие повтора — потерянное письмо.

Требуемое исправление:

- добавить состояние `unknown` или `reconciling`;
- определить формальную state machine отправки;
- зафиксировать at-most-once или effectively-once модель;
- добавить correlation ID;
- протестировать падения до отправки, после принятия SendGrid и перед записью результата.

Приоритет: **High, блокирует production**.

### 3.3. SendGrid-запрос не имеет явного timeout

В `packages/delivery-core/src/send-mail.ts` используется сетевой запрос без `AbortController` и ограниченного времени ожидания.

Зависший запрос может занять worker slot на неопределённое время и снизить пропускную способность всей очереди.

Требуемое исправление: timeout, отмена запроса, классификация timeout как неоднозначного результата и метрики длительности отправки.

Приоритет: **High**.

### 3.4. Segment sweep не ограничен по объёму

В `apps/worker/src/queues/flows/flow-segment-sweep.worker.ts:122` контакты сегмента могут загружаться большим набором за одну операцию.

На аудитории 100 тысяч–1 миллион контактов это создаёт:

- высокий расход памяти;
- длинные транзакции;
- нагрузку на PostgreSQL;
- сложное восстановление после частичного сбоя;
- повторную обработку большого объёма данных.

Требуемое исправление: keyset pagination, короткие транзакции, ограниченные batch jobs и сохранение checkpoint.

Приоритет: **High**.

### 3.5. Жизненный цикл партиций не автоматизирован

Выделенные партиции `events` и `send_events` созданы только для июля и августа 2026 года. Начиная с 1 сентября данные будут попадать в DEFAULT partitions.

Данные не потеряются, но DEFAULT partitions будут неограниченно расти. Последующее подключение нормальной партиции потребует полного сканирования и может блокировать таблицу.

Требуемое исправление:

- автоматическое создание партиций минимум на 2–3 месяца вперёд;
- мониторинг наличия следующей партиции;
- процедура перемещения данных из DEFAULT;
- тест перехода через границу месяца;
- runbook аварийного восстановления.

Приоритет: **High и срочный по времени**.

### 3.6. Live SendGrid UAT не завершён

Автоматические тесты не заменяют проверку настоящего SendGrid API и подписанного webhook.

Не подтверждены в реальном окружении:

- успешная отправка с BYO key;
- Dynamic Template;
- delivered/opened/clicked/bounced события;
- проверка подписи webhook;
- дедупликация повторно доставленных событий;
- поведение при 429 и временных ошибках SendGrid.

Приоритет: **High, выпускной барьер**.

## 4. Безопасность и изоляция тенантов

### 4.1. Admin-scan RLS policies слишком сильно доверяют session flag

Политики для фонового сканирования разрешают межтенантный SELECT при `app.admin_scan=true`, но не всегда содержат дополнительные строковые ограничения.

Само по себе это не доказанная утечка, однако ошибка при установке флага даст слишком широкие права.

Необходимо:

- выделить отдельную DB role;
- ограничить admin-scan конкретными операциями;
- минимизировать время жизни флага;
- проверить невозможность его установки из обычного API;
- добавить отрицательные cross-tenant тесты.

Приоритет: **High**.

### 4.2. RLS policies используют два варианта tenant setting

Часть политик использует безопасный вариант с `NULLIF(current_setting(...))`, а 12 политик делают прямое приведение к UUID.

Это создаёт зависимость от неявного правила: tenant setting всегда должен быть установлен. При нарушении инварианта запрос завершится ошибкой.

Нужно унифицировать политики и добавить тест запроса без tenant context.

Приоритет: **Medium**.

### 4.3. Better Auth таблицы находятся вне RLS

Таблицы `organization`, `session` и `account` не защищены RLS. Среди них присутствуют токены и password-related данные.

Не следует автоматически добавлять RLS: сначала нужно определить trust boundary Better Auth. Рекомендуемый вариант — отдельная DB role с минимальными привилегиями и запрет доступа предметных модулей к auth-таблицам.

Приоритет: **High, требуется архитектурное решение**.

### 4.4. API key scopes сохраняются, но не применяются

Ключ может содержать список scopes, однако маршруты фактически не проверяют их.

Это создаёт ложное ощущение ограниченных полномочий.

Нужно либо реализовать enforcement для каждого маршрута, либо удалить scopes до появления реальной поддержки.

Приоритет: **High**.

### 4.5. Нет replay protection для SendGrid webhook

Подпись проверяется, но временное окно timestamp не контролируется. Также маршрут не имеет собственного rate limit.

Уникальный ключ событий частично защищает от повторной обработки, но не защищает HTTP-слой от повторной нагрузки.

Нужно:

- проверять допустимый возраст timestamp;
- отклонять слишком старые события;
- добавить route-specific rate limit;
- сохранить идемпотентность БД.

Приоритет: **Medium–High**.

### 4.6. Public invite endpoint раскрывает лишнюю информацию

Неавторизованный GET invite может раскрыть email приглашённого пользователя и название организации. Endpoint недостаточно защищён от перебора.

Нужно возвращать минимально необходимую информацию, ограничить частоту запросов и сохранить одинаковое поведение для существующего и несуществующего приглашения.

Приоритет: **Medium**.

### 4.7. API rate limit локален одному процессу

Используется in-memory ограничитель. При запуске нескольких API replicas эффективный лимит умножается на число процессов.

Redis уже присутствует в архитектуре, поэтому production rate limiting должен быть распределённым.

Приоритет: **Medium–High**.

### 4.8. Недостаточная защита логов и секретов

- Минимальная длина `BETTER_AUTH_SECRET` допускает 16 символов.
- Pino redaction ограничен несколькими уровнями вложенности.
- Worker не имеет единой политики redaction.
- `.env` и `dump.rdb` физически находятся в рабочей директории, хотя игнорируются Git.

Нужно усилить требования к production secret, централизовать redaction и убрать секретные/служебные файлы из корня репозитория.

Приоритет: **Medium**.

## 5. Compliance и аналитика

### 5.1. Собственная отписка не полностью отражается в send analytics

При переходе по собственной unsubscribe-ссылке меняется статус контакта, но соответствующая отправка не всегда получает `unsubscribed_at`.

В результате workspace, campaign и send-level метрики могут расходиться.

Необходимо создавать единое unsubscribe-событие и атомарно обновлять подписку, историю согласия и связанную отправку.

Приоритет: **High для email compliance**.

### 5.2. Используются разные временные поля для дневных метрик

Часть reconciliation агрегирует по `sent_at::date`, а dashboard — по `created_at::date`.

Около полуночи, при задержках очереди и разных timezone результаты могут расходиться.

Нужно определить единую UTC-семантику:

- какое поле определяет день отправки;
- где выполняется timezone conversion;
- как обрабатываются provider events с задержкой.

Приоритет: **Medium–High**.

### 5.3. Consent history удаляется вместе с контактом

`subscription_status_history.contact_id` использует cascade delete.

Это может противоречить необходимости подтверждать историю согласия и отписки. Однако бессрочное хранение персональных данных тоже может нарушать retention policy.

Нужно продуктовое/юридическое решение: удаление, обезличивание либо отдельное хранение минимального compliance evidence.

Приоритет: **High, требуется решение владельца продукта**.

### 5.4. Provider timestamp влияет на партицию и дедупликацию

`occurred_at`, полученный от провайдера, участвует в выборе партиции и уникальности события.

Следует ограничить допустимый диапазон provider timestamp и отдельно хранить server receive time.

Приоритет: **Medium**.

## 6. Worker и BullMQ

Обнаружены следующие эксплуатационные проблемы:

- repeatable jobs регистрируются без достаточной централизованной обработки ошибок;
- Queue handles не везде закрываются при shutdown;
- отсутствуют единые worker error listeners;
- failed jobs сохраняются бессрочно через `removeOnFail: false`;
- `defaultJobOptions` продублирован примерно в восьми местах;
- Redis connection options продублированы в нескольких модулях;
- unsubscribe TTL определён более одного раза;
- предполагаемый `DEFAULT_TENANT_RPS=10` не подтверждён нагрузочным тестом или конфигурацией SendGrid.

Это не требует переписывания worker. Нужны общая queue factory, политика retention, graceful shutdown и наблюдаемые retry/dead-letter механизмы.

Приоритет: **Medium–High**.

## 7. PostgreSQL и миграции

### Сильные стороны

- 38 последовательных SQL migrations.
- Используются partial indexes, JSONB и PostgreSQL-specific возможности.
- RLS включён принудительно.
- Событийные таблицы уже подготовлены к partitioning.

### Недостатки

Отсутствует определённый production-процесс применения миграций:

- нет migration gate перед запуском приложения;
- не определено, запускается ли миграция одним процессом;
- нет rollback/forward recovery процедуры;
- нет проверки совместимости старой и новой версии приложения;
- не описаны PostgreSQL TLS и внешний connection pool;
- второй DB pool не имеет `pool.on("error")`.

Также отсутствуют некоторые ограничения целостности:

- unique `(organizationId, userId)` для membership;
- unique `(flow_id, version_number)`;
- внешние ключи для draft/live flow versions.

Нужно добавлять ограничения только после проверки и очистки существующих данных.

Приоритет: **High для migration pipeline, Medium для ограничений**.

## 8. Observability и deployment

Production-контур практически не сформирован.

Отсутствуют:

- app Dockerfiles;
- CI workflow;
- deployment manifests;
- `/healthz`;
- `/readyz`;
- метрики;
- Bull Board;
- централизованные alerts;
- структурированные и редактированные worker logs;
- проверка доступности PostgreSQL и Redis;
- queue-depth и oldest-job-age alerts;
- migration readiness gate;
- документированная процедура rollback.

Для текущего размера команды рекомендуется:

- Sentry для frontend/API/worker exceptions;
- Better Stack для Pino logs, metrics и alerts;
- OpenTelemetry correlation;
- health/readiness endpoints;
- Bull Board с закрытым административным доступом.

Приоритет: **High, блокирует нормальную эксплуатацию**.

## 9. Frontend

Frontend функционально реализован и покрывает значительный объём MVP, однако production bundle содержит крупный chunk:

- примерно 1,49 MB;
- около 431 KB gzip.

Нужно внедрить route-level code splitting, ленивую загрузку canvas/editor и тяжёлых dashboard-компонентов.

Дополнительно требуется проверить:

- обработку API errors;
- empty states;
- pagination;
- отображение устаревших analytics;
- ошибки сохранения canvas;
- предупреждение о несохранённых изменениях.

Приоритет: **Medium**.

## 10. Тестовая стратегия

526 проходящих тестов — сильная сторона, но текущая зелёная проверка не доказывает production reliability.

Не хватает обязательных сценариев:

- падение процесса перед SendGrid-запросом;
- падение после принятия письма SendGrid;
- timeout и разрыв соединения;
- tenant A получает 429, tenant B продолжает отправку;
- повторная доставка webhook;
- segment sweep на большой аудитории;
- смена месячной партиции;
- миграция вперёд и rollback/roll-forward;
- несколько API replicas с общим rate limit;
- восстановление из backup;
- live SendGrid UAT.

Playwright не входит в стандартный тестовый прогон и может использовать development-базу. E2E должен работать только с отдельной временной БД.

В корневом проекте также отсутствуют полноценные lint и coverage gates.

Приоритет: **High для failure-injection и изолированного E2E**.

## 11. Поддерживаемость

Основные источники технического долга:

- `resolveWorkspaceMember` продублирован примерно в девяти модулях;
- queue defaults продублированы;
- Redis options продублированы;
- отдельные значения TTL определены в нескольких местах;
- архитектурные и кодовые conventions формально не зафиксированы;
- обработка ошибок и anti-enumeration поведение отличаются между маршрутами;
- API и worker используют разные подходы к логированию.

Это повышает вероятность расхождения поведения при дальнейших изменениях.

Приоритет: **Medium**.

## 13. Финальный вердикт

Mega CRM — качественно собранный и достаточно зрелый MVP. Проект не выглядит как случайный набор AI-generated файлов: в нём прослеживается архитектура, модульные границы, последовательная модель данных и хорошая функциональная полнота.

При этом его пока нельзя считать надёжной production-системой для массовых email-отправок. Основные риски находятся не в CRUD-коде, а на границах сбоев:

- SendGrid принял письмо, но worker не сохранил результат;
- один тенант исчерпал лимит и затормозил остальных;
- большой segment sweep исчерпал память;
- наступил новый месяц без подготовленной партиции;
- webhook был повторён;
- миграция запустилась параллельно;
- сервис недоступен, но инфраструктура не может определить его готовность.

Рекомендация: **не переписывать проект**, а провести отдельный milestone production hardening. После устранения High-рисков, live SendGrid UAT, нагрузочного теста нескольких тенантов и репетиции миграций проект можно выводить в ограниченный production pilot.
