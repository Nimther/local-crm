## ci-tenant-fairness-double-run — CI `test` (coverage) job flaked on tenant-fairness 0.9-ratio while the dedicated failure-injection job passed the same commit: both load tests were collected by the aggregate, one of them despite its own header claiming it wasn't wired into CI
- **Date:** 2026-08-20
- **Error patterns:** tenant B's contended throughput must stay at or above 0.9 of its own solo baseline, tenant-fairness.test.ts:284, ratio 0.855 vs 0.9, test job fails but failure-injection job passes on same commit, aggregate coverage run vs dedicated lane, marginal miss on slow runners, intermittent red `test` check, WRK-03, WRK-04
- **Root cause(s):** AND-gate, three legs. (1, CONFIG — the leg severed) `apps/worker/vitest.config.ts` excluded only `dist/**`, so root `npm run coverage` (CI job `test`) collected BOTH `failure-injection/tenant-fairness.test.ts` and `loadtest/tenant-rps-sustained.test.ts` — tenant-fairness ran twice per CI run, once quiet in the required `failure-injection` job (passed) and once in the aggregate (flaked). (2, ENVIRONMENT) the aggregate execution carries v8 coverage instrumentation plus ~60 sibling worker files' accumulated Postgres/Redis state (including the 15s loadtest's), penalising the 72-job contended phase more than the 12-job baseline. NOT cross-project parallelism: Vitest 4.1.9 `groupSpecs` puts `maxWorkers:1` projects in their own strictly-sequential trailing group (eliminated by reading the scheduler). (3, CONSTRUCTION) the assertion is quantization-limited — 12 jobs at rpsLimit 4 spans ~3 one-second token-bucket refill windows sampled by a 40ms poll (~0.38s of signal), so one boundary slip spends the whole 0.9 allowance. Secondary defect: `tenant-rps-sustained.test.ts`'s header and `fairness-constants.ts` both claimed "deliberately NOT wired into CI (D-04)" — false; no config implemented it, so 15s of DEFAULT_TENANT_RPS=10 sustained load ran in `test` on every PR.
- **Fix:** Config split, not env gating (PR #23, merged c08f84d): shared `apps/worker/vitest.base.config.ts` exporting `workerTestBase` + `AGGREGATE_EXCLUDED_LOAD_TESTS`; ordinary `vitest.config.ts` adds the two load-test excludes (aggregate inherits via root `projects`); new `vitest.loadtest.config.ts` lane without them; `failure:tenant-fairness` / `loadtest:tenant-rps` scripts pass `--config vitest.loadtest.config.ts`. The 0.9 ratio, volume constants, coverage-baseline.json, and branch protection untouched. Env-var gating rejected: a dropped var runs zero tests and exits 0 (gate silently deleted), whereas a dropped `--config` prints "No test files found, exiting with code 1" — loud on a required check (verified empirically). Coverage delta measured on both sides: exactly ZERO (88.68%, 5752/6486 lines pre and post; file count −2 matching the 2 exclusions).
- **Files changed:** scripts/__tests__/aggregate-loadtest-exclusion.test.mjs (new), apps/worker/vitest.base.config.ts (new), apps/worker/vitest.loadtest.config.ts (new), apps/worker/vitest.config.ts, vitest.config.ts, package.json, SPECIFICATION.md — commits 3500c63 (RED), c7caf7f (fix), 7d865fe (docs) on fix/ci-tenant-fairness-double-run
- **Why not caught:** No executable check bound test files to entrypoints — documentation asserted a wiring invariant ("not wired into CI") that nothing enforced, and the only feedback channel was an intermittent red `test` check that pattern-matched to "runner-load flake" (recorded as such in memory) and was absorbed instead of investigated. Third instance of this repo's recurring lesson: an intermittent failure is a gate reporting a real defect at a low duty cycle.
- **Recurrence guard:** `scripts/__tests__/aggregate-loadtest-exclusion.test.mjs` (9 tests, in the ordinary suite) asserts Vitest's own `vitest list --filesOnly --json` collection against the wiring contract in BOTH directions — the load tests are NOT collected by the aggregate AND ARE still collected by their dedicated lane — plus a >100-file vacuous-pass floor, a `rate-limit-429` positive control against over-broad globbing, and 3 ci.yml drift assertions. Mutation-proven (RED 2/9 → GREEN 9/9). Standing rule: if the guard times out on a cold runner, raise its testTimeout — never weaken the `vitest list` oracle. **Reusable patterns: (i) a timing-sensitive throughput assertion is only valid in the quiet, uninstrumented lane it was calibrated for — run it exactly once there, don't widen its threshold; (ii) prefer a `--config` split over an env-var gate for test-lane routing, because the failure direction of a dropped flag must be LOUD (exit 1) not silent (0 tests, exit 0); (iii) a doc claim that a test "is not wired into CI" is a wiring invariant — enforce it with a collection-list guard or assume it is false; (iv) rolldown parse errors in vite configs point at the ENTRYPOINT config, and a literal `*/`-containing glob inside a JSDoc block comment terminates the comment.**

## segm-04-live-count-race — SEGM-04 E2E flake: live count read as "—" before the response landed, plus 57P01 on every teardown
- **Date:** 2026-08-06
- **Error patterns:** Expected lastGoodText not to be "—", live count stays "—", segments-behavior.spec.ts:146, Playwright flake, passes in sibling CI run on same commit, 57P01, terminating connection due to administrator command, DROP DATABASE, pg_terminate_backend, duplicate CI runs on push and pull_request, no trace artifact
- **Root cause(s):** (A) Missing synchronization in the TEST, not an app bug — SegmentBuilder renders the count paragraph (literal "—" while `lastGoodCount === null`) and the «контактов подходит» label in the SAME React commit, both gated on `canPreview`, which ALSO gates `enabled` on the preview-count query; so the label signals the request is *starting*, and the number arrives one HTTP round-trip later. The test waited on the label, then captured the value with a one-shot non-retrying `textContent()` and asserted on the captured plain string, which Playwright never retries. AND-gate: needed the missing wait (code) AND a round-trip slower than the harness's ~10–30ms CDP read window (loaded CI runner) — which is exactly why the same commit passed in one job and failed in its sibling; (B) teardown ORDERING — Playwright 1.61.1 `unshift`s teardown tasks so they run in reverse of setup order, putting `globalTeardown` BEFORE the webServer plugin's shutdown, so `dropEphemeralDatabase`'s `pg_terminate_backend` killed the still-live API server's pool connections (independent defect: fired on green runs too, was NOT a consequence of A); (C) `on: push:` unscoped, so any branch with an open PR matched both triggers and the `github.ref` concurrency key could not collapse them (refs/heads/<branch> vs refs/pull/N/merge); (D) `trace: "retain-on-failure"` recorded traces but the e2e job had no `actions/upload-artifact` step, so they were discarded with the runner.
- **Fix:** (A) Assert on the value actually read — `await expect(countParagraph).not.toHaveText("—", { timeout: 15_000 })` — a retrying assertion that flips when the response lands; assertions kept and STRENGTHENED with `toMatch(/\d/)`, never relaxed. Plus a permanent 1000ms delay injected into the FIRST preview-count response as stimulus (not remedy), pinning the environment half of the AND-gate ON for every machine; (B) moved the drop OUT of Playwright's lifecycle into a new `test:e2e` wrapper `apps/web/e2e/run-e2e.ts` that spawns the Playwright CLI (via `require.resolve` under the same `process.execPath`), waits for `close`, then drops — `global-teardown.ts` DELETED so the early hook cannot return; `tsx` declared in apps/web devDependencies rather than relied on via root hoisting; (C) `push` scoped to `branches: [master]`; (D) SHA-pinned `actions/upload-artifact` with `if: always()` and `if-no-files-found: ignore`.
- **Files changed:** apps/web/e2e/segments-behavior.spec.ts, apps/web/e2e/run-e2e.ts (new), apps/web/e2e/global-teardown.ts (deleted), apps/web/playwright.config.ts, apps/web/package.json, package-lock.json, SPECIFICATION.md, .github/workflows/ci.yml
- **Why not caught:** No gate existed for this class, and the gates that did speak were structurally muted. The E2E lane DID fire three times in Phase 8 CI — but an intermittent failure reads as noise, so it was recorded as a deferred flake in STATE.md instead of investigated; nobody could reproduce it on demand because the failure depended on an environment condition no gate controlled. (D) made this self-sealing: the exact artifact needed to diagnose it was being generated and thrown away on every occurrence, forcing diagnosis by reading React render order and Playwright's own source. (B) never flaked at all — it happened every run — but `continue-on-error: true` kept the job from going red and its teardown-only output was misread as a symptom of (A). (C) doubled every run, doubling apparent flake frequency while halving confidence in any single result. Process lesson: **a failing gate was downgraded to a note — an intermittent failure is a gate reporting a real defect at a low duty cycle, not a malfunctioning gate.**
- **Recurrence guard:** Regression test `apps/web/e2e/segments-behavior.spec.ts:"degraded live-count state shows the amber marker and preserves the last-good count (SEGM-04)"` — the retrying `not.toHaveText("—")` assertion is the guard, and the permanent injected 1000ms first-response delay is what gives it teeth: it pins the environment condition that made this a flake ON for every machine, so the guard cannot silently rot and a regression now fails on a laptop rather than once every few CI runs. Proven by mutation (revert the assertion → 3/3 failures with the exact reported signature). Plus: `toMatch(/\d/)` closes the oracle gap where `not "—"` alone would accept an empty/spinner paragraph; (B) is a STRUCTURAL guard — the early-firing hook file is deleted, making the ordering defect impossible rather than merely unobserved; (D) trace upload guards against the *diagnosis* cost recurring, which was the larger cost here. **Reusable pattern: when a Playwright test reads a value with `textContent()`, the preceding wait must be on THAT value, not on a sibling element that mounts in the same React commit — and pin the timing condition with an injected delay so the wait is genuinely exercised.**

## aggregate-coverage-run-fails — `npm run coverage` failed 6 tests that `npm run test` passed: all 5 vitest projects silently shared one ephemeral database, plus a phone redaction rule that ate 4% of UUIDs
- **Date:** 2026-08-09
- **Error patterns:** npm run coverage fails but npm run test passes, aggregate vitest run vs per-workspace run, TypeError: Cannot read properties of undefined (reading 'map'), def.groups is undefined, compileSegmentDefinition, packages/segments-core/src/compile.ts:19, flow-segment-sweep.worker.ts, flow-segment-trigger.test.ts, negative-cross-tenant-jobs.test.ts, webhook-events-sibling-drop.test.ts, owningWorkspaceId is [REDACTED], expected sibling workspace id got [REDACTED], globalSetup runs once per project, TEST_DATABASE_URL last-writer-wins, process.env overwritten between vitest projects, shared ephemeral database, tests see another project's fixtures, cross-tenant sweep picks up foreign rows, ~4% flake, UUID matched phone regex
- **Root cause(s):** TWO independent causes. **(A) Failures 1–2, an AND-gate.** (A1, code) `packages/test-support/src/global-setup.ts` published a PER-PROJECT ephemeral DSN by mutating the SHARED parent `process.env`. Vitest (4.1.9) runs every project's `globalSetup` sequentially in ONE parent process before forking any test worker (`Vitest.initializeGlobalSetup`), so with 5 projects registering that same hook file it is last-writer-wins: 5 databases provisioned, every project's workers handed the 5th one's DSN, all 5 projects sharing one physical database. Proven directly by probe (`prevTEST` on invocation #2 already pointed at #1's DB) and by a worker-side probe reading a foreign DSN. (A2, data) `packages/tenant-context/src/__tests__/scan.test.ts` seeded `definition = {operator:"and",conditions:[]}` — not a `SegmentDefinition` (`{version, groups[]}`) — onto flows with `status='live'`, `trigger_type='segment'` and a `live_version_id`, i.e. exactly the rows `findLiveSegmentTriggeredFlows()` selects; apps/worker's deliberately cross-tenant `runFlowSegmentSweepTick()` then compiled them and threw. Removing EITHER condition makes the failures vanish — verified both ways. (A3, latent) the same last-writer-wins also clobbered `GSD_DEV_DATABASE_URL` on the 2nd..Nth invocation, so both fail-closed guard layers (D-14 a and b) compared one ephemeral DSN against another instead of the real dev DSN — the guard stopped guarding for 4 of 5 projects. **(B) Failure 3, independent and probabilistic (~4%/run):** the `phone` valueRule `/\+?\(?\d(?:[\s().-]*\d){9,14}\b/` matched 4.0% of random v4 UUIDs (measured 12067/300000) because `-` is one of its own separators (hex groups chain into one long digit run) and the trailing `\b` let the match START mid-token; `scrub()` applies valueRules to every string regardless of key, so `owningWorkspaceId` came back `[REDACTED]`. **`--coverage` was NOT a cause of anything** — every failure reproduces without it; the real differentiator is aggregate-vs-per-workspace, and coverage was merely the only aggregate entrypoint anyone runs.
- **Fix:** (A1) publish the DSN set into vitest's PER-PROJECT `project.config.env` channel (which vitest merges over inherited `process.env` when spawning that project's workers) in addition to `process.env`, still needed for the Playwright entrypoint and single-project runs; scan/auth DSNs now derived from the freshly provisioned dsn via the new `buildTestRoleDsn` rather than read back out of `process.env`, removing the ordering coupling. (A3) the true dev DSN resolved as `GSD_DEV_DATABASE_URL ?? DATABASE_URL` and stashed once per run. (NEW, D-14 layer c) the second provisioning project poisons the shared `process.env.GSD_TEST_PROJECT` with `AMBIGUOUS_PROJECT_MARKER`; `getTestDatabaseUrl()` fails closed on it, so only a worker the per-project channel failed to reach can observe it. (A2) the scan fixture now stores a real `SegmentDefinition` (defense in depth). (B) the phone pattern anchored between non-alphanumeric-and-non-hyphen boundaries: `/(?<![0-9A-Za-z-])\+?\(?\d(?:[\s().-]*\d){9,}(?![0-9A-Za-z-])/` — inside a canonical UUID every digit run is preceded by a hex letter or `-`, so no legal start position exists and the false positive is gone BY CONSTRUCTION, not made rarer; the digit ceiling is deliberately opened (`{9,}` vs `{9,14}`, user-approved) because with a start anchor the pattern can no longer slide forward, so a capped version would have stopped matching 16+ digit runs the old one caught. No test disabled, no assertion weakened, coverage denominator kept unified (0.8468 vs 0.8126 threshold, 4614 lines).
- **Files changed:** packages/test-support/src/global-setup.ts, packages/test-support/src/db-fixture.ts, packages/test-support/src/provision-db.ts, packages/test-support/src/__tests__/global-setup-project-isolation.test.ts (new), packages/test-support/src/__tests__/db-fixture-advisory-unlock.test.ts, packages/redaction/src/rules.ts, packages/redaction/src/__tests__/scrub-identifier-false-positive.test.ts (new), packages/tenant-context/src/__tests__/scan.test.ts, SPECIFICATION.md (§3.2.1 + §7) — commits ec7f5f6, c975a1f, 3cd3f0c on gsd/phase-10-tenant-isolation-trust-boundaries
- **Why not caught:** No gate existed for this class — and the gate that looks like it should have caught it is structurally incapable of doing so. `npm run test` runs `--workspaces`, i.e. one vitest process per workspace, so exactly ONE project ever registers the globalSetup and last-writer-wins can never occur there; only `npm run coverage` exercises the multi-project path, and nothing asserted the isolation it depends on. The existing `db-fixture-isolation.test.ts` asserts a test is in AN ephemeral database, never that it is in ITS OWN — the exact gap. Typecheck is blind (both DSNs are `string`; `definition` is untyped jsonb with no CHECK constraint), and review is blind too: the defect is invisible in the diff and lives entirely in Vitest's scheduling semantics. For (B) the assertion DID exist (webhook-events-sibling-drop Test 4) but used a RANDOM UUID, so a real standing defect presented as a ~4%-per-run flake and read as noise. Process lesson, and the second time this repo has hit it (cf. segm-04-live-count-race): **an intermittent failure is a gate reporting a real defect at a low duty cycle — and a probabilistic bug "fixed" against a single failing example (here, raising the phone rule's digit floor) has only had its rate lowered until it is verified against a sampled population.**
- **Recurrence guard:** (1) Regression test `packages/test-support/src/__tests__/global-setup-project-isolation.test.ts` — 5 tests, verified passing at HEAD; drives the hook with TWO stub projects exactly as an aggregate run does, asserting each gets its own database in its own `config.env` (Test 1), that app/scan/auth DSNs all name that same project's DB (Test 2), that the dev-DSN guard still compares against the real dev DSN (Test 3), and that the ambiguity marker fires (Test 4). Critically it runs inside the ordinary per-workspace `npm run test`, so the multi-project path is now covered WITHOUT needing the aggregate entrypoint — the missing gate now exists. Mutation-proven: disabling the `config.env` publication fails 4/5. (2) ASSERTION (the strongest guard here) — `AMBIGUOUS_PROJECT_MARKER` + fail-closed `getTestDatabaseUrl()`: because `project.config.env` is a resolved-config field rather than a documented globalSetup API, a future Vitest major could change it; the marker guarantees that regression announces itself by name at runtime instead of resurfacing as a `TypeError` in an unrelated package (mutation-proven: the aggregate repro fails loudly with the layer-c message even with the A2 fixture already corrected). (3) Regression test `packages/redaction/src/__tests__/scrub-identifier-false-positive.test.ts` — 7 tests, verified passing at HEAD; pins DETERMINISTIC UUID literals that the pre-fix pattern matched (converting a 4% flake into a standing assertion), adds a 5000-sample sweep, boundary neighbours (9 vs 10 digits, 16+ digit runs), and Test 7 which asserts the rule cannot match at ANY start position inside a canonical UUID — testing the by-construction property rather than the symptom. (4) SPECIFICATION.md §3.2.1 documents the two-channel DSN contract and §7 documents that valueRules apply to every string regardless of key. **Reusable patterns: (i) a per-project value must never be published through a process-global — vitest runs all `globalSetup` hooks in one parent process, so `process.env` is last-writer-wins and `project.config.env` is the per-project channel; (ii) if a suite passes per-workspace but fails in the aggregate run, suspect shared global state before suspecting the flag that distinguishes the two entrypoints; (iii) any fixture reachable by a cross-tenant scan must be VALID, since an invalid one breaks that scan for every tenant, not just its own; (iv) a regex whose separator class includes `-` will chain the hex groups of a UUID — anchor with lookarounds rather than raising thresholds.**
