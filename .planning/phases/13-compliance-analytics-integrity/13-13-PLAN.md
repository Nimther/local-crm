<objective>
Complete CMP-04 (D-03, D-04): plan 13-10 anonymizes the contact row synchronously and queues this job; this plan does the evidence hygiene. Walk the erased contact's linked `send_events.payload` and `events.properties` rows in bounded, resumable pages, rewrite each JSONB value by reconstructing it from an explicit evidence allowlist, and mark the erasure record complete with per-table counts.

Purpose: the raw SendGrid event payload carries the recipient's email address — sometimes inside free-form SMTP diagnostic text rather than under a field named for it — and tenant-supplied event properties can carry anything at all under key names the platform never sees in advance. Anonymizing the contact row without scrubbing these leaves the erased person's data readable in two of the fastest-growing tables in the platform. Because the tenant key space is unenumerable, the bound has to be on what SURVIVES rather than on what is removed.
Output: an allowlist-based JSONB reconstruction, a checkpointed scrub worker on the Phase 12 sweep template, completion tracking on the erasure record, and a kill-resume failure-injection scenario wired into the phase gate.
</objective>

Implement the scrub as an ALLOWLIST RECONSTRUCTION, not as a denylist filter. This reverses the previous version of this plan, which directed reuse of `@mega-crm/redaction`'s `REDACTION_RULES` — REVIEWS.md (Codex) BLOCKER finding 4. Understand why before writing code, because the rejected approach is the intuitive one and reads as the more conservative choice:

A denylist can only remove what someone anticipated. `REDACTION_RULES` is a good log scrubber precisely because logs are best-effort — a missed field there is an incident, not a compliance breach. Here the requirement is a bound on what SURVIVES, and a denylist cannot state one: its completeness claim depends on the set of PII-bearing key names being enumerable in advance, which is exactly what `events.properties` is not, since tenants choose those key names. The rules' `valueRules` backstop narrows the gap for email- and phone-shaped values but does not close it — a person's name, postal address, date of birth, or order history under a tenant-invented key matches no pattern at all. Reconstructing from an allowlist inverts the burden: an unanticipated field is dropped by default rather than kept by default, and the guarantee stops depending on anyone's foresight. As a bonus the false-positive concern that motivated the reuse disappears, since nothing is being detected.

Add `SEND_EVENT_PAYLOAD_EVIDENCE_ALLOWLIST` to `apps/worker/src/queues/erasure-scrub.worker.ts` as a frozen list of exactly these top-level key names, each with a one-line comment naming what evidence it preserves:

- `event` — the provider's event name; what happened
- `type` — the provider's bounce sub-classification (`bounce` versus `blocked`)
- `timestamp` — the provider's event time
- `sg_event_id` — provider event identity, for forensic correlation
- `sg_message_id` — provider message identity, the join back to the send
- `smtp-id` — the message identity the receiving MTA saw
- `status` — the SMTP status code (for example `5.1.1`); the delivery outcome
- `attempt` — the delivery attempt number
- `asm_group_id` — the SendGrid unsubscribe-group id; consent evidence
- `bounce_classification` — the provider's own bounce category

Write the exclusions into the same comment block with their reasons, because the omissions are the load-bearing part and a future reader will otherwise "restore" one:

- `email` — the recipient address; the entire point of the scrub
- `reason`, `response` — free-form SMTP text that routinely embeds the recipient address verbatim inside a larger string. These are the clearest demonstration of why a key-name denylist fails: neither key name looks like PII, so no key rule would flag them, and the address is a substring of a longer diagnostic message
- `ip`, `useragent` — network and device identifiers about the person, personal data in their own right
- `url`, `url_offset` — a clicked link can carry a per-recipient token or identifier in its query string
- `category`, `unique_args`, `marketing_campaign_*`, and every other custom argument — a tenant-defined key space, unenumerable by construction
- everything else, by default, which is the property that makes the guarantee hold

Implement `buildScrubbedSendEventPayload(payload)` to construct a NEW object by copying only allowlisted keys forward from the input, preserving each copied value exactly. Do not walk the input removing keys — build up, never tear down. The difference matters even though the two look equivalent on a known input: a build-up implementation cannot leak an unanticipated field, and a tear-down one always can. Handle a null, an array, or a non-object input by returning an empty object rather than throwing, since the scrub must not fail on a malformed historical row. Omit allowlisted keys that were absent rather than materializing them as null, so a scrubbed payload does not gain fields the original never had.

Implement `buildScrubbedEventProperties(properties)` to return an empty object unconditionally. `events.properties` gets no allowlist because there is no field in it that can be shown to be evidence: the entire key space is tenant-supplied, so any field named on an allowlist here would be a guess about one tenant's schema applied to all of them. The event's own evidence — that it occurred, when, for which contact — lives in the row's non-JSONB columns and is untouched. If a specific tenant-defined field is ever proven necessary as evidence, adding an allowlist for it is the change to make at that time; until then, empty is the only defensible bound. Record that reasoning in the function's doc comment.

Both functions are pure and both are idempotent by construction — a reconstruction from an allowlist applied to its own output is a fixed point — but assert idempotence anyway, because a resumed page or a replayed job will re-process rows and a future implementation change could break it silently.

Create the scrub's checkpoint helpers against `erasure_records.sends_scrub_cursor` and `erasure_records.events_scrub_cursor` — the two `jsonb` columns plan 13-10's migration 0059 creates for this purpose. This is decided, not an execution choice, and the earlier version of this plan was wrong in both directions — REVIEWS.md MEDIUM finding. The Phase 12 checkpoint table cannot hold this cursor: migration 0053 keys `flow_segment_sweep_checkpoint` `(workspace_id, flow_id)` with `flow_id uuid NOT NULL REFERENCES flows(id) ON DELETE CASCADE`, so an erasure-record id fails the foreign key outright — it is not a question of whether the table is "generic enough". And the stated fallback did not exist either: 0059 as originally planned created status and count columns but no cursor columns, while this wave owns no migration slot of its own. Plan 13-10 now adds the two columns, which is why they must be verified present before this task starts.

The columns are `jsonb` rather than `uuid` because the keyset over both target tables is composite — a timestamp plus an id — and a single uuid cannot express a resume position on a partitioned table. Store the cursor as an object naming each keyset component explicitly rather than a positional array, so a later change to the ordering columns is a visible schema-shaped change instead of a silent misinterpretation of an existing row. A null cursor means the walk for that table has not started; a cursor equal to the last page's final key means it is in progress; record how "finished" is represented and make it distinguishable from "not started", because the resume path branches on exactly that.

Put the helpers in `apps/worker/src/queues/erasure-scrub-checkpoint.ts` as `PoolClient`-first transaction-scoped functions following `flow-segment-sweep-checkpoint.ts`'s shape exactly — that module's structure (PoolClient-first, caller already inside `withTenant`/`withTenantTransaction`, cursor advance as a single statement) is what transfers; only its storage does not.

Implement `scrubSendEventsPage` and `scrubEventsPage` as bounded keyset page walks. For `send_events`, reach the contact through `sends.contact_id`; for `events`, use whatever link the schema actually provides (read the schema — do not assume a `contact_id` column exists). Order by the table's own keyset so pagination is stable across pages, then rewrite each row's JSONB: `scrubSendEventsPage` writes back `buildScrubbedSendEventPayload(payload)` and `scrubEventsPage` writes back `buildScrubbedEventProperties(properties)`. Use a bounded UPDATE in both cases.

Because `buildScrubbedEventProperties` returns an empty object for every input, `scrubEventsPage` does not need to read the existing value at all — it can set the column to `'{}'::jsonb` directly for the page's row range. Prefer that form: it is one statement instead of a read-transform-write cycle, and it makes the "no tenant field survives" property visible in the SQL rather than only in the TypeScript. Route it through `buildScrubbedEventProperties` in the code path anyway, or state in the SUMMARY that you did not and why, so a later decision to allowlist a field has one place to change rather than two. Never issue an unbounded UPDATE over either table: both are partitioned and among the fastest-growing in the platform, and a single statement over a large contact's history holds locks for its whole duration.

Rewrite the JSONB in place. Do not delete rows. The row is the delivery evidence the erasure is explicitly designed to preserve — deleting it would defeat CMP-04's own purpose and break the foreign keys plan 13-10 kept intact on purpose.

Commit the checkpoint advance in the SAME transaction as that page's UPDATE. This is the Phase 12 D-09 rule and it is not a style preference: a checkpoint in a separate transaction lets a kill between the two either re-scrub a page (harmless, since the scrub is idempotent) or silently skip one (a permanent PII leak with no signal). Only the same-transaction form makes the second outcome impossible.

`runErasureScrub(deps)` moves the erasure record from pending to scrubbing with `scrub_started_at`, walks both tables to exhaustion, accumulates the per-table counts, and finally sets status complete with `scrub_completed_at` and both counts. On an unrecoverable error, set status failed and record the message in `scrub_error` rather than leaving the record pending: a pending record is indistinguishable from "the job has not run yet", so a failure that leaves it pending is invisible to an operator, while a failed record with a message is actionable. A job that finds its record already complete returns immediately without resetting anything.
