<objective>
Close the last gap in CMP-04's durability chain (D-04). Plan 13-10 commits the anonymization, the suppression, and the `erasure_records` row atomically and then enqueues the scrub after that transaction commits. That ordering is deliberate and it is the safe one, but it has exactly one failure mode: a crash, a Redis outage, or a process kill between the commit and the enqueue leaves a durable `pending` erasure record with no job behind it, and nothing in the phase as otherwise planned ever looks at it again. This plan adds the reclaimer that does.

Purpose: an erasure that anonymized the contact but never scrubbed the linked JSONB is a half-finished compliance action that reports itself as in progress forever. Plan 13-11's ingestion-health watchdog covers the webhook ingress journal, not `erasure_records`, so without this tick a stranded record is invisible to every existing surface.
Output: a scheduled reclaim tick built on the established `upsertJobScheduler` shape, re-enqueueing through the same shared job-id derivation the request path uses, plus a failure-injection scenario that crashes precisely between the commit and the enqueue.
</objective>

Open the module with a header comment stating why this file exists, because a reader who does not know the ordering will read it as redundant machinery around a queue that already has deterministic job ids. Say it plainly: plan 13-10's `deleteContact` commits the anonymization, the suppression insert, and the `erasure_records` row as one transaction and enqueues the scrub only after that transaction commits. That ordering is chosen over enqueueing inside the transaction because its failure mode is recoverable — a crash in the gap leaves a durable `pending` record — while the inverse leaves a job pointing at an erasure that rolled back, which nothing can detect. This tick is the half that makes "recoverable" true rather than merely possible. Without it the ordering's whole justification is unearned.

`findReclaimableErasureRecords(client, leaseMinutes, limit)` selects `id, workspace_id, contact_id, status` from `erasure_records` where the row is reclaimable, ordered by `requested_at` ascending with `LIMIT $2`. Two disjuncts, both required:

- `status = 'pending' AND requested_at < now() - make_interval(mins => $1)` — the crash-in-the-gap case the finding names.
- `status = 'scrubbing' AND scrub_started_at < now() - make_interval(mins => $1)` — a worker that died mid-scrub. This case is included deliberately and it is not scope creep: a Redis flush or a worker kill is precisely the loss mode this phase exists to survive, and it strands `scrubbing` records exactly as readily as `pending` ones. Re-running one is safe because plan 13-13 writes the resume cursor in the same transaction as each page's UPDATE, so a reclaimed scrub resumes from where it stopped rather than restarting, and the scrub is idempotent regardless.

Exclude `complete` (nothing to do) and `failed` (a recorded, operator-visible outcome — re-enqueueing it would loop on a genuine error and overwrite the `scrub_error` an operator needs). State that exclusion in a comment: `failed` is a terminal state this tick deliberately does not retry, and the right recovery for it is an operator decision, not an automatic loop.

`runErasureScrubReclaim(deps)` enumerates workspaces through `withCrossWorkspaceScan` exactly as `campaign-scheduler.worker.ts` and `send-reconciler.worker.ts` do — the scan block is for DISCOVERY ONLY — then for each workspace opens its own `withTenant` scope, calls `findReclaimableErasureRecords`, and enqueues one scrub job per returned record. This shape is what keeps the tick cross-tenant without `erasure_records` needing a scan grant or a `_scan` policy of its own: migration 0042 already grants `SELECT` on `organization` to `mega_crm_scan`, so the enumeration is covered, and every erasure-record read then happens under the table's own fail-closed `workspace_isolation` policy in that workspace's scope. Introduce no new grant and no new policy. Write that reasoning into a comment — the alternative (granting the scan role access to `erasure_records`) would work and is the more obvious move, and it widens a cross-tenant read surface over a compliance table for no gain.

Build the job through `buildErasureScrubJobPayload(workspaceId, contactId, erasureRecordId)` and pass `jobId: buildErasureScrubJobId(erasureRecordId)`, both imported from `@mega-crm/shared-schemas`. Do NOT derive the id here. This is the load-bearing detail of the whole plan: there are two producers of this job — the api request path and this tick — and if each derived the id independently, each would be internally consistent and the two would still collide on nothing, so reclaiming a record whose job DID get enqueued would queue a second scrub over the same contact. One exported derivation used by both is what turns that race into a no-op. This mirrors the `buildWebhookEventsJobPayload` decision plan 13-01 made for the identical two-producers-one-consumer shape.

Record in the same comment that the job id is a cheap first layer and not the guarantee. BullMQ's id-based deduplication only holds while the job is still in Redis; once a completed job ages out under the retention policy, the same id can be enqueued again. The authoritative idempotency is plan 13-13's own already-complete check — `runErasureScrub` returns immediately when its record's status is `complete` — which holds regardless of Redis state. A reader who trusts the id alone would conclude either that this tick is unnecessary or that the worker's check is, and both conclusions are wrong.

Build the queue's connection and job options through `buildRedisConnectionOptions` and `buildJobOptions(STANDARD_JOB_RETENTION)` from `@mega-crm/queue-core` — never a local copy, which fails Phase 12's cross-application single-definition test. Register the tick with `queue.upsertJobScheduler(stableId, { every: ERASURE_SCRUB_RECLAIM_INTERVAL_MS }, ...)` plus an immediate boot job, inside the same try/catch/finally shape the analytics reconciler uses, and include the `autorun` key in the constructed Worker options only when a caller actually supplied a value (the G-12-1 regression recorded in STATE.md: forwarding `autorun: undefined` clobbers BullMQ's enabling default and silently disables the run loop).

Add three versioned constants with rationale comments in the Phase 9 house style:

- `ERASURE_SCRUB_RECLAIM_INTERVAL_MS` — recommend 5 minutes, matching the sibling sweeps. The tick is nearly free when there is nothing to reclaim (one enumeration plus one indexed read per workspace), and an erasure is a compliance action with a statutory clock, so discovering a stranded one within minutes rather than hours costs nothing and buys the whole margin.
- `ERASURE_SCRUB_RECLAIM_LEASE_MINUTES` — recommend 15. It has to be comfortably longer than the widest plausible gap between the commit and a successful enqueue (a single Redis round trip, so milliseconds in the normal case) and longer than a normal scrub's duration for the `scrubbing` disjunct, or a healthy in-progress scrub would be reclaimed underneath itself. Fifteen minutes is the same order as `INGRESS_JOURNAL_STUCK_THRESHOLD_MINUTES` and for the same reason: an order of magnitude above normal, so crossing it means something actually broke. If plan 13-13's SUMMARY records a page limit and per-page timing implying a long-running scrub for a large contact, raise this value rather than shortening the scrub, and say so in the SUMMARY.
- `ERASURE_SCRUB_RECLAIM_PAGE_LIMIT` — recommend 100 per workspace per tick, so a mass-strand event (a Redis outage during a bulk deletion) degrades into more ticks rather than one tick that floods the scrub queue.

Wrap each workspace's work so a failure for one workspace is logged through `scrubbedConsole` and does not abort the remaining workspaces — a single tenant's transient enqueue failure must not stop every other tenant's erasures from being reclaimed. Return a per-tick summary of workspaces scanned, records reclaimed, and workspaces that errored.

<flagged_assumptions>
Probe row **CMP-04** came back `unclassified` / `unresolved` from the deterministic edge-coverage engine (no SPEC.md exists for this phase). Plan 13-10 carries the primary flag for CMP-04; the durability-specific judgements this plan adds are recorded here rather than buried:

- **CMP-04 (unresolved), durability half:** two unverified judgements. First, that a 15-minute lease is the right boundary between "the enqueue is merely in flight" and "the enqueue never happened". It is reasoned from the normal-case gap being a single Redis round trip and from the `scrubbing` disjunct needing to outlast a normal scrub, not from measurement — plan 13-13's SUMMARY may record per-page timings that force it upward, and this plan says to raise the lease rather than shorten the scrub if so. A lease set too low reclaims healthy work; set too high it delays recovery. Neither failure is silent, which is what makes the guess acceptable.
- Second, that a scheduled tick is the right recovery mechanism rather than a boot-time sweep. A boot-time sweep is cheaper and needs no queue, but recovery would then wait for the next worker restart, which in a stable deployment can be weeks — unacceptable against a statutory erasure clock. The tick is chosen for that reason; the cost is one more registered scheduler, which the phase already pays four times over.
- **Not claimed:** this plan does not surface a stranded erasure to an operator. It recovers one automatically, which is strictly better for the common case, but a record that fails repeatedly ends in `failed` with an error message and no alert — plan 13-11's watchdogs cover the ingress journal and reputation, not `erasure_records`. Adding an erasure-health watchdog is a natural follow-on and is deliberately not in this phase's scope; recorded so it is a known gap rather than an assumed capability.
