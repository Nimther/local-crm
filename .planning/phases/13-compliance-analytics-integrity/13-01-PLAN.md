## Cross-app shared-module placement (decided once for the whole phase)

REVIEWS.md raises a MEDIUM finding that the `apps/api` ↔ `apps/worker` import boundary is hit at four points across plans 13-01, 13-04, 13-06, and 13-08, and anticipated at only one. The decision is made here, in the phase's first wave, and restated verbatim in each affected plan so no executor rediscovers it:

- `apps/worker` declares `@mega-crm/api` as a **devDependency only** (`apps/worker/package.json`), and `apps/api` declares no dependency on `apps/worker` at all. Worker **production** code therefore must never import `@mega-crm/api`. Promoting that devDependency to a production dependency is forbidden.
- A relative cross-app import is not an escape hatch either: `apps/api/tsconfig.json`'s `rootDir: "src"` makes an import from `apps/worker/src/...` a hard `tsc` TS6059 error. This was proven empirically during plan 12-10, which relocated `dead-letter-writer.ts` into `packages/queue-core` for exactly this reason.
- Every `PoolClient`-first query helper both apps need lives under `packages/db/src/<domain>/<module>.ts` and is imported as `@mega-crm/db/src/<domain>/<module>.js`. This is the established in-repo convention, not a new one: `packages/db/src/partitions/maintenance-run.ts` and `packages/db/src/reconciler/reconciler-run.ts` are already imported this way by both `apps/api` and `apps/worker`.

Write migration `0055_webhook_ingress_durability.sql` creating `ingress_journal` with columns `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`, `workspace_id uuid NOT NULL REFERENCES organization(id) ON DELETE CASCADE`, `raw_batch jsonb`, `received_at timestamptz NOT NULL DEFAULT now()`, `ingestion_completed_at timestamptz`, `replay_count integer NOT NULL DEFAULT 0`, `payload_purged_at timestamptz`, plus a table-level `CONSTRAINT ingress_journal_payload_purge_check CHECK (raw_batch IS NOT NULL OR payload_purged_at IS NOT NULL)`.

`raw_batch` being nullable is a decision, not an omission — REVIEWS.md (Codex) WARNING finding 6. The retention horizon has to dispose of two different things that were previously conflated into one DELETE: the recipient PII in the raw payload, and the evidence that a batch was received and never ingested. Deleting the row disposes of both, which means an incomplete or attempt-capped batch silently stops existing the moment it ages out — taking with it the only trace that ingestion lost data, and ending plan 13-11's ability to alert on it. Splitting the two lets the payload go at the horizon while the row survives as a non-PII tombstone. The CHECK is what stops the nullable column from weakening the write-time guarantee: at insert time `payload_purged_at` is null, so `raw_batch` must be present, exactly as `NOT NULL` would have required; the only way to reach a null payload is through the purge, which sets the marker in the same statement. Add a `COMMENT ON COLUMN ingress_journal.payload_purged_at` stating that a non-null value means this row is a tombstone: the batch is permanently unreplayable, its payload has been disposed of at the retention horizon, and it is retained solely so an unrecovered ingestion loss stays visible to the operator.
