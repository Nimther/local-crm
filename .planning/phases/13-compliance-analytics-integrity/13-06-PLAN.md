## Cross-app shared-module placement (decided in plan 13-01, restated here)

REVIEWS.md raised the `apps/api` ↔ `apps/worker` import boundary as a MEDIUM finding, naming this plan as one of three that hit it un-anticipated: the earlier version said the sweep "enqueues through the existing `enqueueWebhookBatch` path", which is an `apps/api` module that also imports `apps/api`'s own `env`. That import is not available:

- `apps/worker` declares `@mega-crm/api` as a **devDependency only**, and `apps/api` declares no dependency on `apps/worker`. Worker production code must never import `@mega-crm/api`, and that devDependency must not be promoted.
- A relative cross-app import is not an escape hatch: `apps/api/tsconfig.json`'s `rootDir: "src"` makes it a hard `tsc` TS6059 error, proven empirically in plan 12-10.

The decision, made once for the phase in plan 13-01:

- Journal query helpers live at `packages/db/src/webhooks/ingress-journal.ts`, imported as `@mega-crm/db/src/webhooks/ingress-journal.js` — the convention `packages/db/src/reconciler/reconciler-run.ts` already established for a helper both apps use.
- `enqueueWebhookBatch` is deliberately **not** relocated: it owns a module-singleton BullMQ `Queue` built from `apps/api`'s `env`, which is an api-side concern. This plan's sweep builds its own producer `Queue` for `WEBHOOK_EVENTS_QUEUE` through `@mega-crm/queue-core` against the worker's own env, and constructs the job payload through the shared pure `buildWebhookEventsJobPayload` that plan 13-01 adds to `packages/shared-schemas/src/queues.ts`. Two producers, one payload builder, one consumer-side schema — so neither app imports the other and the two producers cannot drift on job shape without failing `webhookEventsJobSchema.parse`.
