<objective>
Close Pitfall 14's second half (CMP-07). The current dedup key `(workspace_id, sg_event_id, occurred_at)` rests on an assumption the project has since verified false: `sg_event_id` is not reliably stable across SendGrid webhook retries, so a redelivery with a fresh event id inserts a second row and double-counts delivered/opened/clicked. Re-base the key on server-observed fields — `(workspace_id, send_id, event_type, occurred_at)` — keeping `sg_event_id` as a stored forensic column.

Purpose: this is the phase's highest-risk migration. It combines two independent hazards: a concurrent index build is unsupported on a partitioned parent table, and the historical duplicates that motivate the fix will violate the new index at build time. Sequenced as its own migration, with a duplicate count taken before anything destructive runs.
Output: migration 0057 (pre-check, bounded duplicate resolution, per-partition concurrent unique index build, attach, expand/contract constraint swap), the swapped `ON CONFLICT` target, and tests proving a varying `sg_event_id` no longer bypasses dedup.
</objective>

<assumption_delta_decision>
**Detector result:** `pluralization` signal fired on "A compound-key fallback is required" — a second dedup identity was introduced where there had been one.

**Noun now primary:** the *send event occurrence*, identified by `(workspace_id, send_id, event_type, occurred_at)`.

**Decision: promote.** The compound key becomes the primary dedup identity of a send event, and `sg_event_id` is demoted to a stored forensic-correlation column with no role in uniqueness. This is deliberately NOT `add-alongside`: keeping `sg_event_id` in the enforced key alongside the new columns would preserve exactly the bypass CMP-07 exists to close, because a redelivery varying only `sg_event_id` would still produce a distinct key tuple. The generalization ("an occurrence is identified by what the server observed about it") replaces the specific ("an occurrence is identified by the provider's event id"), and the old specific becomes one non-authoritative attribute of the row.

**Structural constraint on the promotion:** `occurred_at` cannot be dropped from the key even though it is provider-supplied. `send_events` is partitioned by range on `occurred_at`, and Postgres requires every unique constraint on a partitioned table to include all partition-key columns. What makes this safe is plan 13-04's bounding: `occurred_at` is no longer arbitrary provider input by the time it reaches the key.

**Suggested invariant test (advisory, encoded in this plan's tasks):** a redelivery of the same occurrence with a different `sg_event_id` inserts one row — this is the contract test for the generalized intent, and it fails under the old key.
</assumption_delta_decision>

Structure the migration in this order, with each step's hazard named in a SQL comment:

Step 0 — resolve pre-existing duplicates. Delete all but the earliest-`received_at` row within each `(workspace_id, send_id, event_type, occurred_at)` group where `send_id IS NOT NULL`. Earliest-`received_at` wins because it is the first observation of the occurrence, and `received_at` is server-controlled — the only field in the row a redelivery cannot vary. This must be bounded and batched per the Phase 12 sweep conventions, not a single unbounded DELETE: the table is partitioned and potentially large, and a single statement holds locks for its whole duration. Use a bounded loop over a keyset or a `LIMIT`-ed CTE, committing each batch.

Step 1 — create the parent index metadata-only. Issue `CREATE UNIQUE INDEX send_events_dedup_v2_idx ON ONLY send_events (workspace_id, send_id, event_type, occurred_at)`. It must be `UNIQUE`: a non-unique index cannot back dedup and cannot be an `ON CONFLICT` target, so a plain `CREATE INDEX` here produces a migration that applies cleanly and then fails every insert at runtime. `ON ONLY` makes this metadata-only and instant; the parent index stays invalid until every partition's index is attached.

Step 2 — per attached partition, build the matching unique index with `CREATE UNIQUE INDEX CONCURRENTLY` and then `ALTER INDEX send_events_dedup_v2_idx ATTACH PARTITION <partition index>`. A concurrent build issued directly against the partitioned parent errors immediately — this is an unsupported operation, not a lock or permission problem. Enumerate partitions from the catalog the way `ensure-partitions.ts` does rather than hard-coding a month list, so a database with a different set of attached partitions than this dev environment still migrates. Once every partition's index is attached, Postgres marks the parent index valid automatically; assert `pg_index.indisvalid` for the parent afterwards rather than assuming it — this is the same class of silent failure as Phase 14's Pitfall 17, where an invalid index enforces nothing and reports no error.

Note that `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block. Check how this project's migration runner wraps statements (the `--> statement-breakpoint` convention in existing migrations and what `lint:migrations` enforces) and structure the file so the concurrent builds are not wrapped in a transaction. If the runner cannot express that, fall back to a non-concurrent per-partition `CREATE UNIQUE INDEX` and record the trade in the SUMMARY: a brief write lock per partition at migration time, in exchange for a migration that actually applies. Do not silently emit CONCURRENTLY inside a transaction — it fails at apply time.

Step 3 — promote to an enforced constraint if and only if Postgres supports it here. `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX` is documented as not supported on partitioned tables; verify this against the PostgreSQL version in use before writing the statement. If unsupported, do not attempt it: an attached, valid unique index on a partitioned table enforces uniqueness on its own, and `ON CONFLICT (workspace_id, send_id, event_type, occurred_at)` matches a unique index directly without needing a named constraint. Record which of the two paths this database supports in the SUMMARY, because it determines whether a named constraint exists for future migrations to reference.

Step 4 — drop the old dedup constraint. Confirm its actual name from the live catalog first: migration 0020 declares it inline as `UNIQUE (workspace_id, sg_event_id, occurred_at)`, so Postgres auto-generated the name and it must be read rather than assumed. This step is last, after the new index is enforced and valid — dropping first would leave a window with no dedup protection at all.
