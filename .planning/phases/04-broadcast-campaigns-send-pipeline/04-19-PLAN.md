<objective>
Close CR-01 (Critical), the single plannable code gap in 04-VERIFICATION.md (verified 2026-07-07T08:10:00Z, gaps_found 8/10). Every test send's List-Unsubscribe token is signed with the literal placeholder string `"test-send"` (apps/worker/src/queues/send-dispatch.ts:366, `contactId: contactId ?? "test-send"`) because the test-send route (apps/api/src/modules/campaigns/campaigns.routes.ts:446-499) never sets a contactId on the enqueued job. When that link is redeemed — a marketer clicking their own test email, or Gmail/Yahoo auto-firing the RFC 8058 List-Unsubscribe-Post one-click POST — apps/api/src/modules/delivery/unsubscribe.routes.ts:168-171 runs `UPDATE contacts SET subscription_status = 'unsubscribed' ... WHERE id = $1` with a non-UUID literal against a uuid-typed column (packages/db/src/schema/contacts.ts:27). Postgres raises 22P02; there is no try/catch and no route error handler, so the request 500s — and produces a distinguishable response, violating the route's own documented byte-identical-response invariant (unsubscribe.routes.ts threat-model comment, T-04-03-02).

This gap is inherently one thin vertical slice with two defense-in-depth layers plus regression coverage:
1. Worker (root cause): sign a real random UUID when the test-send job has no contactId, so a redeemed link always resolves to either a real contact or an unknown-but-valid UUID (0 rows updated, still the normal 2xx).
2. API (defense-in-depth): guard the public unsubscribe POST against a non-UUID contactId, treating it exactly like an unknown contact — no mutation, same uniform 2xx/HTML response — rather than letting it reach the UPDATE unguarded.
3. Regression: pin both ends so the defect cannot silently return.

Scope guardrail (per 04-VERIFICATION.md): the second remaining gap — populating UNSUBSCRIBE_TOKEN_SECRET / PUBLIC_APP_URL in .env (harness-denied path) and the live SendGrid UAT re-run of Tests 4/5/6/7/12/13 — is human verification, NOT an executable task here. See <verification>.

Purpose: A marketer's own test send carries a List-Unsubscribe link that actually works when redeemed, without crashing the public unsubscribe endpoint (CAMP-04, SUBS-04).
Output: A worker root-cause fix + worker regression assertion; an API route UUID guard + a new API regression test; the full workspace suite stays green (currently 265/265).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `/unsubscribe/:token` (POST) | Unauthenticated, no session, no workspace prefix. The signed token in the URL path is the sole authorization input. Mailbox providers (RFC 8058 one-click) and end recipients both cross here. |
| worker → signed token → API route | The worker signs the token's `contactId`; the API route later trusts `payload.contactId` (HMAC binds it) and passes it straight into a uuid-typed `UPDATE ... WHERE id = $1`. A bad value signed by the worker becomes a bad value trusted by the route. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-19-01 | Denial of Service | `unsubscribe.routes.ts` POST → `UPDATE contacts ... WHERE id = $1` | high | mitigate | Root cause: worker signs a valid random UUID for test-send tokens (Task 1). Defense-in-depth: POST handler gates the UPDATE on `isUuid(payload.contactId)` (Task 2), so a non-UUID contactId can never reach the uuid column and raise an uncaught 22P02 → 500 on the public endpoint. |
| T-04-19-02 | Information Disclosure | `unsubscribe.routes.ts` POST response uniformity | medium | mitigate | A distinguishable 500 for a structurally-invalid contactId (vs the uniform 2xx for unknown/forged/expired tokens) is a weak enumeration oracle and breaks the documented byte-identical-response invariant (T-04-03-02). The UUID guard makes the non-UUID case fall through to the identical response block — no branch on the reply. Pinned by the byte-identical assertion in the new API regression test. |
| T-04-19-03 | Spoofing | `/unsubscribe/:token` token forgery | low | accept | Unchanged/existing: verifyUnsubscribeToken does a timing-safe HMAC compare; any forged/tampered token degrades to the same uniform response. No new surface introduced by this plan. |
| T-04-19-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs in this gap plan — both worker and API vitest lanes already exist (04-16/04-18) and all imports (`randomUUID`, `signUnsubscribeToken`, `verifyUnsubscribeToken`) are already in-tree. No `[ASSUMED]`/`[SUS]` packages, so no legitimacy checkpoint required. |
</threat_model>
