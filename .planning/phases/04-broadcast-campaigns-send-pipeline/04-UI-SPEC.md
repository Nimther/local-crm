# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Provenance note:** 04-CONTEXT.md's decisions (D-01…D-05 user-confirmed, D-06…D-19 auto-selected while the user was away from keyboard — same precedent as Phase 1/2/3) and 04-RESEARCH.md's architecture were both produced without further live user input available at this design-contract session. Following Phase 3's precedent, no new interactive round was run here. Every value below either (a) is inherited unchanged from `01-UI-SPEC.md`/`02-UI-SPEC.md`/`03-UI-SPEC.md` — the established, already-implemented design system (verified live against `apps/web/components.json`, `tailwind.config.ts`, `src/index.css`, and existing feature components) — or (b) is a prescriptive researcher decision for this phase's new screens (campaign list/builder, schedule/launch/cancel dialogs, live-progress sending view, send settings, public unsubscribe page), made by extending Phase 1–3's exact conventions (status-badge semantics, combobox pattern, progress-bar usage, Russian copy register) rather than inventing new ones. Revise by re-running `/gsd-ui-phase 4` if any default should change.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `apps/web/components.json` present) |
| Preset | style: `new-york`, base color: `neutral`, CSS variables: yes |
| Component library | radix (via shadcn) |
| Icon library | lucide-react |
| Font | Inter (variable), system-ui fallback stack |

No changes to Phase 1–3's design-system configuration. `apps/web/tailwind.config.ts` and `apps/web/src/index.css` are reused as-is — no new tokens, no new CSS variables, no new hues.

**No new shadcn components needed this phase.** Every screen in this phase (campaign list, campaign builder, schedule/launch/cancel dialogs, sending progress view, send settings, public unsubscribe page) is buildable from the already-installed set: `button`, `input`, `label`, `form`, `card`, `dialog`, `alert-dialog`, `dropdown-menu`, `select`, `badge`, `table`, `separator`, `sonner`, `tooltip`, `checkbox`, `skeleton`, `popover`, `command` (Phase 3's combobox pattern — reused verbatim for the template/sender pickers), `progress` (Phase 2's CSV-import pattern — reused verbatim for send progress), `radio-group` (Phase 2's pattern — reused for send-now/schedule choice), `textarea` (Phase 2's pattern — reused for the test-send JSON editor), `tabs` (Phase 2's pattern — available for campaign detail sub-views if needed).

**No new date-picker library.** Per Phase 3's established convention ("no date-picker library is needed"), the schedule date/time field reuses a native `<input type="datetime-local">`, matching the codebase's existing native-input-for-date convention (`CustomPropertyEditor.tsx`'s `<input type="date">`). D-06's timezone label ("09:00, Europe/Belgrade") renders as Label/meta text next to the input, derived from `Intl.DateTimeFormat().resolvedOptions().timeZone`.

## Typography

Exactly 4 sizes, 2 weights — identical to Phase 1–3, no new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / meta | 14px (`text-sm`) | 400 regular | 1.5 |
| Body | 16px (`text-base`) | 400 regular | 1.5 |
| Heading (section / card title) | 20px (`text-xl`) | 600 semibold | 1.2 |
| Display (page title, big-number callouts) | 28px (`text-display` token) | 600 semibold | 1.2 |

Phase-4-specific usage of the existing roles:
- Label/meta (14px): status-badge text, field labels (Аудитория, Шаблон, Отправитель, Дата и время), timezone label next to the schedule picker, exclusion-breakdown line items ("320 отписаны", "130 в списке подавления"), "N из M отправлено" progress caption, "тестовое письмо отправлено на …" toast subtext.
- Body (16px): campaign builder helper/description text, dialog body copy (launch confirm, cancel confirm, delete confirm), empty-state body text.
- Heading (20/600): section titles — «Аудитория», «Шаблон и отправитель», «Тестовое письмо», «Прогресс отправки», «Настройки отправки» — and campaign builder/detail page card titles.
- Display (28/600): the sendable-audience count on the launch confirm dialog and campaign builder ("~12 400 получателей"), the live "N отправлено" number during sending — same role Phase 3 used for the segment live-count number; no new size introduced.

## Color

Identical palette to Phase 1–3 — no new hues, no gradients. One documented, narrow extension of the accent's usage (below).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` / `neutral-50` (`--background`) | Page background, main content surface |
| Secondary (30%) | `neutral-100` `#F5F5F5`, `neutral-200` `#E5E5E5` borders | Cards, table header row, sidebar, input/select borders |
| Accent (10%) | `indigo-600` `#4F46E5` (`--primary`) | See reserved list below — nothing else |
| Destructive | `red-600` `#DC2626` (`--destructive`) | Destructive actions only (see list) |

**Accent (`indigo-600`) reserved exclusively for (extends Phase 1–3's list with this phase's screens):**
1. Primary CTA button per screen (one per screen max): «Создать кампанию», «Сохранить черновик», «Отправить сейчас», «Запланировать», «Отправить тестовое письмо», «Сохранить настройки»
2. Active «Кампании» nav item in the workspace sidebar (same rule as Phase 1's active-nav-item reservation)
3. Focus rings (`--ring`), same as Phase 1–3
4. Checked/selected states of checkbox/radio-group/select, same as Phase 1–3
5. **New, narrow extension — "active operation" indicator:** the sending-progress bar's determinate fill (shadcn `Progress`'s default primary fill — same visual mechanism Phase 2 already uses for CSV-import progress, not a new pattern) and the **"Отправляется" status badge** (`indigo-50` background / `indigo-600` text). Both signal the *same* in-flight send operation on a screen; this is the only status badge allowed to use the accent hue, and only because it mirrors the progress bar's own color, not because "in progress" is being newly promoted to a general-purpose UI color.

**Destructive (`red-600`) reserved exclusively for (extends Phase 1–3's list):**
1. «Удалить черновик» button + its confirmation dialog
2. «Остановить отправку» button + its confirmation dialog (D-09 — cancel during sending)
3. Inline validation error text/borders (missing template/sender/audience at launch time, invalid schedule date)
4. The "N ошибок" failed-count callout in the sent-campaign summary (D-10) — text only, not a badge background

**Semantic status colors (badges only, never general UI — extends Phase 1–3's precedent):**

| Campaign status | Badge | Rationale |
|------------------|-------|-----------|
| **Черновик** (draft) | `neutral-500` text on `neutral-100` bg | Resting, non-active state — same treatment as unsubscribed contacts |
| **Запланирована** (scheduled) | `amber-700` text on `amber-50` bg | Pending future action — same amber-as-"needs attention" precedent as Phase 1's email-not-verified banner and Phase 3's degraded-preview warning |
| **Отправляется** (sending) | `indigo-600` text on `indigo-50` bg | The one accent extension above — active operation, mirrors the progress bar |
| **Отправлена** (sent) | `green-600` text on `green-50` bg | Success — same green as "Подписан"/CSV-created precedent |
| **Отменена** (canceled) | `neutral-500` text on `neutral-100` bg | Resting terminal state, not a failure (D-09) — distinguished from draft by an `XCircle` icon, not a new color |

No gradients. No additional hues. No charts in this phase.

## Copywriting Contract

All UI copy is **Russian** (per Phase 1–3 convention). Sentence case, address the user with «вы» (lowercase), no exclamation marks.

### Primary CTAs (verb + noun, one per screen)

| Screen / Element | Copy |
|-------------------|------|
| Campaigns list | «Создать кампанию» |
| Campaign builder — save without sending | «Сохранить черновик» |
| Campaign builder / launch confirm — send immediately | «Отправить сейчас» |
| Campaign builder / schedule dialog — confirm schedule | «Запланировать» |
| Test-send panel | «Отправить тестовое письмо» |
| Campaign detail — cancel a scheduled campaign | «Отменить кампанию» |
| Campaign detail — stop an in-flight send | «Остановить отправку» |
| Campaign row action | «Дублировать» |
| Send settings page | «Сохранить настройки» |
| Template/sender combobox refresh | «Обновить список» |

### Empty states

| Element | Copy |
|---------|------|
| Campaigns list, no campaigns yet | Заголовок: «Кампаний пока нет» · Тело: «Создайте кампанию — выберите сегмент-аудиторию и шаблон, чтобы отправить рассылку через SendGrid.» · CTA: «Создать кампанию» |
| Template combobox, no Dynamic Templates in the tenant's SendGrid account | Helper text: «Шаблоны не найдены — создайте Dynamic Template в SendGrid или введите template_id вручную.» · Secondary action: «Обновить список» |
| Sender combobox, no verified senders | Helper text: «Нет верифицированных отправителей — подтвердите адрес в SendGrid, затем обновите список.» |
| Exclusion breakdown, nothing excluded | Line omitted entirely rather than showing "0 исключено" — only non-zero exclusion reasons render |

### Error / validation states (problem + next step, never a bare code)

| Case | Copy |
|------|------|
| Launch/schedule blocked — no audience selected | «Выберите сегмент-аудиторию» — inline under the audience field, launch/schedule buttons disabled |
| Launch/schedule blocked — no template selected | «Выберите шаблон письма» — inline under the template field |
| Launch/schedule blocked — no sender selected | «Выберите отправителя» — inline under the sender field |
| Schedule date/time in the past | «Выберите дату и время в будущем» — inline under the datetime field |
| Test-send failure | «Не удалось отправить тестовое письмо. Проверьте шаблон и отправителя, затем попробуйте снова.» |
| Empty sendable audience at send-start (D-05) | Non-error informational banner (amber, same style as Phase 3's degraded-preview warning, not destructive-red): «Аудитория была пуста: {N} исключено — {причина}.» Campaign still completes to «Отправлена» with 0 sent — this is expected behavior, not a failure. |
| Segment referenced by a scheduled campaign is edited (D-03) | Warning shown in the **segment editor**, not here: «Используется запланированной кампанией «{campaign}» — изменения повлияют на её аудиторию.» (amber inline note, non-blocking) |
| Segment referenced by any campaign — delete attempt (D-03/Phase 3 D-14) | «Нельзя удалить сегмент — он используется в кампании «{campaign}». Сначала отмените или удалите кампанию.» (shown in the segment delete flow) |
| Generic server error | «Что-то пошло не так. Попробуйте ещё раз — если ошибка повторится, обновите страницу.» (same as Phase 1–3) |

| Action | Confirmation copy |
|--------|-------------------|

| Остановка отправки (D-09 — cancel during sending) | AlertDialog: «Остановить отправку кампании «{название}»?» · Тело: «Оставшиеся письма отправлены не будут. Уже отправленные письма отозвать нельзя. Кампания перейдёт в статус «Отменена» с итоговым числом отправленных писем.» · Кнопки: «Остановить отправку» (red-600) / «Продолжить отправку» |
| Отправка кампании сейчас (consequential but not destructive — primary accent, not red, since sending is the expected main action) | Dialog: «Отправить кампанию «{название}» сейчас?» · Тело: «Будет отправлено ~{sendable_count} писем. {excluded_count} контактов исключено: {breakdown line items}.» · Кнопки: «Отправить» (primary indigo) / «Отмена» |
| Отмена запланированной кампании (D-07 — returns to draft, low-risk/reversible, no destructive styling) | AlertDialog: «Отменить запланированную отправку «{название}»?» · Тело: «Кампания вернётся в черновик. Вы сможете отредактировать её и запланировать заново.» · Кнопки: «Отменить кампанию» (default button, not red) / «Не отменять» |

### System copy notes

- Toasts (sonner): успех — «Кампания создана», «Черновик сохранён», «Кампания запланирована», «Кампания отправлена», «Кампания продублирована», «Тестовое письмо отправлено на {email}», «Отправка остановлена», «Кампания отменена» — существительное + глагол-результат, без восклицательных знаков (same convention as Phase 1–3).
- Campaign status badges use the exact Russian labels from the table in the Color section above: «Черновик», «Запланирована», «Отправляется», «Отправлена», «Отменена».
- Schedule picker: label «Дата и время отправки», input `type="datetime-local"`, timezone caption directly under it in Label/meta muted text: «Время указано в вашем часовом поясе ({resolved IANA zone, e.g. Europe/Belgrade})» — mirrors D-06's "explicit label" requirement without a new component.
- Scheduled campaign's estimated audience count (D-01): Label/meta text next to the estimate, always framed as provisional: «~{count} на момент проверки» — never presented as a final number until send-start freezes the snapshot (D-02).
- Audience breakdown (D-04), rendered as a small list under the Display-size sendable count, same visual idiom as Phase 3's live-count panel: sendable count in Display (28/600) + label «получателей» underneath in Label/meta, then each non-zero exclusion reason as its own Label/meta line prefixed with its count, e.g. «320 отписаны», «130 в списке подавления», «50 без email», «12 превысили частотный лимит». Exact Russian status nouns reused verbatim from `SubscriptionStatusBadge.tsx`'s labels («Отписан» → «отписаны», «В списке подавления» → «в списке подавления»).
- Live progress (CAMP-05): Progress bar (determinate) + caption in Label/meta directly under it: «{sent} из {total} отправлено» — while sending, poll every 3 seconds (TanStack Query `refetchInterval: 3000` gated on `status === 'sending'`, stopped once the campaign reaches a terminal status) — same polling-not-SSE default 04-RESEARCH.md recommends (Assumption A4). On completion with `failed > 0` (D-10), add a second Label/meta line in destructive red: «{failed} ошибок» — never hide partial failures.
- Test-send panel (CAMP-04, D-19): sample `dynamic_template_data` auto-fills from a real contact in the selected segment (fallback: documented placeholder shape per D-18) into a monospace `textarea` (JSON, editable before sending) — same "editable JSON before sending" affordance, styled with `font-mono text-sm`, no syntax highlighting library added.
- Duplicate (D-11): row action «Дублировать» in the campaigns list's row `dropdown-menu` — creates a new `draft` copy with all settings (segment, template, sender), no dialog/confirmation needed since it's non-destructive; toast «Кампания продублирована» and navigate to the new draft's builder.
- Send settings page (workspace-level, Owner/Admin-gated per Phase 1's role-guard pattern): two fields in a single `card` — «Частотный лимит» (number input, default 3, helper text «Не более стольких маркетинговых писем одному контакту за 24 часа») and «Лимит отправки в секунду» (optional number input, placeholder «По умолчанию платформы», helper text «Оставьте пустым, чтобы использовать стандартный лимит платформы»). Single «Сохранить настройки» button, same disabled-during-submit pattern as every other form in the app.
- Public unsubscribe page (D-15, no session/workspace shell — standalone centered card, no sidebar/nav): confirmation state (GET, human click) shows heading «Отписаться от рассылки?» + body «Нажмите кнопку, чтобы больше не получать маркетинговые письма от этой компании.» + button «Отписаться» (primary); success state (after POST, one-click or confirmed) shows heading «Вы отписаны» + body «Вы больше не будете получать маркетинговые письма от этой компании.» — no further action offered, matches the minimal hosted-page scope in 04-CONTEXT.md D-15.

Interaction rules (extends Phase 1–3's, unchanged principles):
- Every mutating button gets a disabled + loading state during the request; no double-submit.
- Focus visible on all interactive elements (accent ring). Dialogs and popovers trap focus, close on Esc.
- Campaign launch/schedule is Owner/Admin-only (Phase 1 D-19 role gate, extended here); Members can create/edit/duplicate/delete drafts and send test emails but the launch/schedule buttons render disabled with a tooltip: «Только Owner или Admin может запускать кампании.» — same disabled+tooltip pattern already used for suppressed-contact controls in Phase 2.
- Live-progress polling uses the campaign's own status as the query-enable gate (`enabled: status === 'sending'`, `refetchInterval: 3000`) — stops automatically on any terminal status, avoiding an orphaned poll loop.
- The audience breakdown and live-count treatments reuse Phase 3's exact `isFetching`-dim + spinner cue (`Loader2`, `animate-spin`) for the estimated-count-while-scheduled state (D-01) — never a full skeleton over a previously-fetched number, since the stale estimate remains meaningful context.
- Same "away from keyboard" precedent applies to this document: no new interactive round was run; all values above are directly extending 04-CONTEXT.md/04-RESEARCH.md's own explicit Russian-language decisions or Phase 1–3's established conventions.
