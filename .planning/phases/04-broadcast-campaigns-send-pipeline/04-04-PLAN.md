<objective>
Build the throttled, idempotent SendGrid dispatch engine: the per-tenant Redis token bucket, the shared `send-dispatch` processor (decrypt tenant key → idempotency insert-gate → pre-send gate → build mail/send with List-Unsubscribe → per-tenant RPS → SendGrid v3 → 429/5xx backoff → record ledger), and the two separate BullMQ workers (`email-broadcast`, `email-triggered`) that both call that one processor.

Purpose: This is the heart of the send loop — SEND-01/02/03/05/06/07 and the enforcement points for SUBS-03/SUBS-04. Both this phase's broadcasts and Phase 6's triggered flows converge here, which is exactly why the pre-send/rate-limit/dispatch logic is one shared function called by two workers (ARCHITECTURE Pitfall 6/7). After this plan an enqueued send job actually reaches SendGrid, throttled and deduplicated — the core of the phase goal.
Output: rate-limiter, send-dispatch, two workers, three Wave-0 test files, worker registration.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker → SendGrid API | Tenant's decrypted key + recipient PII crosses to a third party |
| Redis job payload → worker | Job data is re-parsed and re-scoped; workspaceId re-derived, never ambient |
| broadcast lane vs triggered lane | Two queues must remain isolated so one cannot starve the other |

## STRIDE Threat Register

| T-04-04-01 | Spoofing / Information Disclosure | tenant SendGrid key used for the wrong tenant | high | mitigate | Raw-fetch per-call dispatch (delivery-core.sendTenantMailV3), never @sendgrid/mail's global singleton; workspaceId re-derived from job.data and bound via withTenant per job (Pitfall 2/5) |
