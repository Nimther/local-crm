<objective>
Close the single remaining Phase 4 blocker (SUBS-04 / new CR-01 in 04-REVIEW.md): the public `POST /unsubscribe/:token` endpoint returns HTTP 415 for both real-world callers of the one-click List-Unsubscribe mechanism this phase advertises. Fastify's default parser set (application/json + text/plain) rejects `application/x-www-form-urlencoded` with `415 FST_ERR_CTP_INVALID_MEDIA_TYPE` *before* the route handler runs, so neither (a) a mailbox provider's RFC 8058 one-click POST nor (b) the confirm page's own `<form method="POST">` submit ever unsubscribes the contact.

Purpose: The send pipeline stamps `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` on every email (verified correct). This plan makes the endpoint those headers point to actually accept its two real request shapes — turning a live CAN-SPAM/GDPR-adjacent compliance + sender-reputation gap into a working one-click unsubscribe.

Output: One encapsulated content-type parser registered inside `registerUnsubscribeRoutes`, plus a new regression suite that exercises the parser with explicit Content-Type headers (the existing suites never send one, so they silently miss this).

Scope fence: This closes SUBS-04 only. WR-01..WR-06 from 04-REVIEW.md are explicitly non-blocking and out of scope for this round.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mailbox provider / recipient browser → `POST /unsubscribe/:token` | Untrusted, unauthenticated request body + Content-Type header cross here. Authorization is the HMAC-signed token in the URL path (verifyUnsubscribeToken), never the body. |
| unsubscribe encapsulation context → rest of Fastify app (`/api/auth/*`, campaigns, contacts, segments) | A content-type parser registered inside registerUnsubscribeRoutes must stay scoped to `/unsubscribe/*` and must not weaken body parsing anywhere else. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-14-01 | Denial of Service | urlencoded parser on public POST /unsubscribe/:token | medium | mitigate | Set an explicit `bodyLimit: 1024` on the addContentTypeParser so oversized urlencoded bodies are rejected before buffering; body is parsed as buffer then discarded (done(null, undefined)); ample for the ~24-byte RFC 8058 payload and the empty confirm-form body. |
| T-04-14-02 | Tampering | content-type parser encapsulation scope | high | mitigate | Register the parser INSIDE registerUnsubscribeRoutes (a plain-function, non fastify-plugin encapsulated context per server.ts) so it applies only to /unsubscribe/*, not /api/auth/*/campaigns/contacts. Register the specific media type only — no catch-all "*" (unlike auth/plugin.ts). Test 3 asserts an unregistered content type (application/xml) still yields 415 on the same route, pinning the fix as narrow. |
| T-04-14-03 | Spoofing | forged / empty one-click POST body | low | accept | The parser deliberately discards the body; authorization is unchanged (HMAC-signed token in the URL path). A forged or empty body cannot unsubscribe an arbitrary contact — forged / unknown-contact / expired tokens remain byte-identical no-ops (covered by existing unsubscribe.test.ts cases, re-run in Task 2). |
| T-04-14-SC | Tampering | npm/pip/cargo installs | low | accept | No new packages are installed — addContentTypeParser is a built-in Fastify 5.9 API. No supply-chain surface is added by this plan; no legitimacy checkpoint required. |

ASVS level: L1. Block-on: high. The one high-severity threat (T-04-14-02, parser leakage) is mitigated by encapsulation + a media-type-specific registration + an explicit 415 scope-guard test. No unmitigated high/critical threats remain.
