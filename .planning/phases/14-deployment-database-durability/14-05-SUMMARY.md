# Phase 14 Plan 05: Migration Rollback/Roll-Forward Rehearsal (DB-07) Summary

**Every migration classified into auto-reversible/forward-only tiers (39/24 of 63), an empty-diff gate closed with exactly one backfilled snapshot (not the assumed 52), and a revert-then-roll-forward rehearsal that reuses the real production migrate runner and fails loudly on a corrupted revert -- proven by deliberately breaking it once.**

## Performance

- **Duration:** ~3h (heavy on investigation: reading 63 migration files, reverse-engineering drizzle-kit's diff internals from source, and empirically proving the snapshot-consumption finding before writing any code)
- **Tasks:** 3
- **Files created:** 7
- **Files modified:** 1 (`packages/db/package.json`)

## Accomplishments

- **Tier classification (Task 1):** `packages/db/src/migration-tiers.ts` classifies all 63 shipped migrations (0000-0062). 39 forward-only, 24 auto-reversible. The trailing contiguous auto-reversible run at this commit is exactly `["0062_member_unique_org_user"]` -- migration 0061 (drops the plaintext suppression column + its constraint) is forward-only and stops the run one migration short of the tail. `tierFor` throws for an unknown tag; the test cross-checks the record against an independent SQL scan for the plan's five named forward-only signatures (`CREATE TYPE`, `ALTER TYPE ... ADD VALUE`, `CREATE POLICY`, `ATTACH PARTITION`, `DROP COLUMN`, `DROP CONSTRAINT`) in both directions (every signature match must be forward-only; every forward-only-by-signature migration must actually match).
- **Investigation finding that reshaped Task 2's scope:** drizzle-kit's `generate` diff engine reads **only the alphabetically-last snapshot file** under `meta/` for its "previous state" comparison -- confirmed by reading `node_modules/drizzle-kit/bin.cjs`'s `prepareOutFolder`/`preparePrevSnapshot` (`snapshots[snapshots.length - 1]`) directly, then proven empirically twice: once via the programmatic API (`generateDrizzleJson`/`generateMigration`) and once via the real CLI against a scratch copy of the migrations directory. The repository had 63 shipped SQL migrations and only 11 snapshot files (newest `0034_snapshot.json`) before this plan -- but the empty-diff gate needed **exactly one** new snapshot to close, not a 52-file historical backfill, because `generate` was never going to read the other ~51 regardless of whether they existed. Verified the CLI genuinely needs no `DATABASE_URL`/database connection at all when `--config` is bypassed in favor of explicit `--dialect`/`--schema`/`--out` flags.
- **The backfill (Task 2):** `packages/db/migrations/meta/0062_snapshot.json`, generated by drizzle-kit's own `generateDrizzleJson` (never hand-typed), with `prevId` chained from the prior last snapshot (`0034`)'s id. `packages/db/migrations/meta/_journal.json` was deliberately **not** touched -- 0062 already has a journal entry from plan 14-02; only its missing snapshot was backfilled. `packages/db/scripts/check-empty-diff.ts` (+ `npm run db:check-empty-diff`) never calls drizzle-kit's `writeResult`, so it can never accidentally write a migration/snapshot/journal entry into the repository (T-14-25) -- proven in the test by a byte-identical recursive directory listing before and after.
- **The rehearsal (Task 3):** `packages/db/src/__tests__/migration-rollback-rehearsal.test.ts` applies the full shipped history to a freshly-provisioned ephemeral database via the real `scripts/migrate-runner.mjs` (spawned as a child process, exactly like plan 14-01's own `migrate-runner-advisory-lock.test.ts` does, for the same `.ts`-cannot-import-`.mjs`-cleanly reason), fingerprints the schema (columns with type/nullability, constraints, indexes, enum values -- all four read from `information_schema`/`pg_catalog`, deterministically ordered), reverts the trailing run via a hand-verified per-tag inverse (`MIGRATION_INVERSES`), deletes the corresponding `"drizzle"."__drizzle_migrations"` rows so the migrator sees it pending again, rolls forward via the same runner, and asserts the fingerprints are identical. Guards its own DSN via Phase 8's existing `assertTestDatabaseUrl` (T-14-22) before any DDL statement runs.
- **Demonstrated the assertion has teeth (required by acceptance criteria):** temporarily added an extra, unrelated `ALTER TABLE organization DROP CONSTRAINT organization_slug_unique;` to the revert step and re-ran the test. It failed loudly, naming exactly what was wrong:

  ```
  AssertionError: schema fingerprint mismatch after revert + roll-forward:
  MISSING after roll-forward (constraints): {"name":"organization_slug_unique","table":"organization","definition":"UNIQUE (slug)"}
  MISSING after roll-forward (indexes): {"name":"organization_slug_unique","table":"organization","definition":"CREATE UNIQUE INDEX organization_slug_unique ON public.organization USING btree (slug)"}
  ```

  Restored the clean version immediately after (confirmed byte-identical to the pre-corruption file via `diff`) and re-ran to confirm green. The corrupted version was never committed.
- **Runbook:** `docs/runbooks/migration-rollback-and-roll-forward.md` states the two tiers (citing `migration-tiers.ts` as the single source of truth, never restating the classification itself), how to determine which tier a range of deployed SHAs' migrations belong to, the auto-reversible procedure step by step (mirroring exactly what the rehearsal test does), the forward-only restore-based recovery path (cites `docs/runbooks/restore-drill.md`, plan 14-11's future deliverable, by its exact planned filename), and states honestly that the restore drill has not yet been performed as of this plan -- "documented, not yet rehearsed" for the forward-only tier specifically. Also documents the three-proofs table (schema<->snapshot, SQL-chain<->empty-db, live-db<->journal) so an operator mid-incident cannot misread a green `db:check-empty-diff` as proof a live database matches the code (RESEARCH.md Pitfall D).

## Decisions Made

- **Snapshot backfill scope, measured not assumed:** see key-decisions above -- one file, not 52, because that is literally all `drizzle-kit generate` ever consumes.
- **`_journal.json` left untouched:** Task 2's file scope listed it, but the actual investigation showed no journal change was needed -- 0062's entry already existed.
- **`MIGRATION_INVERSES` as a per-tag registry, not a generic DDL inverter:** narrower scope, hand-verified per entry, throws loudly for any unregistered tag rather than guessing -- treated as evidence of a tier-classification error per the plan's own instruction, not a gap to silently patch.
- **Three additional forward-only classifications beyond the plan's literal five-signature list**, each with its own reasoning documented at the definition site in `migration-tiers.ts`: an irreversible data `UPDATE` (0034, 0046), a pure data `INSERT` with no DDL of its own (0040 -- no table/column/index/constraint to derive a "drop the X" inverse from), and a `GRANT`/`REVOKE`-only access-control change (0045). Also `0043` (`DROP POLICY`, whose own header says "must not be reverted independently") and `0019` (`ALTER POLICY`, an access-control expression change) -- both forward-only by the same access-control-posture reasoning the plan already applies to `CREATE POLICY`.
- **Rehearsal roll-forward via a spawned child process, not an import:** matches plan 14-01's own established precedent and constraint (`.ts` cannot cleanly import a plain `.mjs` script under `tsc`).

## Issues Encountered

- **`vi.resetModules()` does not clear Node's native ESM loader cache for a plain absolute-path dynamic `import()`.** Discovered while writing `migration-empty-diff.test.ts`'s negative case (mutate schema, check, revert, check again, all in one test): the second check silently saw the first (mutated) module instance. Rejected a query-string cache-busting fix in the production script (`?t=<timestamp>` on the import URL) because it broke Vite/oxc's TS transform under vitest with an unrelated parse error on an otherwise-valid union type declaration. Resolved instead by using two genuinely separate schema-directory copies (distinct absolute paths) for the mutated and original cases -- sidesteps the caching question entirely rather than fighting it, and matches how the real CLI is actually invoked (fresh process every time, no caching concern at all in production use).
- **The runbook's first-drafted tier-lookup command (`node -e 'require(".../migration-tiers.ts")'`) does not work** -- `packages/db` is ESM-only TypeScript with no build step; `require()` cannot resolve it, and confirmed empirically it throws `ERR_MODULE_NOT_FOUND`. Fixed to `npx tsx -e '...'` (tsx is already a `packages/db` devDependency, used the same way by every other script in this package) and re-verified it prints the correct tier before finalizing the runbook.
- **`drizzle-kit generate`'s interactive rename-conflict prompt (`promptColumnsConflicts`) throws under a non-TTY** rather than hanging, confirmed while investigating whether the empty-diff check needs the full historical backfill. This is what made the "just run generate for real and take whatever it produces" approach unsafe for a large stale-snapshot gap, and is part of why the one-snapshot-file finding mattered: a small, unambiguous diff (this plan's actual empty-diff and negative-case tests) never triggers this prompt at all.
- **Pre-existing gap noted, not fixed (out of scope):** `packages/db/scripts/*.ts` files (including the new `check-empty-diff.ts`) are not covered by any ESLint config block (`eslint.config.js` only matches `packages/*/src/**/*.ts`, not `packages/*/scripts/**/*.ts`) -- confirmed this is the SAME pre-existing gap `audit-missing-constraints.ts` and `count-member-duplicates.ts` already sit in (plan 14-02), not something this plan introduced. `npm run lint` still exits 0 because eslint silently skips unmatched files rather than warning on `eslint .`.
- **Broken-windows ledger update (informational, not filed here per this worktree's rules):** 14-01-SUMMARY.md and 14-02-SUMMARY.md both flagged `npm run build --workspaces --if-present` as failing in `@mega-crm/test-support` (a `checkStatementBreakpointPlacement` import mismatch in `migration-lint.test.ts`). Re-ran the full monorepo build during this plan's verification and it now exits 0 across every workspace, including `packages/test-support` -- the gap appears to have been resolved by another wave-1/wave-2 plan already merged into this worktree's base. Flagging the observation for whoever tracks the ledger to close that item, since this plan did not touch the files involved.
