<objective>
Close UAT gap **G-14-4**: all three Docker images (`docker/Dockerfile.api`, `.worker`, `.web`) fail at root `npm ci` with EUSAGE from a clean checkout, which also blocks UAT tests 5 and 6.

Root cause (fully diagnosed in `.planning/debug/docker-npm-ci-lockfile-desync.md`, no guessing required): `package-lock.json` is npm-11-shaped. vite 8.1.3 declares esbuild `^0.27.0 || ^0.28.0` as an OPTIONAL peer; npm 11 (dev/CI, Node 26 per `.nvmrc`) tolerates that peer being unsatisfied, so the lockfile only ever carried the hoisted esbuild 0.25.12 that drizzle-kit needs. Phase 14's Dockerfiles deliberately pin `node:22-slim` (npm 10) — whose ideal tree DOES include esbuild 0.28.x plus 26 `@esbuild/*` platform packages — and `npm ci` aborts because those entries are absent from the lock. The Docker build is the first-ever npm-10 consumer in this repo; no pre-merge gate exercises npm 10, which is why every CI run stayed green.

Purpose: make the lockfile satisfy both npm majors, and make it stay that way. The recurrence guard is part of the fix, not a nicety: npm 11's ideal tree does not require the added entries, so any routine `npm install <pkg>` on a dev/CI machine can silently drop them again and reintroduce a defect that only surfaces at `docker build` time.

Output: an additive-only regenerated lockfile, a fail-loud npm-10 guard wired into the required `static` CI job, and a pull_request-time Docker image build that proves the fix end-to-end in the one environment guaranteed to have a Docker daemon.

**Wave note:** wave 4, `depends_on: [14-06]` (the Dockerfiles this fix serves). This plan touches root `package.json`, which plans 14-09 and 14-11 also list — but both of those already committed their `package.json` edits (`test:deploy-script` and `test:restore-drill-script` are present in the working tree today); their only outstanding tasks are file-less human checkpoints on a real VPS. There is therefore no live file conflict, and sequencing this fix AFTER those checkpoints would be backwards: 14-09's first real deploy pulls GHCR images that cannot be built until this lockfile lands.

**No manifest dependency changes.** Every entry added to the lockfile is a transitive materialization of npm 10's ideal tree for packages that are ALREADY declared (vite's optional esbuild peer). Nothing is added to any `package.json`, so RESEARCH.md's package-legitimacy human gate does not apply; the standing check is Task 1's additive-only assertion.
</objective>
