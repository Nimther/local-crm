<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: Perform the point-in-time restore drill against the real repository</name>
  <what-built>
`scripts/restore-drill.sh` — a scripted point-in-time restore into a throwaway container, verified by `db:verify-restored` (row counts against a production baseline, expected partitions attached, RLS enabled-and-forced) and torn down on success. The verifier runs against an ordinary migrated database on every CI pass, and the script's ordering and production-safety guard are covered by dry-run tests.

What automation cannot establish: DB-10's requirement is that a restore has actually been performed. Every part of this that matters — that the real repository's bytes decrypt, that WAL replay reaches the requested moment, how long a restore of this cluster takes — needs the real repository and the real host. A mocked restore would prove the opposite of what is being claimed.
  </what-built>
  <how-to-verify>
Prerequisites: at least one full backup and a span of WAL in the repository (`pgbackrest info`), and enough free disk on the VPS for a second copy of the cluster.

1. Note the current time, then write a recognisable marker row into a non-production-critical table through the application, and note that time too. This gives you two timestamps that bracket a known change.
2. Wait for or trigger a WAL switch so the marker is archived.
3. Run the drill with a PITR target BEFORE the marker was written: `./scripts/restore-drill.sh <target-before-marker>`. Read the dry run first.
4. Confirm the restore completes and the verification passes: expected partitions attached, RLS enabled and forced where required, row counts consistent with the baseline.
5. Confirm the marker row is ABSENT from the restored cluster. This is the step that proves point-in-time recovery rather than backup unpacking — if the marker is present, the WAL replay overshot the target and the drill has not demonstrated PITR.
6. Confirm the production database was untouched: the marker row is still there, and production is still serving.
7. Confirm the scratch container and its volume were destroyed after the successful run.
8. Record the wall-clock duration of the restore, and the disk high-water mark during it.
9. Run the drill once more with a target AFTER the marker and confirm the marker IS present, so both directions of the target selection are demonstrated.
10. Report anything that needed a manual step the runbook did not describe — that is a runbook defect.
  </how-to-verify>

Include the restore duration and the disk high-water mark. Otherwise describe what failed and at which step.</resume-signal>
