<objective>
Give the worker the same health contract the API has (D-14) so the deploy script and Docker healthchecks probe all three services uniformly, and publish the container stop-grace-period as a machine-read value rather than a hand-typed one (Pitfall 7, the derivation Phase 12 expressly left for this phase to consume).

Purpose: the worker is the process a stop-old-then-start-new deploy has to sequence (R-05), and sequencing it correctly requires two observable facts — "the new worker is ready" and "the old worker has stopped accepting work". Neither exists today: `apps/worker/src/server.ts` has no HTTP listener at all. Separately, `apps/worker/src/shutdown-budget.ts` already computes the correct grace period and its own header comment says Phase 14 MUST set the container from that value; a YAML file cannot import a TypeScript constant, so the extraction mechanism has to be built.
Output: `apps/worker/src/health-server.ts` (`node:http`, no new dependency), lifecycle wiring in `WorkerRuntime`, a draining flag flipped by SIGTERM, and `scripts/print-stop-grace-period.mjs` with a test that pins it to the constant.
</objective>

## Planner decision to record (consumed by plans 14-08 and 14-09)

D-14 says the health server is localhost-only. That decision has a consequence the later plans must be built around, so it is settled here rather than left to each: the port is bound to the loopback interface and is **not** published to the host. Container healthchecks therefore probe it from inside the container, and the deploy script observes worker health through the container's own health status (`docker inspect` / `docker compose ps`), never by opening an HTTP connection from the host. The API's `/readyz`, which is already reachable through Caddy, remains the deploy script's HTTP-level gate.
