# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Provenance note:** 03-CONTEXT.md's decisions were themselves auto-selected while the user was away from keyboard (yolo mode, Phase 1/2 precedent — see its own provenance banner). This UI-SPEC session continues that precedent: no new interactive round was run. Every value below either (a) is inherited unchanged from `01-UI-SPEC.md`/`02-UI-SPEC.md` — the established, already-implemented design system — or (b) is a prescriptive researcher decision for phase-3-specific screens (segment builder, segment list, segment detail/member list), made by extending Phase 1/2's exact conventions rather than inventing new ones. Revise by re-running `/gsd-ui-phase 3` if any default should change.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `apps/web/components.json` present) |
| Preset | style: `new-york`, base color: `neutral`, CSS variables: yes |
| Component library | radix (via shadcn) |
| Icon library | lucide-react |
| Font | Inter (variable), system-ui fallback stack |

No changes to Phase 1/2's design-system configuration. `apps/web/tailwind.config.ts` and `apps/web/src/index.css` are reused as-is — no new tokens, no new CSS variables.

**New components to add via shadcn for this phase** (official registry only — no third-party):

```bash
npx shadcn@latest add popover command
```

`popover` + `command` together implement the one new interaction pattern this phase needs: a **combobox** (searchable select with free-text fallback), reused for two distinct fields — the behavioral condition's event-name picker (D-05: observed event names + free-text fallback) and the attribute condition's custom-property key picker (same autocomplete-from-registry pattern already established in Phase 2's `CustomPropertyEditor`, just promoted to a searchable combobox here since the segment builder's field list is longer than a form's property-editor rows).

Already-available components reused this phase (from Phase 1/2, no re-add needed): `button`, `input`, `label`, `form`, `card`, `dialog`, `alert-dialog`, `dropdown-menu`, `select`, `badge`, `table`, `separator`, `sonner`, `tooltip`, `checkbox`, `skeleton`.

**No new non-shadcn frontend dependency.** `@tanstack/react-table` and `@tanstack/react-query` (already installed since Phase 2) are reused as-is for the segment member-list table and the live-count/list queries — same `keepPreviousData` + debounce conventions as `ContactsListPage.tsx`. No date-picker library is needed: date-type attribute conditions (`before`/`after`) reuse the native `<input type="date">` pattern already established in `CustomPropertyEditor.tsx`; `in_last_days` reuses a plain number input, matching the behavioral condition's own day-count field.

## Spacing Scale

Declared values (must be multiples of 4) — identical to Phase 1/2, no changes:

## Typography

Exactly 4 sizes, 2 weights — identical to Phase 1/2, no new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / meta | 14px (`text-sm`) | 400 regular | 1.5 |
| Body | 16px (`text-base`) | 400 regular | 1.5 |
| Heading (section / card title) | 20px (`text-xl`) | 600 semibold | 1.2 |
| Display (page title, big-number callouts) | 28px (`text-display` token) | 600 semibold | 1.2 |

Phase-3-specific usage of the existing roles:
- Label/meta (14px): field/operator/timeframe select labels, condition-row helper text, the И/ИЛИ connector badges (uppercase, 14px/600), member-list table cell text, the "на {дата, время}" freshness meta text next to a segment's participant count.
- Body (16px): the plain-language recap line under each group (e.g. «Страна: RU или KZ», see Copywriting Contract), form helper/description text.
- Heading (20/600): section titles — «Определение сегмента», «Участники», «Сегменты», group-card titles («Группа 1», «Группа 2»).
- Display (28/600): the live-preview count number (D-04/D-08's SEGM-04 requirement) and the segment list/detail page's "участников" stat — same role Phase 2 used for its CSV dry-run stat numbers. No new size introduced for either.

## Color

Identical palette to Phase 1/2 — no new hues, no gradients.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` / `neutral-50` (`--background`) | Page background, main content surface |
| Secondary (30%) | `neutral-100` `#F5F5F5`, `neutral-200` `#E5E5E5` borders | Group cards, table header row, sidebar, input/select borders |
| Accent (10%) | `indigo-600` `#4F46E5` (`--primary`) | See reserved list below — nothing else |
| Destructive | `red-600` `#DC2626` (`--destructive`) | Destructive actions only (see list) |

**Accent (`indigo-600`) reserved exclusively for (extends Phase 1/2's list with this phase's screens):**
1. Primary CTA button per screen (one per screen max): «Создать сегмент», «Сохранить сегмент», «Сохранить изменения»
2. Active «Сегменты» nav item in the workspace sidebar (same rule as Phase 1's active-nav-item reservation)
3. Focus rings (`--ring`), same as Phase 1/2
4. Checked/selected states of checkbox/select, same as Phase 1/2

**Destructive (`red-600`) reserved exclusively for (extends Phase 1/2's list):**
1. «Удалить сегмент» button + its confirmation dialog
2. Inline validation error text/borders (empty group, missing count/days, empty name)

**Semantic status colors (badges/banners only, never general UI — extends Phase 1's amber-banner precedent):**
- Live-count timeout/degraded-preview warning (D-08's "narrow your conditions" escape hatch): `amber-50` background, `amber-800` `#92400E` text — same treatment as Phase 1's email-not-verified banner, not destructive-red, since the segment definition itself is not invalid, just slow to evaluate.
- И/ИЛИ group/condition connector pills: `neutral-500` on `neutral-100` — same neutral scheme as Phase 1's pending-invite badge. Never accent or destructive; these are structural labels, not actionable elements.

No gradients. No additional hues. No charts in this phase.

## Copywriting Contract

All UI copy is **Russian** (per Phase 1/2 convention). Sentence case, address the user with «вы» (lowercase), no exclamation marks.

### Primary CTAs (verb + noun, one per screen)

| Screen / Element | Copy |
|-------------------|------|
| Segments list | «Создать сегмент» |
| Segment builder — new segment | «Сохранить сегмент» |
| Segment builder — editing existing segment | «Сохранить изменения» |
| Add condition (within a group) | «Добавить условие» — dropdown-menu with two items: «По свойству» / «По событию» |
| Add group | «Добавить группу (И)» |

### Empty states

| Element | Copy |
|---------|------|
| Segments list, no segments yet | Заголовок: «Сегментов пока нет» · Тело: «Создайте сегмент — объедините контакты по свойствам и поведению. Он сразу станет доступен как аудитория для кампаний и цепочек.» · CTA: «Создать сегмент» |
| Segment detail, member list has 0 matches | Заголовок: «Пока никто не подходит под условия» · Тело: «Измените условия сегмента — список обновится автоматически.» |
| Event-name combobox, no observed events yet | Helper text under the combobox: «Событий этого воркспейса пока не поступало — введите имя вручную.» |
| Custom-property combobox, no custom properties yet | Helper text: «Кастомных свойств пока нет — они появятся здесь по мере поступления данных через API, события или импорт.» |

### Error / validation states (problem + next step, never a bare code)

| Case | Copy |
|------|------|
| Live count — timeout on complex conditions (D-08) | Inline warning under the count, amber style: «Не удалось быстро посчитать при таких сложных условиях. Уберите часть условий, чтобы увидеть точное число.» The last successfully computed count stays visible, dimmed, labeled «(устарело)» — never blanked to zero. |
| Group has zero conditions (save-time validation) | «Добавьте хотя бы одно условие в каждую группу» — inline under the empty group, save button stays enabled but the group is highlighted with a destructive-red border until fixed. |
| Behavioral condition "выполнено ≥ N раз" without a count | «Укажите количество» — inline under the count input. |
| Behavioral condition "за последние N дней" without a day count | «Укажите количество дней» — inline under the days input. |
| Segment name empty at save time | «Укажите название сегмента» — inline under the name field. |
| Generic server error | «Что-то пошло не так. Попробуйте ещё раз — если ошибка повторится, обновите страницу.» (same as Phase 1/2) |

### Destructive confirmations

| Action | Confirmation copy |
|--------|-------------------|
| Удаление сегмента (D-14 — free deletion in this phase, restrict-when-referenced lands in Phase 4/6) | AlertDialog: «Удалить сегмент «{название}»?» · Тело: «Сегмент будет удалён без возможности восстановления. Сейчас он нигде не используется, поэтому удаление ничем не ограничено — в следующих фазах кампании и цепочки будут блокировать удаление сегмента, на который они ссылаются.» · Кнопки: «Удалить сегмент» (red-600) / «Отмена». |

### System copy notes

- Toasts (sonner): успех — «Сегмент создан», «Сегмент обновлён», «Сегмент удалён» — существительное + глагол-результат, без восклицательных знаков (same convention as Phase 1/2).
- Live-count panel copy: number in Display (28px/600) + label «контактов подходит» underneath in Label/meta (14px), e.g. «12 458 контактов подходит». While the debounced request is in flight, dim the number (same `isFetching` dim cue as `ContactsListPage`, 02-13 precedent) and show a small muted spinner (lucide `Loader2`, `animate-spin`) next to it — never replace the number with a full skeleton, since the previous value is still meaningful context per D-08.
- Group/condition connector labels: «И» between group cards (rendered as a centered neutral pill on the vertical connector line between cards), «ИЛИ» between condition rows inside a group (same pill style, inline between rows). These are structural labels only — never styled as buttons or links.
- Group-card plain-language recap (Body, 16px, under the group title, above the condition rows): a short auto-generated summary of the group's OR'd conditions, e.g. «Страна: RU или KZ» or «Сделал заказ за 30 дней и не открывал письма за 90 дней» (across groups, joined with «и»). Purely descriptive, regenerated from the live definition — not a separate editable field.
- Attribute condition row layout: [поле — combobox: «Стандартные поля» group (Страна/Город/Имя/Фамилия/Телефон/Статус подписки) + «Кастомные свойства» group (registry-sourced, searchable)] → [оператор — select, options depend on the selected field's type per D-03] → [значение — type-appropriate input: text `input`, number `input type=number`, date `input type=date` for до/после or plain number for "в последние N дней", tag-name `input` for есть/нет; hidden entirely for пусто/не пусто and истина/ложь] → [remove row — icon button].
- Behavioral condition row layout: [событие — combobox: наблюдаемые имена (distinct, D-05) + free-text fallback] → [«выполнено ≥ N раз» / «ни разу» — select] → [count `input type=number`, shown only when "выполнено ≥ N раз" is selected] → [«за последние N дней» / «за всё время» — select] → [days `input type=number`, shown only when "за последние N дней" is selected] → [remove row — icon button].
- Segment list "участников" column: Display-weight number + Label/meta muted text underneath, «на {дата, время последнего пересчёта}» (D-11) — same "as of X" framing CONTEXT.md specifies, never implying real-time freshness.
- Segment detail page structure (D-12): «Определение сегмента» (Heading, the builder — same component as the create flow, editable inline) above «Участники» (Heading, paginated member table reusing `ContactsListPage`'s table/search/pagination/`keepPreviousData` pattern verbatim, read-only — no per-row actions here, this is a filtered view of the Contacts feature, not a second contact-management surface).
- Rename is not a separate flow (D-14 "свободное"): the segment name is just the top field of the same builder form; editing it and clicking «Сохранить изменения» renames the segment.

## Component & Screen Inventory (executor reference)

| Screen / Feature | shadcn components | Key states |
|-------------------|--------------------|------------|
| Segments list (`/w/{slug}/segments`) | table, button, dropdown-menu (row actions: edit/delete), alert-dialog (delete confirm), skeleton | empty, loading (skeleton rows), populated |
| Segment builder (shared by create + edit, embedded in both the create page and the segment detail page) | card (per-group container), select (operator/timeframe/count-operator), popover + command (combobox: event name, custom-property field), input, button, dropdown-menu ("Добавить условие" type picker), badge (И/ИЛИ connector pills), tooltip (D-08 timeout hint on hover, optional reinforcement of the inline warning), form | idle, per-row validation error, per-group empty-group error, live-count loading (dimmed+spinner), live-count timeout (amber inline warning) |
| Segment detail (`/w/{slug}/segments/:id`) | builder (above) + table (member list, `@tanstack/react-table`, same pattern as `ContactsListPage`), skeleton, badge | definition view/edit, member-list loading/empty/populated |
| Delete segment | alert-dialog, button | confirm |

Interaction rules (extends Phase 1/2's, unchanged principles):
- Every mutating button gets a disabled + loading state during the request; no double-submit.
- Focus visible on all interactive elements (accent ring). Dialogs and popovers trap focus, close on Esc.
- Live-count requests use the full `SegmentDefinition` JSON as the TanStack Query `queryKey` (Pitfall 6 from 03-RESEARCH.md) so stale/out-of-order responses never overwrite a newer one — no manual `AbortController` needed given this pattern.
- The debounce interval is 300ms, matching `ContactsListPage`'s existing `useDebouncedValue` hook (reused, not reimplemented) — per 03-RESEARCH.md Assumption A1.
- Segment management (create/edit/delete) has no role gate in this phase (03-CONTEXT.md is silent on roles here, matching 03-RESEARCH.md's Security Domain note that ordinary workspace membership is sufficient) — every workspace member sees the same actions, unlike Phase 1/2's Owner/Admin-gated actions.
