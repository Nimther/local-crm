  <decision>Point Sentry SDKs at live DSNs for this project (api, worker, and — under the same decision — web in plan 15-11), or keep error tracking DSN-less for now.</decision>
  <context>
    This is the phase's one-way door. Sentry has no retroactive redaction: once an event containing a secret or a contact's data is stored, the only remedy is deleting the entire project's event history (Pitfall 18). Everything protecting that door is now in place — plan 15-06's `sentryBeforeSend` routes every event body through `packages/redaction`'s depth-unbounded `scrub()`, and its fixture test (two roadmap-named leak scenarios, a five-level freeform payload, a breadcrumb case and a negative control) runs as a blocking step in CI's required `static` job. Both SDKs will be configured error-only: tracing off, profiling off.
    Choosing to proceed does not by itself send anything: a missing DSN leaves the SDK uninitialized and both processes run normally. What this decision authorizes is supplying real DSNs to the deployed environment.
  </context>
  <options>
    <option id="proceed-live-dsn">
      <name>Proceed — wire the SDKs and supply real DSNs</name>
      <pros>OPS-08 is satisfied end to end; exceptions from all three surfaces become visible with tenant and request correlation; the redaction gate is already blocking in CI.</pros>
      <cons>Irreversible if the scrub has a gap the fixtures did not model; the residual risk is a secret shape covered by neither a key rule nor a value rule.</cons>
    </option>
    <option id="proceed-code-only">
      <name>Proceed with the code, leave DSNs unset for now</name>
      <pros>All wiring lands and is tested; no event leaves the host until a DSN is supplied later; the one-way door stays shut.</pros>
      <cons>OPS-08 cannot be observed as true at phase verification; an exception in production goes unreported until the DSNs are added.</cons>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application process → Sentry SaaS (EU) | Exception events with attached context leave the host to a third party |
| secrets file → container environment | New DSN values are delivered through the existing `MEGA_CRM_ENV_FILE` convention |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-29 | Information Disclosure | event bodies leaving the trust boundary | critical | mitigate | `sentryBeforeSend` on both `beforeSend` and `beforeSendTransaction`, backed by plan 15-06's blocking fixture gate; tags carry ids only |
| T-15-30 | Information Disclosure | tracing/profiling opening a second, unscrubbed data channel | high | mitigate | Tracing sample rate 0 and profiling disabled, asserted by test; `beforeSendTransaction` also scrubbed as defence in depth |
| T-15-31 | Denial of Service | control-flow throws flooding Sentry and consuming the free-tier quota | high | mitigate | Capture is wired only through plan 15-08's reporter seam, which the allowlist already filters; asserted by a zero-capture test for `DelayedError` |
| T-15-32 | Denial of Service | a hanging Sentry flush extending SIGTERM shutdown | medium | mitigate | Bounded flush timeout in the existing shutdown sequence |
| T-15-33 | Information Disclosure | DSN treated as a secret or as not-a-secret inconsistently | low | mitigate | Backend DSNs travel through the existing secrets file; the frontend DSN's build-time, non-secret handling is documented in SPECIFICATION section 3 before it is introduced |
| T-15-SC | Tampering | npm/pip/cargo installs | high | mitigate | No installs in this plan; all dependency additions are gated by plan 15-01's blocking human legitimacy checkpoint |
