    **Why rotation is safe here.** One short paragraph: signing always uses the primary secret only; verification tries the primary and then each retained previous secret in list order; already-mailed links carry a five-year TTL, so a retired secret must outlive the last token it signed. State that both processes read these variables at boot only — there is no live-reload path — which is why every step below ends in a restart.

    **Prerequisites.** The environment file's location is resolved outside the working root; both the API and the worker must receive identical values for both variables; a new secret must be at least 32 characters, contain no comma and no whitespace, and differ from the primary and from every existing entry; at most five entries may be retained. State that a violation of any of these fails the process at boot rather than at first use, and name the three sites that enforce it.

    **Step 1 — make the new secret verifiable everywhere.** Generate the new secret. Append it to the previous-secrets list on **every** service — API and worker — and restart both. Nothing signs with it yet; every process can now verify it. State the invariant this step buys: at no point is there a secret that some process can verify and another cannot.

    **Step 2 — promote.** Move the current primary into the previous-secrets list, set the new secret as the primary, and restart every service again. State the ordering explicitly and warn that promoting before Step 1 has been applied and restarted everywhere creates exactly the window this procedure exists to eliminate.

    **Rollback.** If a restart fails validation at boot, the process refuses to start and names the offending variable and rule; correct the value and restart.
