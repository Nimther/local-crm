<objective>
Close the **read-site half** of WR-06 (D-01) and discharge the D-03 sweep audit: give the
dashboard growth query an explicit, self-documenting UTC anchor using the **double-hop**
`AT TIME ZONE 'UTC'` idiom this codebase already established, and prove with an executable
test that the day buckets survive a deliberately non-UTC reading session.

Purpose (read this before writing any SQL): RESEARCH.md proved empirically, against a real
Postgres 17, that the expression 13-REVIEW.md's WR-06 write-up and CONTEXT.md's D-01 both
literally name — `(created_at AT TIME ZONE 'UTC')::date` — is **wrong** for a naive
`timestamp` column. One hop turns the naive value into a `timestamptz`; casting a
`timestamptz` to `date` then converts to the *session's* `TimeZone` before truncating, so the
single-hop form re-introduces exactly the session dependence the fix is supposed to remove.
The **double-hop** form `((created_at AT TIME ZONE 'UTC') AT TIME ZONE 'UTC')::date` converts
back to a naive UTC wall-clock value first, making the final cast a pure truncation with no
timezone involved. That is the form `packages/db/src/partitions/relocate-default.ts:112`
already uses in this repo for the same column-type situation. Implementing the literal
CONTEXT.md text would fail the very test CONTEXT.md's D-02 mandates.

The pool pin (plan 17-01) is what closes WR-06's actual write-path hazard. This plan's cast
change is the defense-in-depth half D-01 asks for: the query stays correct even when executed
by a pool bypass, an external client, or a psql session an operator opened with their own
timezone — and it is now self-documenting rather than correct-by-accident.

Output: two exported SQL constants (so the regression test executes production's exact string),
the double-hop cast, a non-UTC read-session regression test that also encodes Pitfall 1 as an
executable fact, and the completed D-03 audit record.
</objective>
