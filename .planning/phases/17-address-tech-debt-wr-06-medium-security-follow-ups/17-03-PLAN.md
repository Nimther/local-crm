<objective>
Close the code half of T-14-58 and T-14-88 (D-05, D-06): make the custom `megacrm-postgres`
image (used by both the `db` service and the `pgbackrest` sidecar) CI-built, GHCR-published on
an immutable git-SHA tag, pull-only in production, and covered by the same compose
immutable-tag gate the application images already sit behind.

Purpose: Phase 14 plan 10 introduced `build:` sections for `db`/`pgbackrest` on a mutable
`POSTGRES_IMAGE_TAG` (default `local`) and explicitly excluded those two services from
`FIRST_PARTY_IMAGE_SERVICES`. That was a scoped, documented decision at the time, not an
oversight — but it means production can run a Postgres image built from whatever happened to be
in the operator's working tree, outside code review and outside the gate that exists precisely
to prevent that. Extending the mechanism that already covers `api`/`worker`/`web`/`migrate`/`alloy`
closes both threat rows outright, with no new checking logic — only set membership and a
registry-shaped image reference.

Output: two new CI jobs in the existing workflow, a pull-only production compose, a fail-loud
`POSTGRES_IMAGE_TAG`, a gate that covers the two services with a fixture proving it, and a
runbook whose forward flag no longer describes a model this plan removes.

**Reversibility — costly (D-05).** Going back to host builds re-opens T-14-58 and T-14-88 and
would require reverting the compose reference, the gate membership, the runbook, plan 17-04's
drill image reference, and the operator's `POSTGRES_IMAGE_TAG` on the VPS. This is a deliberate
one-direction hardening, taken with the user's locked decision.

**Recorded divergence from CONTEXT.md § Integration Points.** CONTEXT.md states
"`deploy.sh` pull-and-flip flow gains the postgres image in its pull set", while RESEARCH.md
Pitfall 4 argues the routine deploy path must stay untouched. This plan follows RESEARCH:
`scripts/deploy.sh` is NOT modified. Rationale — pre-pulling buys nothing here (the D-07
cutover checkpoint pulls the image itself, once, as its first action), while every edit to
`deploy.sh`'s service list is an opportunity for `db`/`pgbackrest` to drift into the routine
restart path, which `deploy.sh`'s own header explicitly forbids. CONTEXT.md's own next sentence
already agrees on the important half ("db/pgbackrest are NOT part of the app-container flip").
The divergence is limited to the pull half and is recorded here rather than decided silently.
</objective>
