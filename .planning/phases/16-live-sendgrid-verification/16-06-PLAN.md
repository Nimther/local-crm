  <behavior>
    - In pass-through mode the proxy forwards the request to the configured upstream exactly once and returns the upstream status, headers and body unchanged.
    - In rate-limit mode the proxy responds 429 with a retry-after header and the upstream receives zero requests.
    - After firing rate-limit mode once, the next request is forwarded normally — the mode is one-shot.
    - In timeout mode the upstream receives exactly one request.
    - In timeout mode the proxy's own response is emitted only after the configured delay margin has elapsed.
    - After firing timeout mode once, the next request is forwarded with no added delay.
    - The control endpoint accepts each of the three mode names and rejects an unknown mode name without changing the current mode.
    - `nextMode` returns pass-through after any one-shot mode fires, and leaves pass-through unchanged.
    - The request method, authorization header and body bytes reaching the upstream are identical to those the proxy received.

Create `scripts/uat-fault-proxy.mjs` — a dependency-free pass-through HTTP proxy built on Node's built-in server and fetch, following RESEARCH.md Architecture Pattern 2. No npm package: RESEARCH.md's Package Legitimacy Audit records none, and an off-the-shelf proxy would solve a far larger problem than "forward everything, but once return a canned rate-limit response or stall".

The two injection modes are asymmetric and the asymmetry is the point:

- **Rate-limit mode** synthesises the 429 response and performs **no upstream call whatsoever**. The send path releases its already-committed dispatch claim and retries on a 429; if the request had also been forwarded, SendGrid would have accepted and sent the mail, and the retry would deliver a second, genuinely duplicate message to a real person.
- **Timeout mode** forwards the request upstream, awaits the upstream call so SendGrid really does accept and send the mail, and only then delays emitting its own response past the margin so the caller's abort fires first. A dropped or refused connection here would mean the send genuinely never happened, leaving the row ambiguous forever with no webhook evidence to resolve it — a real lost mail.

Both modes are one-shot: firing returns the proxy to pass-through with no operator action.

The control endpoint is a POST on a distinct path that sets the mode. It has no authentication, which is acceptable only because the proxy is session-scoped, torn down after this phase, and reachable only from inside the compose network — never give it a published port.

Write `scripts/__tests__/uat-fault-proxy.test.mjs` covering the `<behavior>` list against a local stub upstream that counts the requests it receives. The two most important assertions are the ones that catch the asymmetry being inverted: rate-limit mode leaves the upstream request count at zero, and timeout mode leaves it at exactly one with a measured response latency exceeding the injected margin. Use a small injected margin so the case fits the lane's timeout.

Add npm scripts `uat:fault-proxy` and `test:uat-fault-proxy`.
