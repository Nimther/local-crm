# Phase 21 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Provenance note:** this phase adds exactly one new surface — an Export action on the existing contact card (`ContactDetailPage.tsx`) — plus its disabled/error states. 21-CONTEXT.md's decisions (D-01…D-16, all user-confirmed) fix the mechanics (fetch+blob, typed 410, filename convention, no confirmation dialog); this document fixes the remaining visual/copy details CONTEXT.md left to discretion, by directly extending the closest existing precedents in this codebase rather than inventing new ones:
> - The button itself copies `CsvImportWizard.tsx`/`CsvImportHistory.tsx`'s existing `variant="outline"` + `<Download />` icon download-button shape — the only other "download a file" affordance in this app.
> - The Owner/Admin visibility gate copies `TeamPage.tsx`'s `{canManage ? <X/> : null}` conditional-render precedent (hidden entirely), **not** `LaunchScheduleActions`' disabled+tooltip precedent — SC3 requires a Member to not *see* the action at all, a stricter rule than the campaign send actions use.
> - The disabled-with-reason erased-contact state copies `computeIncompleteReason`'s exact `text-sm text-destructive` inline-paragraph shape (D-14 names this precedent explicitly).
> No shadcn preset change, no new hue, no new component is needed anywhere in this phase.

## Copywriting Contract

All UI copy is **Russian** (per Phase 1–4 convention). Sentence case, address the user with «вы» (lowercase), no exclamation marks. Every string below is either quoted verbatim from a locked CONTEXT.md decision or marked **(this spec's call)** where CONTEXT.md explicitly left the wording to discretion.

### Primary CTA (verb + noun)

| Element | Copy |
|---------|------|
| Export button, idle **(this spec's call — CONTEXT.md fixes the mechanism (D-09/D-12), not this exact string; wording follows DSR-01's own requirement phrasing "скачать … файл с персональными данными контакта")** | «Скачать данные контакта» |
| Export button, in-flight | «Скачиваем…» (disabled while pending — matches `DeleteContactDialog`'s «Удаляем…» / `PropertiesTab`'s «Сохраняем…» present-continuous-with-ellipsis convention) |
| Export success **(this spec's call — a confirmatory toast, consistent with every other successful mutation on this page: "Контакт обновлён", "Контакт удалён")** | toast (sonner, default/success call): «Файл с данными контакта скачан» |

### Empty state

Not applicable to the Export action itself — a contact with zero events/sends/campaign memberships still produces a valid, complete file (empty arrays per section, D-06's row counts read `0`); this is a content fact inside the downloaded artifact, not a UI empty-state to design. No placeholder/empty-state UI is rendered on the page for this case.

### Error states

| Case | Copy |
|------|------|
| Generic request failure (network error, 500, or any error outside the typed 410) | Reuse `ContactDetailPage.tsx`'s existing `GENERIC_ERROR` constant verbatim: «Что-то пошло не так. Попробуйте ещё раз — если ошибка повторится, обновите страницу.» — do not invent a second generic-error string for this one action. |
| Typed 410 `contact_erased` race (export attempted in the narrow window between page load and a since-completed erasure — D-13/D-15 backstop) **(this spec's call — CONTEXT.md fixes the API contract, not the inline UI copy for this specific race)** | Same fixed string as the disabled-state reason below («Контакт обезличен — персональные данные удалены»), rendered inline in the same reserved message slot; the handler also invalidates the contact query so the button flips to its disabled state on the next render, instead of remaining clickable. |
| 403 role refusal (Member) | **Not a reachable UI state.** SC3 requires the button to not exist in the DOM for a Member (see Component Inventory); a 403 can only occur via a direct API call bypassing the UI, which has no corresponding screen to render into. No inline copy is designed for this case. |
| 404 cross-tenant / nonexistent contact id | **Not a reachable UI state via normal navigation** — the page's own `GET /contacts/:id` load would already have 404'd before the Export button ever renders. No inline copy is designed for this case; it is an API-only test scenario (SC4). |

### Erased-contact disabled state (SC5, D-13/D-14/D-15 — locked verbatim)

| Element | Copy |
|---------|------|
| Export button when `contact.anonymizedAt` is non-null | Button renders **visible but disabled** (never hidden — distinct from the Member role-hide rule above); inline reason directly below: «Контакт обезличен — персональные данные удалены» (D-14, verbatim). |

### Destructive confirmation

Not applicable — Export is non-destructive (a read, not a mutation of tenant data) and fires with no confirmation step, per D-12. This phase introduces no new destructive action; the existing `DeleteContactDialog` confirmation is unchanged.

## UI Considerations

Applicable state considerations resolved: 5 covered, 1 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| populated | Export action, role variants | ✅ covered | Owner/Admin: button renders enabled (or disabled-if-erased per below). Member: button is not rendered at all — conditional render (`{canExport ? <ExportContactButton/> : null}`, `TeamPage.tsx` precedent), not a disabled/tooltip state (SC3). |
| loading | Export button, request in flight | ✅ covered | Label swaps to «Скачиваем…», button `disabled`, no double-submit — mirrors `DeleteContactDialog`'s pending-label pattern. |
| error | Export request fails (generic) | ✅ covered | Reuses the page's existing `GENERIC_ERROR` inline paragraph shape (`text-sm font-medium text-destructive`) — see Copywriting Contract. |
| error | Typed 410 mid-session erasure race | ✅ covered | Same fixed erased-reason copy, same reserved inline slot, plus a contact-query invalidation so the button state catches up — see Copywriting Contract. |
| zero-one-many | Erased vs active contact (binary state, not a count) | ✅ covered | Exactly two states — `anonymizedAt` null vs non-null — no partial/intermediate rendering; D-15's fail-closed rule guarantees the binary is decided server-side inside one transaction, so the UI never needs to represent an "in-between" erasure state. |
| long-text | Erased-reason and generic-error strings | 🧪 backstop | Both are short, fixed, non-interpolated Russian sentences (no contact-supplied or variable-length content is ever inserted into either string) — overflow is structurally unlikely in the button-adjacent single-line slot, held out as backstop rather than "covered" because no explicit line-wrap test exists for either sentence at narrow viewport widths. |

Not applicable to this phase: empty/overflow of a scrollable list or table (no new list/collection surface is introduced — the export action is a single button, not a data grid), partial-load pagination states (the keyset pagination in D-10 is entirely server-side and produces one atomic file; there is no partial-results UI to design).

## Component & Screen Inventory (executor reference)

| Screen / Feature | Files touched | shadcn components | Key states |
|-------------------|----------------|--------------------|------------|
| Contact card — header actions cluster | `ContactDetailPage.tsx` (existing file; new `ExportContactButton`-shaped code added to the header actions `<div>` alongside `DeleteContactDialog`) | button (outline), lucide-react `Download` icon | role-hidden (Member — not rendered), enabled (Owner/Admin, active contact), disabled-erased (Owner/Admin, `anonymizedAt` set, inline reason), in-flight, error (generic or 410-race) |

Interaction rules:
- **Placement:** the Export button sits in the same page-header `<div className="flex items-center justify-between gap-4">` row `DeleteContactDialog` already occupies, positioned before (to the left of) the destructive Delete button — non-destructive action first, destructive action last, matching the left-to-right severity ordering already implied by that row's single existing button.
- **Visibility gate is a conditional render, not a disabled state.** This is the one deliberate deviation from the `LaunchScheduleActions`/`canLaunch` tooltip-disabled precedent used elsewhere in this codebase for Owner/Admin gates — SC3's wording ("does not see the export action") is stricter than the campaign-actions pattern and instead follows `TeamPage.tsx`'s `{canManage ? <InviteModal/> : null}` shape. Determining `canExport` requires the page to know the viewer's role (today `ContactDetailPage.tsx` fetches no workspace query at all — wiring that read is a backend/data-fetching concern for the planner, not a visual contract detail, but is flagged here so the executor does not assume the role is already available).
- **`anonymizedAt` is not yet on the wire — this corrects a claim in RESEARCH.md/CONTEXT.md.** Both upstream artifacts assert "the page already knows the contact row (including `anonymizedAt`) so the disabled state costs nothing extra." Verified directly against `packages/shared-schemas/src/contact.ts` in this research session: `contactResponseSchema` does **not** include `anonymizedAt` today — it exists only in `packages/db/src/schema/contacts.ts` and inside `contact.repository.ts`'s internal queries, never in the `GET /contacts/:id` response shape the frontend actually receives. Without adding `anonymizedAt` to `contactResponseSchema` (and the repository's `CONTACT_COLUMNS`-equivalent select for the single-contact GET), the D-14 disabled-with-reason state has no field to read and will never trigger — the button would render enabled even for an erased contact, leaving only the 410 API backstop to catch the case (safe, but defeats the courtesy UI state SC5/D-14 asks for). This is a required backend/schema task for the planner, not optional polish.
- **The erasure disabled-reason is visible, not hidden.** Unlike the Member role gate (hidden), an erased contact's Export button stays in the DOM, disabled, with its reason directly visible — never a tooltip-only explanation — matching D-14's explicit instruction to extend the `computeIncompleteReason` inline-copy pattern, not the tooltip pattern.
- **No confirmation dialog.** A single click fires the export fetch immediately; there is no `AlertDialog`/`Dialog` step, unlike `DeleteContactDialog`'s destructive-confirmation flow.
- **Client-side filename construction, not a `<a href download>` navigation.** Deliberately diverges from this codebase's only other download precedent (`CsvImportWizard.tsx`/`CsvImportHistory.tsx`'s `<a href={...} download>`) because that pattern renders a non-2xx JSON error body as raw text in a new tab — unacceptable for the three typed error codes this action must render in-app (D-12). Instead: `apiGet<DsrExportDocument>(...)` (typed `ApiError` already covers 403/404/410 parsing "for free" per RESEARCH.md Pitfall 4) → on success, `new Blob([JSON.stringify(data, null, 2)], { type: "application/json" })` → `URL.createObjectURL` → a synthetic anchor click using the exact D-08 filename convention (`dsr-export-{contactId}-{YYYY-MM-DD}.json`, date = the moment of download, not `metadata.generatedAt`) → `URL.revokeObjectURL` after the click.
- Same "no further live user input" precedent as 20-UI-SPEC.md's provenance note applies here: every value in this document is either a locked CONTEXT.md decision quoted verbatim, or an explicit, narrow "this spec's call" fill-in following established house style — revise by re-running `/gsd-ui-phase 21` if any default should change.
