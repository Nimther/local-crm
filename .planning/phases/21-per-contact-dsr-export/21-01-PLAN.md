<objective>
Prove the whole Per-Contact DSR Export architecture end-to-end on one thin path: an Owner clicks the Export action on the contact card, one authenticated request reaches a new Fastify route gated by a new `contact:export` permission, the route opens a snapshot-stable `REPEATABLE READ` tenant transaction, checks `contacts.anonymizedAt` as its very first read (D-15 fail-closed), assembles a document with `metadata`, `profile` and `customProperties`, and answers with `Content-Disposition: attachment` — and the browser saves it as a file. The same plan nails down the three refusal shapes (403 / 404 / 410) that every later section inherits.

This is the phase's tracer: the genuinely new architectural piece is the isolation-level transaction wrapper (RESEARCH.md Pitfall 1 — `withTenantTransaction` cannot be reused unmodified), and it must be proven before any section walk is built on top of it. Every expansion plan adds sections *into* the shape this plan establishes.

Purpose: DSR-01 (a machine-readable file from the contact card) and DSR-04 (the Owner/Admin gate at both API and UI) reach a working, tested state on one contact's profile before the remaining sections are added.
Output: a registered route, a repository with the transaction + gate, the shared document schema, the access-control resource, the isolation-level helper, an HTTP integration test, and the Export button on `ContactDetailPage`.
</objective>
