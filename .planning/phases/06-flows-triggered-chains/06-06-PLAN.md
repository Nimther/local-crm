<objective>
Build the event-trigger evaluator and re-entry control: after an event is ingested, match its name against live event-triggered flows, apply re-entry rules (FLOW-04) and the one-active-run guard (D-07), create a version-pinned flow_run, and enqueue it for advancement. This is the entry half of the first user-observable E2E slice (event → run → email).

Purpose: Delivers FLOW-02 (event trigger) and FLOW-04 (re-entry control). Segment-entry triggers + sweep are the later 06-08 slice; this plan does event triggers only.
Output: flow-trigger-evaluator worker + re-entry logic + events-ingest hook, integration-tested.
</objective>

> MVP user story (phase): **As a** marketer, **I want to** have a contact enter my chain when they fire an event, **so that** the right people get enrolled automatically — without duplicate or overlapping runs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ingested event → run creation | Untrusted client event name selects which flows enroll; concurrent duplicates possible |
| worker → Postgres | RLS-scoped; one-active-run is a DB-enforced invariant |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-06-01 | Tampering | duplicate/interleaved runs from concurrent triggers | high | mitigate | flow_runs_one_active_per_contact partial unique index + ON CONFLICT DO NOTHING + canEnterFlow active-run pre-check (D-07) |
| T-06-06-02 | Information Disclosure | evaluator reads flows cross-tenant | medium | mitigate | withTenant(workspaceId from job payload) around all DB work (Pitfall 5) |
| T-06-06-03 | Repudiation | run pinned to a mutating version | high | mitigate | flow_version_id stamped = live_version_id at entry, never re-pointed (FLOW-07) |
| T-06-06-04 | Denial of Service | high-volume events flood the evaluator | low | accept | evaluator is a bounded per-event job on its own queue; rate concerns handled downstream by the send token bucket. Rationale: event ingest is already the throughput boundary and unchanged by this plan |
</threat_model>
