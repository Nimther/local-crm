<objective>
Add branching (FLOW-03/D-12) and the segment-entry trigger (FLOW-02/D-02) with the enroll-existing publish choice (D-04). Branch routing and segment-entry detection both reuse the shared segment engine (isContactInSegment / compileSegmentDefinition) — never a second segment implementation. The sweep is engineered around the on-the-fly (non-materialized) segment model to avoid the Pitfall-1 cost cliff.

Purpose: Completes the second trigger path and the conditional-branch node, plus the "reliability visible to the user" enroll-existing dialog backend (D-04).
Output: branch handler + segment-sweep + trigger-evaluator segment path + enroll-existing batch, integration-tested.
</objective>

> MVP user story (phase): **As a** marketer, **I want to** branch my chain on segment membership and enroll contacts by segment entry (optionally back-filling those already in it), **so that** the chain reacts to who a contact is and what they do.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sweep/enroll → Postgres | Cross-tenant discovery + large-set iteration under RLS + statement_timeout budget |
| segment reference → branch/trigger | A segment definition drives enrollment and routing |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08-01 | Denial of Service | O(flows×contacts) sweep exhausts the DB / hits statement_timeout | high | mitigate | bulk per-segment compiled query diffed against snapshot (O(flows)); 15-min interval; chunked batches (RESEARCH Pitfall 1) |
| T-06-08-02 | Information Disclosure | sweep/enroll admin-scan grants cross-tenant writes | high | mitigate | admin-scan is SELECT-only discovery; every run/snapshot write re-enters withTenant per-tenant (Pitfall 5) |
| T-06-08-03 | Tampering | segment membership drift creates duplicate/overlapping runs | high | mitigate | canEnterFlow + one-active-run partial index guard on every entry path (event, re-check, sweep, enroll) |
| T-06-08-04 | Denial of Service | giant enroll transaction locks tables | medium | mitigate | resumable-cursor chunking (recipient-snapshot pattern), no unbounded transaction |
</threat_model>
