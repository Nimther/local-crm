## Canvas & Node Visual Language

This is the one genuinely new UI surface in the product (FLOW-01). Rules below are additive to, not a replacement for, the base design system above.

### Node card anatomy
- Every node is a fixed-width (240px) `card`-styled rectangle: `bg-white`, `border` `neutral-200`, `rounded-lg` (matches `--radius`), `shadow-sm`.
- Header row: 24px icon chip (see Node type indicators below) + node title (Label/meta role, 14px/600) + optional overflow menu (`⋮`, lucide `MoreVertical`) for delete/duplicate-node.
- Body: 1–2 lines of Label/meta (14px/400) muted-foreground summarizing the node's configuration (e.g. «Событие: `order_placed`», «14 дней», «Сегмент: VIP клиенты», «Шаблон: Welcome Series #1»). Unconfigured nodes show muted placeholder text: «Не настроено» in `neutral-400`, which also drives the D-17 publish-blocking state (see Error states).
- Selected state: `ring-2 ring-primary` (indigo-600), same focus-ring token used everywhere else in the app — no new selection color invented.
- Invalid-for-publish state (D-17): `ring-2 ring-destructive` (red-600) + a small destructive-red dot badge in the header, tooltip on hover showing the specific hard error (e.g. «Добавьте шаблон и отправителя»).

### Node type indicators (canvas-only categorical set — NOT part of the 60/30/10 budget)

Five node types need to be instantly distinguishable while scanning a canvas — the same need that justified Phase 4's semantic status-badge palette. This is declared as a scoped, documented exception exactly like Phase 4's "semantic status colors (badges only, never general UI)" carve-out: these five hues appear ONLY inside the small icon chip in a node's header, never as a button, page background, or link color.

| Node type | Icon (lucide-react) | Chip color | Rationale |
|-----------|---------------------|------------|-----------|
| Trigger | `Zap` | `indigo-600` text on `indigo-50` bg | Entry point of the flow — reuses the accent hue structurally (there is exactly one trigger node per flow, mirroring the "one primary accent element per screen" spirit, not a CTA) |
| Delay / Wait | `Clock` | `amber-600` text on `amber-50` bg | "Waiting" semantics — same amber-as-pending precedent as Phase 4's «Запланирована» badge |
| Conditional branch | `GitBranch` | `blue-600` (`#2563EB`) text on `blue-50` (`#EFF6FF`) bg | **New hue, tightly scoped**: the one net-new color this phase introduces, used exclusively for this single icon chip — standard Tailwind `blue`, not an arbitrary value. Justified because branch nodes must be visually distinct from both delay (amber) and send (green) at a glance; this is the same class of exception Phase 4 already established for status badges, applied to node-type chips instead. |
| Send email | `Mail` | `green-600` text on `green-50` bg | "Action taken" — same green as Phase 4's «Отправлена» success precedent |
| Exit | `LogOut` | `neutral-500` text on `neutral-100` bg | Resting terminal marker, not a failure — same treatment as Phase 4's «Отменена» (canceled, non-error terminal state) |

### Edges
- Default edge: `neutral-300` stroke, 2px, `@xyflow/react`'s default bezier/smoothstep — no custom edge styling beyond stroke color.
- Branch node's two outgoing edges are always labeled inline on the edge itself: «Да» (green-600 text) / «Нет» (neutral-500 text) — never unlabeled, since D-13's binary branch is meaningless without knowing which edge is which.
- Selected/hovered edge: `primary` (indigo-600) stroke, matching node selection.

### Canvas chrome
- Background: `@xyflow/react`'s dot-grid `Background` component, dot color `neutral-200`, on the app's standard `neutral-50` page background (Dominant 60%) — canvas is a full-bleed content area, not a card.
- `Controls` (zoom/fit-view) and `MiniMap` (lucide-styled, default xyflow chrome) render bottom-left/bottom-right respectively — standard xyflow defaults, no custom repaint.
- Node palette: a `card`-styled panel docked to the canvas's top-left (`Panel` component from `@xyflow/react`), listing the 5 node types as draggable rows (icon chip + label from the table above) — drag-and-drop onto canvas per FLOW-01's literal requirement, not click-to-add.
- Autosave: draft nodes/edges persist on every meaningful change (node add/remove/move-settle, edge connect/disconnect, node config save) via a debounced (1s) TanStack Query mutation — no explicit "Save" button on the canvas itself; a small Label/meta status text in the canvas toolbar reads «Сохранено» / «Сохранение…» (mirrors the segment builder's live-save-state affordance, never a blocking spinner).
- Node **position** (x/y drag coordinates) is explicitly exempt from the 4px spacing scale below — it is free-form 2D placement data, not layout spacing. `@xyflow/react`'s `snapGrid` is set to `[16, 16]` (a multiple of 4) purely so drag placement feels aligned, not because position values are spacing tokens.

## Spacing Scale

Declared values (must be multiples of 4) — identical to Phase 1–4, no changes:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside node header, badge inner padding |
| sm | 8px | Gaps inside a node's header row, gaps between exit-condition list rows |
| md | 16px | Default gap between form fields in node-config side panels, card inner padding (compact), node palette row spacing |
| lg | 24px | Card padding (flow detail sections: «Триггер», «Условия выхода», «Повторный вход», «Тихие часы»), gap between form sections |
| xl | 32px | Gap between page header and content, gap between the canvas and the node-config side panel |
| 2xl | 48px | Flows table row height (matches Contacts/Segments/Campaigns table density) |
| 3xl | 64px | Page-level top/bottom margins on flows list/detail pages |

Exceptions: **canvas node x/y position only** (see Canvas chrome above — free-form drag coordinates, not a layout-spacing value). Every other spacing value in this phase uses Tailwind's standard scale (`p-1/2/4/6/8/12/16`, `gap-1/2/4/6/8`); no arbitrary `p-[Npx]` values outside the canvas library's own internals.

## Typography

Exactly 4 sizes, 2 weights — identical to Phase 1–4, no new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / meta | 14px (`text-sm`) | 400 regular | 1.5 |
| Body | 16px (`text-base`) | 400 regular | 1.5 |
| Heading (section / card title) | 20px (`text-xl`) | 600 semibold | 1.2 |
| Display (page title, big-number callouts) | 28px (`text-display` token) | 600 semibold | 1.2 |

Phase-6-specific usage of the existing roles:
- Label/meta (14px): node card titles and config summaries, flow status badge text, run-counter caption («{N} контактов в цепочке (M на старых версиях)»), timezone caption under the wait-until/quiet-hours inputs, exit-condition list rows, re-entry radio-group option labels.
- Body (16px): node-config side-panel helper text, dialog body copy (publish/enroll/pause/delete/eject confirms), empty-state body text.
- Heading (20/600): side-panel section titles — «Настроить триггер», «Настроить задержку», «Настроить условие», «Настроить письмо» — and flow detail page card titles («Триггер», «Условия выхода», «Повторный вход», «Тихие часы», «Контакты в цепочке»).
- Display (28/600): the enroll-existing dialog's segment member count («~{N} контактов»), the flow detail page's active-run count if given visual emphasis — same role Phase 3/4 used for live-count/audience-count numbers; no new size introduced.

## Color

Identical base palette to Phase 1–4 — no new page-level hues, no gradients. One canvas-scoped categorical exception (declared above in Canvas & Node Visual Language) and one direct reuse of Phase 4's "active operation" indigo extension.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` / `neutral-50` (`--background`) | Page background, canvas background, main content surface |
| Secondary (30%) | `neutral-100` `#F5F5F5`, `neutral-200` `#E5E5E5` borders | Cards, table header row, sidebar, node card borders, canvas dot-grid |
| Accent (10%) | `indigo-600` `#4F46E5` (`--primary`) | See reserved list below — nothing else |
| Destructive | `red-600` `#DC2626` (`--destructive`) | Destructive actions only (see list) |

**Accent (`indigo-600`) reserved exclusively for (extends Phase 1–4's list with this phase's screens):**
1. Primary CTA button per screen (one per screen max): «Создать цепочку», «Сохранить черновик», «Опубликовать», «Зачислить и опубликовать», «Возобновить»
2. Active «Цепочки» nav item in the workspace sidebar (same rule as Phase 1's active-nav-item reservation)
3. Focus rings (`--ring`) and node-selection ring on the canvas, same mechanism as every other focusable element
4. Checked/selected states of checkbox/radio-group/select/switch, same as Phase 1–4
5. Trigger node's icon chip (Canvas & Node Visual Language table above) — the one structural (non-CTA) reuse of the accent hue, justified by there being exactly one trigger node per flow
6. **Reused, not new — "active operation" indicator (Phase 4's own precedent, extended to flow lifecycle):** the **«Live»** flow-status badge (`indigo-50` bg / `indigo-600` text). A live flow is continuously processing contacts — the same "ongoing operation" semantics Phase 4 assigned to «Отправляется» — so it reuses that exact color decision rather than introducing a new one.

**Destructive (`red-600`) reserved exclusively for (extends Phase 1–4's list):**
1. «Удалить цепочку» button + its confirmation dialog (only never-published or paused-with-zero-runs flows are deletable, D-22)
2. «Удалить из цепочки» (eject) button + its confirmation dialog
3. Inline validation error text/borders in node-config panels and the publish blocker list (D-17: no trigger / empty send node / branch missing exit)
4. Invalid-node selection ring on the canvas (see Node card anatomy above)

**Semantic status colors (badges only, never general UI — extends Phase 1–4's precedent):**

| Flow status | Badge | Rationale |
|--------------|-------|-----------|
| **Черновик** (draft — never published) | `neutral-500` text on `neutral-100` bg | Resting, non-active state — same treatment as campaign draft |
| **Live** (published, running) | `indigo-600` text on `indigo-50` bg | Active, ongoing operation — direct reuse of Phase 4's «Отправляется» rationale (see accent list item 6 above) |
| **Приостановлена** (paused) | `amber-600` text on `amber-50` bg | Needs-attention / manually held state, distinct from a failure — same amber-as-"needs attention" precedent as Phase 4's «Запланирована» |

No gradients. No additional page-level hues beyond the one documented canvas-scoped exception (branch-node blue). No charts in this phase (Phase 7's territory).

### System copy notes

- Toasts (sonner): успех — «Цепочка создана», «Цепочка опубликована», «Цепочка приостановлена», «Цепочка возобновлена», «Цепочка продублирована», «Контакт удалён из цепочки» — существительное + глагол-результат, без восклицательных знаков (same convention as Phase 1–4).
- Flow status badges use the exact Russian labels from the Color section's table above: «Черновик», «Live», «Приостановлена». («Live» kept as a short Latin-script status word by deliberate parallel to how the team already writes technical states like «API» — if this reads inconsistently against the fully-Russian copy register at build time, the executor may substitute «Активна»; either is acceptable, but pick one and use it everywhere the status appears, including the runs-page caption.)
- Canvas autosave status (Canvas chrome): Label/meta text in the top-right of the canvas toolbar, states «Сохранено» (default/idle) → «Сохранение…» (while the debounced mutation is in flight) → back to «Сохранено» — never a toast for routine autosave, toasts are reserved for explicit user actions (publish/pause/resume/duplicate/eject).
- Run visibility (D-21): flow detail page header shows «{N} контактов в цепочке» with a parenthetical when non-zero: «{N} контактов в цепочке ({M} на старых версиях)» — Label/meta role, same idiom as Phase 4's exclusion-breakdown line items (only render the parenthetical when M > 0).
- Re-entry control (FLOW-04): `radio-group` with three options, same visual idiom as Phase 4's send-now/schedule choice — «Только один раз», «Не чаще, чем раз в N дней» (reveals a number input for N inline when selected), «Каждый раз».
- Quiet hours (FLOW-05): workspace-level defaults live in Send Settings (`/w/{slug}/settings/sending`, Phase 4's existing page, extended with two new fields: «Часовой пояс по умолчанию» select + «Тихие часы» from/to time inputs). Per-flow override lives in the flow detail page as a card «Тихие часы»: a `switch` labeled «Использовать своё окно для этой цепочки» — off by default (inherits workspace setting, shown as muted read-only preview text below the switch), on reveals the same from/to time inputs plus a second switch «Отключить тихие часы для этой цепочки» for the explicit disable case.
- Delay node config (D-11): `radio-group` with two options — «Фиксированная длительность» (reveals a number input + unit `select`: минуты/часы/дни) and «Дождаться времени» (reveals a native `time` input + optional day-of-week `select`, with a Label/meta caption underneath reusing Phase 4's timezone-disclosure idiom: «По часовому поясу контакта, иначе — {workspace default zone}»).
- Contact timezone field (D-08): added to the existing Contact form (standard field, alongside country/city) and the CSV column-mapping picker (Phase 2 pattern), rendered as a searchable `command`+`popover` combobox (same interaction as the segment/template pickers) populated from `Intl.supportedValuesOf('timeZone')`, never a bare free-text input — this prevents the exact invalid-string error case documented above.
- Duplicate (D-23): row action «Дублировать» in the flows list's row `dropdown-menu` — creates a new `draft` copy with all nodes/edges, no confirmation dialog since it's non-destructive; toast «Цепочка продублирована» and navigate to the new draft's canvas.

Interaction rules (extends Phase 1–4's, unchanged principles):
- Every mutating button gets a disabled + loading state during the request; no double-submit.
- Focus visible on all interactive elements (accent ring), including canvas node selection.
- Publish/pause/resume/enroll-existing are Owner/Admin-only (D-23, mirrors Phase 4's campaign launch/schedule gate exactly); Member creates/edits drafts and can duplicate, but publish/pause/resume/enroll controls render disabled with the same tooltip pattern Phase 4 established: «Только Owner или Admin может публиковать цепочки.»
- The canvas's autosave status text and the publish-blocker list are the ONLY place client-side validation is trusted for immediate feedback — the actual publish action always re-validates server-side (Pitfall 3 in `06-RESEARCH.md`) and the dialog/toolbar must be able to render a server-returned blocker list identically to the client-computed one.
