# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Provenance note:** this phase is a correctness fix, not a new screen. 20-CONTEXT.md's decisions (D-01…D-12, all user-confirmed) and the four execution plans (20-02, 20-03, 20-05, 20-06) already specify almost every visual and copy detail verbatim — file names, class strings, exact Russian sentences. This document does not invent alternatives to those; it consolidates them into one contract and inherits everything not respecified from `04-UI-SPEC.md` (Broadcast Campaigns), which is the direct ancestor of every component this phase touches (`CampaignBuilderPage.tsx`, `LaunchScheduleDialogs.tsx`, `TestSendPanel.tsx`, `CampaignStatusBadge.tsx`). Where a plan left a wording genuinely open (flagged below as "this spec's call"), the resolution follows the same house style rather than introducing a new one. No shadcn preset change, no new hue, no new component is needed anywhere in this phase.

## Color

Identical palette to Phase 1–4 — no new hues, no gradients. Two existing color roles are extended to a new *reason*, not a new *hue*.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` / `neutral-50` (`--background`) | Unchanged |
| Secondary (30%) | `neutral-100` `#F5F5F5`, `neutral-200` `#E5E5E5` borders | Unchanged |
| Accent (10%) | `indigo-600` `#4F46E5` (`--primary`) | Unchanged — no new accent usage this phase (see reserved list below, unmodified) |
| Amber (existing, non-reserved-accent status color) | `amber-200` border / `amber-50` bg / `amber-700` text | **Extended this phase:** the unsaved-changes banner reuses `CampaignBuilderPage.tsx`'s exact non-draft-notice classes (`border-amber-200 bg-amber-50` on the `Card`, `p-4 text-sm text-amber-700` on the `CardContent`) — same "needs attention, not yet actionable-red" semantic Phase 3/4 already established for this hue. No new amber shade introduced. |
| Destructive | `red-600` `#DC2626` (`--destructive`) | **Extended this phase:** the version-conflict and illegal-transition copy render in the launch/schedule dialogs' EXISTING `serverError` paragraph (`text-sm font-medium text-destructive`) alongside the generic error it already used — same element, same class, different string. The dirty-block inline reason next to launch/schedule/test-send buttons reuses `computeIncompleteReason`'s exact element (`text-sm text-destructive`). Neither is a new destructive *use case* by kind (both are "why this action is currently unavailable/failed" — the same family the destructive color already covers), only a new *message*. |

**Accent (`indigo-600`) reserved list — unchanged from 04-UI-SPEC.md, this phase adds nothing to it.** In particular: the banner's «Сохранить» button is the DEFAULT primary button variant (same variant as the builder's own «Сохранить черновик» it invokes) — this is not a new accent surface, it is the same save action the builder already renders, now also reachable from the banner.

**Accent reserved for (unmodified list, restated for completeness):** primary CTA per screen (one per screen max), active nav item, focus rings, checked/selected form controls, and the sending-progress bar + «Отправляется» badge (04's narrow "active operation" extension). Nothing in Phase 20 adds to this list.

**Semantic status colors (badges only) — unchanged from 04-UI-SPEC.md.** `CampaignStatusBadge.tsx`'s visual output (label text, `CLASSES` map) is **not modified** by this phase; only its internal `LABELS` map gains an export (`CAMPAIGN_STATUS_LABELS`) so `campaignSendConflict.ts`'s illegal-transition copy can name the real state using the exact same Russian word the badge already shows — one label source, never two independently-worded names for the same status.

No gradients. No additional hues. No charts in this phase.

## Copywriting Contract

All UI copy is **Russian** (per Phase 1–4 convention). Sentence case, address the user with «вы» (lowercase), no exclamation marks. Every string below is either quoted verbatim from a locked decision/plan, or marked **(this spec's call)** where the plan explicitly left the wording open.

### Primary CTAs (verb + noun, unchanged from 04-UI-SPEC.md — restated, none added)

| Screen / Element | Copy |
|-------------------|------|
| Launch confirm dialog — send immediately | «Отправить» (unchanged) |
| Schedule dialog — confirm schedule | «Запланировать» (unchanged) |
| Test-send panel | «Отправить тестовое письмо» (unchanged) |
| Campaign builder — save without sending | «Сохранить черновик» (unchanged) |
| **New — unsaved-changes banner's save button** | «Сохранить» (pending label: «Сохраняем…») — invokes the SAME save mutation as «Сохранить черновик», per D-03; not a new save path |

### Unsaved-changes state (TMPL-01, D-01/D-02/D-03)

| Element | Copy |
|---------|------|
| Banner message (fixed, from 20-05-PLAN.md Task 2 verbatim) | «Есть несохранённые изменения — сохраните черновик, чтобы отправить, запланировать или отправить тестовое письмо.» |
| Banner save button | «Сохранить» / pending: «Сохраняем…» |
| Inline dirty-block reason, shown next to launch/schedule and test-send when disabled solely because the form is unsaved **(this spec's call — 20-CONTEXT.md leaves the exact wording to discretion; 20-05-PLAN.md fixes only the mechanism, not this string)** | «Сохраните изменения, чтобы отправить, запланировать или отправить тестовое письмо» — deliberately echoes the banner's own phrasing (D-02's "one mental model") without repeating "Есть несохранённые изменения", since the banner directly above already states that; the inline line answers "why is this button disabled" specifically. |
| Precedence when both an incomplete-field reason and the dirty reason apply | The incomplete reason wins and is the ONLY line shown (per 20-05-PLAN.md Task 3: "the incomplete reason when there is one, otherwise the context's block reason" — one line, one `<p>` element, never both stacked). |

### Version-conflict and stale-state recovery (TMPL-02, D-08/D-09/D-10)

| Case | Copy |
|------|------|
| `version_conflict` on launch or schedule (D-08, verbatim from 20-CONTEXT.md and 20-06-PLAN.md) | «Кампания была изменена — данные обновлены, проверьте и повторите» — rendered in the dialog's existing `serverError` paragraph; dialog stays OPEN; no auto-retry. |
| `illegal_transition` on launch or schedule (D-09, template fixed by 20-06-PLAN.md, `{label}` filled from `CAMPAIGN_STATUS_LABELS`) | «Кампания уже в статусе «{label}» — данные обновлены, проверьте и повторите» — e.g. «Кампания уже в статусе «Отправляется» — данные обновлены, проверьте и повторите». |
| `version_conflict` on test-send (D-11, same copy as launch/schedule per the uniform-contract principle) | Same string as above: «Кампания была изменена — данные обновлены, проверьте и повторите» — rendered in `TestSendPanel`'s existing error paragraph, panel stays visible (there is no dialog to keep open). |
| `illegal_transition` on test-send | Not reachable — test-send performs no status transition (20-06-PLAN.md Task 1, action 4); falls through to the existing generic test-send failure copy if some other error occurs. |
| D-10 refresh notice, shown as an informational (not error) toast whenever a conflict-triggered refetch replaces unsaved local edits **(this spec's call — wording not fixed by any plan; mechanism — "informational, not an error toast" — is fixed by 20-06-PLAN.md Task 1 action 3)** | «Данные кампании обновлены — несохранённые изменения заменены сохранёнными значениями.» |

### Existing generic/error copy (unchanged, restated for completeness)

| Case | Copy |
|------|------|
| Generic server error (any 4xx/5xx outside the two recoverable 409 codes) | «Что-то пошло не так. Попробуйте ещё раз — если ошибка повторится, обновите страницу.» (unchanged `GENERIC_ERROR`) |
| Test-send failure (any error outside `version_conflict`) | «Не удалось отправить тестовое письмо. Проверьте шаблон и отправителя, затем попробуйте снова.» (unchanged `TEST_SEND_FAILURE`) |
| Missing audience/template/sender at launch time | «Выберите сегмент-аудиторию» / «Выберите шаблон письма» / «Выберите отправителя» (unchanged `computeIncompleteReason`, still takes precedence over the dirty reason above) |

### Toasts (sonner, unchanged conventions)

Existing success toasts are unchanged: «Кампания отправлена», «Кампания запланирована», «Черновик сохранён», etc. The one new toast is the D-10 refresh notice above, which uses sonner's default (informational) call, never `toast.error`.

| populated | Unsaved-changes banner | ✅ covered | Dirty state → banner renders the fixed message + save button, per the Copywriting Contract above. |

| error | 409 `version_conflict` / `illegal_transition` on launch, schedule, test-send | ✅ covered | Typed-code branch renders the specific copy in the existing error paragraph; every other error keeps the pre-existing generic copy (Copywriting Contract, "Version-conflict" and "Existing generic" rows). |

Interaction rules (extends Phase 1–4's, unchanged principles unless noted):
- Every mutating button keeps its existing disabled + loading state during the request; no double-submit. (unchanged)
- The unsaved-changes banner is the FIRST child of the draft view's `space-y-6 px-8 pb-8` container, directly above `TestSendPanel` — next to the actions it blocks, per D-01.
- **New rule:** launch, schedule and test-send are additionally disabled whenever the campaign form differs from the saved row (`isDirty`), on top of their existing completeness/permission gates. The three gates compose (any one disables the action); only one reason line renders per D-01/Task-3 precedence (incomplete > dirty).
- **New rule:** a version-conflict or illegal-transition response to launch/schedule never closes the dialog and never re-submits the mutation automatically — the marketer's next click is the only thing that may resend. Selection of which copy to show is by the response body's typed `code` field, never by matching `err.message` text (D-08/D-09, Pitfall #2).
- **New rule:** no `beforeunload` listener and no router-blocker of any kind is introduced anywhere in this phase (D-04) — navigating away from an unsaved campaign is not guarded; only the three send actions are.
- Same "no further live user input" precedent as 04-UI-SPEC.md's provenance note applies here: every value in this document is either a locked plan decision quoted verbatim, or an explicit, narrow "this spec's call" fill-in following the established house style — revise by re-running `/gsd-ui-phase 20` if any default should change.
