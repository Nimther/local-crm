## Flagged assumptions (phase-wide, spec-less probe fallback)

This phase has no SPEC.md, so plan-phase ran the deterministic edge probe against the three requirement IDs instead. All three rows came back `unclassified` → `unresolved` (the probe's classifier is English-keyed; `.planning/REQUIREMENTS.md` is written in Russian — a known, recurring behaviour in this project, not a new defect). Per the fallback protocol an `unclassified` row is never auto-backstopped and never silently dropped, so all three are recorded here as explicit assumptions:

1. **TMPL-01 — unresolved.** No edge predicate was derived. These plans assume TMPL-01's edge surface is exactly D-02's four compared fields (name, segmentId, templateId, fromSenderId), the three blocked actions (launch, schedule, test-send), and the saved/unsaved boundary. An edge outside that set (e.g. a field added to the campaign form by a later phase) is not covered here.
2. **TMPL-02 — unresolved.** No edge predicate was derived. These plans assume TMPL-02's edge surface is exactly: version equal (proceed), version lower or higher (409 `version_conflict`), version absent or non-integer or below 1 (400), and status not `draft` (409 `illegal_transition`). Concurrency beyond a single row lock (e.g. two API instances) rides on Postgres `FOR UPDATE` and is not separately probed.
3. **TMPL-03 — unresolved.** No edge predicate was derived. These plans assume TMPL-03's edge surface is exactly: a job carrying the snapshot fields, a job carrying neither (a pre-Phase-20 in-flight job), and a campaign row whose template changed between enqueue and dispatch.

|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-01-01 | Tampering | `ALTER TABLE campaigns ADD COLUMN version` | low | accept | The statement adds a column with a constant default and no `UPDATE`/backfill, so it cannot read, move or overwrite any tenant value; every pre-existing row deterministically reads 1. |
