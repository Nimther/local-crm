<objective>
The tracer slice: one send path — launch — carried end to end through every layer this phase touches, with the version precondition enforced inside the existing locked transaction and the client sending the version it read.

Purpose: this is the thinnest path that proves the whole architecture of the phase (column → zod contract → locked check-and-bump → typed 409 with a code → client echo) before the same shape is applied to schedule and test-send in plan 20-03. It also resolves, in production code, the one genuine gap between two independently-made decisions that RESEARCH.md found: `resolveCampaignFromEmail` writes `campaigns.from_email` in its own transaction BEFORE the launch transaction runs, so under D-05's any-write-bumps rule the primary sender path would 409 on its first, blameless attempt.

Output: launch refuses a stale or absent version with a typed 409/400 and dispatches nothing; launch with the confirmed version sends and bumps once; the launch route validates a body for the first time; and the campaign response publishes `version`.
</objective>

The fallback edge-coverage row for TMPL-02 came back `unclassified`/`unresolved` (the probe's classifier is English-keyed, the requirement text is Russian). This plan assumes TMPL-02's launch-path edge surface is exactly: version equal → proceed; version stale → 409 `version_conflict`; version absent/non-integer/below 1 → 400; status not `draft` → 409 `illegal_transition`. An edge outside that set is not covered here. Full statement in `20-01-PLAN.md`.

## Resolved research questions

- **RESEARCH Pitfall #1 (the sender-resolution write races the version check): resolved by splitting resolve from persist, for the launch path in this plan.** A new read-only `resolveCampaignSenderEmail` performs the SendGrid `verified_senders` match and returns the address without touching the row; `launchCampaign` persists it inside the same locked transaction that checks and bumps the version. The SendGrid HTTP call stays OUTSIDE the lock deliberately — holding `FOR UPDATE` across a provider round-trip would be a far worse hazard than the one being fixed.
- **The transient state this plan leaves on purpose:** the existing persisting `resolveCampaignFromEmail` stays in place for the schedule and test-send routes, which plan 20-03 migrates. Removing it here would strip `from_email` persistence from those two paths mid-phase and the dispatch worker hard-requires that column. Its pre-transaction write therefore still bumps nothing for those paths until 20-03 — do not "clean this up" early.
- **RESEARCH Open Question 1 (should the draft PATCH also require expectedVersion): no.** D-06 enumerates launch/schedule/test-send only. Two marketers clobbering each other's draft edits is a pre-existing gap, out of this phase's scope; this plan does not widen `updateCampaignSchema`.
- **Check order inside the locked transaction: not_found → status → version → incomplete.** Status first so a concurrent launch/cancel reports the real state (D-09's copy needs it) rather than a conflict; version before the field-completeness check so a stale view never produces a misleading per-field error.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → launch route | untrusted JSON body crosses here; after this plan it carries `expectedVersion` and nothing else |
| route → locked campaign row | the only place the send decision is made; the row, not the request, supplies template/sender/segment |
| api → SendGrid `/v3/verified_senders` | outbound read used to resolve a sender id to an address; never trusts a client-supplied address |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-02-01 | Tampering | launch precondition (check-then-act) | high | mitigate | The version comparison happens inside the same `SELECT … FOR UPDATE` transaction that performs the status flip and the bump, in `launchCampaign` — never as a route-level pre-check followed by an unlocked write. Proven by the stale-version integration test asserting the row is untouched. |
| T-20-02-02 | Tampering | send decision reading client-supplied campaign fields | high | mitigate | `launchCampaignSchema` accepts exactly one integer field; template, sender and segment are read from the locked row, and the kickoff job carries ids only. No code path in this plan reads a template or address from the request body. |
| T-20-02-03 | Spoofing | sender resolution moved ahead of the lock | medium | mitigate | Resolution remains a read-only match against SendGrid's own `verified_senders` list (an id SendGrid vouches for), and its result is persisted only inside the locked transaction — whose version check would already have rejected a row that changed since the pre-read. |
| T-20-02-04 | Information Disclosure | `currentVersion` in the 409 body | low | accept | An integer counter for a campaign the caller already holds workspace membership and `campaign:launch` for; it discloses nothing beyond "this row changed", which the caller is entitled to know. |
| T-20-02-05 | Repudiation | a launch the marketer never confirmed | high | mitigate | The precondition is required (400 without it) and compared under lock, so a send can only proceed against the exact state the marketer's client read; the conflict path returns before the kickoff enqueue, asserted by the absence of the kickoff job. |
| T-20-02-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs no package; RESEARCH.md's Package Legitimacy Audit records "not applicable" for the phase. |
