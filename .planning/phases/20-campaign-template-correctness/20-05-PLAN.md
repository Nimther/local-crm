<objective>
Make the unsaved state of the campaign form visible and make it block all three send actions until the marketer saves (TMPL-01, SC1).

Purpose: this is the located bug's other half. The builder's template/sender/segment choices live in local React state while `TestSendPanel` and `LaunchScheduleActions` act on the saved server row, so an unsaved dropdown change is silently ignored and the old template goes out. Plans 20-02…20-04 make the server refuse a stale version; this plan makes the client refuse to ask in the first place, and says so.

Output: a pure comparison module, one shared context computed above all three consumers, an amber banner with a one-click save, and disabled actions with inline reasons — plus unit and rendered-markup coverage in the existing web test lane.
</objective>

## Resolved research questions

- **State-sharing mechanism (CONTEXT.md leaves this to the planner): a scoped React context, not lifted props and not a store.** `CampaignBuilderPage` is mounted TWICE in this app — embedded by `CampaignDetailPage` for `/campaigns/:id`, and standalone for `/campaigns/new` where there is no parent to lift into and no saved row to compare against. Converting its form state to controlled props would make the create page carry a dual-mode component for no benefit; a context whose default value is inert keeps the create page byte-identical in behaviour. Zustand is reserved in this project for canvas/editor state and adding a store for one boolean with one producer and three consumers mounted on one page would be heavier than the problem.
- **Why the comparison lives in a pure module:** `apps/web`'s vitest lane runs in `environment: "node"` with no jsdom and no `@testing-library/react`, so interaction cannot be simulated in a unit test. `segmentSaveGate.ts` is the established answer to exactly this constraint: put the decision in a pure function, test it exhaustively, and assert the rendered consequence with `renderToStaticMarkup`. The click-through proof is the Playwright spec in plan 20-06.
- **`fromEmail` is excluded from the comparison** (RESEARCH Pattern 1): it is system-resolved by the sender resolver, not marketer-edited, and including it would show a false unsaved state right after a resolution persisted a new address.

       - `export const CampaignDirtyStateContext` created with an INERT default value — `isDirty: false`, `blockReason: null`, a null save handle, `isSaving: false`, and a no-op publish function. Exporting the context object itself is required: it is how a test renders a consumer against a hand-made state, and how the create page stays unaffected.

       - `export function CampaignDirtyStateProvider({ saved, children })` where `saved` is the `CampaignResponse` the detail page already has. It holds the published form snapshot (initially null) and the published saving flag in state, holds the published save callback in a ref, exposes a stable `save` callback that invokes whatever the ref currently holds, computes `isDirty`/`blockReason` via the pure module ONLY when a snapshot has been published (a null snapshot means the builder has not synced yet and must read as clean), and memoises the context value.
       - `export function usePublishCampaignFormState({ form, save, isSaving, enabled })` — the builder-side hook. It reads the context's publish function and calls it from an effect whose dependency list is exactly the four field values plus `isSaving` and `enabled`, so a provider re-render cannot re-fire it. When `enabled` is false it publishes nothing. Outside a provider the default no-op publish makes the whole hook inert, which is what keeps `/campaigns/new` working.
       - Document the two traps directly on the code: the publish must not fire before the builder's server-row sync has landed (otherwise the empty initial fields read as dirty for one commit and the banner flashes), and the save callback is held in a ref rather than in state so a re-publish cannot loop while still never holding a closure older than the last field change.
