Exported pure functions (parameters passed explicitly, never read from `process.env` or
`process.cwd()` inside the pure logic, so tests call them directly):
  - `BLOCKING_SEVERITIES` — the frozen set of severities that block, per D-09.
  - `collectAdvisories(vulnerabilities)` — walks the `vulnerabilities` object from an
    auditReportVersion-2 report. For each package key, iterate `via[]`: a string element is a
    reference to another package key and must be recursed into; an object element is a leaf
    advisory and yields one record `{ package, advisoryId, severity, title, url }` where
    `advisoryId` is the last path segment of `via.url` and `severity` is the LEAF advisory's own
    severity. Never read the package-level `severity` field — it is a max-rollup across that
    package's advisories and would mis-classify a package that carries both a high and a moderate
    advisory. Attribute each advisory to the package whose `via[]` produced it, so a compound
    parent that owns no advisory of its own contributes none. Carry a `seen` Set so a cyclic or
    diamond reference terminates. Build accumulators with `Object.create(null)` / `Map` and read
    package entries with an own-property check so a registry-supplied key cannot reach
    `Object.prototype`.
  - `runNpmAuditWithRetries(cwd, maxRetries)` — the one I/O function. Invokes
    `npm audit --json` via `execFileSync` with `encoding: "utf8"`. npm exits non-zero whenever it
    finds ANY vulnerability and still writes the full report to stdout, so on a thrown error the
    function must read `err.stdout` and attempt `JSON.parse` before treating the attempt as a
    failure — the `runCapture` idiom in check-lockfile-npm10.mjs is the pattern. Assert the parsed
    document has `auditReportVersion === 2` and an object-valued `vulnerabilities`; anything else
    is a failed attempt. Retry up to `maxRetries` (default 3) and then THROW a fail-closed error
    whose message states that npm audit was unreachable/unparseable after N attempts. There is no
    skip path and no env flag that downgrades this to a pass — D-03 makes unavailable tooling a
    violation, matching the Alloy-gate precedent.
  - `selectBlockingFindings(advisories, acceptList, now)` — filters to `BLOCKING_SEVERITIES`, then
    removes any finding covered by an accept-list entry whose `advisoryId` AND `package` both
    match the finding. Match on the LEAF package name, which is what `collectAdvisories` attributes
    to. In this plan `acceptList` is consumed as a plain list of already-validated entries; plan
    18-02 adds the schema validation that produces it. Return the surviving findings sorted by
    package name then advisory id, so the report is byte-stable across runs.
  - `formatFailureReport(findings)` — the actionable report. For each finding print the leaf
    package name, the GHSA id, the severity and the advisory url. Follow the sibling scripts'
    three-part failure shape: what failed, the raw evidence, then an explicit `Remediation:`
    section naming `npm audit fix`, the direct-pin bump form
    `npm install <pkg>@<version> -w <workspace>`, and — for a finding proven unreachable — adding
    a justified, owned, time-limited entry to `.advisory-accept-list.json`.

`main()` orchestrates only, guarded by the repo-standard `isDirectInvocation()` helper (copy the
`pathToFileURL` form from check-lockfile-npm10.mjs verbatim). It runs the audit, collects
advisories, reads `.advisory-accept-list.json` from the repo root, selects blocking findings,
prints the report and exits 1 when any survive; on a clean tree it prints a one-line pass naming
how many advisories were examined and how many accept-list entries were applied. A run that
examined zero advisories because the audit output could not be parsed is never a pass.
