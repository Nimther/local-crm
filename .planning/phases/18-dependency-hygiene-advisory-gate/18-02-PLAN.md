<objective>
Make the accept-list self-enforcing: an acceptance without justification, owner or a bounded,
unexpired date cannot pass the gate.

Purpose: DEP-03 and ROADMAP SC4. The accept-list is the only sanctioned way a blocking advisory
stops blocking, so its schema is the whole integrity story — D-04 makes every field mandatory,
D-05 caps expiry at 90 days, D-06 makes the justification field itself the reachability analysis
(one artifact, one review surface), and D-07 pins the owner to a git-author email. The gate
validates all of it, so an acceptance decays into a red build instead of quietly becoming
permanent.

Output: `loadAcceptList` / `validateAcceptListEntry` and their constants inside the existing gate
script, plus the fixture suite that proves each rejection.

EXPECTED STATE AFTER THIS PLAN: the gate is still RED against the unfixed tree (plan 18-03 fixes
that). The accept-list ships empty; SC4 is proven by fixtures, not by a manufactured live entry.
</objective>

<feature>
  <name>Accept-list schema validation with bounded, owned, justified expiry</name>
  <files>scripts/check-dependency-advisories.mjs, scripts/__tests__/check-dependency-advisories.test.mjs</files>
  <behavior>
    Entry shape (D-04): `{ advisoryId, package, justification, owner, expiry }`, all mandatory.
    - `advisoryId` — non-empty string in GHSA form (`GHSA-` followed by three dash-separated groups).
    - `package` — non-empty string, matched against the LEAF package a finding is attributed to.
    - `justification` — non-empty string of at least `MIN_JUSTIFICATION_LENGTH` characters after trimming (D-06; the field IS the reachability analysis, so a one-word value is rejected).
    - `owner` — non-empty, email-shaped string (D-07: the git author email of the accountable person).
    - `expiry` — `YYYY-MM-DD`. Valid through the end of that date inclusive; compared as a UTC date, never as a local timestamp.
    Boundaries (D-05): expiry equal to today is valid; expiry equal to today minus one day is expired; expiry equal to today plus `MAX_EXPIRY_DAYS` (90) is valid; today plus 91 days is rejected as exceeding the cap.
    File-level: missing file → empty accept-list plus a printed notice; unparseable JSON → gate failure; `entries` absent or not an array → gate failure; duplicate (advisoryId, package) pair → gate failure; `{"entries": []}` → valid.
    Matching: a valid entry suppresses exactly the finding whose advisoryId AND leaf package both equal the entry's; an entry matching no current finding is a printed stale-entry warning, not a failure.
  </behavior>
  <implementation>
    Hand-rolled validation using Node built-ins only — no schema library, no date library. A single
    `Date.UTC`-based day comparison covers both expiry rules. Extend the existing gate script's
    exported pure functions; keep the file dependency-free.
  </implementation>
</feature>
