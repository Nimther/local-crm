<objective>
Close verification gap 2: `recordAuthPurgeCounts` can destroy the immutable
`table_counts` compliance census with zeros in a real crash window, and no
regression test exercises that window.

Purpose: `purge_records.table_counts` is the durable, PII-free evidence that a
workspace's rows were actually destroyed (D-10). Today the auth step's tail is
three statements across two connections — (1) `deleteWorkspaceAuthRows`
commits on the `mega_crm_auth` pool, (2) `recordAuthPurgeCounts` writes the
returned counts on the platform pool, (3) `markPurgeTableDone` appends the
`auth` marker. A kill between (1) and (2)/(3) leaves the marker absent; the
next tick re-enters, deletes zero rows, and writes `member: 0, invitation: 0`
as the FIRST successful write — the real counts are gone forever.

**Why a write-once guard alone is not the fix, and why this plan does not take
the verifier's literal "capture counts atomically with the delete" option
either.** A write-once merge only prevents *overwriting*; in this exact window
there is no prior value, so zero still lands as the first write (the review's
own wording: "overwriting **or being the first successful write of**").
Capturing the counts atomically with the delete would require a
`purge_records` UPDATE inside `deleteWorkspaceAuthRows`'s transaction on the
elevated pool — which directly violates plan 22-07's declared, verified
prohibition that the `mega_crm_auth` connection issues exactly two statements
against exactly two tables. The only fix that satisfies BOTH the gap and the
standing prohibitions is: **count the rows on the ordinary platform pool
BEFORE the delete, record them write-once, then delete.** `mega_crm_app`
already holds `SELECT` on `member`/`invitation` (migration 0045 — the same
grant `workspace-purge-resume.test.ts`'s own `memberCount`/`invitationCount`
helpers already rely on), so no new grant and no migration is needed.

Both halves are load-bearing: reordering alone still lets a resumed tick
re-count zero and overwrite; write-once alone still records zero as the first
write. Together the window is closed by construction.

**Seam placement note for re-verification.** The verifier asked for a kill case
that "freezes strictly between the auth delete's commit and
`recordAuthPurgeCounts`". The new `afterAuthDelete` seam fires the instant
`deleteWorkspaceAuthRows` returns. Under the CURRENT code that is literally
between the delete's commit and `recordAuthPurgeCounts`; under the CORRECTED
ordering it is between the delete's commit and `markPurgeTableDone` — the same
window, and the last unmarked one in the auth step, because
`recordAuthPurgeCounts` has moved ahead of the delete. The seam position is
stable across both versions, which is exactly what lets the same test be RED
before the fix and GREEN after it.

Output: a write-once, crash-safe auth-step census; an eighth real-SIGKILL
regression case; corrected doc comments; SPECIFICATION.md reconciled in the
same change.
</objective>
