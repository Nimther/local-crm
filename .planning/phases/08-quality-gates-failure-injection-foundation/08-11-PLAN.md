## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

Coverage has never been measured in this repository. This plan measures it once, correctly, and records the number the gate in 08-14 will enforce.

## Artifacts this phase produces

- Root `vitest.config.ts` with `test.projects`
- `packages/segments-core/vitest.config.ts` and `packages/shared-schemas/vitest.config.ts` (minimal, so both are addressable as projects)
- `coverage-baseline.json` (keys: `lines`, `measuredLines`, `measuredAt`, `increment`, `scope`)
- Root npm script `coverage`
- devDependency `@vitest/coverage-v8` in `apps/api` and `apps/worker`

<objective>
Produce one aggregated coverage run over the backend scope, measure the real number, and record a threshold set at that number plus a deliberate increment — in that strict order, because the baseline cannot exist before coverage has been measured once.

Purpose: SPEC R3 requires the threshold to come from a measured baseline plus a deliberate increase rather than a round number (Pitfall 22). And the aggregation shape matters more than the provider: `packages/kms`, `packages/tenant-context` and `packages/contacts-core` have no tests of their own but are executed by `apps/api`'s tests — a per-workspace report merge would show them at 0% and drag the threshold down to a meaningless number.
Output: an aggregated coverage run and a recorded threshold with its provenance.
</objective>

    Recording `measuredLines` alongside the enforced `lines` is what makes the increment auditable. A bare threshold number invites the exact downward drift the ratchet in 08-14 exists to prevent, because nobody can tell whether a lowered value is a correction or a capitulation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Coverage report → the number that gates merges | A per-workspace report merge would show executed-but-untested packages at 0% and produce a meaninglessly low threshold |
| Aggregated run → per-project settings | Losing `fileParallelism: false` on `apps/worker` reintroduces a real BullMQ worker stealing sibling files' jobs, which presents as flakiness rather than a config regression |
| Threshold value → future edits | A bare number with no recorded provenance invites silent downward drift |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-11-01 | Repudiation | A workspace silently dropping out of the denominator | high | mitigate | A single aggregated run with `test.projects`: a project whose tests fail or do not run fails the whole run, verified empirically by breaking a `packages/flows-core` test and observing a non-zero exit |
| T-08-11-02 | Tampering | A threshold derived from a round number rather than a measurement | medium | mitigate | `coverage-baseline.json` records `measuredLines`, `measuredAt` with the raw `covered`/`total` integers, and the explicit `increment`, so any future change to `lines` is auditable against its own provenance |
| T-08-11-03 | Denial of Service | Losing `fileParallelism: false` under project aggregation | medium | mitigate | Verified after the first aggregated run and restated on the worker project entry if not inherited; the discrepancy is recorded in the summary either way |
| T-08-11-04 | Repudiation | Coverage percentage standing in as evidence that crash scenarios exist | medium | mitigate | Out of scope for this number by decision (D-20); the five scenarios are tracked by name in a separate checklist produced in 08-13, never by a percentage |
| T-08-11-SC | Tampering | npm install of `@vitest/coverage-v8` | high | mitigate | Approved in 08-RESEARCH.md § Package Legitimacy Audit (official `vitest-dev` scope, 31M weekly downloads); its `SUS` verdict is the documented "too-new" false positive.
