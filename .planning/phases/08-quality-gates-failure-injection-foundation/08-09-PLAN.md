## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

Thirty-eight migrations exist and none of them has ever been verified as a chain. This plan makes both the from-scratch path and the incremental-with-data path automatic.

## Artifacts this phase produces

- `packages/test-support/src/migration-runner.ts` exporting `listMigrationFiles(dir)`, `applyMigrationFile(client, dir, filename)`, `applyMigrationsUpTo(client, dir, lastFilename)`, `applyRemainingMigrations(client, dir, afterFilename)`
- `packages/db/vitest.config.ts` and a `test` script in `packages/db/package.json`
- `packages/db/src/__tests__/migrate-from-empty.test.ts`, `packages/db/src/__tests__/migrate-incremental.test.ts`
- Fixture migration used only by run B's NOT NULL assertion (created and discarded in-test, not committed to `packages/db/migrations`)

<objective>
Prove the migration chain twice: once against an empty database, once against a database already carrying representative rows at a prior-release checkpoint — with both runs unable to pass vacuously.

Purpose: SPEC R5 exists because the only thing that has ever applied these 38 files is a test fixture running inside unrelated tests. Nobody has verified that the chain applies cleanly from zero, and nobody has verified that a later migration is safe against a populated table — which is the failure mode that actually breaks a deploy.
Output: two automatic runs, both blocking, both defended against a green that proves nothing.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Migration chain → production schema | An untested chain is applied for the first time during a deploy, where a failure is an outage rather than a red test |
| Migration → existing production rows | A NOT NULL column added without a DEFAULT blocks or fails against a populated table, and nothing in the current setup would catch it |
| Test provisioning → non-test databases | Both runs create and drop their own databases, exercising the same privileged path 08-02 guarded |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-09-01 | Denial of Service | Untested migration chain failing at deploy time | high | mitigate | Run A applies every file to a guaranteed-empty database and asserts the resulting schema and RLS posture, not merely the absence of an exception |
| T-08-09-02 | Tampering | Unsafe DDL against populated production tables | high | mitigate | Run B seeds representative rows before applying the remainder and asserts that a NOT-NULL-without-DEFAULT fixture migration rejects against a non-empty table |
| T-08-09-03 | Repudiation | A vacuously green run B where nothing was applied | high | mitigate | `applyRemainingMigrations` returns the applied filename list and the test asserts length ≥ 1 with an explicit message; seeds are inserted inside a tenant scope so RLS cannot silently drop them to zero |
| T-08-09-04 | Tampering | Out-of-order migration application from a non-padded filename | medium | mitigate | `listMigrationFiles` throws on any filename lacking a zero-padded numeric prefix, unit-tested against a temp directory |
| T-08-09-05 | Tampering | Provisioning path dropping a non-test database | critical | mitigate | Both runs use `createEphemeralDatabase`/`dropEphemeralDatabase` from 08-02, whose name validation is inside the drop function |
| T-08-09-SC | Tampering | npm/pip/cargo installs | high | mitigate | Only `vitest@4.1.9` (already present elsewhere in the repo at that exact version) and the internal `@mega-crm/test-support` link are added to `packages/db`; no new external package enters the tree |
</threat_model>
