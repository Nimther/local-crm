## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

This is the fourth of the five audit-named failure modes, and the only one that needs a real process to die.

## Artifacts this phase produces

- `packages/test-support/src/harness/spawn-and-kill.ts` exporting `spawnAndAwaitReady(options)` and `killAndAwaitExit(child)`
- `apps/worker/src/test/harness/sigkill-entrypoint.ts` (child-process entrypoint, IPC-driven)
- IPC message markers `run` (parent→child) and a ready marker (child→parent)
- npm script `failure:sigkill`
- Env var `SIGKILL_HARNESS_JOB_DATA` (job payload passed to the child)
- The D-22 deviation record below, to be carried into the plan summary

<objective>
Kill a real worker process with SIGKILL at a deterministically-chosen instant inside the claim-committed-but-not-yet-recorded window, and prove that a restart does not re-send the email.

Purpose: SPEC R6 states outright that an arbitrary kill moment proves nothing. The window this scenario targets is exactly where the CR-04 duplicate-send bug lived, and Phase 11 cannot change the delivery state machine without a harness that can reproduce it.
Output: one command that spawns, freezes, kills and asserts — with no timer and no polling anywhere in the mechanism.
</objective>

## Deviation from D-22 (recorded deliberately)

D-22 places the SIGKILL harness entrypoint in `packages/test-support`. Taken literally that requires `packages/test-support` to import `processSendJob` from `@mega-crm/worker`, but `apps/worker/package.json` declares no `main`, `types` or `exports` field, and no `packages/*` workspace in this repository depends on any `apps/*` workspace — every dependency arrow today points app → package.

This plan therefore splits D-22's intent across the boundary rather than inverting it: the **generic, reusable** spawn/IPC/kill orchestration lives in `packages/test-support/src/harness/spawn-and-kill.ts` exactly as D-22 requires, and the **worker-specific child entrypoint** that imports `processSendJob` lives in `apps/worker/src/test/harness/sigkill-entrypoint.ts`, passed to the generic helper by path. This satisfies every substantive clause of D-22 — a real separate process, a real BullMQ-adjacent code path, live Postgres and Redis, only `sendMail` injected, no new seam — while avoiding a dependency direction that exists nowhere else in the repo. 08-RESEARCH.md flags this same gap and makes the same recommendation (§ Flag: D-22 mechanics gap, Assumption A5). This deviation is recorded here so the executor and any reviewer see it rather than discovering it.

  <behavior>
    - `spawnAndAwaitReady({ entrypoint, env, readyMessage })` starts a child with an IPC channel, sends the `run` message, and resolves with the child handle once the child sends `readyMessage`.
    - It rejects if the child exits before sending the ready message, surfacing the child's stderr in the rejection so a crashing entrypoint is diagnosable rather than a hang.
    - It rejects after a bounded wait if no ready message arrives, again surfacing captured stderr.
    - `killAndAwaitExit(child)` sends SIGKILL and resolves once the child's exit event fires, returning the observed exit code and signal.
    - The returned signal is `SIGKILL`, proving the process was killed rather than having exited on its own.
    - Neither function contains a timer that decides WHEN to kill — the bounded wait exists only to convert a hang into a diagnosable failure.
  </behavior>
  <action>
    Write `packages/test-support/src/harness/spawn-and-kill.ts` exporting the two functions above. Use Node's `child_process.fork` with an IPC channel (or execa's equivalent — pick one, record the choice and the reason in the plan summary, and do not mix both).

    Keep the module completely generic: it takes an entrypoint path, an env object, and the ready-message value as parameters. It must contain no reference to `processSendJob`, to the worker, to sends, or to any domain concept — that genericity is what lets the child entrypoint live in `apps/worker` without inverting the workspace dependency direction.

    Capture the child's stdout and stderr and attach them to any rejection. A child entrypoint that throws during module load exits before sending its ready message, and without captured stderr the parent sees only a timeout — which reads as flakiness and gets a retry loop bolted on instead of a fix.

    Include a bounded wait for the ready message purely as a hang-to-failure converter, and document in a comment that it is not the kill trigger. The kill trigger is the ready message itself; a timer-based kill is what SPEC R6 rejects as proving nothing.

    Export both functions from `packages/test-support/src/index.ts`. Do not add any `apps/*` workspace to `packages/test-support/package.json`.

    Write a small unit test for the helper against a throwaway fixture entrypoint (a few lines that send the ready message and then hang), asserting: the resolve-on-ready path, the reject-on-early-exit path with stderr surfaced, and that `killAndAwaitExit` reports signal `SIGKILL`.

That ordering is load-bearing: the parent's kill is triggered by the marker, and the marker is emitted from inside the call that the claim commit immediately precedes, so the process is provably frozen inside the window rather than approaching it. Reversing the two lines, or emitting the marker from anywhere outside the injected function, reintroduces exactly the race D-23 eliminated.
