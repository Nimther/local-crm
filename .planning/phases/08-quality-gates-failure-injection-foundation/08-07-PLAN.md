## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

08-03 built the gate and proved it can fail. This plan brings the existing 57k-LOC codebase to zero violations so the gate can be turned on without a permanent red.

## Artifacts this phase produces

- `docs/lint-rule-exceptions.md` — the register of rules disabled repo-wide, each with its reason
- Rule-disable block in `eslint.config.js` (rules turned off wholesale, with adjacent justification comments)

<objective>
Drive `npx eslint . --max-warnings=0` from its current violation count to zero, using the D-06 threshold rule: a violation appearing in many places because the rule does not fit this codebase gets the rule turned off with a written reason; a genuine one-off gets a line-scoped, rule-named, reason-bearing suppression; everything else gets fixed.

Purpose: a gate that is red on `master` from the day it ships is a gate everybody learns to ignore. Zero debt is what makes `--max-warnings=0` enforceable (D-06).
Output: a clean tree, a written exceptions register, and a file count still at or above the recorded floor.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Cleanup diff → gate strength | Reaching zero by broadening `ignores`, blanket-disabling files, or turning off the async rule class would leave a green gate protecting nothing |
| Added `await` → runtime ordering | Awaiting a previously-unawaited promise changes execution order in the send pipeline and the BullMQ workers, where ordering is behavior |
| Focused test markers → vacuous green suites | A `.only` left in a spec means everything else in that file has silently not been running |
