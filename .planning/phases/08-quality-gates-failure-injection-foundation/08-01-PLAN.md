## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

This is the **tracer plan**. It wires one thin, production-quality path through every layer the phase will later expand: GitHub Actions → `docker compose` services → ephemeral test database → fail-closed DSN guard → the existing worker test suite → a required status check on `master`. Nothing here is a prototype: the workflow file, the guard, and the `packages/test-support` workspace created here are the skeleton every later plan builds on.

## Artifacts this phase produces

- Workspace `@mega-crm/test-support` at `packages/test-support` (new npm workspace)
- `assertTestDatabaseUrl(testUrl, devUrl)` exported from `packages/test-support/src/guard.ts`
- `normalizeDsn(raw)` (module-internal helper in `guard.ts`)
- `packages/test-support/src/global-setup.ts` — vitest `globalSetup` default export
- `.github/workflows/ci.yml` with CI job name `test`
- `.nvmrc` pinning the CI Node major to the local runtime
- Ephemeral database name literal `mega_crm_test_worker` (tracer-only; replaced by per-run naming in 08-02)
- Required-status-check name `test` on branch `master`

<objective>
Prove the whole quality-gate chain end-to-end on the thinnest possible slice: one CI job, triggered on push and pull_request, that stands up real Postgres and Redis via `docker compose up -d --wait`, creates one ephemeral test database, runs a fail-closed DSN guard before any test executes, typechecks the monorepo via `npm run build --workspaces --if-present`, and runs the existing 24-file `apps/worker` suite. Then confirm on a real throwaway pull request that branch protection actually blocks a red run.

Purpose: catch an architectural dead-end after one commit instead of after ten. Every other requirement in this phase (lint-zero, coverage gate, five failure scenarios, redis.conf, migration tests, hygiene, docs) is an additive layer on this proven pipe.
Output: a green CI run on a real push, a red-then-green throwaway PR proving branch protection, and the `packages/test-support` workspace that later plans extend.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → third-party action code | Any action referenced by a floating tag can be re-pointed at attacker-controlled code with access to the job's secrets and the checked-out repo |
| CI job → developer's dev Postgres | The guard's whole purpose: a misconfigured DSN would let a CI or local test run write to real dev data |
| Test process → `packages/test-support` guard | A bypass parameter or env var in the guard would silently reopen the boundary it exists to close |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01-01 | Tampering | `.github/workflows/ci.yml` third-party action references | high | mitigate | `actions/checkout` and `actions/setup-node` pinned to full 40-char commit SHAs resolved via `gh api`, with the tag only in a trailing comment; no non-`actions/*` action is used |
| T-08-01-02 | Tampering | Test run resolving to the dev database | high | mitigate | `assertTestDatabaseUrl` runs in vitest `globalSetup` and throws before any test file is collected; both SPEC conditions (prefix + normalized triple inequality) are enforced together |
| T-08-01-03 | Elevation of Privilege | Guard bypass surface | high | mitigate | `assertTestDatabaseUrl` takes no opt-out parameter and reads no environment variable; asserted by a source grep in the acceptance criteria |
| T-08-01-04 | Information Disclosure | CI job env exposing DB credentials in logs | low | accept | Credentials are the docker-compose dev defaults (`postgres`/`mega_crm_dev_pw`) that already live in the public repo's `docker/init-app-role.sql`; no production secret is introduced by this workflow |
| T-08-01-SC | Tampering | npm installs (`execa` added to the new workspace manifest) | high | mitigate | 08-RESEARCH.md § Package Legitimacy Audit approved `execa@10.0.0` (sindresorhus, 152M weekly downloads, official repo); its `SUS` verdict is the documented "too-new" false positive. No `[SLOP]` package is installed. |
