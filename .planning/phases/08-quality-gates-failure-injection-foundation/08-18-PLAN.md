## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

Every gate this phase built now exists and is individually proven. This plan wires them into the workflow and turns the lock.

## Artifacts this phase produces

- CI job ids `static`, `test`, `failure-injection`, `e2e`
- Required-status-check set on `master`: `static`, `test`, `failure-injection`
- `.planning/config.json` `git.branching_strategy` set to the phase-branch model

<objective>
Expand the tracer's single job into the four-job workflow the phase designed, register the three blocking ones as required status checks on `master` with administrator bypass disabled, and switch the project to the branch-per-phase model that the pull-request gate presumes.

Purpose: every gate built in plans 02 through 17 is currently a script somebody could choose to run. This is the plan that makes them unavoidable.
Output: a four-job workflow, an enforced required-check set, and a demonstrated block on a red pull request.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Pull request → `master` | The only place every gate this phase built becomes unavoidable rather than optional |
| Administrator privilege → branch protection | With bypass enabled, every required check becomes advisory and the whole phase is decorative |
| GitHub Actions runner → third-party action code | An action referenced by a floating tag can be re-pointed at attacker-controlled code with access to the job's environment and the checkout |
| Aggregate convenience script → per-scenario independence | Running the five failure commands as one step hides a scenario that only passes when a sibling ran first |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-18-01 | Elevation of Privilege | Administrator bypass of branch protection | high | mitigate | `enforce_admins` set to true and verified by reading the protection API back in the checkpoint; the requirement is stated as a blocking condition, not a preference |
| T-08-18-02 | Tampering | Unpinned third-party action references | high | mitigate | Every `uses:` reference pinned to a full 40-character commit SHA, asserted mechanically by counting pinned references against total references |
| T-08-18-03 | Repudiation | A required check that never runs, leaving the pull request permanently pending or silently mergeable | high | mitigate | Both `push` and `pull_request` triggers present; required-check names taken from the workflow's job ids, which is what GitHub matches on; verified end to end by the throwaway pull request in the checkpoint |
| T-08-18-04 | Repudiation | Failure scenarios passing only in aggregate | medium | mitigate | Five separate steps; the aggregate script is asserted absent from the workflow |
| T-08-18-05 | Denial of Service | A flaky browser run blocking every merge | medium | mitigate | The `e2e` job carries `continue-on-error` and is deliberately excluded from the required-check set, per SPEC's explicit boundary; its machine-checkable value — the connection-string assertion — is still produced |
| T-08-18-06 | Information Disclosure | Repository secrets exposed to a fork's pull-request run | medium | accept | The workflow references no repository secret; every credential it uses is a docker-compose dev default already public in this repository. Revisit if a deployment job is added in Phase 14 |
| T-08-18-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; `npx playwright install` in the `e2e` job downloads browser binaries for the already-declared `@playwright/test` version |
</threat_model>
