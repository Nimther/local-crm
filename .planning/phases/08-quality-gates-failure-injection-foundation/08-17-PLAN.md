## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

This plan is deliberately last among the substantive work. Both documents describe machinery that only exists after the preceding plans land; writing them earlier would mean writing them about intentions.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Documentation → a reader's mental model | A document describing planned behavior as current sends the reader to look for code that does not exist, or worse, to assume a protection that is not in place |
| Written rule → enforced rule | A convention worded differently from what the linter accepts produces the exact ambiguity it was written to remove |
| Update rule → future changes | A rule that names no triggers is unenforceable, and the documents rot until they are actively misleading |
