## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

The working root currently holds a live configuration file with real secrets and a Redis dump. This plan moves the configuration decision into one function, points all six readers at it, and adds a check that fails when either file comes back.

## Artifacts this phase produces

- `resolveEnvPath()` exported from `scripts/env-path.mjs`, with types in `scripts/env-path.d.mts`
- Env var `MEGA_CRM_ENV_FILE`
- `apps/api/src/load-env.ts` and `apps/worker/src/load-env.ts` (side-effect modules)
- `checkRootHygiene(entries)` exported from `scripts/check-root-hygiene.mjs`, plus a CLI
- Root npm script `check:root-hygiene`
- `packages/test-support/src/__tests__/root-hygiene.test.ts`

<objective>
Reduce six independent hardcoded configuration paths to one function, move the file itself out of the repository working root, and add a blacklist check proven to fail when it comes back.

Purpose: the configuration file in the working root holds real platform secrets and is read from at least six places, each with its own hardcoded relative path. SPEC R9 requires the location to be settable in one place and the working root to be defended by a check. Moving the file without unifying the readers would just relocate the problem six times.
Output: one resolver, six updated readers, a fail-first-proven hygiene check, and an explicit operator instruction for the file move itself.
</objective>

## Operator task (agent must not perform it)

SPEC § Constraints places the configuration file under a hard tool-deny for the executor: the agent plans and documents the move but does not touch the file. The move itself is the operator's, and it is a blocking checkpoint in this plan. The agent's work is to make every reader look in the new place first and to make the check fail if the old place is repopulated.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repository working root → anything reading the repository | A file holding real platform secrets sitting in the working root is readable by every tool, script, editor extension and agent operating on this checkout |
| Six independent hardcoded paths → one decision | A location that is decided in six places cannot be moved, and each site drifts independently |
| Module import order → boot-time configuration validation | A configuration load that runs after the validating module has evaluated produces a boot failure that reads as missing configuration |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-15-01 | Information Disclosure | Secrets file in the repository working root | high | mitigate | The file moves out of the working root (operator checkpoint) and `scripts/check-root-hygiene.mjs` fails the build if it or a Redis dump reappears, proven fail-first against a fixture directory |
| T-08-15-02 | Tampering | Divergent hardcoded configuration paths | medium | mitigate | `resolveEnvPath()` is the single decision point; an acceptance check asserts no hardcoded working-root path survives in any of the six readers |
| T-08-15-03 | Denial of Service | Configuration loaded after the boot-time schema evaluates | medium | mitigate | `./load-env.js` is imported first in both `server.ts` files; the ordering is asserted by reading the import block and verified empirically by booting the API with the file only at the new location |
| T-08-15-04 | Information Disclosure | The agent reading or writing the secrets file | high | mitigate | The physical move is a blocking operator checkpoint; no task in this plan lists the configuration file in its `files_modified`, and the hygiene check operates on directory-entry names rather than file contents |
