## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

This plan makes Redis refuse writes at its ceiling instead of silently evicting BullMQ job state, and proves the check can actually fail.

## Artifacts this phase produces

- `docker/redis.conf` (directives: `maxmemory`, `maxmemory-policy`, `appendonly`, `appendfsync`)
- `packages/test-support/src/__tests__/redis-config.test.ts`
- docker-compose `redis` service `command:` override and read-only config bind mount

<objective>
Put Redis's durability and eviction posture under version control and behind an automated assertion that reads the live server's own `CONFIG GET` output — after first observing that same assertion fail against an unconfigured `redis:7`.

Purpose: every worker-reliability fix in Phase 12 is void if Redis can silently evict BullMQ job state under memory pressure (Pitfall 20). And a check that asserts only `maxmemory-policy` passes against a completely unconfigured server, proving nothing — `noeviction` is Redis 7's default and cannot trigger while `maxmemory` is 0.
Output: a versioned `redis.conf`, a compose mount, and a three-value assertion with a recorded fail-first observation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BullMQ job state → Redis memory ceiling | Under an eviction policy other than `noeviction`, Redis silently discards job data and the queue loses work with no error anywhere |
| Redis container lifecycle → enqueued jobs | Without AOF, a container restart drops everything written since the last RDB snapshot |
| Automated check → Redis reachability | A check that treats an unreachable server as "skipped" reports WRK-12 satisfied on a run where nothing was verified |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-04-01 | Denial of Service | Redis eviction of BullMQ job state | high | mitigate | `maxmemory 512mb` + `maxmemory-policy noeviction` in the version-controlled `docker/redis.conf`, applied by an explicit `command:` override and asserted by a live `CONFIG GET` test |
| T-08-04-02 | Repudiation | Vacuous WRK-12 check | high | mitigate | All four values asserted together, and the assertion observed failing against an unconfigured `redis:7` before the config existed; no conditional-skip construct is permitted in the test file |
| T-08-04-03 | Denial of Service | Job loss across a container restart | medium | mitigate | `appendonly yes` + `appendfsync everysec`; survival across `docker restart` is separately asserted by 08-13's scenario |
| T-08-04-04 | Elevation of Privilege | Dev Redis exposed on 6379 with no `requirepass` | medium | accept | Pre-existing condition of the dev-only compose file (SPECIFICATION.md §1.3), not introduced or regressed by this phase; production hardening belongs to Phase 15 |
| T-08-04-05 | Tampering | Read-write mount allowing a container to rewrite its own config | low | mitigate | The bind mount is `:ro`, matching the existing `docker/init-app-role.sql` mount |
| T-08-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan; `ioredis` was already declared in the test-support manifest by 08-01 |
</threat_model>
