<objective>
Deliver the Contacts integration API (CONT-03) and the single hardest correctness problem in this phase: the prioritized two-key upsert (CONT-04) that resolves contact identity by external_id then email, with the D-03 attach-identity and D-04/A1 conflict-logging semantics. This is the shared `upsertContactByIdentity` function that the event worker (02-06) and CSV worker (02-07) will both reuse — so it is built test-first with explicit coverage of every branch (RESEARCH Pitfall 2) and the reserved-key mass-assignment defense (Pitfall 4).

## Phase Goal

**As a** marketer, **I want to** build and maintain my contact base through the UI, CSV import, and a server-side API — while my product backend streams freeform behavioral events — **so that** my contacts are created and enriched in real time and every contact carries an accurate subscription status.

This slice makes the contact base programmatically writable: a tenant backend can now create/update contacts over HTTP with an API key, using the same identity rules that will govern events and CSV — a capability that did not exist after 02-03.

Purpose: `upsertContactByIdentity` is invoked from three call sites (this API route, the event worker EVNT-02, the CSV worker); it must be one function so D-03/D-04 semantics cannot drift.
Output: the upsert function (green under four-branch + reserved-key tests), the API-key-authed /v1/contacts routes, and their shared schemas.

## Assumption surfaced (must be honored, not silently dropped)
RESEARCH Open Question 1 / Assumption A1: when an incoming call matches an existing contact by EMAIL but that contact already has a DIFFERENT external_id set, this plan treats the incoming external_id as ignored (external_id immutable per D-06) and logs a structured conflict analogous to D-04/D-05. This is the researcher's recommended interpretation of a genuine gap in the locked decisions; it is implemented here and covered by a test. If the developer disagrees, revisit before this branch ships.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04-01 | Tampering | reserved-key mass assignment via properties | high | mitigate | Denylist {id, workspace_id, external_id, email, subscription_status} stripped before JSONB merge; test asserts subscription_status cannot be flipped (Pitfall 4) |
| T-02-04-02 | Tampering | identity-anchor overwrite (immutable external_id) | high | mitigate | Branch C ignores an incoming different external_id and logs a conflict (D-06/A1) |
| T-02-04-03 | Denial of Service | unauthenticated large-body parsing on /v1/contacts | medium | mitigate | apiKeyAuth on onRequest (before body parse) + @fastify/rate-limit + Fastify body-limit on the scope |
| T-02-04-04 | Information Disclosure | cross-tenant write via wrong workspace resolution | high | mitigate | Workspace resolved solely from request.apiKeyWorkspaceId; upsert runs inside withTenant + RLS |
| T-02-04-05 | Repudiation | silent data conflicts (D-04/A1) | low | accept | Structured Pino conflict logs are the v1 visibility surface; a UI for conflicts is explicitly deferred to v2 (D-05) |
