# Phase 2: Contacts & Event Ingestion - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Маркетолог собирает и ведёт базу контактов тремя путями — UI (CRUD), CSV-импорт с маппингом колонок, Contacts CRUD API — а бэкенд тенанта стримит свободные события (имя + JSON-свойства) через HTTP Event API с API-ключом. Event API отвечает 2xx сразу, обработка асинхронная через очередь; событие для неизвестного контакта создаёт его по upsert (external_id + email). Каждый контакт несёт 3-state статус подписки (subscribed / unsubscribed / suppressed). Эта фаза вводит в проект очередь (Redis + BullMQ по STACK.md) и partition-ready схему событий. Требования: CONT-01…05, EVNT-01…03, SUBS-01.

<decisions>
## Implementation Decisions

### Идентификация контакта и merge-конфликты
- **D-01:** Email уникален внутри воркспейса: один контакт = один email (Klaviyo-модель). Уникальность и upsert детерминированы.
- **D-02:** Минимум идентификаторов — email ИЛИ external_id (хотя бы один). Контакт только с external_id валиден: копит события и свойства, но писем не получает, пока не появится email (pre-signup/анонимный сценарий).
- **D-03:** Upsert-приоритет: сначала матч по external_id; если не найден — по email. Событие/API-вызов с НОВЫМ external_id и email существующего контакта без external_id → external_id ПРИВЯЗЫВАЕТСЯ к существующему контакту (сшивка CSV-базы с боевым трафиком, классический онбординг тенанта).
- **D-04:** Жёсткий конфликт (событие меняет email контакта A на адрес, занятый контактом B): событие и остальные свойства применяются к A, смена email ПРОПУСКАЕТСЯ, конфликт логируется. Ручной merge контактов — v2.
- **D-05:** Видимость конфликтов в v1 — только структурированные серверные логи (Pino); UI-поверхность не строим.
- **D-06:** External_id из UI/CSV можно ЗАДАТЬ (при создании или если пуст), но установленный менять нельзя — это якорь идентичности. Полностью редактируемый external_id запрещён.
- **D-07:** Email контакта можно менять из UI с проверкой уникальности; статус подписки при смене сохраняется.
- **D-08:** Удаление контакта — реальное (контакт + события удаляются), НО unsubscribed/suppressed email остаётся в отдельном suppression-списке воркспейса: ре-импорт/ре-создание того же email не воскрешает его как subscribed. Compliance-защита от «удалил → переимпортировал → снова шлём отписавшемуся».

### Модель контакта: поля, свойства, статус
- **D-09:** Стандартные поля (выделенные колонки, типизация, индексы под сегментацию Phase 3): имя, фамилия, телефон, город, страна + теги (массив) + created/updated. Всё остальное — кастомные свойства (JSONB).
- **D-10:** Авто-реестр обнаруженных кастомных свойств: свойство регистрируется при первом появлении (из API/события/CSV/UI) с наблюдаемым типом (string/number/bool/date). Без enforcement — реестр только для подсказок: CSV-маппинг, редактор свойств, сегмент-билдер Phase 3. НЕ путать с реестром типов СОБЫТИЙ (EVNT-V2-01, отложен).
- **D-11:** Дефолтный статус подписки при создании — subscribed для всех каналов (UI/CSV/API/событие): ответственность за согласие на тенанте (server-side модель Klaviyo). CSV/API могут явно передать другой статус (колонка/поле subscription_status). Suppression-список (D-08) перебивает дефолт.
- **D-12:** Ручная смена статуса в UI асимметрична: subscribed ↔ unsubscribed можно руками (просьба клиента голосом/письмом); suppressed (bounce/spam) снять из UI НЕЛЬЗЯ — это защита репутации домена, не предпочтение.
- **D-13:** Список контактов: таблица с поиском (email/имя/external_id) + фильтры по статусу подписки и тегам, сортировка, пагинация. Фильтры по кастомным свойствам не строим — это территория сегмент-билдера Phase 3.
- **D-14:** Карточка контакта уже в этой фазе показывает простую ленту событий (имя + время + раскрываемый JSON) — мгновенная обратная связь «события доходят» для отладки интеграции тенантом. Полный timeline (письма, открытия) — Phase 7 (ANLT-03).

### CSV-импорт
- **D-15:** Политика дубликатов — переключатель на шаге настройки импорта: «обновить существующие» (merge: непустые значения из CSV перезаписывают; дефолт) или «пропустить существующие».
- **D-16:** Импорт выполняется фоновой джобой через очередь; страница импорта показывает прогресс (обработано/всего), можно уйти и вернуться. Масштаб — файлы 100k+ строк.
- **D-17:** Превью: первые ~20 строк с применённым маппингом + dry-run валидация ВСЕГО файла до применения («98 500 будет создано, 1 200 обновлено, 300 с ошибками») — маркетолог жмёт «Применить» осознанно.
- **D-18:** Отчёт по завершении: сводка на экране (создано / обновлено / пропущено / ошибки по типам) + скачиваемый CSV ошибочных строк с колонкой «причина» — правишь и перезаливаешь только их.
- **D-19:** В маппинге колонок можно создать НОВОЕ кастомное свойство на лету (стандартные поля + известные свойства из реестра + «создать свойство») — первый импорт тенанта при пустом реестре иначе невозможен.
- **D-20:** История импортов (файл, дата, автор, сводка, ссылка на отчёт об ошибках) — да; undo импорта — v2.

### API-ключи и интеграционный API
- **D-21:** Несколько именованных API-ключей на воркспейс («prod backend», «staging»); Owner/Admin создаёт и отзывает каждый независимо — ротация без даунтайма. Это серверные ключи платформы, не SendGrid-ключ тенанта.
- **D-22:** Секрет показывается полностью один раз при создании; в БД хранится только хеш (как пароль); в списке — префикс + последние 4 символа. KMS для этих ключей не нужен (в отличие от SendGrid-ключа — тот нужно расшифровывать для использования, эти только сверяются).
- **D-23:** Без scopes в v1 — любой ключ даёт полный доступ к Event API и Contacts API; схему заложить расширяемой (колонка scopes на будущее).
- **D-24:** Event API принимает одно событие ИЛИ батч (массив до ~1000) в POST /events; ответ — по-элементный статус принятия. Контракт сразу батчевый, чтобы не ломать интеграции тенантов позже.

### Claude's Discretion
- Нормализация email (lowercase/trim), формат и длина external_id, формат префикса API-ключа — стандартные подходы.
- CSV: кодировки, разделители, лимит размера файла, потоковый парсинг (csv-parse по STACK.md).
- Схема таблиц, партиционирование events (по месяцу, по created_at — из CLAUDE.md/STACK.md), индексы, RLS-политики новых таблиц по паттерну Phase 1.
- Очередь: BullMQ + Redis (добавить в docker-compose), структура джоб, ретраи, идемпотентность обработки события, rate limiting Event API (@fastify/rate-limit уже в зависимостях).
- Семантика client-supplied timestamp у событий и дедупликация событий — по ресёрчу.
- UX редактора кастомных свойств в карточке контакта, валидации форм.

## Specific Ideas

- Лента событий в карточке контакта как инструмент отладки интеграции: тенант шлёт тестовое событие и сразу видит его в UI — «события доходят» видно глазами, согласуется с Core Value про надёжность.
- CSV-отчёт об ошибках в формате «исправь и перезалей только ошибочные строки» (скачиваемый CSV с колонкой причины).
- Klaviyo как референс модели: email-уникальность, свободные события, server-side ответственность за согласие.
