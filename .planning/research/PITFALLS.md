# Pitfalls Research — Hardening a Live Multi-Tenant Send Pipeline

**Domain:** Production hardening of a shipped multi-tenant email marketing automation platform (Fastify + Drizzle/Postgres RLS + BullMQ/Redis + SendGrid BYO keys) — milestone v1.1
**Researched:** 2026-07-27
**Confidence:** HIGH for BullMQ/Postgres/RLS mechanics (verified against first-party docs, GitHub issues, mailing-list threads); MEDIUM for Sentry/Testcontainers/Docker operational claims (cross-checked blog + vendor docs, no incident postmortem with this exact stack). Every claim below is tied to a specific finding in `AUDIT-2026-07-27-production-readiness.md` and a specific file/line in `SPECIFICATION.md` where applicable — this document supersedes the v1.0-era `PITFALLS.md` (2026-07-03, greenfield-design-oriented) for the v1.1 hardening milestone.

This document assumes the reader has read `AUDIT-2026-07-27-production-readiness.md` (source of every finding referenced) and `SPECIFICATION.md` (as-built state referenced by file/line). Phase names below use the audit's own "Рекомендуемый порядок исправлений" (§12): Phase 1 Quality gates, Phase 2 Delivery correctness, Phase 3 Security & tenant isolation, Phase 4 Compliance & analytics, Phase 5 Worker reliability, Phase 6 Database lifecycle, Phase 7 Observability & deployment. The roadmap may rename these; map by content, not label.

## Critical Pitfalls

### Pitfall 1: Fixing the ambiguous-outcome bug reintroduces duplicate sends via the fix itself

**What goes wrong:**
The audit (§3.2) correctly identifies that `send-dispatch.ts:224` and `flow-send.ts:158` collapse "SendGrid may have accepted the mail, but the process died/network failed before the result was persisted" into a hard `failed`, which a naive retry then re-sends. The natural fix — add an `unknown`/`reconciling` state — is where a *second*, easier-to-miss bug gets introduced: whichever code path *reconciles* an `unknown` send (a cron sweep, a webhook match, a manual retry endpoint) now races the *retry* path. If both a reconciliation worker and a retry-on-next-tick worker can independently decide the terminal state of the same `sends` row, you get two writers racing to resolve one `dispatching`/`unknown` row — and if the retry path re-calls SendGrid without first placing an exclusive claim on the row, you now have the exact duplicate-send bug the audit flagged, just moved one level up. This is the single most common failure mode reported when teams add "unknown" states to payment/messaging pipelines: the reconciler and the retrier are both allowed to act on the same ambiguous row.

**Why it happens:** The existing system already has the right pattern for this — `claimCampaignSend`/`claimFlowSend` (SPECIFICATION.md §5.5) use a claim transaction that writes `dispatching` *before* the SendGrid call and treats "interrupted claim on resume" as permanently `failed`, deliberately trading a lost email for no duplicate (documented as the current at-most-once choice). Adding `unknown` means *deliberately reopening* that closed door — the whole point of the new state is that some `unknown` sends should eventually resolve to `sent` via reconciliation. That reintroduces exactly the concurrent-writer hazard the current code avoids by always failing closed. Teams get this wrong because they design the new `unknown → sent | failed` transition without also re-deriving the row-locking invariant that made the old `dispatching → failed` transition safe.

**How to avoid:**
- Define the send state machine as an explicit table (state, valid transitions, who is allowed to write each transition) *before* touching `send-dispatch.ts` — this is exactly what the audit demands in §3.2 and it should be a design artifact reviewed independently of the code change.
- Reconciliation must claim the row (`SELECT ... FOR UPDATE SKIP LOCKED` inside `withTenantTransaction`, matching the existing pattern at `claimCampaignSend`) before reading provider state and writing a terminal status — never a blind `UPDATE sends SET status=... WHERE status='unknown'`.
- The correlation ID (custom_args already carries `send_id`, `workspace_id`, `campaign_id` per §5.5) must be the *only* way reconciliation matches a provider-side event back to a `sends` row — never re-derive by (contact, timestamp, template) heuristics, which is how teams accidentally reconcile the wrong row under retry storms.
- Retry logic must be forbidden from calling SendGrid again for any row currently in `unknown`/`reconciling` — only the reconciler may resolve that state; the job processor's own retry path should treat `unknown` as "not my job," not "try again."
- Write the crash-injection tests the audit demands (§3.2, §10) against the *new* state machine specifically for the three-way race: crash before send / crash after SendGrid 2xx before write / reconciler and retry-worker both touching the same row concurrently.

**Warning signs:** Any code path that transitions `unknown → sent` or `unknown → failed` without first taking a row lock scoped to the tenant transaction; a reconciliation worker that queries provider webhook data by (contact_id, timestamp window) instead of `send_id`/correlation ID; failure-injection tests that only test "crash then never retry" instead of "crash, reconciler runs, retry-worker also runs against the same job."

**Phase to address:** Phase 2 (Delivery correctness) — this is the literal subject of that phase; the state-machine design must be reviewed and the crash tests must include the reconciler-vs-retry race specifically, not just the three failure points named in the audit.

### Pitfall 2: Changing idempotency semantics on a table that already has rows silently reclassifies old data

**What goes wrong:** `sends.status` currently only has `('dispatching','sent','failed','excluded')` (SPECIFICATION.md §4.2). Adding `unknown`/`reconciling` to this enum, or adding a new correlation-ID column, means every row written before the migration is retroactively ambiguous about which semantics it followed. If a backfill script infers `unknown` status for old `failed` rows that were *actually* legitimately failed (4xx from SendGrid, per §5.5's documented rule "`>=400` → `failed`, never `sent`"), it corrupts historical compliance/analytics data — `sends.failed_count` and downstream `campaigns` counters silently change meaning mid-history. Conversely, if the migration does *not* touch historical rows but the new `unknown` state relies on a correlation ID column that old rows don't have, reconciliation code that assumes "every row has a correlation ID" will throw or silently no-op on the oldest rows.

**Why it happens:** Enum/state-machine changes are designed against the *new* write path and tested against freshly-created rows. Nobody runs the new reconciliation logic against the actual historical `sends` table before shipping, because the local/CI database doesn't have production-shaped history.

**How to avoid:**
- Before writing any migration that changes `sends.status` semantics, run a read-only audit query against the actual (or a restored) production-shaped dataset: how many rows are `failed` with no matching `send_events`? How many predate the correlation-ID column?
- Postgres enum types cannot have a value removed and are awkward to reorder; prefer adding `unknown` as a new enum value (`ALTER TYPE send_status ADD VALUE 'unknown'` — note this cannot run inside the same transaction as code that uses the new value on some Postgres versions/drivers; verify against the actual Drizzle/pg driver behavior in this codebase before scripting it) rather than reshaping the enum.
- Treat the backfill (if any) as a separate, reviewed migration from the schema change, run manually with a dry-run report, never as an automatic "migrate on deploy" step for existing rows.
- Any reconciliation code must explicitly handle "row has no correlation ID" as an out-of-scope-for-reconciliation case, not an exception.

**Warning signs:** A migration that both alters the enum/column *and* runs an `UPDATE` on existing rows in one migration file; reconciliation code with no branch for missing correlation ID; analytics rollups (`workspace_daily_rollup`) whose historical totals shift after the migration runs — this is the tell that old rows got reclassified.

**Phase to address:** Phase 2 (Delivery correctness), coordinated with Phase 6 (Database lifecycle) for the migration mechanics themselves (see Pitfall 12).

### Pitfall 3: Running old and new dispatch code concurrently during rolling deploy produces the exact bug being fixed

**What goes wrong:** The audit doesn't mention a blue/green or rolling-deploy strategy anywhere, and neither does SPECIFICATION.md (§1.3: "Dockerfile, CI-конфига, деплой-манифестов... в репозитории нет"). This means Phase 7 will be *choosing* a deploy shape for the first time in this milestone, at the same moment Phase 2/5 are changing the send pipeline's core semantics. If the chosen deploy strategy involves even a brief window with two `apps/worker` container instances running different code versions against the same Redis/Postgres (the default behavior of most container orchestrators doing a rolling restart, and trivially possible on a single VPS if a deploy script starts the new container before stopping the old one) — the old dispatch code's assumptions about `sends.status` values, job payload shape, or claim semantics can diverge from the new code's assumptions for the entire deploy window. Two workers with different definitions of "this send is claimed" can both pass their own claim check and both call SendGrid.

**Why it happens:** Backward-compatibility between adjacent app versions during rolling deploys is a distinct discipline from correctness of either version in isolation — it's easy to fully verify version N and version N+1 independently and still have a window where they're unsafe together, because nobody explicitly tests "N and N+1 processing the same queue simultaneously."

**How to avoid:**
- Single-VPS Docker deploys (as chosen, per PROJECT.md "v1.1: деплой — Docker на self-hosted VPS") should default to stop-old-then-start-new for the worker process specifically (accepting a short queue-processing pause) rather than a rolling/overlapping restart, *unless* the team explicitly designs and tests the two-version-compatible schema/queue-payload contract. A pause in worker processing is safe (BullMQ jobs wait in Redis); overlapping incompatible dispatch code is not.
- If overlap is unavoidable (e.g., API and worker deploy independently and API enqueues jobs the old worker doesn't understand), version the job payload schema explicitly (a `schemaVersion` field) and make the worker reject/defer jobs it doesn't recognize rather than best-effort processing them.
- Any migration that changes `sends.status` semantics (Pitfall 2) must be deployed *before* the worker code that depends on the new semantics, and the old worker code must be proven safe to run against the new schema for at least one deploy cycle (expand/contract migration pattern) — this is standard zero-downtime-migration practice and is conspicuously absent from the audit's migration section (§7), which the roadmap should add explicitly.
- Add this scenario to the failure-injection harness demanded by the audit (§3.2, §10): two dispatch-code versions against the same queue/tenant.

**Warning signs:** Deploy script that starts the new container before `docker stop` on the old one; no `schemaVersion` on BullMQ job payloads; any migration PR that ships in the same deploy as the worker code change that depends on it, with no verified "old worker + new schema" compatibility check.

**Phase to address:** Phase 7 (Observability, deployment) must define the deploy/rollback procedure *before* Phase 2/5 land, or Phase 2/5 must explicitly design for safe overlap — flag this dependency in roadmap sequencing (see Pitfall-to-Phase Mapping).

### Pitfall 4: `worker.rateLimit()` throttles the entire worker process, not the tenant that triggered it (confirmed, currently shipped)

**What goes wrong:** This is not hypothetical — it's the audit's own top finding (§3.1), confirmed by BullMQ's own documented behavior: `worker.rateLimit(ms)` "overrides the rate limit to be active for the next jobs" and the mechanism is global per worker — "if you have for example 10 workers for one queue with the given settings, still only 10 jobs will be processed by second" (BullMQ docs/API). When `send-dispatch.ts` calls `await worker.rateLimit(ms); throw Worker.RateLimitError()` after tenant A's per-tenant token bucket (`rate-limiter-flexible`) rejects a job, it delays the *worker*, not just tenant A's jobs — tenant B's already-queued jobs behind it in the same worker's fetch loop also wait out that delay, even though tenant B's own rate-limiter-flexible bucket had capacity. This is precisely the "one tenant can throttle all others" bug the whole product-level `rate-limiter-flexible`-per-tenant-bucket architecture (STACK.md/CLAUDE.md) was designed to prevent, reintroduced at the worker-loop layer.

**Why it happens:** `worker.rateLimit()` looks like exactly the right BullMQ primitive for "this job got rate-limited, retry me later without burning an attempt" — and it is, *for the job itself*. The bug is using it as if it were job-scoped when its actual effect (per BullMQ's own docs) is worker-scoped.

**How to avoid:**
- Never call `worker.rateLimit()` on a per-tenant rejection. Instead, when `consumeTenantToken` rejects (rate-limited), re-queue *only that job* with a delay (`job.moveToDelayed(timestamp, token)` or `queue.add` with a `delay` derived from `rateLimitMs`) and return without throwing `Worker.RateLimitError()`.
- Verify the replacement doesn't reintroduce a different problem: `moveToDelayed` requires the job's lock token and must be called from inside the active processor before returning — calling it incorrectly (wrong token, or after the lock has already expired) throws; test this path under the crash-injection harness too.
- If BullMQ's OSS `groupKey` rate-limiter option (present in `RateLimiterOptions` per current BullMQ docs, distinct from BullMQ Pro's fuller groups feature) is evaluated as an alternative to the current app-level `rate-limiter-flexible` bucket, verify its actual current OSS feature scope directly against BullMQ's docs before relying on it — community sources disagree on exactly how much of "per-group" limiting is OSS vs Pro-only, and the existing STACK.md claim that it's Pro-only should be re-verified against the BullMQ version actually pinned (`bullmq@5.79.1`) rather than assumed correct from prior research.

**Warning signs:** Any `await worker.rateLimit(...)` call remaining anywhere in `apps/worker/src/queues/` after this phase closes; a load test with two tenants where tenant A is deliberately over its rate limit and tenant B's throughput visibly drops during A's throttling window — this is the concrete regression test the audit implicitly demands.

**Phase to address:** Phase 2 (Delivery correctness) — audit already scoped this as the top finding; the fix (`job.moveToDelayed`) must ship with a two-tenant load test proving isolation, not just a code review.

### Pitfall 5: `job.moveToDelayed` and delayed-job scheduling interact badly with `lockDuration` and stalled-job detection under a slow SendGrid call

**What goes wrong:** The audit (§3.3) flags the missing timeout/`AbortController` on the SendGrid call in `send-mail.ts` as a separate High finding — but it compounds with the `worker.rateLimit()` fix above. If a job holds a slow (or now-timed-out-but-slowly-unwinding) `fetch` call, BullMQ's lock-renewal mechanism must keep extending the job's lock past `lockDuration` (BullMQ docs: stalled-job detection kicks in when a worker "cannot renew its lock on a job in time," commonly because the event loop is blocked or the configured `lockDuration` is shorter than actual job runtime) or the job gets marked stalled and picked up by *another* worker process while the original is still mid-flight — a second concurrent SendGrid call for the same send. This is the queue-level version of the exact duplicate-send bug the audit is asking Phase 2 to fix at the application level; fixing it in `send-dispatch.ts`'s state machine without also correctly tuning `lockDuration`/`lockRenewTime` against the new bounded timeout leaves a second, queue-level path to the same duplicate.

**Why it happens:** `lockDuration` is set once, early, based on "how long do I expect a job to take," and rarely revisited when downstream call behavior changes. Node's single-threaded event loop means CPU-heavy work (JSON parsing large webhook batches, template rendering) can also starve lock-renewal even when the HTTP call itself isn't slow.

**How to avoid:**
- Set the SendGrid call's `AbortController` timeout to a value *strictly less than* `lockDuration` (BullMQ's own recommendation) so a hung request is guaranteed to resolve (timeout → treated as `unknown`/ambiguous per Pitfall 1) well before BullMQ's stall detector could double-schedule the job.
- After adding the timeout, verify `lockDuration` is still generous enough to cover the claim transaction + timeout + terminal-write transaction combined, with margin — not just the network call.
- Because the claim-then-send-then-write pattern already exists (§5.5), a stalled/duplicate-picked-up job re-entering the *same* code path should hit the "claim already taken, this attempt is now `interrupted`→`failed`" branch that's already implemented — but verify this explicitly under a stalled-job simulation (kill lock renewal mid-job in a test), since it wasn't listed among the tests the audit names (§10) and it's the queue-level analogue of the crash points that *are* named.

**Warning signs:** `lockDuration` at its BullMQ default (30s) while the new SendGrid timeout is set to something close to or above it; no test that forcibly stalls a job (e.g., by pausing lock renewal) mid-SendGrid-call and asserts no duplicate `sends` row results.

**Phase to address:** Phase 2 (Delivery correctness), verified together with Phase 5 (Worker reliability, since `lockDuration`/stalled-job tuning is worker-config hygiene the audit already flags as needing a shared queue factory, §6).

### Pitfall 6: `removeOnFail`/`removeOnComplete` retention changes silently break debugging or blow up Redis memory in the opposite direction

**What goes wrong:** The audit (§6) flags `removeOnFail: false` (failed jobs retained forever in Redis) as a finding to fix. The naive fix — set `removeOnFail: { age: N }` or a count-based limit, copied uniformly across the "8 places" the audit says `defaultJobOptions` is duplicated (§6, §11) — has two opposite failure modes depending on which direction the fix errs: (a) too aggressive retention limits mean a failed job that needed manual investigation (e.g., a send stuck in the new `unknown` state, Pitfall 1) gets garbage-collected by BullMQ's own cleanup before anyone looks at it, destroying the audit trail Phase 2's crash tests are supposed to make debuggable; (b) too generous retention on a queue with much higher volume than others (e.g., `webhook-events`, which the audit notes batches "весь батч одним джобом" per SPECIFICATION.md §6.8, or `email-triggered` at concurrency 20) reproduces the original unbounded-Redis-growth problem just with a higher ceiling, and now with count-based limits (`removeOnComplete: { count: N }`) there's a new failure mode: BullMQ evicting completed-job records that a reconciliation window still needed to reference for idempotency checks.

**Why it happens:** Retention policy gets treated as one global constant applied uniformly via the "shared queue factory" the audit correctly recommends (§6, §11) — but different queues have structurally different retention needs (dead-letter-worthy failures on `email-triggered` vs. high-volume idempotent-anyway `webhook-events` batches vs. `flow-run-advance`, which already deliberately uses `removeOnComplete: true` / `removeOnFail: { age: 86400 }` per §5.3, a different policy than the rest — meaning "unify the 8 duplicated blocks" is not actually correct if applied naively as one config).

**How to avoid:**
- Don't collapse retention policy into a single shared constant; the shared queue factory (audit's own recommendation) should take retention as a parameter per queue, with the *existing* differentiated policy on `flow-run-advance` treated as a deliberate precedent to preserve, not an inconsistency to erase.
- Retention for queues feeding the new `unknown`/dead-letter path (Pitfall 1) must outlive the reconciliation window with margin — if reconciliation runs on a 60s tick (matching the existing `flow-reconciliation`/`campaign-scheduler` pattern, §5.1), retention should be measured in hours/days, not minutes.
- Add a dead-letter queue (the audit explicitly asks for this, §6/Phase 5) as the durable record of terminal failures, separate from relying on BullMQ's own job retention as the audit trail — retention settings then only need to cover the operational debugging window, not permanent compliance history.
- Monitor Redis memory before/after the retention change ships (ties to Pitfall 20/Redis persistence) — a load test that runs the actual expected daily send volume against the new retention settings, checking peak Redis memory, should gate this change.

**Warning signs:** A single shared `defaultJobOptions` constant used identically across all 13 registered workers with no per-queue override; a support/debug incident where the team can't find a failed job because it was already cleaned up; Redis `used_memory` climbing unexpectedly post-deploy.

**Phase to address:** Phase 5 (Worker reliability) — audit explicitly scopes retention + shared queue factory here (§12, Фаза 5).

### Pitfall 7: Graceful shutdown that closes `worker.close()` correctly still loses in-flight jobs if the container is killed before it returns

**What goes wrong:** SPECIFICATION.md (§5.1) confirms `worker.close()` is already called on SIGINT/SIGTERM for all workers, plus `connection.disconnect()`. BullMQ's own docs confirm `worker.close()` is graceful — it stops fetching new jobs and *waits* for active processors to finish, but "this call will not timeout by itself." The pitfall specific to *this* milestone is Docker/VPS deploy (Phase 7, newly introduced): if the container orchestration layer (Docker's own stop timeout, `docker stop -t <seconds>`, or a VPS deploy script) sends SIGTERM and then SIGKILLs after a default or short grace period (Docker's default is 10 seconds) *before* `worker.close()`'s in-flight jobs — which include a SendGrid call now bounded by a timeout that could itself be several seconds (Pitfall 5) plus DB transaction writes — actually finish, the process is hard-killed mid-job. This reproduces the exact "process died between SendGrid accepting and result being written" scenario the whole `unknown` state machine (Pitfall 1) exists to handle — except now it's a *routine deploy event* instead of a rare crash, meaning it will happen on every single deploy unless the shutdown timeout is set generously enough.

**Why it happens:** Application-level graceful shutdown code (already present and correct here) gives a false sense of completeness; the container/orchestration-level timeout that actually determines whether that code gets to finish is a separate, easily-overlooked configuration surface, especially when Dockerfiles/deploy scripts are being written for the first time in this milestone.

**How to avoid:**
- Set the container stop grace period (`docker stop --time=N` / Compose `stop_grace_period` / systemd `TimeoutStopSec` for a VPS-managed service) to comfortably exceed the maximum plausible in-flight job duration: SendGrid call timeout (Pitfall 5) + claim/write transaction time + retry/backoff margin. Document the derived number, don't guess.
- Explicitly test this: send SIGTERM to the worker container mid-load-test and verify zero duplicate/lost sends and that the process actually exits within the configured window (not just that it *starts* shutting down).
- Since BullMQ jobs that were in-flight and killed hard become the responsibility of the stalled-job detector on the *next* worker to pick them up (Pitfall 5's mechanism), verify the claim/state-machine correctly resolves this specific "SIGKILL during dispatch" case as part of the crash-injection suite, not just "process crash" in the abstract — deploy-triggered kills are a distinct, recurring instance of the general crash case and deserve their own explicit test.

**Warning signs:** No documented derivation for the container stop timeout value (a bare Docker default left unexamined); a deploy runbook that doesn't mention waiting for/verifying worker drain before killing the old container; any dropped/duplicated send correlated with deploy timestamps once metrics/logs exist (Phase 7).

**Phase to address:** Phase 7 (Observability, deployment) for the container/timeout configuration and documented rollback procedure; Phase 2's crash-injection tests (Phase 1's harness) should include this scenario explicitly.

### Pitfall 8: Repeatable-job registration across multiple worker containers — currently safe, but only under an assumption Phase 7 is about to violate

**What goes wrong:** SPECIFICATION.md (§5.1) states the four repeatable jobs (`scan-due-campaigns`, `scan-due-flow-runs`, `reconcile-rollups`, `scan-segment-triggered-flows`) are deduplicated by BullMQ "по repeat-конфигу + `jobId`," so multiple boots of the *same* worker process don't create competing schedules — this is correct today because there's exactly one worker container. The moment Phase 7 introduces Docker deploys, horizontal scaling of the worker for capacity (mentioned nowhere yet, but a natural next step once concurrency limits from `DEFAULT_TENANT_RPS` validation, §5.5/§12, are load-tested) becomes possible — and BullMQ's repeatable-job dedup by `(repeat config, jobId)` prevents *duplicate schedules*, not duplicate *executions*: every worker process that registers a repeatable job with a matching config will still independently run its own tick handler on that schedule, meaning `N` worker containers means `N`× as many `scan-due-campaigns` executions per interval, each doing its own admin-scan SELECT and potentially each attempting to claim the same due campaigns — increasing lock contention exactly where the audit's `SELECT ... FOR UPDATE SKIP LOCKED` pattern (§5.4) is supposed to make concurrent claims safe, but was verified/tuned assuming one scanner. There is also a documented BullMQ issue (#2876, "Duplicate job scheduler tasks") where deduplication itself can fail under crash-loop restarts, independent of the multi-container question.

**Why it happens:** "BullMQ dedupes repeatable jobs" is true for the schedule-registration step but is routinely misread as "BullMQ ensures only one worker executes the tick" — those are different guarantees, and the confusion is common enough that it's a recurring GitHub issue topic.

**How to avoid:**
- If/when the worker is horizontally scaled (even just "for zero-downtime deploys, briefly run two"), the four `repeat: { every }` tick registrations must move to a single dedicated "scheduler" role (either one designated container, or a Postgres-advisory-lock-guarded tick, mirroring the migration-lock pattern in Pitfall 16) rather than relying on BullMQ repeatable-job dedup to prevent multi-execution — because it doesn't.
- Even at N=1 container, protect against the documented BullMQ dedup-failure-under-crash-loop issue by using `upsertJobScheduler` with a stable, explicit scheduler ID (current BullMQ-recommended API) rather than the older repeatable-job registration path, if not already doing so — verify which API `apps/worker` currently uses.
- Because the actual claim logic (`SELECT ... FOR UPDATE SKIP LOCKED`) is already safe against concurrent claimers by design (§5.4), the practical risk here is redundant *work* (wasted admin-scan queries, wasted lock attempts) rather than data corruption — but this should be explicitly load-tested before any horizontal worker scaling ships, not assumed safe by extrapolation from the current single-container behavior.

**Warning signs:** A Dockerfile/Compose file that sets `worker` replica count > 1 without an explicit decision about which container owns the repeatable-job ticks; `pg_stat_activity` showing multiple concurrent admin-scan queries at the same repeat interval once scaling happens.

**Phase to address:** Phase 7 (Observability, deployment) if horizontal scaling is in scope for this milestone at all — otherwise explicitly flag as an accepted single-instance-worker constraint and document it, since the audit itself does not ask for worker horizontal scaling.

### Pitfall 9: `FORCE ROW LEVEL SECURITY` fixes owner-bypass, but the app's own DB role already claims `NOBYPASSRLS` — the real gap is elsewhere

**What goes wrong:** `docker/init-app-role.sql` (SPECIFICATION.md §1.3) already creates `mega_crm_app` as `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`, and all 22 domain tables have `RLS ENABLE + FORCE` (§4.2, §4.3) — so the classic "table owner silently bypasses RLS" footgun (confirmed as PostgreSQL's actual default behavior: "Table owners normally bypass row security... unless `FORCE ROW LEVEL SECURITY`" is set) is *already* correctly handled for the 22 domain tables. The pitfall specific to *this* milestone is elsewhere and easy to miss because the FORCE-RLS pattern looks solved: (a) the audit's own admin-scan finding (§4.1) is not an owner-bypass problem, it's that the bypass *policies* (`app.admin_scan='true'`) on `flow_runs` (`0027`) and `flows` (`0032`) have **no row predicate at all** beyond the GUC check (SPECIFICATION.md §4.3, flagged explicitly in §9 item 1) — this is strictly worse than owner-bypass, because it's an intentional, policy-level, cross-tenant SELECT grant with no scoping, reachable by anyone who can get that GUC set to `'true'` in their transaction; (b) `mega_crm_app` being the table *owner* (init script "передаёт ей владение БД") combined with `NOBYPASSRLS` means the role attribute is what protects RLS today, but if a future ops task (Phase 6, database lifecycle — pooling/TLS/roles work) introduces a *second* role (e.g., a read-only reporting role, a migration-runner role) without explicitly copying `NOBYPASSRLS` and `FORCE`, that new role is unprotected by default the moment it's granted table ownership or superuser-adjacent privileges for migration convenience.

**Why it happens:** RLS correctness is verified once, against the roles that exist at verification time; adding a new DB role later (which the audit's own §4.1 fix — "выделить отдельную DB role" for admin-scan — explicitly requires) is exactly the moment this class of bug gets reintroduced, because the new role is provisioned by copying connection-string patterns, not by re-deriving the RLS-safety checklist.

**How to avoid:**
- When creating the dedicated admin-scan DB role the audit demands (§4.1) and the dedicated auth-trust-boundary role for Better Auth tables (§4.3, "Open decision" in PROJECT.md), explicitly grant `NOBYPASSRLS` on both and verify neither is a table owner — do not assume "new role = safe by default."
- Fix `flow_runs_due_scan` (0027) and `flows_segment_sweep_scan` (0032) to include the same status/date predicate pattern as the `0018` precedent they claim to mirror but don't (confirmed gap, SPECIFICATION.md §9 item 1) — this is a straight policy bug, independent of role/ownership questions, and should be the first fix in this pitfall's scope since it's the actual currently-exploitable gap, not the theoretical owner-bypass one.
- Add automated negative tests (the audit demands these, §4.1, §12 Phase 3) that specifically assert: setting `app.admin_scan='true'` from a normal tenant-scoped API-triggered transaction is impossible (verify no API code path can set that GUC), and that a query against `flow_runs`/`flows` with `admin_scan=true` set is still scoped by the *query's own* WHERE clause being the only thing protecting cross-tenant data — document this as a known-accepted defense-in-depth gap if the predicate fix is deferred, rather than leaving it silently unflagged.
- Minimize the admin_scan GUC's lifetime to the single query that needs it (already partially done via `withTenantTransaction`'s `SET LOCAL` semantics, §4.3) and never set it on a connection that will process other tenant-scoped queries afterward without an intervening transaction boundary.

**Warning signs:** Any new Postgres role creation script that doesn't explicitly set `NOBYPASSRLS` and doesn't check `pg_tables.tableowner`; a policy using only `current_setting('app.admin_scan', true) = 'true'` with no additional WHERE-equivalent predicate (exact current state of `0027`/`0032`); no negative test asserting a non-admin code path cannot set `app.admin_scan`.

**Phase to address:** Phase 3 (Security & tenant isolation) — audit explicitly scopes this (§12 Фаза 3, admin-scan RLS).

### Pitfall 10: `SET LOCAL` is correct *inside* a transaction — but PgBouncer transaction-mode pooling (not yet in this stack) will break it silently the moment it's introduced

**What goes wrong:** The current implementation is actually already doing the *right* thing: `withTenantTransaction` uses `SELECT set_config('app.current_workspace_id', $1, true)` with the third argument `true`, which is the `SET LOCAL` (transaction-scoped) semantics (SPECIFICATION.md §4.3) — this is exactly the pattern that avoids the classic PgBouncer footgun where a plain `SET` (session-scoped) GUC "outlives the transaction that set it and leaks into the next tenant's transaction on the same backend" under transaction-mode pooling, because PgBouncer shares one physical backend connection across many logical client sessions and only guarantees transaction boundaries, not session boundaries. But: SPECIFICATION.md §8.1 confirms PgBouncer is *not currently deployed* ("PgBouncer/RDS Proxy в репозитории отсутствуют") despite the existing STACK.md recommending it "before an incident, not after," and Phase 6 (database lifecycle: "TLS и pooling") is explicitly where it's likely to get introduced in this milestone. The pitfall: `SET LOCAL`/`set_config(..., true)` is correct under PgBouncer transaction pooling *only if every GUC-setting statement and every GUC-dependent query happen inside the same explicit transaction, with no autocommit statements slipping in between*. If PgBouncer is added and *any* code path currently relying on `pool.connect()` + a bare query outside `withTenant`/`withTenantTransaction` (the audit itself documents at least one: `campaign-scheduler.worker.ts`'s `findDueCampaignCandidates` uses `pool.connect()` directly with only `app.admin_scan` set in a short read-only transaction, §5.4; `analytics-reconciliation.worker.ts` queries `organization` "напрямую, вне `withTenant`", §5.7) is not equally careful about transaction scoping, adding PgBouncer will not break those paths *today* (transaction-mode pooling still honors within-one-transaction correctness) but will make any *future* accidental bare-`SET` (session-scoped, not `SET LOCAL`) statement a silent, hard-to-reproduce cross-tenant data leak instead of a same-connection-reuse bug that's easier to catch locally without a pooler in front.

**Why it happens:** Code that's correct against a direct `pg.Pool` (where each pooled connection roughly maps to one client's session lifetime under normal, low-connection-churn usage) can pass all existing tests and still be one `SET` (not `SET LOCAL`) statement away from a cross-tenant leak that only manifests once a transaction-mode pooler is introduced, because the pooler is what turns "leaked session state" into "leaked to a *different tenant's* next request" instead of "leaked to the same client's next query."

**How to avoid:**
- Before introducing PgBouncer (Phase 6), grep the entire codebase for any bare `SET` (not `SET LOCAL`, not `set_config(..., true)`) statement against a tenant-scoped GUC — there should be none, but this should be a verified fact, not an assumption, given the two independent pools already in this codebase (`packages/tenant-context` and `packages/db`, §3.6) and the direct-`pool.connect()` admin-scan paths (§5.4, §5.7) that bypass the standard `withTenant` wrapper.
- Configure PgBouncer explicitly in `transaction` pool mode (not `session`), and pair it with an appropriate reset-on-return behavior — PgBouncer's own docs recommend a server-reset step on connection return in transaction mode specifically to prevent leaked session state from a misbehaving client, as defense-in-depth on top of (not instead of) correct `SET LOCAL` usage in application code.
- If a `SET ROLE` pattern is introduced for the new admin-scan or auth-trust-boundary DB roles (Pitfall 9), be aware `SET ROLE` is session-scoped by default (`SET LOCAL ROLE` exists and must be used explicitly) — this is a second, distinct GUC-leak vector from the tenant-ID GUC and needs the same `LOCAL` discipline.
- Add an explicit integration test that simulates the PgBouncer transaction-boundary hazard: two "requests" sharing one physical connection back-to-back (achievable even without PgBouncer installed, by manually checking out and reusing one `pg.Client` across two `withTenant` calls in a test) and asserting tenant B never sees tenant A's `SET LOCAL` value.

**Warning signs:** Any `pool.query("SET ...")` (not `SET LOCAL` or `set_config(..., true)`) in the codebase; PgBouncer configured in `session` mode instead of `transaction` mode (defeats the pooling benefit that motivated adding it); no test exercising connection reuse across tenants.

**Phase to address:** Phase 6 (Database lifecycle, "TLS и pooling") for the PgBouncer introduction itself; Phase 3 (Security & tenant isolation) should own the codebase-wide bare-`SET` audit as one of its "negative cross-tenant tests" (audit §12 Фаза 3).

### Pitfall 11: Unifying the two RLS policy variants (bare cast vs. NULLIF-guard) can flip working tables into fail-open instead of fail-closed

**What goes wrong:** SPECIFICATION.md §4.3 documents that 12 tables (including `events` and `send_events`, both written by the worker) use the bare-cast policy `workspace_id = current_setting('app.current_workspace_id', true)::uuid`, while 10 tables use the NULLIF-guarded variant `workspace_id = NULLIF(current_setting(...), '')::uuid`. The documented reason the NULLIF variant exists at all (`0006`/`0019` migration comments) is that once the custom GUC has been touched at all in a session, an *unset* read of it returns `''` rather than NULL, and casting `''::uuid` throws `invalid input syntax for type uuid` — a hard error — rather than silently comparing NULL and matching zero rows. The audit (§4.2) recommends unifying these two variants — and the *safe* direction is bare-cast (fail with an error if the GUC is somehow unset, per the app's own current documented rationale that reads without `withTenantTransaction` "не должно случаться"). But a team doing this "unification" pass under time pressure, and reading only the audit's one-line summary ("унифицировать политики"), can easily standardize on the *NULLIF variant* instead — because it's newer, touches more tables (10 vs 12 is close, and NULLIF is the pattern used everywhere a bug was fixed, so it reads as "the correct one") — which silently converts the currently-fail-closed bare-cast tables (`events`, `send_events`, `contacts`, `sends`, etc.) into fail-open-to-zero-rows tables: any future code path that queries these tables *without* setting the tenant GUC first (a bug that today would throw loudly and get caught in testing/staging) would instead just return an empty result set — the single most dangerous outcome for a table like `contacts` or `sends`, because "no rows" is frequently treated by application code as "this tenant/contact doesn't exist" rather than "the safety check silently failed," and is far harder to detect in code review or casual testing than a thrown error.

**Why it happens:** "Unify the two variants" reads as a low-risk consistency cleanup, and the variant that looks more "defensive" (NULLIF, which avoids an ugly cast error) is the intuitive choice for someone not aware that avoiding the error is exactly the security regression — the throw *is* the safety mechanism for tables where the app's own invariant ("always call via `withTenantTransaction`") might someday be violated by a bug.

**How to avoid:**
- Unify toward the bare-cast (fail-with-error) variant, not NULLIF — the audit's own stated fix for this finding is "добавить тест запроса без tenant context" (§4.2), meaning the intended prevention mechanism is a *test that expects an error*, which only works if the policy is the error-throwing variant. Flag this explicitly in the roadmap/plan so it isn't left as an implementation-detail decision made without this context.
- If NULLIF is chosen instead for a specific reason (e.g., wanting SELECT-then-empty-result over a thrown 500 for a specific admin-scan-adjacent table), that must be a documented, deliberate, per-table decision — not a blanket "unify everything to the newer pattern" pass.
- The new "test a query without tenant context" (audit's own recommendation) must assert the *error*, not just "returns no rows" — a test asserting `rows.length === 0` would pass under either variant and would not catch a regression from bare-cast to NULLIF; the test must assert the specific Postgres error class/message.
- Run this unification pass as its own reviewed, isolated change (not bundled into an unrelated schema PR) precisely because it touches 22 security-critical policies at once — a single wrong sed-style find/replace here is a fleet-wide regression.

**Warning signs:** A migration that changes all 22 policies to the NULLIF pattern "for consistency"; a new test that asserts empty result set rather than a thrown error for the no-tenant-context case; code review approving this change without re-reading the `0006`/`0019` migration comments that explain *why* the two variants diverged in the first place.

**Phase to address:** Phase 3 (Security & tenant isolation) — audit explicitly scopes this (§12 Фаза 3, though grouped loosely with admin-scan; treat as its own reviewed sub-task given the fail-open risk).

### Pitfall 12: Adding RLS to Better Auth tables (`organization`, `session`, `account`) breaks login before anyone notices why

**What goes wrong:** The audit (§4.3) is explicit that this should *not* be done reflexively — "не следует автоматически добавлять RLS: сначала нужно определить trust boundary Better Auth" — and PROJECT.md lists this as an "open decision within the milestone" requiring architectural work. The concrete failure mode if a team skips that design step and just runs `ALTER TABLE organization ENABLE ROW LEVEL SECURITY` (the reflexive, audit-checklist-driven move, since 22 other tables already have it and "why not these too" is an easy trap): Better Auth's own internal queries against these tables run through `packages/db`'s non-tenant Drizzle client (SPECIFICATION.md §1.2, §4.3) — a plain pooled connection that never calls `withTenant`/sets any GUC, because it has no concept of "current workspace" at the point where a user is *logging in* (there is no workspace context yet — you don't know which workspace a session belongs to until *after* authentication resolves it). Any RLS policy modeled on the same `workspace_id = current_setting(...)::uuid` pattern used elsewhere would either throw (bare-cast variant, Pitfall 11) or return zero rows (NULLIF variant) for literally every Better Auth query, because the GUC is never set on that connection path — this breaks login, signup, session validation, and organization/member lookups platform-wide, for every tenant, immediately on deploy. Worse, `organization` specifically has no natural `workspace_id`-style tenant column to scope by in the first place — it *is* the workspace registry that every other table's `workspace_id` points to — so a naive copy-paste of the existing RLS pattern doesn't even have an obvious column to key on.

**Why it happens:** Checklist-driven security hardening ("22 tables have RLS, 7 don't, audit flagged it, fix it") is exactly the failure mode the audit is trying to preempt by explicitly calling this one out as requiring a decision, not a mechanical fix — but that caveat lives in prose (§4.3) separate from any enforcement mechanism, so it's easy for a phase-planning pass to schedule "add RLS to auth tables" as if it were the same kind of task as the other 22.

**How to avoid:**
- Treat this strictly as the architectural-decision task PROJECT.md already flags it as ("Открытое решение внутри milestone... Требует архитектурной проработки на discuss-phase") — do not let it collapse into a generic "add RLS" implementation task in a plan.
- The audit's own recommended direction — a separate DB role with minimal privileges, with domain modules denied direct access to auth tables (§4.3) — is a *privilege/role* boundary, not a *row-level* boundary, and should be evaluated on those terms: what does `packages/db`'s non-tenant client actually need to do (auth flows, org/member CRUD triggered by admin actions) vs. what domain code should never touch these tables directly at all (it currently doesn't appear to, per the package boundary in §1.2, but this should be explicitly verified, not assumed).
- If RLS is eventually deemed necessary on some of these tables (e.g., `session`/`account`, which do have a `userId` → indirectly resolvable workspace via `member`), any policy must be paired with an explicit non-tenant-context escape hatch for the Better Auth library's own internal queries (which cannot easily be made workspace-aware, since Better Auth's session/account model is user-centric, not workspace-centric) — likely via a dedicated bypass role for the Better Auth code path specifically, verified with `NOBYPASSRLS` still off only for that one deliberately-scoped role, and documented as an explicit, reviewed exception.
- Before shipping any change here, run the full login/signup/invite-accept flow against a staging environment with the new policy — this is cheap and would catch the "breaks login" failure mode immediately, but only if it's actually done as a deploy gate rather than assumed to work because the migration ran without SQL errors (a policy that returns zero rows produces no SQL error at all — it just makes login silently fail with "user not found").

**Warning signs:** A migration titled something like "add RLS to auth tables" that mechanically mirrors the `workspace_isolation` policy pattern from domain tables; no design doc/decision record for the Better Auth trust boundary before the migration is written; staging login flow not explicitly re-tested after this specific change.

**Phase to address:** Phase 3 (Security & tenant isolation) — explicitly gated on the discuss-phase architectural decision PROJECT.md already calls for; should not be scheduled as a mechanical implementation task until that decision is recorded.

### Pitfall 13: Attaching a fresh monthly partition to `events`/`send_events` takes a full-table `ACCESS EXCLUSIVE` scan against the `DEFAULT` partition once one exists

**What goes wrong:** This is the audit's own "urgent by time" finding (§3.5, §12 Фаза 6) — partitions exist only through August 2026, and PROJECT.md repeats the hard deadline ("до 1 сентября 2026"). The mechanics matter for how the fix is built: `ATTACH PARTITION` itself only needs a `SHARE UPDATE EXCLUSIVE` lock on the parent table (allows concurrent reads/writes to continue), but Postgres must still verify the new partition's data doesn't violate the partition constraint — and per PostgreSQL's own documented behavior, if a `DEFAULT` partition exists (both `events` and `send_events` have one, SPECIFICATION.md §4.4) and any future partition is attached, Postgres has no way to prove the `DEFAULT` partition doesn't already contain rows that *should* belong to the new range without scanning the `DEFAULT` partition under an `ACCESS EXCLUSIVE` lock on that partition specifically. Because September 1 is the deadline for *fixing this before it becomes a problem*, if the automation ships even slightly late, real production rows will already have landed in `events_default`/`send_events_default`, and every subsequent `ATTACH PARTITION` for a normal monthly partition thereafter will pay this full-scan-under-exclusive-lock cost against a `DEFAULT` partition that keeps growing — on a table that's actively being written by the send pipeline at hundreds of thousands of rows/day (PROJECT.md scale target). An `ACCESS EXCLUSIVE` lock on `events_default` blocks all reads and writes to that partition for the scan's duration — on the live events table, that's a self-inflicted outage on ingestion.

**Why it happens:** "Add automated future partition creation" (the audit's literal fix, §3.5) is necessary but not sufficient — teams that ship the automation itself without also handling the case where it ships *after* the deadline (or without a CHECK-constraint-based workaround for future attaches) still take the full-scan hit on the first attach that has to reason about `DEFAULT` partition contents, whether that attach happens in July, September, or later. The urgency framing in the audit is correct, but "shipped before September 1" and "shipped in a way that avoids the DEFAULT-partition scan cost forever" are two different bars.

**How to avoid:**
- Ship the automated future-partition creation (2–3 months ahead, per audit §3.5) *before* September 1 — this is the literal deadline and prevents any production rows from landing in `DEFAULT` at all, which is the cleanest outcome (attaching against an empty `DEFAULT` partition is fast).
- If any rows have already landed in `DEFAULT` by the time this ships (verify with a query before assuming otherwise), do not attach new partitions naively — first create a `CHECK` constraint on the `DEFAULT` partition matching the *complement* of all currently-defined partition ranges (PostgreSQL's documented technique for this exact scenario: a CHECK constraint on the DEFAULT partition proving it can't contain rows in the new partition's range lets Postgres skip the scan), then run the migration procedure in §3.5's own fix list ("процедура перемещения данных из DEFAULT") to move any misrouted rows out.
- Schedule partition creation itself well ahead of the boundary — the audit's "2-3 months ahead" recommendation directly avoids ever being in the position of attaching against a DEFAULT partition that contains real data, and should run as its own low-traffic-window job (even though `ATTACH` doesn't block reads/writes on the parent under normal circumstances, an unexpected DEFAULT-scan-with-exclusive-lock should still be treated as a maintenance-window operation until proven otherwise on this table's actual production row counts).
- Explicitly write the "test transitioning across a month boundary" the audit demands (§10) as an automated test against a partition-boundary-crossing scenario, including the case where the automation runs late and `DEFAULT` already has rows — not just the happy path where automation runs on schedule.
- Because `send_events.occurred_at` is provider-supplied (see Pitfall 14), also verify the partition-creation/attach procedure accounts for `send_events` rows that could route to a partition far outside the "current month" window even after automation is in place.

**Warning signs:** Any manual/undated `ATTACH PARTITION` run against production without first querying whether `events_default`/`send_events_default` already has rows in the target range; a partition-creation cron/job with no monitoring/alerting if it fails to run (the audit explicitly asks for "мониторинг наличия следующей партиции," §3.5); an `ATTACH PARTITION` statement that measurably blocks ingestion when run (this itself is the signal the safe-CHECK-constraint technique wasn't used).

**Phase to address:** Phase 6 (Database lifecycle) — audit's own hard deadline (before 2026-09-01), independent of the rest of that phase's scope; sequence this ahead of everything else in Phase 6 given the calendar constraint.

### Pitfall 14: Provider-supplied `occurred_at` on `send_events` drives both partition routing and dedup — an out-of-range or malicious timestamp can misfile or bypass dedup

**What goes wrong:** SPECIFICATION.md §4.2/§4.4/§9 (item 17) documents this precisely: `send_events.occurred_at` "берётся из поля `timestamp`, присланного SendGrid," and this single value simultaneously (a) determines which monthly partition the row is routed to (`PARTITION BY RANGE (occurred_at)`), and (b) is part of the dedup unique key `(workspace_id, sg_event_id, occurred_at)`. The audit (§5.4) flags exactly this as a Medium finding and recommends bounding the provider timestamp's acceptable range and storing server receive time separately (`received_at` already exists as a separate column, §4.2 — the fix reuses an existing column, it doesn't need a new one). Two concrete failure modes if this isn't bounded: (1) a SendGrid webhook payload with a `timestamp` far outside any existing partition range (a SendGrid bug, a clock-skewed relay, or genuinely malicious replay via the webhook endpoint, which the audit separately notes has no replay protection, §4.5) either lands in the `DEFAULT` partition (harmless but defeats the point of partitioning, and — per Pitfall 13 — makes every future `ATTACH` pay the DEFAULT-scan cost against a growing bucket of stray-timestamp rows) or, worse, fails to insert entirely if no partition (including DEFAULT, in some routing edge cases) accepts the range, causing webhook processing to error; (2) because `occurred_at` is part of the *dedup key*, an attacker (or a buggy SendGrid retry with a slightly different timestamp field) resending the same `sg_event_id` with a different `timestamp` value bypasses the UNIQUE constraint's deduplication entirely — the constraint is `(workspace_id, sg_event_id, occurred_at)`, not `(workspace_id, sg_event_id)`, so varying only the timestamp produces a "duplicate" event that the dedup key does not recognize as a duplicate, double-counting delivered/opened/clicked events in analytics.

**Why it happens:** Using the provider's own event timestamp as the partition key is the obvious, natural choice (it's the semantically correct "when did this happen" field) and the dedup key naturally includes it because `sg_event_id` alone isn't guaranteed globally unique across a long enough time window without a range bound — but neither design decision anticipated that a hostile or malformed timestamp could be adversarially controlled by an untrusted webhook sender, because the primary threat model at MVP time was probably "SendGrid sends slightly-off-normal data," not "the timestamp field is itself a manipulable dedup-bypass vector."

**How to avoid:**
- Validate `occurred_at` against a bounded, sane range (e.g., not more than N days in the past, not in the future beyond small clock-skew tolerance) *before* it's used for either partition routing or the dedup key — reject or clamp out-of-range values, routing rejected events to an explicit quarantine/dead-letter path rather than silently accepting them into DEFAULT or erroring the whole webhook batch (recall §6.8: the whole webhook batch is enqueued as one job — a single malformed event's timestamp shouldn't be able to fail the entire batch).
- Change the dedup key to not depend on a value the sender can freely vary: either dedup on `(workspace_id, sg_event_id, received_at::date)` (server-controlled, coarse-grained) or on `sg_event_id` alone scoped to workspace with a much wider, server-controlled window, or add a secondary dedup check that isn't timestamp-dependent at all (e.g., a content hash) if `sg_event_id` collisions across time are actually a real concern worth guarding against — the current design conflates "prevent a hostile actor from bypassing dedup" with "keep the unique index small enough to be useful," and those need separate solutions.
- Since replay protection (audit §4.5) and this timestamp-bounding fix (§5.4) are adjacent concerns on the same endpoint, implement them together: rejecting stale/future-shifted `timestamp` header values (the webhook signature timestamp, §4.5) doesn't by itself validate the *payload's* per-event `timestamp` field used for partitioning/dedup — these are two different timestamp fields in the SendGrid payload and both need independent bounding.

**Warning signs:** Any `send_events` row with `occurred_at` more than a few days outside `received_at`; analytics counters (`open_count`/`click_count` on `sends`, `workspace_daily_rollup`) that increment more than once for what should be a single provider event; a webhook batch that errors entirely because one event in the batch had an out-of-range timestamp.

**Phase to address:** Phase 4 (Compliance & analytics, §5.4 timestamp bounding) coordinated with Phase 3 (webhook replay protection, §4.5) — these should land in the same reviewed change since they touch the same endpoint and adjacent timestamp fields.

### Pitfall 15: Migrations gain a gate/rollback process for the first time on a database that already has 27 un-snapshotted, hand-written migrations

**What goes wrong:** SPECIFICATION.md §4.6 documents that only 11 of 38 migrations have drizzle-kit snapshots, the remaining 27 are hand-written SQL with no snapshot, and there is currently *no* migration-runner invocation from either `apps/api` or `apps/worker` at startup — migrations only run via a dev-only npm lifecycle script (§4.6). The audit (§7, §12 Фаза 6) asks for a migration pipeline with a gate before app startup, rollback/roll-forward procedure, and a check for old/new app-version compatibility. Building this for the first time against *existing* history introduces several concrete traps distinct from designing it greenfield: (a) `drizzle-kit`'s own diffing/generate step relies on the snapshot chain to compute the next migration's diff — with 27 migrations missing snapshots, and a documented past incident where a missing baseline caused "generate" to emit a full-table-recreation false diff (§4.6, the `0034` comment referenced), any *new* migration generated by drizzle-kit against this history is at elevated risk of the same false-diff class of bug recurring, silently, unless the snapshot gap is either backfilled or drizzle-kit's generate step is not trusted blindly for the next migration and every generated migration is manually diffed against intent before being applied; (b) a rollback procedure designed against a clean, fully-snapshotted migration history and then pointed at this actual history may find several of the 27 non-snapshotted migrations are not cleanly reversible even in principle (e.g., migrations that already ran `ALTER POLICY` fixes, enum value additions which Postgres cannot trivially remove) — "rollback" for those specific historical migrations may simply not be a real option, and the new rollback tooling needs to explicitly special-case or document them as forward-only, rather than silently failing or (worse) attempting a rollback that corrupts state.

**Why it happens:** Migration tooling is usually evaluated against its own test suite and a small number of freshly-generated migrations during a hardening pass — nobody runs the new gate/rollback machinery against the *actual*, messy, partially-hand-written 38-migration history until it's needed for real, by which point a gap surfaces in production instead of in review.

**How to avoid:**
- Before building the gate/rollback pipeline, run `drizzle-kit generate` against current `HEAD` schema state and diff the output against what's actually expected — confirm whether the snapshot gap causes any spurious diff *today*, not just historically at `0034`.
- Treat "backfill missing snapshots for the 27 un-snapshotted migrations" as an explicit task inside Phase 6, not an assumed side effect of adding CI — snapshots are what make future `generate` calls trustworthy, and per the audit's own quality-gates ask (Phase 1: "migration tests"), the migration test suite should specifically assert that `generate` produces an empty diff against current schema state as a smoke test, catching this class of bug before it reaches a migration file.
- Design "rollback" as two explicit tiers: schema migrations verified safe to auto-reverse (simple `ADD COLUMN`/`CREATE TABLE` patterns going forward) vs. migrations that are documented forward-only (anything touching enums, RLS policies with data-dependent correctness, or partition DDL) — do not build a rollback tool that silently attempts a generic reverse-migration against arbitrary historical SQL.
- The audit's "compatibility check between old and new app version" (§7) should be implemented as an explicit CI check (e.g., run the previous app version's test suite against the new schema state) rather than a manual review step, given this milestone is specifically about closing gaps that manual review already missed once.
- Because no migrator currently runs at app startup at all (§4.6), the "migration gate before app startup" is new infrastructure, not a modification of existing infrastructure — treat it with the same rigor as Pitfall 16 (advisory locking) below, since it will be exercised on every single deploy going forward, unlike a migration itself which runs rarely.

**Warning signs:** A new migration generated by `drizzle-kit generate` that includes unexpected `DROP`/`CREATE` pairs for tables that shouldn't have changed (the exact `0034`-precedent failure mode recurring); a rollback script that has no special-casing for enum-touching or RLS-policy-touching migrations; CI green on migration tests without ever having run them against the actual 38-migration production-shaped history.

**Phase to address:** Phase 6 (Database lifecycle, migration pipeline) — audit explicitly scopes this as "High for migration pipeline" (§7, §12 Фаза 6); the snapshot-backfill sub-task should be sequenced first since it de-risks everything after it.

### Pitfall 16: Advisory-lock migration gating on a single-VPS multi-container deploy has its own failure modes if the lock isn't released cleanly

**What goes wrong:** The standard, well-documented fix for "multiple containers racing the same migration" (both `api` and `worker` starting simultaneously on a fresh VPS deploy, each potentially trying to run migrations if the gate is naively implemented as "run migrations on my own startup") is a Postgres advisory lock (`pg_advisory_lock`) wrapping the migration run, so concurrent runners serialize and late arrivals no-op once migrations are already applied — this is the documented pattern used by tools like `node-pg-migrate`. But advisory locks have their own documented failure modes directly relevant here: (a) if the process holding the lock crashes or is hard-killed (SIGKILL, OOM-kill — directly relevant given the audit's Docker/VPS section has no memory-limit guidance yet, see Pitfall 19) *without* releasing the lock and the lock was taken as a session-level lock on a connection that then gets returned to a pool rather than closed, the lock can persist and block all future migration attempts indefinitely — a documented GitHub-issue class of bug ("Migration runner's `pg_advisory_lock` leaks across pool connections — disables autovacuum on busy deployments"); (b) if the second/waiting process uses a plain blocking `pg_advisory_lock` call with no timeout, a stuck first process hangs the *entire deploy* indefinitely rather than failing fast and alerting; (c) database crash/restart scenarios mid-deploy mean "all replicas race to migrate on boot" the moment the DB comes back, which is a documented recurrence pattern for advisory-lock-gated migrations specifically at restart time, not just at normal deploy time.

**Why it happens:** Advisory locks are correctly identified as *the* standard solution to the racing-migrations problem, and teams stop the design process there — without also designing for "what if the lock holder dies uncleanly" and "what if the waiter should give up and alert instead of hanging forever," both of which are edge cases that don't show up in a normal, successful deploy test but are exactly the scenarios that matter for a production incident.

**How to avoid:**
- Use `pg_try_advisory_lock` (non-blocking) in a retry loop with a bounded total wait and an explicit timeout/failure path that surfaces clearly (fails the deploy loudly, alerts) rather than `pg_advisory_lock` (blocking indefinitely) for the waiting containers — a stuck migration should never manifest as "the deploy just hangs with no signal."
- Take the advisory lock on a *dedicated, short-lived connection* used only for the migration step, not on a connection that will be returned to a general-purpose pool afterward — this avoids the "lock leaks across pool connections" class of bug directly, since the connection (and thus the session-scoped lock) is simply closed when the migration step finishes, guaranteeing release even on ungraceful termination of that specific connection.
- Explicitly designate exactly one of the two processes (`api` or `worker`) — or a dedicated third "migrate" step/container that runs to completion before either `api` or `worker` starts — as the migration runner, rather than having both attempt to acquire the lock; this avoids the multi-way race entirely for the common case and only needs the advisory lock as a safety net for the actual concurrent-deploy edge case (e.g., a redeploy triggered while a previous deploy is still finishing).
- Test the unclean-death case explicitly: kill the migration process mid-migration (mid-lock-hold) and verify the next deploy attempt can still proceed (lock released because the connection closed) rather than hanging.

**Warning signs:** A migration runner using blocking `pg_advisory_lock` with no timeout; a lock acquired on a connection later returned to a shared pool instead of closed; no test that simulates the migration process being killed mid-run.

**Phase to address:** Phase 6 (Database lifecycle) alongside Pitfall 15 — this is the concrete locking mechanism for the "migration gate" the audit demands (§7).

### Pitfall 17: Long-running `ALTER TABLE`/`CREATE INDEX` in the new migration pipeline blocks the app at exactly the moment it's supposed to be gating startup safely

**What goes wrong:** The audit (§7) explicitly flags missing constraints that need to be added — unique `(organizationId, userId)` on `member`, unique `(flow_id, version_number)` on `flow_versions`, foreign keys for `flows.draft_version_id`/`live_version_id` — and separately warns "нужно добавлять ограничения только после проверки и очистки существующих данных" (only add constraints after verifying/cleaning existing data). Two distinct pitfalls compound here: (a) `CREATE INDEX` without `CONCURRENTLY` takes a table-wide lock that blocks writes for the index's build duration — on `member` (small) this is fine, but the audit's general recommendation applies platform-wide, and any future index added to a large, actively-written table (`sends`, `events`, `send_events`) without `CONCURRENTLY` would stall the send pipeline for the build duration, which is exactly the kind of self-inflicted outage this milestone is trying to prevent, not introduce; (b) adding a UNIQUE constraint requires either an exclusive-locking, blocking `ADD CONSTRAINT` (which internally builds a unique index non-concurrently) or the documented two-step workaround — `CREATE UNIQUE INDEX CONCURRENTLY` first, then `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX` (near-instant, catalog-only) — and if *duplicate data already exists* (plausible for `(organizationId, userId)` on `member` given no such constraint exists today and the app may have created duplicate memberships via a race in the invite-accept flow), the `CREATE UNIQUE INDEX CONCURRENTLY` step doesn't fail loudly — Postgres marks the resulting index `INVALID` and leaves it in place, silently *not enforcing uniqueness* while looking like the migration succeeded, unless the migration script explicitly checks for and handles the `INVALID` index state.

**Why it happens:** `CONCURRENTLY` + `USING INDEX` is the textbook-correct pattern and is easy to get right in isolation, but the *duplicate-data-already-exists* precondition check is a separate step that's easy to skip when a migration is being written under the audit's own time pressure — and the failure mode (index silently invalid, constraint not actually enforced) produces no migration-time error at all, so it looks done but isn't, directly matching this document's own "Looks Done But Isn't" pattern below.

**How to avoid:**
- For every new constraint the audit lists (§7), run a pre-migration audit query identifying existing duplicates *first*, as its own step with its own output reviewed by a human — do not assume "no duplicates" without checking, especially for `member (organizationId, userId)` where the invite-accept flow (SPECIFICATION.md §6.2) could plausibly race.
- Use `CREATE UNIQUE INDEX CONCURRENTLY` + `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX` for every constraint addition on any table with production traffic, and explicitly check `pg_index.indisvalid` after the `CONCURRENTLY` step as an automated migration-test assertion, not a manual step that can be forgotten.
- Never run bare `CREATE INDEX` (non-concurrent) as part of the automated migration pipeline for any table the send pipeline reads/writes during normal operation (`sends`, `events`, `send_events`, `campaigns`, `flow_runs`) — this should be an explicit CI/lint rule in the migration test harness the audit asks for (Phase 1), not a matter of developer discipline alone.
- If duplicates are found, resolve them with a reviewed, explicit data-cleanup migration (which one row wins, what happens to the other) *before* the constraint migration — don't let the constraint migration silently choose by whichever `CREATE INDEX CONCURRENTLY` happens to keep.

**Warning signs:** A migration file containing `ADD CONSTRAINT ... UNIQUE` (not `USING INDEX`) directly against a production table; no pre-migration duplicate-check query in the PR; `pg_index` showing any `indisvalid = false` row post-deploy (silent, must be actively checked for — it won't surface as an error anywhere else).

**Phase to address:** Phase 6 (Database lifecycle, constraints) — audit explicitly scopes this as "Medium for ограничения" (§7) but the CONCURRENTLY/duplicate-check discipline should be enforced by Phase 1's migration-test harness for every future migration, not just this one-time batch.

### Pitfall 18: Sentry/hosted-log redaction gets configured against generic PII patterns and misses this system's two specific highest-value secrets

**What goes wrong:** The audit (§4.8) already documents that pino's existing redaction covers only `sendgridKey`/`apiKey`/`password`/`token` at up to two levels of object nesting, and that the worker has *no* redaction at all (plain `console.log`/`console.error`, SPECIFICATION.md §7). Sentry's own documented default scrubbing catches generic patterns like "password," "secret," and credit-card-shaped strings, but explicitly does *not* cover arbitrary PII like email addresses by default, and critically — Sentry has no retroactive redaction: "After log data has been ingested by Sentry, there is currently no way to retroactively redact specific fields... the only workaround is deleting an entire project's data." This is the single highest-stakes fact for this milestone specifically: the two secrets this system cannot afford to leak are (a) tenant SendGrid API keys (which, decrypted, live in worker-process memory during `sendTenantMailV3`, per §3.4 — an unhandled exception thrown from anywhere in that call stack, if it includes the key in its message/stack and Sentry is wired up naively, ships the plaintext key to a third-party SaaS with no way to undo it after the fact) and (b) contact email addresses at scale (this is a marketing platform; ordinary application errors routinely include contact objects in their context, e.g., a failed segment-compile error, a failed contact-upsert error — Sentry's default scrubbing does not treat "email" as sensitive by default, so every unhandled exception touching a `Contact` object is a potential PII leak into a third-party tool unless explicitly scrubbed).
The existing `redactApiKey(err, apiKey)` helper (§3.4) is a manual, call-site-specific redaction — it protects log lines that go through that specific function, but Sentry's SDK captures unhandled exceptions and their full context (breadcrumbs, local variables in some configurations, request bodies) *before* any application-level redaction helper gets a chance to run, unless Sentry's own `beforeSend` hook (the documented, correct mechanism: "Sentry recommends using `before_send` in SDKs to scrub data before it's sent... ensure sensitive data never leaves the local environment") is explicitly configured to re-apply the same redaction rules.

**Why it happens:** Application-level log redaction (pino's `redact.paths`) and Sentry's error-capture pipeline are two entirely separate code paths that happen to look like "the same problem, already solved" — teams wire up Sentry, see that pino redaction already exists, and assume the coverage transfers, when in fact Sentry's SDK hooks into uncaught exceptions and HTTP request/response capture independently of the logger.

**How to avoid:**
- Configure Sentry's `beforeSend`/`beforeSendTransaction` hooks explicitly, on both `apps/api` and `apps/worker` SDK initializations, to strip the same fields pino already redacts (`sendgridKey`, `apiKey`, `password`, `token` and their nested variants) *plus* explicitly scrub `email`, `phone`, and any `properties`/`payload` JSONB blob fields (these carry arbitrary tenant-supplied event/contact data per §4.2's `events.properties`/`contacts.properties` — freeform by design, meaning *any* PII a tenant's own customers submit could appear here) — do not rely on Sentry's default scrubbing, which the vendor's own docs confirm does not cover email/PII by default.
- Since Sentry has no retroactive redaction (confirmed limitation), treat the `beforeSend` scrub rules as a pre-launch gate, not a post-launch fix — test them against representative error payloads (a thrown error from inside `sendTenantMailV3` with the decrypted key in scope, a thrown error from contact-upsert with a `Contact` object in context) *before* Sentry is wired to receive live traffic, since any leak that does happen is only remediable by deleting the whole project's data.
- Extend structured, redacted logging to the worker (currently `console.log`/`console.error` with zero redaction, §7) as part of this same phase — Sentry captures unhandled exceptions, but routine operational logs (e.g., a caught-and-logged SendGrid error that still contains the decrypted key in its message before `redactApiKey` runs, if any code path logs the raw error before calling that helper) are a second, independent leak surface that Sentry configuration alone doesn't close.
- Deepen pino's redaction beyond two levels of nesting (audit-flagged, §4.8) using redaction paths with wildcards that match arbitrary depth (pino supports this), rather than manually enumerating every plausible nesting level — the freeform `properties`/`payload` JSONB fields mean nesting depth is not bounded by the schema.

**Warning signs:** Sentry dashboard showing a raw error message containing `SG.` (SendGrid key prefix format, per §3.4's `key_mask` documentation) or a bare email address in an unredacted `message`/`extra` field; no `beforeSend` hook configured in either SDK init; worker still logging via `console.log` after Sentry/hosted-logs are wired up.

**Phase to address:** Phase 7 (Observability, deployment) for the Sentry wiring itself; must be sequenced *after* Phase 3's secrets/redaction centralization work (audit groups "secrets/redaction" under Phase 3, §12) so the redaction rule set exists once and is reused by both pino and Sentry's `beforeSend`, rather than being defined twice and drifting.

### Pitfall 19: No memory limits on a single-VPS Docker deploy lets a runaway worker (or a segment sweep, before it's bounded) OOM-kill Postgres, not itself

**What goes wrong:** SPECIFICATION.md confirms no Dockerfiles/deploy manifests exist yet (§1.3) and the dev `docker-compose.yml` sets no resource limits on any service. On a single VPS running Postgres, Redis, `api`, and `worker` as sibling containers (or processes) with no `mem_limit`/cgroup constraints, the Linux OOM killer's victim-selection heuristic is not "kill the container that's misbehaving" — it scores processes by memory usage and killer-badness heuristics system-wide, and Postgres (which the OOM killer has historically been documented to target, since a well-utilized Postgres instance with a large shared-buffers/work_mem footprint often has one of the largest resident-memory footprints on the box) can be selected as the OOM victim even when the actual root cause is a *different* process (e.g., the currently-unbounded segment sweep the audit flags in §3.4, or a webhook-batch job processing an unexpectedly large payload) consuming memory it shouldn't. Killing Postgres mid-transaction is far more disruptive than killing the misbehaving worker container would have been — in-flight `withTenantTransaction` blocks across every concurrent request abort, and Postgres's own crash-recovery (WAL replay on restart) adds downtime the equivalent worker-only failure wouldn't have caused.

**Why it happens:** Resource limits are the kind of configuration that has zero effect on functional testing (everything works identically with or without `mem_limit` set, until the box is actually under memory pressure) and therefore gets deferred past a hardening milestone's functional-correctness-focused review, especially when — as here — a *different* fix for the underlying unbounded-memory cause (bounded segment sweep, §3.4/Phase 5) is already in scope and might be assumed to make container-level limits redundant. It doesn't: bounding one known unbounded-memory code path doesn't protect against every future one, and defense-in-depth resource limits are cheap to add once Dockerfiles exist anyway.

**How to avoid:**
- Set explicit memory limits (Docker `--memory`/Compose `mem_limit`, or systemd `MemoryMax=` if not using Docker for some services) on every container/process on the VPS as part of Phase 7's Dockerfile/deploy work, sized with headroom below total VPS RAM such that no single container's OOM event can starve Postgres — Postgres should either have the most generous limit (least likely to be picked) or, better, run with its own dedicated `oom_score_adj` tuning so the kernel strongly prefers killing `worker`/`api` over `postgres` if global memory pressure occurs despite per-container limits.
- Ship the bounded segment sweep (audit §3.4, Phase 5) *before or alongside* the container memory limits — treat them as complementary, not either/or: the sweep fix removes the known-largest unbounded-memory code path; the container limits are the safety net for the ones not yet known.
- Load-test the actual expected production data volume (100k-1M contacts, PROJECT.md target) against the worker's memory footprint under the configured limit *before* going live, specifically exercising the segment sweep, CSV import, and webhook-batch-processing code paths, which are the most likely large-payload sources per the audit's own findings (§3.4, §6.8's "весь батч одним джобом").
- Configure Postgres's own `shared_buffers`/`work_mem`/`max_connections` conservatively for the VPS's actual total RAM (not left at defaults tuned for a larger dedicated instance), reducing the chance Postgres itself becomes the memory-pressure trigger rather than just the OOM-killer's victim.

**Warning signs:** `docker-compose.yml`/production Compose file with no `mem_limit`/`deploy.resources.limits` on any service; `dmesg`/journal logs showing `Out of memory: Killed process` for `postgres` after a deploy; no documented VPS RAM budget allocated per-service before Phase 7 ships.

**Phase to address:** Phase 7 (Observability, deployment) for the container limits themselves; sequenced after or alongside Phase 5's bounded segment sweep, since that fix reduces (but does not eliminate) the risk this pitfall describes.

### Pitfall 20: Redis persistence/eviction defaults, unexamined until now, silently discard queued jobs on restart or under memory pressure

**What goes wrong:** The dev `docker-compose.yml` (§1.3) runs `redis:7` with a named volume but no explicit `maxmemory`/`maxmemory-policy`/persistence (`save`/AOF) configuration documented anywhere in SPECIFICATION.md — meaning whatever Redis ships as its image default is what's currently in effect, and that has not been evaluated against this system's actual requirement, which is strict: BullMQ's own production guidance states plainly that "BullMQ cannot work properly if Redis evicts keys arbitrarily" and that `maxmemory-policy` must be set to `noeviction` — the *only* setting that guarantees correct queue behavior — because any LRU/LFU/random eviction policy can and will delete job data (including in-flight `sends`-pipeline jobs, delayed flow-wake jobs, repeatable-job schedule state) the moment Redis hits its memory ceiling, with zero application-visible error; jobs simply vanish. Separately, Redis's default persistence (RDB snapshotting on a schedule, or no persistence at all depending on image defaults and any `redis.conf` overrides) determines what happens on a Redis restart (VPS reboot, container OOM-kill per Pitfall 19, or a routine Redis upgrade during Phase 7's deploy work): without AOF (`appendonly yes`) or frequent-enough RDB snapshots, a Redis restart loses every job enqueued since the last snapshot — including, notably, the delayed `flow-run-advance` jobs that are the *primary* (not backstop) mechanism for flow wake-ups (§5.6: the 60-second `flow-reconciliation` scan is explicitly documented as a backstop for exactly this loss scenario, but only catches `flow_runs` whose `next_wake_at` has already passed by the time the next 60s tick runs — a Redis data loss immediately followed by an extended outage before Redis/worker recovery could still produce missed wake-ups outside that backstop's effective window if the outage is long).

**Why it happens:** Redis's out-of-the-box defaults are tuned for "general-purpose cache," not "durable job queue," and nothing in a functional-correctness-focused development cycle exercises the eviction/persistence boundary — it only manifests under real memory pressure or a real restart, neither of which happens routinely in dev/CI.

**How to avoid:**
- Set `maxmemory-policy noeviction` explicitly in the production Redis configuration (Phase 7) — this is a one-line, high-leverage fix directly sourced from BullMQ's own "going to production" guidance, and should be a named, tested line item, not an assumed default.
- Enable AOF (`appendonly yes`, with `appendfsync everysec` as the standard durability/performance tradeoff) for the BullMQ-backing Redis instance specifically, since RDB-only snapshotting has a data-loss window measured in the snapshot interval (commonly minutes), which is unacceptable for in-flight send-pipeline and flow-wake job data; the audit doesn't explicitly call this out as a named finding, but it's a direct, sourced consequence of the "worker reliability" and "queue depth/oldest job age" observability goals the audit does ask for (§8/Phase 7) — those alerts are meaningless if a Redis restart can silently erase the queue they're monitoring.
- Set `maxmemory` explicitly (paired with `noeviction`) sized with headroom against the VPS's memory budget (coordinate with Pitfall 19's per-container limits) — `noeviction` without a `maxmemory` ceiling just means Redis grows until the OS OOM-kills it instead of Redis gracefully rejecting new writes with an error the application can catch and alert on.
- Verify the `dump.rdb` currently sitting in the working tree (SPECIFICATION.md §3.1, flagged as a repo-hygiene item, §4.8/§9 item 19) isn't itself evidence that dev Redis persistence has been silently accumulating stale queue state across restarts already — treat its removal (Phase 1, repo hygiene) as a reminder to explicitly design the *production* persistence story, not just delete the dev artifact.
- Test explicitly: kill and restart the Redis container mid-load-test and verify BullMQ's job data survives (with AOF) or is acceptably backstopped (verify the 60s reconciliation scan actually recovers all affected `flow_runs` within its effective window) — this is a direct instance of the failure-injection testing the audit demands (§10), specific to the infrastructure layer rather than the application layer.

**Warning signs:** No `maxmemory-policy` line in the production Redis config (defaults to `noeviction` on stock `redis:7` images in most distributions, but this must be verified, not assumed, and is different behavior on managed Redis providers); no AOF/`save` configuration reviewed against expected data-loss tolerance; a Redis container restart during testing that isn't followed by a check that all previously-queued jobs are still present or correctly recovered via the reconciliation backstop.

**Phase to address:** Phase 7 (Observability, deployment) for the Redis production configuration; the restart/recovery test belongs in Phase 1's failure-injection harness once that infrastructure exists.

### Pitfall 21: E2E tests that "use an isolated database" in config but silently fall back to the dev database the moment setup fails

**What goes wrong:** The audit is explicit and specific here (§10): "Playwright не входит в стандартный тестовый прогон и может использовать development-базу... E2E должен работать только с отдельной временной БД" — this is flagged as a concrete, already-observed risk, not a hypothetical. The generic version of this pitfall (E2E tests pointing at a shared/dev database) has a specific *second-order* failure mode worth naming for this exact codebase: even after Phase 1 wires Playwright to a dedicated ephemeral database, a common way this silently regresses is that the test setup/global-setup script falls back to a default `DATABASE_URL` (e.g., `.env`'s value, which SPECIFICATION.md §3.1 confirms already exists and is loaded via `tsx --env-file` in dev scripts) whenever the dedicated test-database environment variable is unset or the ephemeral database provisioning step fails for any reason — and because Playwright tests then *run successfully* against the dev database (it has real schema, often has some real-ish data), the failure is invisible: tests pass, CI is green, but every E2E run has been silently mutating the shared dev database (creating/deleting workspaces, contacts, sends) the whole time. This exact failure shape — "isolation config exists, but a benign-looking fallback silently defeats it" — is the single most common reason "we already added test DB isolation" projects still have DB-isolation incidents.

**Why it happens:** Test infrastructure that's designed to "fall back gracefully" for developer convenience (so a developer without a fully-configured test DB can still run *something* locally) is the same mechanism that makes the failure silent in CI — the fallback that's helpful on a laptop is exactly what makes the CI signal untrustworthy.

**How to avoid:**
- Make the E2E test setup fail loudly (hard error, non-zero exit, test suite refuses to start) if the dedicated test database's connection string is unset, unreachable, or — critically — resolves to the same connection string as any known dev/prod value, rather than silently proceeding with whatever `DATABASE_URL` happens to be in the environment. A simple, effective guard: assert the resolved test DB name/connection string is *not equal to* the value of `DATABASE_URL` (dev) before any test runs, and fail the whole run if they match.
- Provision the ephemeral test database via the same mechanism CI will use (Testcontainers, or a docker-compose service scoped to the test run) *locally too*, so there's no separate "local fallback path" with different semantics than CI — the two environments should use the identical provisioning script, not a CI-only path and a locally-more-permissive one.
- Given Testcontainers' documented flakiness/performance risk in CI specifically (Docker-in-Docker overhead, port conflicts under parallel pipelines, slow container startup under resource-constrained shared runners), pin image versions, use explicit health/wait strategies rather than default readiness heuristics, and avoid fixed port bindings (let Testcontainers assign ephemeral ports) if adopting Testcontainers for this — a flaky E2E suite that developers learn to re-run-until-green is functionally equivalent to no E2E suite, and is a common enough failure mode to name as its own risk alongside the DB-isolation one.
- Add a CI assertion (not just a local guard) that inspects the actual connection string the test run used post-hoc (e.g., logged at test-setup time) and fails the build if it doesn't match the expected ephemeral-database naming pattern — belt-and-suspenders against the fallback risk, verifiable even if the in-process guard above has its own bug.

**Warning signs:** Any `catch`/fallback branch in E2E global-setup that assigns a default `DATABASE_URL` value; local dev database showing unexpected test-fixture-looking data (a workspace named `e2e-test-*`) after running `npm run test:e2e` without first confirming the test DB was actually used; CI E2E job that never explicitly asserts which database it connected to.

**Phase to address:** Phase 1 (Quality gates) — audit explicitly scopes this (§12 Фаза 1, "отдельная E2E-БД").

### Pitfall 22: A coverage gate added under time pressure gets gamed by exactly the kind of test that looks thorough but proves nothing

**What goes wrong:** The audit (§10) notes the absence of coverage gates as a finding but also, implicitly, warns against treating "526 passing tests" as proof of production reliability ("текущая зелёная проверка не доказывает production reliability"). The specific risk of *adding* a coverage gate now, on an existing 91-file/526-test suite, rather than growing it organically from zero: teams under a coverage-percentage deadline (a natural artifact of "add coverage gates" being a checklist item in Phase 1) tend to close the gap with tests that execute code paths without asserting meaningful behavior — e.g., a test that calls `claimCampaignSend` and asserts only "it doesn't throw," rather than asserting the row ends up in the correct state, or a test that mocks `sendTenantMailV3` entirely and therefore never exercises the actual timeout/AbortController logic Phase 2 is adding (Pitfall 5) even though the coverage tool reports that code as "covered" because the mock's call site executes. This is especially acute for exactly the failure-injection tests the audit is separately demanding (§3.2, §10: crash before send, crash after SendGrid accepts, timeout/disconnect, tenant A rate-limited while tenant B continues) — these are inherently harder to write than straight-line unit tests, and a coverage-percentage gate creates schedule pressure to hit the number via the *easy* tests instead, satisfying the metric while leaving the actual production-risk scenarios (the whole point of this milestone) unverified.

**Why it happens:** Coverage percentage is a proxy metric for "this code has been exercised," not for "this code's actual failure modes have been verified" — the gap between the two widens specifically for concurrency/crash-injection scenarios, which are exactly the category this milestone's highest-priority findings live in (delivery correctness, worker reliability, tenant isolation), and which are exactly the category a generic percentage-based gate is worst at incentivizing.

**How to avoid:**
- Treat the coverage-percentage gate (Phase 1) and the failure-injection test suite (also Phase 1, feeding Phase 2/5) as two separate, independently-tracked deliverables — do not let "coverage % target met" stand in as evidence that the audit's named crash scenarios (§3.2, §10) are actually tested; require an explicit checklist mapping each named crash/race scenario from the audit to a specific test file/test name, reviewed separately from the coverage number.
- Set the coverage gate's threshold based on the *current* baseline (measure it first) plus a modest, deliberate increase — not an arbitrary round number (80%, 90%) chosen without reference to what's actually achievable without gaming, which is the more common root cause of gamed coverage gates than malice: an unreachable target forces corner-cutting.
- Exclude or separately track coverage on code that's structurally hard to cover meaningfully without integration/failure-injection infrastructure (the SendGrid call path, the claim-transaction race conditions, the reconciliation logic) — folding these into the same blanket percentage as, say, a Zod schema validator, hides exactly the parts of the codebase this milestone cares most about behind an aggregate number.
- Review new tests added specifically to close a coverage gap (identifiable by being added in the same PR as a coverage-threshold-adjacent change) with extra scrutiny for "does this test assert the state/behavior that matters, or does it just execute the line" — a lightweight, specific code-review checklist item for this phase.

**Warning signs:** A PR that raises coverage percentage but adds no new assertions on database state, job status, or provider-call parameters; failure-injection scenarios named in the audit (§3.2, §10) with no corresponding named test file even after Phase 1's coverage gate is reported as passing; mocked `sendTenantMailV3`/SendGrid calls in every test that touches the send pipeline, with none exercising the real (or realistically faked, e.g., via `nock`, which is already a dev dependency per §2.2) timeout/error-response behavior.

**Phase to address:** Phase 1 (Quality gates) for the gate/harness design; Phase 2 and Phase 5 own actually writing the specific crash/race tests the harness makes possible, and should not be considered done merely because Phase 1's coverage number is met.

| Integration | Common Mistake | Correct Approach |
|-------------|-----------------|-------------------|
| BullMQ `worker.rateLimit()` | Treating it as job/tenant-scoped throttling | It delays the entire worker's job-fetch loop; use `job.moveToDelayed` for a single job's per-tenant backoff instead (Pitfall 4) |

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| `ATTACH PARTITION` against a `DEFAULT` partition that already has rows | Ingestion writes to `events`/`send_events` stall for the duration of an `ACCESS EXCLUSIVE`-locked scan | CHECK-constraint-first attach technique, or (preferably) never let rows land in `DEFAULT` by automating partition creation ahead of the boundary (Pitfall 13) | The moment any real production row lands in `events_default`/`send_events_default` before the next month's partition exists — deadline is 2026-09-01 |
| Unbounded segment sweep loading all matching contacts in one query (audit §3.4) | Worker memory spikes, long transactions, slow/failed recovery after partial crash | Keyset pagination + checkpoint + bounded batch jobs (already scoped, Phase 5) | At the platform's own stated target scale, 100k-1M contacts per tenant |
| `CREATE INDEX`/`ADD CONSTRAINT` without `CONCURRENTLY` on a live table | Write-blocking table lock during index build, visible as a send-pipeline stall | Always use `CONCURRENTLY` + `USING INDEX` two-step for any table under active write load (Pitfall 17) | Any table with meaningful row count/write rate — `member` is safe today, `sends`/`events` never are |
| Redis without `maxmemory` ceiling paired with `noeviction` | Redis grows unbounded until OS-level OOM kill, silently taking the queue backend down | Explicit `maxmemory` sized against VPS RAM budget, monitored (Pitfall 20) | Whenever job volume/retention settings combine to exceed the box's available memory — directly interacts with Pitfall 6's retention choices |
| No per-container memory limits on a shared single-VPS deploy | Postgres OOM-killed by kernel due to a *different* process's runaway memory use | Explicit `mem_limit` per service, `oom_score_adj` tuning favoring worker/api over postgres (Pitfall 19) | Any future unbounded-memory code path, not just the currently-known segment sweep |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Admin-scan RLS policies with no predicate beyond the GUC check on `flow_runs`/`flows` (confirmed current state, §4.3/§9) | Any code path that can set `app.admin_scan='true'` gets unscoped cross-tenant SELECT on those two tables | Add the missing predicate matching the `0018` precedent; add a negative test proving no non-admin path can set the GUC (Pitfall 9) |
| Unifying the two RLS policy variants toward the more "forgiving" NULLIF pattern | Converts fail-closed tables (throw on missing tenant context) into fail-open-to-empty-result tables — the more dangerous failure mode for `contacts`/`sends`/`events` | Unify toward bare-cast (fail loudly); assert thrown errors, not empty results, in the new negative test (Pitfall 11) |
| Adding RLS to Better Auth tables as a mechanical checklist item | Breaks login/signup/session-validation platform-wide on deploy, since the non-tenant auth client never sets the workspace GUC | Treat as the architectural decision PROJECT.md already flags it as; test full login flow against staging before any auth-table RLS ships (Pitfall 12) |
| Introducing PgBouncer without first auditing every GUC-setting statement for `SET LOCAL` discipline | Session-scoped GUC leak becomes a cross-*tenant* leak once a transaction-mode pooler shares backends across tenants | Full-codebase audit for bare `SET`/`SET ROLE` before PgBouncer goes live; explicit `SET LOCAL ROLE` if role-switching is added for the new admin-scan/auth-trust-boundary roles (Pitfall 10) |
| Trusting provider-supplied `send_events.occurred_at` as both partition key and (implicitly) part of the dedup uniqueness guarantee | A varied/malicious timestamp on the same `sg_event_id` bypasses dedup, double-counting delivery/open/click events; out-of-range timestamps misfile into `DEFAULT` | Bound the timestamp's acceptable range; base dedup on server-controlled fields, not the sender-supplied one (Pitfall 14) |
| Wiring Sentry with default scrubbing and assuming existing pino redaction "covers it" | Permanent leak of a tenant's decrypted SendGrid key or contact PII to a third-party SaaS — no retroactive redaction exists | Explicit, tested `beforeSend` hooks on both API and worker SDKs before Sentry receives live traffic (Pitfall 18) |

## "Looks Done But Isn't" Checklist

- [ ] **`unknown`/reconciling delivery state:** Often missing an exclusive-claim guard on the reconciliation write path — verify the reconciler and any retry-worker cannot both resolve the same row's terminal status without a row lock scoped to `withTenantTransaction`.
- [ ] **Tenant-local throttling fix (replacing `worker.rateLimit()`):** Often verified only by unit-testing the rate-limiter-flexible bucket in isolation — verify with an actual two-tenant load test that tenant B's throughput is unaffected while tenant A is being throttled.
- [ ] **`CREATE UNIQUE INDEX CONCURRENTLY` for new constraints:** Often assumed to succeed silently — explicitly query `pg_index.indisvalid` post-migration; an `INVALID` index produces zero migration-time error while leaving the constraint unenforced.
- [ ] **Partition auto-creation automation:** Often verified only by "the cron job exists" — verify it has monitoring/alerting for its own failure to run (audit explicitly asks for this, §3.5) and that it's tested against the case where it already ran late once (DEFAULT partition already has rows).
- [ ] **RLS unification across the two policy variants:** Often verified with "does the query still work" — verify the *negative* test (no tenant context) throws an error, not that it returns anything at all, for tables unified toward bare-cast.
- [ ] **Migration gate/advisory lock:** Often verified only under the happy path (single deploy, clean shutdown) — verify by killing the migration process mid-run and confirming the lock releases for the next deploy attempt.
- [ ] **Sentry PII redaction:** Often verified by checking pino's `redact.paths` config exists — verify Sentry's own `beforeSend` hook independently, since it intercepts unhandled exceptions before the logger's redaction ever runs.
- [ ] **Container graceful shutdown:** Often verified by confirming `worker.close()` is called — verify the *container-level* stop-grace-period is long enough for it to actually finish, under a real SIGTERM sent mid-load-test, not just that the code path exists.
- [ ] **Redis persistence/eviction config:** Often left at image defaults with no explicit review — verify `maxmemory-policy=noeviction` and AOF are explicitly set, and test a Redis restart mid-load-test to confirm no silent job loss.
- [ ] **E2E test database isolation:** Often "fixed" by pointing Playwright config at a test DB variable that has a silent fallback to `DATABASE_URL` if unset — verify the fallback path is a hard failure, not a graceful default, and that the resolved connection string is asserted to differ from dev/prod.
- [ ] **Coverage gate:** Often satisfied by tests that execute a code path without asserting the state that matters — verify each named crash/race scenario from the audit (§3.2, §10) maps to an explicitly named test, independent of the aggregate coverage percentage.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|------------------|
| Duplicate sends from a reconciler/retry race (Pitfall 1) | MEDIUM | Add the missing exclusive-claim guard; backfill-audit any `sends` rows that show two `send_events`/provider-message-IDs for one logical send during the exposure window; no data loss, but requires a manual dedup pass on affected analytics counters |
| RLS unified to the wrong (fail-open) variant (Pitfall 11) | HIGH | Revert the policy to bare-cast immediately; audit query logs/application logs for the exposure window for any query that ran without tenant context and returned zero rows silently (hard to reconstruct after the fact — this is why prevention matters more than recovery here) |
| Auth tables broken by naive RLS addition (Pitfall 12) | LOW | Roll back the migration (straightforward `DISABLE ROW LEVEL SECURITY` / drop policy); this is a fast, clean rollback precisely because it fails loudly (login breaks immediately) rather than silently |
| Production rows landed in `DEFAULT` partition before automation shipped (Pitfall 13) | MEDIUM–HIGH | Run the documented CHECK-constraint-first attach technique; move misrouted rows out of `DEFAULT` via the audit's own recommended migration procedure (§3.5); no data loss, but requires a maintenance window for the first corrective `ATTACH` |
| Sentry receives an unredacted SendGrid key or contact PII (Pitfall 18) | HIGH | No retroactive redaction exists per Sentry's own documentation — recovery is deleting the affected project's data (losing all other captured errors too) or accepting the exposure and rotating the leaked tenant's SendGrid key immediately, treated as a real secret-compromise incident, not a logging bug |
| Redis data loss on restart erases in-flight jobs (Pitfall 20) | MEDIUM | The 60s `flow-reconciliation`/`campaign-scheduler` backstop scans recover most cases automatically; manually audit any `sends` rows stuck in `dispatching`/`unknown` older than the backstop's effective window and resolve them through the reconciliation logic manually |
| Migration advisory lock left held by a crashed process (Pitfall 16) | LOW–MEDIUM | If the lock was taken on a dedicated connection (recommended design), it releases automatically on connection close; if taken on a pooled connection (the anti-pattern), manually identify and terminate the holding backend via `pg_terminate_backend` after confirming the process is actually dead, not just slow |
