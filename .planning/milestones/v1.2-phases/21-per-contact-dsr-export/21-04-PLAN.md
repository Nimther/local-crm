Close SC5's courtesy half. </objective>

<flagged_assumptions>
**Reachability caveat for the D-14 disabled state — read before implementing.**

`getContact` (and `listContacts`) filter `anonymized_at IS NULL`, a deliberate Phase 13 ruling (CMP-04 / threat T-13-10-03: an anonymized contact must never be presented to a tenant as a live contact, and `contacts.routes.ts` maps `contact_anonymized` to 404 for the same reason). Consequently `GET /contacts/:id` returns 404 for an already-erased contact and the card never renders for it through normal navigation.

So the disabled-with-reason state is reachable in production only through a **stale client cache**: the card was loaded while the contact was live, the contact was erased in another session, and the still-mounted page re-renders from cached data or receives the typed 410. That is exactly the race D-14 names ("the typed 410 remains the API backstop for races"), and it is why the 410 handler and the disabled state are both required.

This plan implements D-14 verbatim and **does not relax the Phase 13 filter** — reversing another phase's threat mitigation is outside this phase's authority. The state is therefore proven at the component level with a synthetic `anonymizedAt`-set contact, not through an end-to-end navigation test.

**Known consequence to accept, not fight:** UI-SPEC locks "the 410 handler also invalidates the contact query". That refetch will 404 (the filter), so the page transitions to its existing not-found / error state. That is the correct, honest outcome — the contact genuinely is no longer a tenant-visible contact — and it is expected behaviour, not a defect to work around. Record it in the SUMMARY.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API contact response → browser | A new field (`anonymizedAt`) is added to a tenant-facing response shape consumed by the SPA and by any client reading it |
| stale client cache → export request | The browser may hold a contact that has since been erased; the client-side state is untrusted and the API remains the authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-04-01 | Information Disclosure | widening the contact response shape | low | mitigate | Only a lifecycle timestamp is added, never a scrubbed PII column; the value is `null` for every contact a tenant can read because the tenant-facing selects keep filtering anonymized rows. |
| T-21-04-02 | Elevation of Privilege | relaxing a read filter to make a UI state reachable | high | mitigate | The `anonymized_at IS NULL` predicate set is provably untouched (before/after grep count recorded); `CONTACT_COLUMNS` in the shared package is provably unmodified (`git diff --stat`). |
| T-21-04-03 | Spoofing | trusting the client's erased/enabled state | medium | mitigate | The disabled state is a courtesy only; the typed 410 from the route remains the enforcement point for a contact erased after page load. |
| T-21-04-04 | Information Disclosure | erased-contact reason copy | low | accept | The copy states that personal data was deleted and names no personal data; it is the same fixed string in both the disabled state and the 410 branch. |
| T-21-04-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task in this phase (RESEARCH.md Package Legitimacy Audit: not applicable). |
