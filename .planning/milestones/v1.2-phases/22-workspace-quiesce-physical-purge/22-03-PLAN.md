<objective>
Close the ingress half of quiesce (D-04): a soft-deleted workspace accepts no new data from anywhere. Its API keys stop being honoured, inbound SendGrid webhooks for it are dropped indistinguishably from an unknown token, and the two ingest workers refuse jobs that were already in the queue when the delete happened. Nothing accumulates new PII in a workspace that is waiting to be purged.

Two deliberate calls are made here and named so a later reader sees them as decisions rather than accidents. **First:** the check lives inside `apiKeyAuth` itself, not scoped to the events route. `apiKeyAuth` also fronts the public contacts API, which writes contact PII — the literal D-04 wording says "events", but the stated purpose ("nothing accumulates new PII") covers both, and the user chose the fail-closed option at every earlier fork in this phase. **Second:** RESEARCH Open Question 1 (the bounded queue-drain window after soft delete) is resolved as zero tolerance rather than as a documented gap: both ingest processors get the same guard, which is cheap once the API-side pattern exists.

Purpose: PRG-06's ingestion half.
Output: one shared API-side lookup, refusals at both ingress entry points, guards on both ingest workers, and three test files proving each refusal and its live-workspace negative control.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client → events/contacts API (API key) | Key-authenticated but workspace-state-untrusted; the key outlives the workspace's right to accept data |
| anonymous internet → SendGrid webhook route (`:pathToken`) | Fully unauthenticated until the signature check; the pathToken is a guessable-shaped secret and any response difference is an oracle |
| BullMQ queue → ingest processors | Job payloads assert a workspace state that may have changed since enqueue |
