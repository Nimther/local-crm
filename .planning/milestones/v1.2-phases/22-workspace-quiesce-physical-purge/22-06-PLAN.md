<objective>
Give the 30-day retention window a real recovery story and give PRG-05 a real path to guard. An operator-only CLI clears `deletedAt` for a workspace that has not yet been touched destructively, and refuses with a typed error the moment the purge's point of no return has passed. A second CLI prints, on demand, the same eligibility census the report-only tick writes — so an operator can see what is about to be destroyed without waiting for a tick.

D-14's boundary is the design's spine, and it is a check-then-act pair, so the two sides must contend on one lock rather than two independent reads: restore takes the same per-workspace advisory lock the purge takes before stamping `first_destructive_batch_at`. Whichever side gets it first wins; the other refuses. And D-15's exception to "freeze means freeze" lands here rather than in the scheduler: an overdue `scheduled` campaign is flipped to `draft` inside the same transaction that un-deletes the workspace, because relying on the scheduler's own re-check leaves a race between the restore commit and the next tick — and surprise mail is worse than surprise silence.

Purpose: PRG-05 (a restored workspace is refused, not skipped) and PRG-01's operator-visibility half (D-07's on-demand report).
Output: two exported functions, two operator CLIs with npm scripts, and a test suite that races a restore against a purge in both directions.
</objective>
