<objective>
Apply the tracer's proven shape to the two remaining send paths: schedule takes the same locked version precondition, and test-send takes it too and additionally pins the template and sender it verified into the job payload, closing the enqueue-to-dispatch gap that let a save swap the template under a queued test.

Purpose: TMPL-02 is only true when all launch and schedule paths are preconditioned, and TMPL-03's "exactly the template that is confirmed saved" is only provable if the value that reaches SendGrid is captured at the moment the precondition passed. This plan is also where the transient two-implementation state plan 20-02 left behind is retired: once schedule and test-send resolve read-only, the persisting sender resolver has no callers.

Output: schedule and test-send refuse a stale or absent version with the same typed 409/400 as launch; the kind='test' job carries a templateId/fromEmail snapshot; cancel bumps the version; sender resolution has one implementation.
</objective>

## Resolved research questions

- **RESEARCH Open Question 2 (does test-send still need to persist from_email at all): yes, keep persisting it — but only under the lock, and only when it actually changed.** Two independent reasons. (1) Rolling-deploy safety: an old worker draining a new job ignores the snapshot fields entirely and falls back to reading `campaigns.from_email`, so dropping the persist would break test sends for a `fromSenderId`-only campaign that has never launched, during exactly the window the additive-optional payload design exists to protect. (2) `launchIncompleteFields`/`computeIncompleteReason` treat the sender as configured when either `fromSenderId` or `fromEmail` is set, so persisting keeps the current UI semantics unchanged. The write is made conditional (`from_email IS DISTINCT FROM` the resolved address) so the uniform "any write bumps" invariant holds without bumping on a no-op test send.
- **Why the client must refetch after a successful test-send:** the conditional persist above can legitimately bump the version. Without an invalidation the browser keeps the pre-bump value and the marketer's next launch 409s — a client-side re-run of RESEARCH Pitfall #1. The invalidation is safe because a dirty form blocks test-send (plan 20-05), so a refetch cannot clobber unsaved edits.
- **Cancel takes no `expectedVersion`.** D-05 says every mutation bumps; D-06 enumerates only launch/schedule/test-send as requiring the precondition, and CONTEXT.md never lists cancel. Bump, do not gate.
- **Only one producer of `kind='test'` jobs exists.** A repository-wide grep over `apps/` and `packages/` finds the campaigns route as the sole producer; `emailTriggeredJobSchema`'s comment allows a triggered campaign test-send but nothing enqueues one. The snapshot therefore lands on `emailBroadcastJobSchema` only.
