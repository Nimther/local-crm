<objective>
Close ROT-02 completely: prove the previous-secret path on both redemption paths named in SC2, prove the no-token-oracle invariant survives rotation across every response shape named in SC3, and put executable gates under the two properties that are otherwise invisible — exhaustive loop evaluation and the D-05 log line's contents.

Purpose: the tracer in 19-01 proved one path works. ROT-02 is a statement about *all* the paths and about what the response does **not** reveal. The two properties this plan gates — that the loop does not early-exit, and that the log line carries a position and nothing else — are exactly the ones a future refactor would silently break, because both look like harmless optimisations.

Output: a dedicated unit suite for the rotation loop's invariants, and route-level coverage of the remaining redemption paths and response shapes.
</objective>

    - A token verified via the primary produces zero `info` calls.
    - A token verified via a previous secret at position 1 produces exactly one `info` call whose first argument carries the value 1 under the position field, and at position 2 carries 2.
    - Serialising the entire first argument, plus the message string, contains none of the secret values in play, and contains no substring of the token's signature — asserted directly, since this logger deliberately does not route through `packages/redaction`.
    - A token that matches nothing produces zero `info` calls.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `GET /unsubscribe/:token` | An attacker-controllable token reaches the confirm page; the page must not become an oracle for whether a token is valid or which era it came from. |
| public internet → `POST /unsubscribe/:token` | The mutating path; its response is the highest-value oracle surface in the system. |
| process internals → log sink | D-05's line; asserted here to carry a position and nothing else. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-15 | Information Disclosure | POST response distinguishing a retired-secret match from a primary match or a forgery | high | mitigate | A four-way byte-identical assertion across primary-valid, previous-valid, unretained-secret and forged tokens, plus the expired case, all in one test so the shapes are compared against each other rather than against a remembered constant. |
| T-19-16 | Information Disclosure | GET confirm page revealing token validity or era | high | mitigate | Page bodies compared across the three token classes after token-placeholder substitution, and the page asserted non-mutating for a previous-secret-signed token. |
| T-19-17 | Information Disclosure | loop iteration count leaking the matched position | medium | mitigate | HMAC invocation counts asserted equal across primary-match, last-previous-match and no-match, and equal to the candidate count — the deterministic proxy for the timing property, since a wall-clock assertion would flake. |
