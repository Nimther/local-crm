## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

08-11 measured the number and recorded it. This plan builds the two checks that make the number mean something: one that enforces it, and one that stops it from being quietly reduced.

## Artifacts this phase produces

- `scripts/coverage-gate.mjs` exporting `checkCoverageGate(summary, baseline)` plus a CLI
- `scripts/coverage-ratchet.mjs` exporting `checkRatchet(current, base)` plus a CLI
- Root npm scripts `coverage:gate` and `coverage:ratchet`

<objective>
Implement the coverage threshold comparison with the exact boundary and precision semantics SPEC R3 specifies, and the ratchet that makes lowering the threshold a failing check rather than a silent edit.

Purpose: Vitest's built-in `coverage.thresholds` offers neither an unrounded comparison nor any protection against a threshold being reduced (D-18). Both of those are the difference between a gate and a decoration — a threshold anyone can lower in the same commit that broke it is not a gate at all.
Output: two dependency-free checks with their edge cases unit-proven before either is wired into CI.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Coverage report → merge decision | A rounded comparison lets a genuine regression through by presenting it as equal to the threshold |
| Recorded threshold → future diffs | A threshold anyone can lower in the same commit that broke it is a decoration, not a gate |
| Empty coverage report → the gate | A report with a zero denominator means nothing was measured; passing on it is the coverage equivalent of linting zero files |
