## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

Today all five E2E specs run against the dev database and write to it. This plan closes that hole with the same guard the vitest suites use.

## Artifacts this phase produces

- `apps/web/e2e/global-setup.ts` (Playwright `globalSetup`, with a paired teardown)
- npm script `dev:e2e` in `apps/api` and in `apps/web`
- Root npm script `test:e2e`
- Console line emitted by the E2E global setup reporting the resolved connection string

<objective>
Make the Playwright E2E run physically unable to reach the dev database, using the same provisioning and guard code the vitest suites use, and make it announce which connection string it actually used.

Purpose: `apps/web/playwright.config.ts` currently boots `npm run dev -w apps/api` and `npm run dev` with `reuseExistingServer: true`. Those dev scripts load the developer's own config and connect to the dev database, and the reuse flag means that even a correctly-provisioned run silently attaches to an already-running dev stack. Every one of the five E2E specs writes to real dev data today.
Output: an E2E lane that aborts rather than falls back, and that proves which database it touched.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| E2E run → dev database | All five specs write to the dev database today; this is the largest remaining hole in QG-04 |
| Playwright webServer → developer configuration file | `npm run dev -w apps/api` loads the developer's own config, which points at the dev database by definition |
| An already-running dev stack → the E2E run | `reuseExistingServer: true` attaches to whatever is listening, defeating provisioning entirely |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-10-01 | Tampering | E2E specs writing to the dev database | high | mitigate | `apps/web/e2e/global-setup.ts` provisions an ephemeral database and runs `assertTestDatabaseUrl` on the resolved DSN before any browser launches; the run aborts on failure |
| T-08-10-02 | Tampering | Silent attachment to a running dev stack | high | mitigate | `reuseExistingServer: false` on both `webServer` entries, asserted by a source check and by an empirical run with a dev stack already listening |
| T-08-10-03 | Tampering | Dev configuration leaking into the E2E process | high | mitigate | `dev:e2e` scripts carry no `--env-file`; the API's entire environment comes from `webServer.env`, enumerated from `apps/api/src/env.ts`'s boot schema |
| T-08-10-04 | Repudiation | Configuration claimed but not verified | medium | mitigate | The global setup prints the redacted resolved DSN behind a stable marker; the non-blocking CI `e2e` job asserts on that line (wired in 08-18) |
| T-08-10-05 | Information Disclosure | Connection string printed to CI logs | low | mitigate | The printed string is redacted of its password; the credentials involved are the docker-compose dev defaults already public in the repo |
| T-08-10-SC | Tampering | npm/pip/cargo installs | high | mitigate | Only the internal `@mega-crm/test-support` workspace link is added to `apps/web`; no external package enters the tree |
</threat_model>
