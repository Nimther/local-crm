## Phase Goal

Any change to the send pipeline can be proven safe before it ships — CI blocks broken code, tests cannot touch the dev database, and every failure mode the audit names can be reproduced on demand.

This is the fifth and last audit-named failure mode, and it is also the proof that 08-04's Redis durability configuration does what it claims.

<objective>
Restart the Redis container underneath a live queue and prove that jobs enqueued before the restart are still there and still get processed afterwards — then write down the five-scenario checklist that the coverage percentage must never be allowed to stand in for.

Purpose: this scenario is simultaneously QG-06's fifth mode and WRK-12's separate survival check. It is also the only thing that empirically validates 08-04's `appendonly yes` / `appendfsync everysec` choice; without it, that configuration is an assertion about a config file rather than about behavior.
Output: one command that restarts a real container and asserts queue survival, plus the written scenario checklist.
</objective>

  <behavior>
    - `restartContainer("redis")` invokes `docker compose restart redis` and resolves when the command exits 0.
    - It rejects with the captured stderr when the command exits non-zero, so a missing Docker daemon is diagnosable rather than a hang.
    - `waitForHealthy("redis")` polls the container's health status until it reports healthy, and rejects with a clear message after a bounded number of attempts.
    - `waitForHealthy` returns promptly once the container is healthy — it does not wait a fixed duration.
    - Both functions are generic over the service name; neither hardcodes `redis`.
  </behavior>
  <action>
    Write `packages/test-support/src/harness/docker-restart.ts` exporting `restartContainer(service)` and `waitForHealthy(service, options)`. Use the same child-process library `spawn-and-kill.ts` chose in 08-12 — read that file and match it rather than introducing a second mechanism for shelling out.

    `waitForHealthy` must poll the container's actual health status (via `docker compose ps` output or `docker inspect`) rather than sleeping for a fixed duration. A `sleep` here is the anti-pattern RESEARCH.md calls out by name: if the container needs longer than the guess, the test fails intermittently and the fix everyone reaches for is a longer sleep. Polling a real readiness signal converts a timing question into a boolean one. Bound the polling attempts so an unhealthy container produces a clear failure instead of an infinite wait.

    Surface captured stderr on every rejection path. `docker compose restart` failing because the daemon is not running must read as "Docker is not available" and not as an unexplained timeout.

    Keep both functions free of any domain reference — no queue names, no BullMQ, no sends. Export them from `packages/test-support/src/index.ts`.

    Write a unit test asserting: `restartContainer("redis")` resolves against a running compose stack; `waitForHealthy("redis")` resolves after it; and `restartContainer("nosuchservice")` rejects with stderr text naming the unknown service.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Redis container lifecycle → enqueued job data | Without AOF, a restart drops everything since the last RDB snapshot and the queue silently loses work |
| Test queue → production queue names | Restarting Redis under a shared production queue name would interfere with every other test file using it |
| Coverage percentage → evidence of failure-mode coverage | A percentage that stands in for the scenario checklist means the scenarios can rot away while the gate stays green |
