<objective>
Make the two new states visible where a marketer actually looks, and stop the test-send flow from claiming an outcome it never observed.

Purpose: this phase's whole point is that the system stops asserting outcomes it does not know. That is only true end to end if the surfaces a tenant reads reflect it — a send log that silently renders `unknown` as `sent`, or a toast that says "письмо отправлено" when the request timed out, reintroduces the dishonesty one layer up.
Output: `reconciling`/`unknown` in the send-log vocabulary on both sides of the API boundary, a third test-send outcome, and confirmation copy that matches what the system can actually observe.
</objective>

## Flagged assumption — the test-send surface

D-11 says the test-send response contract gains a third outcome shown as "outcome unknown — check the inbox before manually re-sending". The route (`POST /api/workspaces/:slug/campaigns/:id/test-send`) returns `202 { queued: true, to }` immediately and the actual send happens in a BullMQ job, so there is no synchronous response in which an outcome could be reported, and no polling surface exists.

The assumption this plan makes, stated so it can be overruled rather than discovered later: the honest minimal implementation is (a) `processSendJob`'s test branch classifies an ambiguous throw and returns a distinct `unknown` outcome without throwing, so BullMQ does not retry it (D-11: no automatic retry for test sends); (b) that outcome is logged for an operator; and (c) the UI copy is corrected to describe what the system actually knows at 202 — queued, not delivered — and to carry the check-the-inbox-before-re-sending guidance. Building a polling or result-callback surface for test sends is deliberately out of scope; the CONTEXT's Deferred Ideas already place recovery tooling in a later phase.
