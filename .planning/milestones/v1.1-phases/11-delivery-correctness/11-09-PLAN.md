<objective>
Give the reconciler a dead-man's switch: a health row it writes on every tick, and a watchdog in a different process that alerts an operator when ticks stop or when ambiguity is piling up unresolved.

Purpose: the reconciler is now the only component that can move a send out of `reconciling`. If it silently stops — a scheduler that never registered, a Redis loss, a poisoned tick — sends accumulate in an ambiguous state with nothing to notice. Phase 9 already built and proved this exact two-process pattern for partition maintenance; this reuses it rather than inventing a second one.
Output: `send_reconciler_runs` written per tick, a parameter-driven watchdog module, its boot-time wiring in the API process, and tests for the unhealthy-on-missing-data rule and the cross-replica claim.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker process -> API process | Liveness is asserted by one process and judged by another, deliberately, so neither can mask the other's death |
| watchdog -> operator inbox | An outbound email built from database contents, sent with the platform's own SendGrid key |
| API replica <-> API replica | N replicas each independently evaluating the same health row |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-11-09-01 | Repudiation | missing or unreadable health row | high | mitigate | `evaluateReconcilerHealth(null, ...)` returns unhealthy with `missing_health_row`, asserted by test; migration 0050 additionally seeds the singleton at epoch so the claim `UPDATE` always has a row to match |
| T-11-09-02 | Information Disclosure | operator alert body | high | mitigate | Plain text, counts/ages/timestamps/reason-names only; the module imports no tenancy or KMS module; mechanical test asserts the body matches no UUID pattern, no email pattern, and does not contain `Bearer` |
