<objective>
Bound the SendGrid call in time, and make the ambiguity of a bounded-out call explicit and classifiable.

Purpose: `sendTenantMailV3` is a bare `fetch` with no timeout at all — a hung TCP connection pins a worker concurrency slot indefinitely and, worse, can outlive BullMQ's lock so the stalled-checker hands the same job to a second worker while the first is still alive and will eventually attempt its own terminal write. That is the duplicate-send race arriving through the timeout boundary rather than the crash boundary.
Output: `AbortSignal.timeout()` on the provider call, a pure transport-error classifier with fail-closed defaults, explicit `lockDuration` on both send workers, a machine-asserted timing invariant, and bounded retry for provider backoff.
</objective>

## Scope boundary — the `cause` discriminator versus Phase 12's WRK-01

CONTEXT.md defers "`SendJobResult` cause split (`tenant_bucket` vs `provider_backoff`)" to Phase 12. This plan introduces the discriminator field anyway, and the reason is D-10, a locked decision of *this* phase: "HTTP 429 / 5xx → release claim + bounded exponential retry (a deliberate change from today's unbounded `Retry-After`-driven backoff)." Both a tenant token-bucket denial and a provider 429/5xx currently return the same undifferentiated `rate_limited` outcome, so bounding one without a discriminator would also bound the other — turning a tenant's own throughput ceiling into a job failure after five attempts.

What this plan therefore does: introduce the field and use it for exactly the retry-boundedness distinction D-10 requires. What it does **not** do, and leaves entirely to Phase 12's WRK-01: per-tenant fairness, queue-depth-aware backoff, tier-based worker pools, or any other behavior keyed off the cause. CONTEXT.md's own Claude's-Discretion entry asks for the shape to be designed so Phase 12 extends rather than reshapes it, which is what introducing the field now accomplishes. If the intent was that even the discriminator waits for Phase 12, say so and this plan falls back to bounding both paths together — accepting that a throttled tenant's jobs then land in the failed set.

## Trust Boundaries

|----------|-------------|
| worker process -> SendGrid | An outbound call to a third party that may hang, reset, or return an ambiguous status, holding a decrypted tenant API key |
| BullMQ lock -> job processor | The lock renewal timer and the job's own promise are independent; their relative durations decide whether one job can have two live processors |
