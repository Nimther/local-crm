<objective>
Build the production topology D-01 chose: one VPS, everything containerized under docker compose — Postgres, Redis, api, worker, Caddy, plus a one-shot migrate service — promoting the development compose vocabulary rather than inventing a second one. This is where Pitfall 19 (memory limits and `oom_score_adj` protecting Postgres), the server half of DB-13 (Postgres TLS), the connection budget that justified deferring PgBouncer (D-09) and the derived worker stop-grace-period (Pitfall 7) all land as configuration.

Purpose: the deploy script in plan 14-09 orchestrates this file. Everything the script does — pull, migrate, wait on readiness, flip containers — is only correct if the topology underneath it is. And the parts most likely to be wrong are the ones with no local feedback: a memory limit that starves Postgres, a `max_connections` left at its default under eight pools, a stop-grace-period hand-typed once and never updated again.
Output: `docker/docker-compose.prod.yml`, the production Postgres bootstrap and TLS entrypoint, a documented example env file with no secrets in it, a compose-invariant validation gate wired into CI, and a topology runbook.
</objective>

Make the migrate service one-shot by construction. Add a comment saying so, and give the service a profile or equivalent so a plain `up` does not start it at all.

Set the worker's `stop_grace_period` from an interpolated variable whose value the deploy script fills using `node scripts/print-stop-grace-period.mjs`. Never type the number. ARCHITECTURE.md §10 states the container value MUST come from the published constant, and the failure mode of a hand-typed value is invisible: it silently disagrees with the constant after the next change to the SendGrid timeout, and the symptom appears months later as ambiguous sends after a routine deploy.

Give every service an explicit memory limit from the checkpoint's answer, and give `db` a negative `oom_score_adj` while leaving api and worker at their default. Both halves are required and neither works alone — an unset memory limit means a container can exhaust host RAM before the kernel ever compares scores, so the adjustment achieves nothing (Pitfall 19). Comment the chosen numbers with their derivation, not just their values.

Reference images only by SHA-interpolated tag. No `latest`, no branch tag, no `build:` section — production pulls what CI built (D-03), and a `build:` stanza here would let an operator accidentally deploy an unreviewed local tree.

Write `docker/postgres/init-prod-roles.sql`: the production equivalent of the development role bootstrap, producing the same role set with the same grants, idempotent, and reading its passwords from environment variables the entrypoint provides rather than embedding them. Write `docker/postgres/prod-tls-entrypoint.sh` for the server half of DB-13, mirroring the mechanism plan 14-03 established for development: generate a self-signed certificate if absent, set the ownership and permissions Postgres requires of a key file, then exec the image's entrypoint with `ssl=on` and the cert paths. | Boundary | Description |
|----------|-------------|
| internet → Caddy (ports 80/443) | The only host-published surface in production |
| container → container on the compose network | Postgres, Redis and the API are reachable by every service on the network |

| kernel OOM killer → container set | Which process dies under memory pressure is a configuration decision, not chance |
