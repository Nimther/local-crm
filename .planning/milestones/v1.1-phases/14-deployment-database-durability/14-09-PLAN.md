<objective>
Close OPS-02 and OPS-03: one reproducible operator-invoked deploy command (D-04 — "the command is reproducible; the human decides when") and a documented rollback that returns the previous version without manual surgery. The deploy gates on `/readyz`, never on a timer — this is the whole reason the ROADMAP ordered OPS-04/OPS-05 ahead of OPS-02.

Purpose: today there is no way to deploy this platform at all. The two things that make a deploy script either trustworthy or dangerous are its failure ordering (does a failed migration stop it before it replaces anything?) and its worker handling (R-05 chose stop-old-then-start-new because a short queue pause is safe and overlapping incompatible dispatch code is not).
Output: `scripts/deploy.sh` with a dry-run mode, a test asserting its ordering properties, the deploy-and-rollback runbook, and a blocking checkpoint for the first real deploy.
</objective>

  <action>
Write `scripts/deploy.sh` taking a full git SHA as its single required argument, plus `--dry-run` and `--rollback-to`. Enable strict shell error handling at the top — unset-variable and pipeline-failure detection included — because every guarantee in the behavior list depends on the script stopping when a command fails rather than continuing to the next stage.

Validate the argument against a full-length hexadecimal SHA pattern and reject anything else, naming what was rejected. A branch name or `latest` would defeat the immutability that OPS-03's rollback depends on, and the registry would happily serve it.

Order the stages so a failure cannot leave a half-flipped system: read and record the currently deployed SHA first; pull all three images for the target SHA (a pull failure must abort before anything is replaced — a partially pulled deploy is the worst state to be interrupted in); resolve the worker stop-grace-period by invoking the print script and export it for Compose to interpolate; run the migrate step as an explicit `docker compose run --rm` invocation and check its exit code, per RESEARCH.md Pitfall C — never express this ordering with a completion-condition `depends_on`, which Compose has been documented to re-trigger on a later `up`; then bring up `web` and `api`; then wait on the API's `/readyz` until it returns 200 or the bounded timeout elapses; then replace the worker.

Never wait on a sleep. The wait loop polls `/readyz` with a short interval and a bounded overall timeout, and on timeout it exits non-zero naming the service, the timeout and the last response it saw. A fixed sleep is precisely the failure mode the ROADMAP ordered OPS-04/OPS-05 ahead of OPS-02 to eliminate; if the loop ever needs longer, the timeout is raised explicitly and visibly.

Replace the worker stop-old-then-start-new (R-05): stop the old container and confirm it is actually gone before starting the new one. A short queue pause is safe — jobs wait in Redis — while two workers running incompatible dispatch code is not, which is the whole reason R-05 chose backward-compatible payloads plus this sequencing rather than a rolling restart. After starting the new worker, wait for its container health status to become healthy rather than opening an HTTP connection: plan 14-04 recorded that the worker's health port is loopback-bound and deliberately unpublished, so the container's own healthcheck is the observation channel. Derive the worker's wait timeout from the stop-grace-period plus a stated margin, not from a round number.

Write the previous SHA to a record file on the host before replacing anything, and print the exact rollback command on both success and failure paths. An operator reading a failed deploy's output should not have to reconstruct what was running before.

Make `--rollback-to <sha>` run the same sequence for an older SHA, and print a warning naming the migration-tier question before it starts: a rollback across a forward-only migration is not a redeploy, and the runbook is where that decision is made. Do not attempt to determine the tier inside the script — it does not have the migration list for the target SHA — but do make the warning unmissable.

Give `--dry-run` a machine-readable output: one command per line, in execution order, with no side effects. This is what makes the ordering testable, and it is also what an operator reads before their first real deploy.

Write `scripts/__tests__/deploy-script.test.mjs` driving the dry run and asserting every ordering property in the behavior list by inspecting the printed sequence, plus the argument-validation rejections. For the abort-on-migrate-failure property, run the script with a stubbed compose command that exits non-zero for the migrate invocation and assert no application container command was attempted — inject the stub through PATH so the script itself needs no test-only branch.

Register `test:deploy-script` in the root `package.json`. Do not add a CI step for it: `scripts`' suite already runs inside the aggregate `test` job, and another plan owns the workflow file in a neighbouring wave.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → production host | The deploy runs with full control over the running system |
