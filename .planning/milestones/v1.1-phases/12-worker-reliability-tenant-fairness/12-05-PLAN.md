<objective>
Prove tenant fairness by measurement rather than by code review (WRK-03) and back `DEFAULT_TENANT_RPS` with both a sustained-throughput run and documented provider guidance (WRK-04).

Purpose: the phase's first success criterion is explicitly "proven by a two-tenant load test, not by code review". D-04 puts a scaled-down deterministic scenario into the existing failure-injection CI job so a fairness regression is caught on every pull request, plus an on-demand full-target-volume variant. D-05 makes "measurably unaffected" a relative-to-baseline assertion — tenant B against its own solo baseline in the same run — because absolute throughput floors are machine-dependent and rot in CI. D-06 makes `DEFAULT_TENANT_RPS` answerable from both halves: the platform's own sustained throughput, and the provider's published guidance with the bring-your-own caveat.
Output: two scenario files, a versioned constants module, the CI wiring and the documented rationale on the constant.
</objective>

3. **No provider traffic.** Assert the fake seam recorded every dispatch and that no real transport was constructed, so the scenario cannot silently start hitting SendGrid.

Measure throughput by counting terminal ledger rows over a wall-clock window rather than by timing individual jobs, and give each phase its own fresh queue state so the baseline and the contended run are comparable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test harness → SendGrid | A scenario that accidentally constructs a real transport would send live mail from CI |
| tenant A workload → tenant B measurements | The fairness claim is only meaningful if the two tenants are genuinely isolated in the fixture |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-05-01 | Spoofing | scenario reaching the real provider | high | mitigate | Both variants inject the fake `ProcessSendJobDeps.sendMail` seam, and the CI scenario asserts no real transport was constructed, so no API key or live send can escape from CI. |
| T-12-05-02 | Denial of Service | a vacuously passing fairness assertion | high | mitigate | The scenario asserts tenant A actually received tenant-scoped deferrals during the contended phase, so a run where A never saturated fails instead of certifying fairness it did not test. |
| T-12-05-03 | Repudiation | an unsourced RPS default | medium | mitigate | The constant's rationale records the provider figure, its source URL and its retrieval date alongside the sustained-throughput scenario path, so the number is auditable rather than folklore. |
| T-12-05-04 | Information Disclosure | tenant identifiers in scenario output | low | accept | Scenario fixtures use generated workspace ids only; no production tenant data enters CI. |
</threat_model>
