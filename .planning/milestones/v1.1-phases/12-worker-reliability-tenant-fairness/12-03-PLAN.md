<objective>
Build the per-tenant-per-lane concurrency semaphore (WRK-02, D-01/D-02/D-03) as a TTL-leased Redis primitive, test-first.

Purpose: a correct RPS token bucket still lets one tenant's large backlog occupy worker slots ahead of another tenant's small batch — that is the gap WRK-02 names. This plan builds and proves the primitive in isolation; 12-04 wires it into the dispatch path.
Output: `tenant-lane-semaphore.ts` plus a test suite covering the cap boundary, lease expiry, both isolation axes, env-override parsing and the fail-closed Redis-error path.

  <action>
Implement `apps/worker/src/queues/tenant-lane-semaphore.ts` to make the RED suite pass, using a **sorted-set** semaphore with per-holder lease expiry, not a plain counter. One `EVAL` script performs, atomically: purge holders whose score is older than `now - leaseTtlMs` via `ZREMRANGEBYSCORE`; read the survivor count via `ZCARD`; if it is below the cap, `ZADD` the caller's token at score `now` and `PEXPIRE` the key by the lease TTL, returning success; otherwise read the oldest survivor's score and return rejection together with that holder's remaining lease. Release is a single `ZREM` of the caller's token, which is idempotent by construction and therefore safe to call unconditionally.

The sorted set is required rather than an increment/decrement counter with a key-wide expiry: a key-wide expiry is refreshed by every new acquire, so under sustained traffic a crashed holder's increment would persist indefinitely and the slot would leak — exactly what D-01's "TTL-leased so a crashed worker cannot leak a slot forever" forbids. Per-holder scores are what make expiry per holder. This is the algorithm `redis-semaphore` implements; it is reproduced here rather than taken as a dependency, per the decision recorded in `12-01-PLAN.md`.

Key shape is `tenant-lane-sem:{workspaceId}:{lane}` — the tenant and the lane together (D-02); a tenant-only key would recreate, inside one tenant, the starvation the two-queue split exists to prevent. Tokens are generated per acquisition with `randomUUID` from `node:crypto` so two concurrent holders in the same process can never collide.

Export `TENANT_LANE_CONCURRENCY_DEFAULTS` as a versioned constant (D-03, Phase 9 D-12 convention) with a rationale comment: broadcast defaults to 3 against that lane's worker concurrency of 5, triggered defaults to 12 against its concurrency of 20 — roughly 60% per lane, leaving a real share of every lane reachable by other tenants while a single-tenant platform still gets most of its throughput. `resolveTenantLaneCap(lane)` reads `TENANT_LANE_CONCURRENCY_BROADCAST` / `TENANT_LANE_CONCURRENCY_TRIGGERED`, accepts only a positive integer, and otherwise returns the default after warning through `scrubbedConsole` — a malformed override must never widen or void the cap.

Derive the lease as `SEND_SLOT_LEASE_TTL_MS = SENDGRID_TIMEOUT_MS + CLAIM_TX_MARGIN_MS + RECORD_TX_MARGIN_MS + SEND_SLOT_LEASE_MARGIN_MS` with `SEND_SLOT_LEASE_MARGIN_MS` at 10000, computed rather than hand-typed so a change to any input propagates. Document in its comment that this is the dispatch worst case plus margin — deliberately not derived from `SEND_LOCK_DURATION_MS`, because the two bound different things (redelivery risk versus a Redis slot leak) — and that the resulting value stays below `SEND_LOCK_DURATION_MS` so a leaked slot expires before BullMQ would consider the job stalled. Assert that ordering in the test suite.

Let a genuine Redis error propagate; never map it to a rejection result. Mirror `consumeTenantToken`'s comment on the same point: swallowing the error would defeat the cap this module exists to enforce, and would dispatch uncapped during a Redis outage.

Commit as `feat(12-03): implement the tenant+lane concurrency semaphore`. If an obvious cleanup follows, make it a separate `refactor(12-03): …` commit with the suite still green.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker process → Redis (semaphore keys) | The cap is only as real as the shared Redis state; unavailability must not silently disable it |
| tenant A's slot holders → tenant B's available slots | Cross-tenant fairness boundary this module exists to enforce |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-03-01 | Denial of Service | leaked semaphore slot after a worker crash | high | mitigate | Per-holder lease scores plus `ZREMRANGEBYSCORE` purge on every acquire mean an un-released holder stops counting after `SEND_SLOT_LEASE_TTL_MS`; a counter with a key-wide expiry would leak indefinitely under sustained traffic. Asserted by the lease-expiry test case. |
| T-12-03-02 | Denial of Service | one tenant saturating a lane | high | mitigate | The cap is keyed on tenant and lane, so a tenant's holders can never exceed its configured share and can never consume the other lane's slots (D-02). Asserted by both isolation test cases. |
| T-12-03-03 | Tampering | malformed lane-cap environment override | medium | mitigate | `resolveTenantLaneCap` accepts only a positive integer and otherwise falls back to the versioned default with a warning, so a typo cannot silently void or widen the cap. |
| T-12-03-04 | Spoofing | release of a slot the caller does not hold | low | mitigate | Release removes the caller's own randomly generated token only; an unheld token is a no-op and cannot free another holder's slot. |
</threat_model>
