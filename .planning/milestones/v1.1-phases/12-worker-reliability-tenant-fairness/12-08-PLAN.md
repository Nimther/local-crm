<objective>
Close every queue handle on shutdown, put every worker behind the shared error listener, and finish migrating the remaining repeatable ticks to the scheduler-upsert form — with the multi-instance and drain-budget assumptions written down (WRK-07, WRK-08, WRK-13).

Purpose: this plan closes the four concrete gaps D-11 enumerated. Shutdown today closes only the worker array. Six factories construct at least one queue inside themselves that never reaches that array, and several long-lived producer singletons are never closed at all, so the process holds Redis connections open past shutdown. Three tick registrations still use the older repeat-config form with no guard and no close, which both leaks a connection and — as this repo has already experienced once — turns a transient Redis hiccup at boot into an unhandled rejection that terminates every worker in the process. And the container stop-grace period is an unexamined default well below the worst-case in-flight dispatch, which turns a routine deploy into exactly the ambiguous-outcome scenario the previous phase's reconciler exists to resolve.
Output: a tracked-queue registry, a complete shutdown path, listeners on every worker wired to the dead-letter writer, three migrated registrations, and the derived drain budget plus multi-instance constraint documented.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container runtime signal → worker process | A grace period shorter than the worst-case in-flight dispatch converts a deploy into a data-ambiguity event |
| worker process → Redis connections | Handles never closed keep connections open past shutdown |
| operator expectation → documented guarantees | Overclaimed multi-instance safety would licence an unsafe deployment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-08-01 | Denial of Service | leaked Redis connections after shutdown | high | mitigate | Every long-lived handle registers with the tracked-queue registry and shutdown closes all of them after the workers, asserted by the graceful-shutdown test's zero-open-handles check. |
| T-12-08-02 | Denial of Service | registration failure crashing the process | high | mitigate | All three migrated registrations run inside a guard that logs and swallows, matching the two existing precedents; the rejecting-registration test asserts nothing escapes. |
| T-12-08-03 | Repudiation | silent worker failures | high | mitigate | Both listener kinds are attached across the exhaustive worker registry and terminal failures reach the durable dead-letter record; the test iterates the whole registry rather than a subset. |
| T-12-08-04 | Denial of Service | duplicate tick execution under a multi-instance deployment | medium | accept | Execution exclusivity is out of scope for this milestone. Accepted with the constraint documented explicitly in the architecture notes, including what a future multi-instance move would have to add. Recorded as flagged assumption A-1. |
| T-12-08-05 | Tampering | in-flight job killed mid-dispatch by a short grace period | high | mitigate | The drain budget is derived from the provider timeout plus both transaction margins plus an explicit safety margin and published for the deployment phase to apply as the container stop-grace period. |
</threat_model>
