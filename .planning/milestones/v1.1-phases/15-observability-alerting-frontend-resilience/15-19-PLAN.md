<objective>
Close verification gap **G-15-1**, dispatch half: OPS-11 names four correlation identifiers (`request_id`, `tenant_id`, `job_id`, `send_id`) and only three of them actually flow. `CorrelationStore.sendId` is declared in `packages/tenant-context/src/index.ts`, both Pino loggers' `mixin()` would stamp it, `apps/api`/`apps/worker` Sentry event processors would tag it — but no production call site ever writes it. An operator cannot query Loki by `sendId` today.

Root cause, verified by reading the source (no guessing needed): `apps/worker/src/queues/send-dispatch.ts` threads `sendId` extensively as a plain domain value — function return payloads, DB query parameters, SendGrid `custom_args` — and never once through `withCorrelation`. It also emits **zero** Pino lines: its only logging is two `scrubbedConsole` sites. So closing this gap needs BOTH halves — bind the field, and emit a line inside the binding. Either half alone leaves `send_id` exactly as absent from stdout as it is today, while making a grep-level check look green.

Purpose: make D-07's stated contract ("the ALS extension carries `request_id`/`job_id`/`send_id` through HTTP → queue → worker into every log line") literally true on the send path, so success criterion 1's "follow a single send using one correlation identifier" holds for the identifier the requirement names for a *send* specifically.

Output: three `withCorrelation({ sendId })` scopes in `send-dispatch.ts`, four Pino call sites inside them, an executable proof that a captured worker log line carries `sendId` together with `requestId`/`jobId`, and the SPECIFICATION.md §7 entry filed in the same change.

**Scope boundary.** This plan owns the SEND-DISPATCH side only. `apps/worker/src/queues/webhook-events.worker.ts`'s per-event binding is plan 15-20 (it touches a different file and needs a different fixture shape); the two stale docs are plan 15-21. All three plans edit SPECIFICATION.md, which is why they run in strict wave order rather than in parallel.
