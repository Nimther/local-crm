<objective>
The OPS-09 gate: prove no secret and no PII can reach Sentry, before any Sentry SDK exists in this codebase.

Purpose: this is the phase's highest-priority finding (Pitfall 18). Sentry has no retroactive redaction — the only remedy for a leaked field is deleting the project's entire event history. The control is a `beforeSend` hook that routes the whole event body through `packages/redaction`'s depth-unbounded `scrub()`, tested against the two representative payloads the roadmap names, and wired as a blocking CI step before any `init` call exists anywhere.
Output: `sentryBeforeSend`, its fixture test, and a named blocking CI step.
</objective>

  <behavior>
    - Given an event whose exception message embeds a provider-key-shaped string, the returned event's message no longer contains it.
    - Given an event with a contact email under `contexts`, the returned event no longer contains that email.
    - Given an event with a five-level-deep freeform object under `extra`, secret-shaped and PII-shaped leaves are censored at every level.
    - Given an event with nothing to scrub, an equivalent event is returned (never undefined, never null).
    - Given an event containing arrays of objects, elements inside the arrays are scrubbed too.
    - The function is pure with respect to its input: repeated calls on the same input produce the same output.
  </behavior>
  <action>
    Create `packages/redaction/src/sentry-scrub.ts` exporting `sentryBeforeSend`, matching the Sentry SDK's `beforeSend` signature (event plus hint, returning the event or null) so it can be assigned directly to both `beforeSend` and `beforeSendTransaction` at all three SDK initialization sites. Type the event parameter from `@sentry/node`'s exported `ErrorEvent`/`EventHint` types — imported as types only, from the devDependency plan 15-01 added, so this package gains no runtime dependency on any Sentry package.
    The implementation delegates the entire event body to the existing `scrub()`. Do not re-implement rules here, do not add a Sentry-specific rule list, and do not rely on Sentry's own built-in data scrubber — it covers a fixed list of common patterns and does not know this system's secret shapes or that a contact email is PII.
    If `scrub()` turns out not to walk some part of the event body (for example a non-plain-object class instance the SDK attaches), fix that in `scrub()` itself rather than adding a parallel walker here — one walker, one set of rules, per SEC-13.
