</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>How does the DEFAULT-partition relocation path obtain the cross-workspace row visibility that PostgreSQL's automatic foreign-key re-validation needs when a NON-EMPTY child partition is attached, once the marker-GUC policy that currently supplies it is deleted?</decision>
  <context>
Migration 0039 (Phase 9, deviation 09-04) added a SELECT-only marker-gated policy on `contacts` and `sends` because attaching a non-empty child triggers PostgreSQL's own re-validation of the inherited foreign keys `events.contact_id -> contacts(id)` and `send_events.send_id -> sends(id)`, and both referenced tables carry FORCE ROW LEVEL SECURITY. Without visible rows the ATTACH fails with a spurious foreign-key violation.

Unlike the other five consumers, this one cannot simply move to `mega_crm_scan`: `ALTER TABLE ... ATTACH PARTITION` requires ownership of the parent table, and the scan role owns no tables — an acceptance criterion of this very phase (SPEC R2). Granting it ownership, or granting it membership in the owning role, would defeat the boundary the phase exists to build.

This decision is also a precondition for plan 10-07: after the fail-closed unification, an app-role connection that has never set the tenant context throws rather than returning zero rows, so any path that today depends on being tenant-context-free must be resolved before that migration lands.

RESEARCH.md did not resolve this — it treated the partition consumer as a read like the other four. The three viable options below were derived at plan time from the ownership constraint.
  </context>
  <options>
    <option id="option-a">
      <name>Attach empty, then move rows through the ordinary tenant-scoped path</name>
      <pros>Removes the sixth touchpoint entirely rather than migrating it — no cross-workspace visibility is needed at ATTACH time because the child is always empty when attached. Every row movement re-enters `workspace_isolation` under a real tenant context, which is the discipline the whole codebase already states. No new role, no new credential, no residual policy on `contacts`/`sends` for this purpose.</pros>
      <cons>Changes the operator procedure Phase 9 UAT'd: relocation becomes per-workspace batched INSERT-then-DELETE into an already-attached partition instead of a bulk build-then-attach. Slower for a large backlog and needs its own idempotency/resume story, which the existing batching with row-level skip-locking partly but not wholly provides.</cons>
    </option>
    <option id="option-b">
      <name>Operator-only elevated DSN for the relocation CLI's attach step</name>
      <pros>Keeps Phase 9's procedure and its UAT intact. The relocation tool is already operator-invoked and already builds its own dedicated pool, so an elevated DSN is a natural fit and is held by no long-running service — neither the API nor the worker gains anything.</pros>
      <cons>Introduces a credential capable of bypassing row-level security, which Pitfall 9 warns against on principle. The bypass is real even though its holder is a human-invoked CLI, and it must be documented and kept out of every service environment.</cons>
    </option>
    <option id="option-c">
      <name>Keep one marker-gated policy on contacts and sends for this path only</name>
      <pros>Zero change to Phase 9's code or procedure; smallest diff.</pros>
      <cons>Contradicts SPEC R2 directly — the marker pattern is to be deleted, policies and code. Any code holding the tenant pool could set the marker and read every tenant's contacts and sends, which is the exact vulnerability SEC-01/SEC-02 exist to close. Listed so the tradeoff is explicit, not as a recommendation.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>
