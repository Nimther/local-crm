<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API-key holder → integration routes | A credential issued to a tenant's integration; its capability breadth is what scopes bound |
| authentication hook → authorization guard | Ordering matters: an authorization check that runs first would reveal key validity through response shape |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-10-01 | Elevation of Privilege | scopes stored but never checked | high | mitigate | Per-route `requireApiKeyScope` guard on every API-key route, with a route-enumeration test that fails when a new route is added without one |
| T-10-10-02 | Elevation of Privilege | empty scope list treated as unrestricted | high | mitigate | Set-membership check with no empty-list special case; an explicit test per route |
| T-10-10-03 | Information Disclosure | 403 body enumerating the scope vocabulary | medium | mitigate | One fixed 403 body naming no scope; test asserts byte-identical bodies across two different scoped routes |
| T-10-10-04 | Denial of Service | existing tenant integrations breaking on enforcement day | high | mitigate | Backfill and enforcement ship in the same migration-plus-code change, per D-07 |
| T-10-10-05 | Spoofing | authorization running before authentication | medium | mitigate | The guard reads `request.apiKeyScopes`, which only the authentication hook sets; a test pins that an invalid key gets 401 rather than 403 |
| T-10-10-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager installs in this plan (RESEARCH.md § Package Legitimacy Audit) |
</threat_model>
