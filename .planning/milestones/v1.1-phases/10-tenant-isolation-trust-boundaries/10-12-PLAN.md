<objective>
Move the API rate limiter onto a Redis-backed store shared across instances, give the webhook endpoint its own independent bucket, and prove both properties with an in-process two-instance test.

Purpose: SEC-11 and SEC-08. The limiter is per-process today, so a second replica silently doubles every configured limit; and the webhook receiver currently shares whatever bucket its route falls into, so a flood on one surface can consume the other's allowance. Multi-replica deployment stays out of this milestone — correctness is proven in-process by running two server instances against one Redis.
Output: a Redis-backed limiter with a loud fail-open, an independent webhook bucket, and the two-instance plus Redis-down tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any HTTP client → rate-limited routes | Brute-force and abuse surface; the limit is only real if it is shared across whatever instances serve the traffic |
| API instances → Redis | The coordination point; its absence must degrade visibly rather than silently |
| webhook surface ↔ session surface | Two independently-reachable surfaces that must not consume each other's allowance |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-12-01 | Elevation of Privilege | per-process limiter multiplying limits by replica count | high | mitigate | Redis-backed shared store; two-instance test asserts the exact request count at which the first 429 appears |
| T-10-12-02 | Denial of Service | webhook flood consuming the invite/API-key allowance | medium | mitigate | Independent route-level bucket for the webhook endpoint; isolation asserted in both directions |
| T-10-12-03 | Denial of Service | limiter store outage taking the API down | medium | accept | Deliberate fail-open: availability is preferred over throttling during a store outage, and the condition is logged so it cannot go unnoticed |
| T-10-12-04 | Repudiation | silent loss of limiting | high | mitigate | An error listener on the limiter's client logs through the structured logger; the Redis-down test asserts the entry is emitted |
| T-10-12-05 | Tampering | limiter keys colliding with queue keys in shared Redis | medium | mitigate | Explicit key namespace on the limiter registration |
| T-10-12-06 | Denial of Service | limiter client holding requests open during a slow store | medium | mitigate | Short connect timeout and low retry ceiling on the limiter's client, distinct from the queue client's settings |
| T-10-12-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager installs — both the rate-limit plugin and the Redis client are already installed dependencies of apps/api (RESEARCH.md § Standard Stack) |
</threat_model>
