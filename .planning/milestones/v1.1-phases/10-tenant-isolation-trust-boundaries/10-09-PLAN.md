<objective>
Put the Better Auth tables behind a real database boundary — a dedicated `mega_crm_auth` login role that owns exclusive access to the secret-bearing tables — and refuse to boot production with a weak `BETTER_AUTH_SECRET`.

Purpose: SEC-05 and SEC-12. Today all seven Better Auth tables sit behind no boundary at all: Better Auth rides the same non-tenant Drizzle pool as the workspace-slug lookups, connecting as the same role that serves every tenant query. Pitfall 12 makes the naive alternative explicit — copy-pasted RLS on these tables breaks login platform-wide with no SQL error, because Better Auth sets no session variable and `organization` has no workspace column to key on.
Output: migration 0045's grant partitioning, an auth-role Drizzle client wired into `drizzleAdapter`, the production secret floor, the SEC-05 ADR, and an auth-flow regression suite.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Confirm the grant matrix for the seven Better Auth tables before the revocations ship, since they are forward-only.</decision>
  <context>
CONTEXT D-04 locks the mechanism (dedicated `mega_crm_auth` login role plus grant partitioning) and rates it one-way: revocations ship as forward-only migrations per DB-07's rollback model, and the acceptance gate is the auth-flow end-to-end suite. What is NOT locked is the per-table matrix — D-05 leaves it to be derived from live query sites, and RESEARCH.md Assumption A2 flags that its own audit found read sites but did not exhaustively cover write sites.

The plan-time audit of `apps/api/src` found these direct (non-Better-Auth-API) query sites against the seven tables:
  - `organization`: read in `workspace-lookup.ts`, `workspaces.ts` (slug uniqueness), `invites.ts`; written in `workspaces.ts` (soft-delete sets `deletedAt`)
  - `member`: read in `members.ts`
  - `invitation`: read in `invites.ts` (three sites)
  - `user`: read in `invites.ts` (register-from-invite)
  - `session`, `account`, `verification`: no direct query site anywhere outside Better Auth itself

Proposed matrix: `mega_crm_auth` gets full data-manipulation privileges on all seven. `mega_crm_app` keeps SELECT on `organization`, `member`, `invitation`, `user`, plus UPDATE on `organization`; everything else is revoked from it, including all privileges on `session`, `account` and `verification`.

One property to acknowledge rather than discover later: `mega_crm_app` owns these tables, so it retains the ability to grant privileges back to itself. The revocation is a real boundary against an application bug or an injected query, not against an attacker who already controls a session as the owning role. Confirm this is the intended strength, or say so now if table ownership should move as well — that is a materially larger migration and is not in this plan's scope.
  </context>
  <options>
    <option id="option-a">
      <name>Ship the proposed matrix as stated</name>
      <pros>Matches D-04/D-05 exactly; every retained privilege is backed by a named live query site; the auth-flow suite gates it.</pros>
      <cons>Owner-can-re-grant caveat stands; a write site the audit missed would surface as a failing route rather than a silent error, but only once its test runs.</cons>
    </option>
    <option id="option-b">
      <name>Ship the matrix but keep `mega_crm_app`'s privileges on `verification` as well</name>
      <pros>Lower risk if any email-verification or password-reset path turns out to touch that table outside Better Auth's server API.</pros>
      <cons>Weakens the boundary on a secret-bearing table for a case the audit found no evidence of; the auth-flow suite would have caught it anyway.</cons>
    </option>
    <option id="option-c">
      <name>Move table ownership of the three secret-bearing tables to `mega_crm_auth`</name>
      <pros>Closes the owner-can-re-grant caveat; the boundary holds even against the app role itself.</pros>
      <cons>Migrations apply as `mega_crm_app`, which would then be unable to alter those three tables — every future Better Auth schema change needs a privileged out-of-band step, and the alternative (granting membership) reintroduces exactly the latent-privilege problem D-01 rejected for the scan role.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application code → Better Auth secret tables | Session tokens, password material and verification tokens; the highest-value rows in the database after tenant provider keys |
| API process → Postgres (auth pool) | A second credential in the same process; its blast radius is the auth tables only |
| operator config → `BETTER_AUTH_SECRET` | A weak value silently weakens every session in production |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-09-01 | Information Disclosure | `session` / `account` / `verification` readable by every tenant query path | high | mitigate | All privileges revoked from `mega_crm_app`; catalog assertions across all four verbs, plus a runtime permission-error test |
| T-10-09-02 | Spoofing | session forgery from a weak signing secret | high | mitigate | 32-character production floor enforced at boot with a descriptive, actionable message |
| T-10-09-03 | Denial of Service | naive row-level security silently breaking login | high | mitigate | RLS explicitly not used on auth tables; the mechanism is grants, and signup/login/invite-accept run against the real database as the acceptance gate |
| T-10-09-04 | Elevation of Privilege | over-broad auth-role grants | medium | accept | The auth role needs full data manipulation on all seven tables for Better Auth's adapter; it is scoped to those seven and holds nothing on any tenant table |
| T-10-09-05 | Elevation of Privilege | owner re-granting itself the revoked privileges | medium | accept | Acknowledged at the checkpoint; closing it requires moving table ownership, which would break the migration path. Documented in the ADR rather than left implicit |
| T-10-09-06 | Denial of Service | a missed write site breaking a route after revocation | medium | mitigate | Matrix derived from an enumerated audit of live query sites, confirmed at the checkpoint; the full API and e2e suites are the detection net |
| T-10-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager installs in this plan (RESEARCH.md § Package Legitimacy Audit) |
</threat_model>
