<objective>
Stop persisting a sibling workspace's raw event payloads into the receiving workspace's `send_events` when several workspaces share one BYO SendGrid key, by resolving each candidate `send_id`'s true owner through the scan role and dropping the ones that do not match.

Purpose: SEC-09, and the Phase 5 review finding WR-01 that has been carried in PROJECT.md since. Under RLS this cannot be built with tenant-scoped queries alone: from inside the receiving workspace's transaction, "this send_id belongs to a sibling" and "this send_id does not exist" both resolve to zero rows, which is exactly the existing D-15 orphan case the worker already handles differently.
Output: a per-event ownership resolution step, a counted and payload-free drop signal, and a mixed-batch test.
</objective>

  <action>
Insert one ownership-resolution step into `processWebhookEventBatch`, before the existing `withTenant(...)` block rather than inside it — the scan runs under a different role on a different pool and must not be nested inside the tenant transaction.

After `candidateSendIds` is computed, and only when it is non-empty, call `withCrossWorkspaceScan` with a query selecting `id, workspace_id` from `sends` for those ids. The SELECT list is exactly those two columns: this is what makes the payload-free prohibition true by construction rather than by review discipline, and the scan role's grant is SELECT-only on the whole table, so the column restriction has to come from the query. Add a comment saying so, naming the prohibition.

Partition the results three ways:
  - id resolves to the receiving workspace → unchanged, flows into the existing liveness check and insert path;
  - id resolves to a different workspace → the event rows carrying that id are dropped from `rows` entirely before the insert, and each drop is signalled;
  - id resolves to nothing → unchanged, keeps the existing D-15 orphan behaviour (stored with a null `send_id`, side effects skipped).

Drop granularity is per event, not per batch: filter the extracted `rows` array, never return early or throw. Recompute `candidateSendIds` from the surviving rows so the tenant-scoped liveness query does not carry ids that were just dropped.

For the signal, follow the worker's existing observability surface (`console` today; plan 10-13's shared scrubbing wraps it later, and Phase 15 replaces it with structured logging). Emit one entry per dropped event with a stable event name such as `webhook.sibling_workspace_event_dropped`, and a payload of exactly: receiving workspace id, owning workspace id, and the count of events dropped for that owner in this batch. Do not include the `send_id`, the event type, the payload, or any contact identifier — a `send_id` is a sibling workspace's identifier and belongs in the same excluded set as its payload.

Update `processWebhookEventBatch`'s doc comment to describe the new step and why the ownership fact cannot come from inside the tenant transaction.

Write `apps/worker/src/queues/__tests__/webhook-events-sibling-drop.test.ts` covering all six behaviors, modelled on `webhook-events-attribution.test.ts`'s fixture. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SendGrid delivery → webhook endpoint | One BYO key can back several workspaces, so a delivery can carry another workspace's events |
| worker scan pool → `sends` across workspaces | The ownership fact crosses the tenant boundary; the read must be minimal |
| drop path → logs/metrics | A naive "log what we dropped" leaks exactly the content the drop exists to protect |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-08-01 | Information Disclosure | sibling payloads persisted into the receiving workspace's `send_events` | high | mitigate | Per-event ownership resolution drops non-matching events before the insert; mixed-batch test asserts absence |
| T-10-08-02 | Information Disclosure | drop-path log carrying sibling content | high | mitigate | Prohibition P1: the signal carries three scalar fields; the test negative-matches a seeded email, a seeded payload marker, and the send id |
| T-10-08-03 | Denial of Service | one sibling event failing the whole delivery | medium | mitigate | Filtering is per event with no early return or throw; a test asserts the batch still inserts and applies side effects |
| T-10-08-04 | Information Disclosure | over-broad cross-workspace SELECT | medium | mitigate | Two-column SELECT list, backed by a SELECT-only grant; RESEARCH.md Assumption A3 is the recorded reason this is checked at the query rather than the policy |
| T-10-08-05 | Spoofing | forged `send_id` naming a sibling's send | medium | mitigate | The signature check upstream already establishes the delivery's authenticity; a forged id now resolves to a sibling and is dropped rather than persisted |
| T-10-08-06 | Tampering | orphan behaviour silently changing | medium | mitigate | Test 5 pins the existing D-15 orphan path; the four existing webhook-events suites must pass unmodified |
| T-10-08-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager installs in this plan (RESEARCH.md § Package Legitimacy Audit) |
</threat_model>
