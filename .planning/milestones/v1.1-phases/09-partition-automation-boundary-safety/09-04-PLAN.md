<objective>
Give the operator a documented, tested way to empty a DEFAULT partition without taking the
live ingestion table offline — and cover the case where the automation ran late and DEFAULT
already holds rows for the new month.

Purpose: the DEFAULT partition is a correctness catch-all, but rows sitting in it are a
permanent tax: every future `ATTACH PARTITION` against a non-empty DEFAULT pays a full scan
under an `ACCESS EXCLUSIVE` lock. Postgres has no primitive for moving a row between
partitions, so this must be a deliberate batched procedure. D-08 requires it to be an
executable script plus a runbook, and requires the criterion-3 automated test to run that
exact script rather than a parallel reimplementation. D-09 requires it to handle every month
actually present in the data, including the provider-supplied timestamps that will not be
bounded until Phase 13 / CMP-05.

Output: `relocate-default.ts` with the shared callable core, a thin CLI wrapper and npm
scripts, the operator runbook, and two test suites — one for the relocation itself, one for
the late-automation boundary case.
</objective>

<flagged_assumptions>
**DB-03 (unclassified, unresolved)** — the spec-less edge probe produced no edge category
for "a procedure exists to move data out of DEFAULT without a long lock". Planner
assumptions, recorded rather than dropped:

- "Without a long lock" is treated as: no statement in the procedure holds `ACCESS
  EXCLUSIVE` on a parent table or on a DEFAULT partition for longer than one bounded batch
  or one metadata-only DDL statement. This is asserted structurally (batch size bound,
  one transaction per batch, CHECK-constraint-first attach) rather than by measuring wall
  clock lock duration, which would be a flaky assertion. If a reviewer requires a measured
  lock-duration bound, it is unplanned.
- Concurrency during a relocation run is not covered: the procedure claims batches with
  `FOR UPDATE SKIP LOCKED`, so a concurrent writer inserting into DEFAULT for a month the
  run has already finished would leave rows behind. The runbook records this and the
  guidance is to re-run until both DEFAULT counts reach zero. A single-pass guarantee under
  concurrent ingestion is not planned.
- The unbounded-partition-count case is accepted, not solved — see threat T-09-18.
</flagged_assumptions>

Implement `relocateMonth(client, table, monthStart, monthEnd)`. Create the destination as a freestanding table with `CREATE TABLE IF NOT EXISTS <child> (LIKE <parent> INCLUDING ALL)` so it carries the parent's composite primary key, unique constraints and indexes. Then loop: per iteration open a transaction, run one statement that claims a bounded batch and moves it — a common table expression whose `DELETE FROM <table>_default WHERE ctid IN (SELECT ctid FROM <table>_default WHERE <key> >= $1 AND <key> < $2 LIMIT $3 FOR UPDATE SKIP LOCKED) RETURNING *` feeds an `INSERT INTO <child> SELECT * FROM moved` — commit, and stop when the statement moved fewer rows than the batch size. Delete and insert must be one statement so a crash between them is impossible; that single-statement atomicity is what conserves rows. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → live partitioned data | An operator-invoked script performs `DELETE` and `INSERT` against the two fastest-growing tenant-scoped tables in the system. |
| DEFAULT partition ← provider-supplied `occurred_at` | Month buckets are discovered from unvalidated provider timestamps; they decide how many partitions get created. |
