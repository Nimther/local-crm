<objective>
Close the 2026-09-01 partition deadline with a deploy artifact, and prove the whole
detection-to-alert spine end to end on one path before anything is scheduled.

Purpose: `events` and `send_events` have monthly partitions only through August 2026.
From 2026-09-01 every new row routes into the DEFAULT partition, after which every
subsequent `ATTACH PARTITION` pays a full DEFAULT scan under an `ACCESS EXCLUSIVE`
lock — an ingestion outage on the live events table. This plan ships the one-time
catch-up migration that makes 1 September safe regardless of runtime behaviour (D-06),
plus the single source of partition DDL (D-05) and the two-process dead-man's-switch
signal path (D-01, D-02, D-04, D-10), wired end to end and verified against a real
ephemeral Postgres.

Output: migration 0038 (catch-up partitions + `partition_maintenance_runs`),
`packages/db/src/partitions/{ensure-partitions,maintenance-run}.ts`,
`apps/api/src/modules/ops/partition-watchdog.ts`, and two integration test files that
drive migration → DDL function → health row → cross-process read → plain-text alert.
</objective>

## D-01 — Bull Board half of the alert is deferred to Phase 15 (OPS-14)

CONTEXT.md **D-01** specifies the alert as two signals: an operator email through the
existing `PLATFORM_SENDGRID_API_KEY`, **plus** a loud failure of the job itself, "failed job
visible in Bull Board". This plan delivers only the first, deliberately, and the divergence
is recorded here rather than left to be inferred:

- **Why:** Bull Board is not installed in this repository. RESEARCH.md assumption **A1**
  (confidence HIGH, verified by `grep -rln "bull-board\|BullBoard"` across `apps/**/*.ts`
  and every `package.json`) found exactly one hit — a comment in
  `apps/worker/src/server.ts` describing it as future wiring. RESEARCH.md Pitfall 3 records
  the same finding: CONTEXT.md's `canonical_refs` treat Bull Board as already wired, and it
  is not. A "failed job visible in Bull Board" is therefore not an operational signal that
  exists today; it is an operational signal that exists in Phase 15.
- **Where it lands:** installing Bull Board under closed administrative access is
  **Phase 15 / OPS-14** (`REQUIREMENTS.md`: «Bull Board доступен под закрытым
  административным доступом»). Out of scope here; this phase adds nothing to it and takes
  nothing away from it.
- **What Phase 9 therefore ships:** the plain-text operator email is the **sole loud
  signal** for **DB-02**, the deadline-critical requirement. Every design consequence in
  this phase follows from that single-channel reality rather than from a two-channel
  assumption: the email path is the one thing that must not fail silently (a `sendMail`
  rejection propagates rather than being swallowed — task 2, test 8), a missing or
  unreadable health row evaluates **unhealthy** rather than healthy, and the watcher is
  placed in a different process from the watched job (D-02) so "the job stopped entirely"
  still produces an email with no queue UI in the loop.
- **What is preserved for Phase 15:** plan 09-02 sets `removeOnFail: false` on the
  maintenance job, so a failed job is retained in Redis and becomes visible the moment
  OPS-14 wires Bull Board up — the second D-01 signal is deferred, not designed out.
- **Reversibility:** D-01 itself is marked *reversible* ("Phase 15 подключит настоящий
  алертинг к тому же сигналу"). The health row carries the structured signal (buffer,
  DEFAULT counts, last-run) that Phase 15's real alerting reattaches to, so this deferral
  costs nothing later.
- **Known limitation this leaves standing:** if the operator alert itself bounces after
  SendGrid accepts it, nothing in this phase notices — recorded in `COVERAGE.md` and in
  `09-VALIDATION.md` § Manual-Only Verifications as the accepted bridge-to-Phase-15 gap.
</context_deviation>

<assumption_delta_decision>
The `assumption-delta` detector fired on `pluralization` ("second") and `chosen`
("custom"). Both literals come from the ROADMAP's rejected-alternative prose about
`pg_partman` (custom Postgres image, second scheduling paradigm), not from a change to
this system's identity model — those two signals are false positives and are recorded
here rather than acted on.

There is nonetheless one genuine pluralization in scope, and it is decided here:

- **The now-primary noun:** the `(partitioned table, month)` pair. "Months of buffer
  remaining" is a property of a *table*, not of the system: `events` and `send_events`
  are maintained independently and can drift apart (a manual attach on one, a failed
  run on the other).
- **Decision: `promote`.** The per-table buffer is primary and is persisted per table
  (`events_buffer_months`, `send_events_buffer_months`). The scalar
  `buffer_months_remaining` the watchdog compares against the threshold is a *derived
  minimum* over the configured tables, never an average and never a single-table
  reading. Rationale: one health row serves two tables, and any aggregate other than
  the minimum would let a healthy `events` mask an exhausted `send_events`.
- Suggested (not required) contract test encoding the generalized intent: seed the two
  tables with different partition horizons and assert `buffer_months_remaining` equals
  the smaller of the two per-table values. This is covered by the plan-03 boundary
  suite.
</assumption_delta_decision>

The migration has two halves. First, catch-up partitions: for each of `events` and `send_events`, one `CREATE TABLE <table>_YYYY_MM PARTITION OF <table> FOR VALUES FROM (...) TO (...)` statement per month from 2026-09 through 2027-06 inclusive (20 statements total), with bounds written as explicit UTC timestamps — lower `'2026-09-01 00:00:00+00'`, upper `'2026-10-01 00:00:00+00'`, and so on — so the stored bound is independent of the session TimeZone at DDL time. The horizon deliberately overshoots D-11's +3-month steady state: the deadline-closing artifact must carry slack independent of when the migration is actually deployed and when the job's first tick runs. Do NOT add RLS statements for these partitions — 0007/0020 put ENABLE/FORCE ROW LEVEL SECURITY and `workspace_isolation` on the parent, and Postgres propagates parent policies to every child automatically.

Second, the health table `partition_maintenance_runs`, the durable cross-process signal (D-02). Columns: `id integer PRIMARY KEY DEFAULT 1 CHECK (id = 1)` (a singleton row — retention/deletion is Phase 14 / DB-11 and out of scope here, so an append-only history would grow unbounded with no owner), `last_run_at timestamptz NOT NULL`, `lookahead_months integer NOT NULL`, `buffer_alert_threshold_months integer NOT NULL`, `events_buffer_months integer NOT NULL`, `send_events_buffer_months integer NOT NULL`, `buffer_months_remaining integer NOT NULL`, `events_default_count bigint NOT NULL`, `send_events_default_count bigint NOT NULL`, `partitions_created text[] NOT NULL DEFAULT '{}'`, `last_alert_sent_at timestamptz`, `updated_at timestamptz NOT NULL DEFAULT now()`. Persisting both `lookahead_months` and `buffer_alert_threshold_months` is what makes D-11's "someone changed the lookahead without changing the threshold" case visible in the data and not only in the diff. This table carries no `workspace_id` — it is platform-level operational metadata, so it must NOT get the RLS ENABLE/FORCE/`workspace_isolation` treatment every tenant-scoped table gets; add a comment saying exactly that so a future reviewer does not "fix" it.

Implement `monthRangeUtc(year, monthIndex)` returning the `[start, end)` pair as explicit-offset UTC timestamp strings, and `monthPartitionName(parentTable, date)` returning `<parentTable>_YYYY_MM` derived only from calendar arithmetic on a `Date`. Partition and table identifiers must never be constructed from row data — Postgres cannot parameterise a partition bound or an identifier, so calendar-only construction plus the hard-coded `PARTITIONED_TABLES` allowlist is the injection mitigation (threat T-09-01).

Implement `attachPartitionCheckFirst(client, table, monthStart, monthEnd)` as the sequence RESEARCH.md Pattern 3 quotes from the PostgreSQL documentation, run for **every** attach unconditionally rather than only when a DEFAULT count first shows rows (RESEARCH.md Open Question 1's recommendation, taken): create the child as a freestanding table with `CREATE TABLE IF NOT EXISTS <child> (LIKE <parent> INCLUDING ALL)`; add a `NOT VALID` CHECK constraint on the `_default` partition excluding the new range (metadata-only, no scan); `VALIDATE CONSTRAINT` it (scans under SHARE UPDATE EXCLUSIVE, concurrent reads and writes continue); `ALTER TABLE <parent> ATTACH PARTITION <child> FOR VALUES FROM (...) TO (...)`, which Postgres now performs without scanning DEFAULT because the validated constraint already proves the range disjoint; then drop the now-redundant constraint. Wrap the whole five-statement sequence for one month in a single transaction (`BEGIN` / `COMMIT`, `ROLLBACK` on error, client released in `finally`) using the same shape `campaign-scheduler.worker.ts`'s `findDueCampaignCandidates` uses. The transaction is a correctness requirement, not tidiness: a crash between create and attach would leave a freestanding `events_YYYY_MM` table that carries `workspace_id` and has no RLS, which is both a cross-tenant read path (threat T-09-02) and a failure of `migrate-from-empty.test.ts`'s "every workspace_id-bearing table must have RLS enabled and forced" assertion.

Implement `ensurePartitions(client, tables, now, lookaheadMonths)`: for each configured table, walk months `0 .. lookaheadMonths` forward from the UTC month containing `now`, and for each month whose partition relation is absent (probe `pg_class` joined to `pg_inherits`, or `to_regclass`), call `attachPartitionCheckFirst`. Return, per table, the list of partition names actually created this call — the empty array on a no-op run is what makes idempotency observable.
