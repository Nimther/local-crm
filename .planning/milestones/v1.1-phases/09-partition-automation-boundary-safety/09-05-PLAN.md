Cover: that `events` and `send_events` are range-partitioned by month with a DEFAULT catch-all, and that a missing month is a correctness non-event but a performance cliff, because an attach against a non-empty DEFAULT scans it under an exclusive lock; that the horizon is maintained by one idempotent function in `packages/db` which is the single source of partition DDL and is called from three places — the daily worker tick, the worker's boot-time run, and the test fixture — so production and test databases cannot drift; and that health is a two-process arrangement in which the worker writes a row to Postgres and a watchdog in the `apps/api` process reads it, because a watcher inside the process it watches cannot report that the process stopped. Name Postgres as the only shared state between the two, and explain that this is deliberate: shared in-memory state would defeat the entire point.

Also state which failure this arrangement is designed to make loud, and which it is not. It makes "the job stopped", "the horizon is shrinking", and "DEFAULT is holding rows" loud, through one plain-text email to a platform operator. It does not provide dashboards, queue-depth alerting, or error aggregation — that is Phase 15. Move nothing into the "Forward-looking" section that is now true, and if that section previously described partition automation as forward-looking, update it.

Add two conventions to `CONVENTIONS.md`, each stated as a binding rule with its reason, matching the document's existing style.

First: partition DDL has exactly one source. Monthly partitions for a range-partitioned table are created by `ensurePartitions` in `packages/db/src/partitions/ensure-partitions.ts` and never by a per-month migration; a migration creates partitions only as a one-time catch-up to a fixed horizon. Every attach against a table that has a DEFAULT partition goes through the CHECK-constraint-first sequence unconditionally, and that sequence exists in exactly one function — a second copy is the failure mode, because the copy that drifts is the one that runs in production. Any new partitioned table registers itself in the `PARTITIONED_TABLES` constant rather than growing its own maintenance path.

Second: a BullMQ tick that needs to run at a fixed wall-clock hour registers through the job-scheduler form with a stable scheduler id and an explicit timezone; a tick that only needs a cadence may keep the interval form. Record why the distinction matters — a fixed hour is what lets a separate watchdog reason about staleness with a concrete threshold — and record that the four pre-existing interval-form ticks are deliberate precedent, not drift, so a future reader does not "unify" them without a reason.

If either convention is already partially stated elsewhere in the document, extend that place rather than adding a duplicate section.
