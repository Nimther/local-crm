<objective>
Close UAT Test 1 (severity: major): "After resetting filters in the send log, the user can re-apply a campaign filter to filter sends by campaign."

Today the send-log page exposes the campaign/flow filter ONLY as a URL-param-driven deep-link chip set by CampaignMetricsSummary's «Смотреть в журнале отправок» link. `resetFilters()` (SendLogPage.tsx:190-192) wipes every search param, and the page's only interactive filter controls are the status multi-select and the period presets — so once the campaign param is cleared there is no in-page way to re-apply it (root cause: `.planning/debug/send-log-campaign-filter-after-reset.md`). The backend already accepts `campaignOrFlowId` (send-log.routes.ts:21,117) — this is a frontend-only, zero-backend-change gap.

Fix: add a persistent, searchable «Кампания / цепочка» selector to the send-log filter toolbar (Popover+Command combobox listing this workspace's campaigns and flows), mirroring the existing status multi-select pattern and the TimezoneCombobox searchable-combobox precedent. The selector writes the `campaign`/`flow` URL search param (mutually exclusive) so it drives the existing backend filter unchanged. The existing chip display and CampaignMetricsSummary deep-link behavior stay exactly as-is (per the diagnosis).

Purpose: restore the UAT truth "filters in the send log should allow filtering by campaign at any time" without touching the API or the deep-link contract.
Output: a persistent campaign/flow selector on the send log, plus a node-testable pure helper for the mutual-exclusion param logic.
</objective>
