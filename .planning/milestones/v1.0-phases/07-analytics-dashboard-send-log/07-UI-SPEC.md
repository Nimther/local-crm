Spacing, typography, and the core 60/30/10 color contract are **not renegotiated** here — they are restated for executor convenience and extended only where Phase 7 introduces a genuinely new surface (charts, a drawer, per-step canvas badges, additional status-badge values). ## Typography

Exactly 4 sizes, 2 weights — **unchanged from `01-UI-SPEC.md`** (already generalized to cover "big-number callouts" by `06-UI-SPEC.md`, which this phase's KPI cards and hero figures reuse as-is):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / meta | 14px (`text-sm`) | 400 regular | 1.5 |
| Body | 16px (`text-base`) | 400 regular | 1.5 |
| Heading (section / card title) | 20px (`text-xl`) | 600 semibold | 1.2 |
| Display (page title, **KPI-card hero numbers, chart headline stat**) | 28px (`text-display` token) | 600 semibold | 1.2 |

Additional rules for this phase:
- Dashboard KPI-card numbers (sent, delivered %, opened %, new contacts, unsubscribes) use `text-display`; the KPI label sits above at 14px/400 muted, matching the existing dl/dt-dd pattern in `CampaignProgress.tsx`.
- Chart axis ticks and legend text: 12px is **not** a new size — reuse `text-sm` (14px) throughout; do not introduce a smaller "chart caption" size. Muted-foreground color, per dataviz skill's "text wears text tokens, never the series color" rule.
- Send-log/timeline row timestamps: reuse the existing `relativeTime()` helper (`ContactEventFeed.tsx`) verbatim — Russian relative time via `Intl.RelativeTimeFormat`, no new formatting logic.
- Table numeric columns (counts, percentages) that must align vertically: `font-variant-numeric: tabular-nums` (new utility class `tabular-nums`, Tailwind built-in — apply to send-log count columns and KPI numbers only, not prose).

### Semantic status-badge colors (badges only, not general UI — extends Phase 1's precedent, zero new hues)

Reuses the exact three existing badge hue families (green / neutral / red) established by `SubscriptionStatusBadge.tsx` and Phase 1's SendGrid-status badge — extended to cover the send-log "current status" column (Phase 5 D-06 priority chain + D-15's `failed`/`excluded`):

| Send status | Bucket | Badge classes | Label |
|---|---|---|---|
| `sent` | neutral (in-flight) | `bg-neutral-100 text-neutral-500` | «Отправлено» |
| `delivered` | good | `bg-green-50 text-green-600` | «Доставлено» |
| `opened` | good | `bg-green-50 text-green-600` | «Открыто» |
| `clicked` | good | `bg-green-50 text-green-600` | «Клик» |
| `bounced` / `dropped` / `spam` | bad | `bg-red-50 text-destructive` | «Не доставлено» |
| `unsubscribed` | neutral | `bg-neutral-100 text-neutral-500` | «Отписался» |
| `failed` | bad | `bg-red-50 text-destructive` | «Ошибка отправки» |
| `excluded` | neutral | `bg-neutral-100 text-neutral-500` | «Пропущено» |

Rationale: the send-log status column shows exactly **one** collapsed current status per message row (never side-by-side alternatives for the same message), so reusing one hue across the "good" bucket (delivered/opened/clicked) costs no distinguishability — the label text and the row's own position in the D-06 priority chain already carry that information. This keeps the badge-color vocabulary closed at 3 hues project-wide, matching Phase 1's original constraint.

### Chart Palette (new this phase — the one documented exception to "no additional hues")

Dashboard trend/growth charts are **data-ink**, a different job than UI chrome — the `dataviz` skill's method was invoked and the palette below was **computed and validated**, not eyeballed (`node scripts/validate_palette.js "#2a78d6,#4F46E5,#16A34A" --mode light --pairs all --surface "#FFFFFF"` → all 6 checks PASS: lightness band, chroma floor, CVD separation worst-pair ΔE 26.6/16.9, contrast ≥3:1 all three).

| Series | Hex | Role |
|---|---|---|
| Отправлено (sent) | `#2A78D6` | Categorical slot 1 (new hue, chart-only — never used elsewhere in the UI) |
| Доставлено (delivered) | `#4F46E5` (= `--primary`, brand indigo) | Categorical slot 2 — intentional reuse of the brand accent as a chart identity color |
| Открыто (opened) | `#16A34A` (= existing `green-600` success semantic) | Categorical slot 3 — intentional reuse of the existing badge-success hue |

**Fixed order, never cycled or reassigned per-filter** (dataviz skill non-negotiable): sent → delivered → opened, left to right in the legend, matching the natural funnel reading order. A legend is always present (3 series); no per-point value labels (selective direct-label only for the final data point of each line, per dataviz skill mark specs).

**Contact-growth chart (single series):** one hue, brand indigo `#4F46E5`, line + a lightened area fill (`#4F46E5` at 12% opacity) — per dataviz skill, a single series needs no legend box; the chart title (D-08: «Рост базы контактов») names it.

**Reuse-vs-reservation note (resolves RESEARCH.md's implicit tension):** Reusing `indigo-600`/`green-600` inside chart series does **not** violate their "reserved for CTA/nav/badges" role — chart color performs a different semantic job (categorical identity within one plot, scoped to that plot) than UI chrome (calls to action, navigation state). This is an explicit, documented exception, not a silent scope creep of the accent color's meaning — flag for `gsd-ui-checker` Dimension 3 (Color) as intentional.

Dark mode: **out of scope.** `tailwind.config.ts` declares `darkMode: ["class"]` but no theme toggle exists anywhere in this codebase (verified — zero `dark:` classes, no `ThemeProvider`). Charts ship light-mode-only, matching every other screen.

No gradients outside the one contact-growth area-fill tint above. No further hues.

### Destructive confirmations

**None.** This phase introduces zero new destructive/mutating user-facing actions — it is a read surface over data Phases 4–6 already write. (The one new *write* path, `subscription_status_history`, is system-generated at four existing mutation call sites, not a new user-triggered destructive action — no confirmation dialog applies.)

### System copy notes

- Send-log drawer (D-14) section headings: «Хронология письма» (event timeline), «Причина» (shown only when bounce/drop/exclusion reason is present).
- Excluded-row copy in campaign/flow summaries (D-07): «Пропущено: {N}» with an expandable breakdown «из-за подписки/suppression: {n}» / «из-за лимита частоты: {n}» — reuses the exact «Пропущено» term the send-log status badge also uses (terminology consistency, per CONTEXT.md's discretion note).
- Period-preset control label (dashboard + send log, D-08): buttons «7 дней» / «30 дней» / «90 дней», default selected = «30 дней». No «Произвольный период» option in v1 (deferred, D-08).
- Contact-timeline record-type filter (D-10): a single `Select`/segmented control with values «Всё» / «События» / «Письма» / «Статусы» — no separate tabs.
- Canvas node metric badge (D-03) hover tooltip: reuses existing `Tooltip` component, format «{count} прошли · {rate}% доставлено» for send nodes, «{count} прошли» for all other node types.
- Multi-select status filter (send log, D-15): a `Popover` + `Command` + `Checkbox` list (mirrors the existing `FieldCombobox`/`EventCombobox`/`TimezoneCombobox` composed-component pattern) — trigger button reads «Статус» when empty, «Статус: {N}» when N values selected.

Interaction rules (unchanged house rules, restated):
- Every mutating action still gets disabled+loading state — not applicable to most of this phase (read-only), but the send-log filter reset button follows the same convention.
