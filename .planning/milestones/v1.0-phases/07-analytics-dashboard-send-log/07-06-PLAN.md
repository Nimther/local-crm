## Phase Goal

**As a** marketer, **I want to** see end-to-end email performance — per campaign, per flow step, per contact, and across my whole workspace, down to the status of every individual message — **so that** I can tell what is working and always answer why a contact did or did not receive an email.

This plan builds the rollup foundation the workspace dashboard (07-07) reads: a per-workspace-per-day aggregate table maintained incrementally (fresh) and reconciled periodically (correct), so trend charts never scan the partitioned sends/send_events/events tables on load (D-08b).

## Artifacts this phase produces

- `workspace_daily_rollup` table (columns: `id`, `workspace_id`, `day`, `sent_count`, `delivered_count`, `opened_count`, `clicked_count`, `bounced_count`, `unsubscribed_count`) with a `(workspace_id, day)` unique key
- Migration `0037_workspace_daily_rollup.sql` + journal entry idx 37
- `incrementWorkspaceDailyRollup(client, workspaceId, occurredAt, metric)` in `apps/worker/src/queues/analytics-rollup.ts`
- `createAnalyticsReconciliationWorker(connection)` repeatable reconciliation worker + its queue name constant

<objective>
Create the workspace_daily_rollup table (07-01 ROADMAP) and apply it via a BLOCKING migration, wire same-transaction incremental increments into the webhook worker's genuinely-new-event branches, and add a repeatable reconciliation worker that overwrites each recent-day rollup from a fresh scan of sends.

Purpose: Give the dashboard a cheap, freshness-bounded (a few minutes, D-08b) read path for send/deliver/open trends without heavy on-the-fly scans of the fastest-growing partitioned tables. Incremental increments keep the webhook-driven metrics near-real-time; the reconciliation overwrite is the correctness backstop that also fills "sent".
Output: New table + migration applied, increment wiring, and a self-healing reconciliation worker — all covered by idempotency, overwrite, and tenant-isolation tests.
</objective>
