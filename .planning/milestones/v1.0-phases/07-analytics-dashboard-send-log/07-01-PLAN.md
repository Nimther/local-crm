## Phase Goal

**As a** marketer, **I want to** see end-to-end email performance — per campaign, per flow step, per contact, and across my whole workspace, down to the status of every individual message — **so that** I can tell what is working and always answer why a contact did or did not receive an email.

This plan builds the one genuinely new write path the analytics phase needs: a durable subscription-status audit log (D-09) plus per-send repeat open/click counters (A4). It renders nothing itself; it is the write foundation the contact timeline (07-02) and send log (07-05) read from.

## Artifacts this phase produces

- `subscription_status_history` table (columns: `id`, `workspace_id`, `contact_id`, `old_status`, `new_status`, `source`, `reason`, `changed_at`)
- `sends.open_count`, `sends.click_count` integer columns
- Migration `0036_analytics_status_history_counts.sql` + journal entry idx 36
- `recordSubscriptionStatusChange(client, params)` exported from `@mega-crm/contacts-core`
- Source-tag vocabulary for status history: `webhook_suppression`, `webhook_unsubscribe`, `unsubscribe_route`, `manual_ui`, `csv_or_api_upsert`

<objective>
Create the subscription-status history table (D-09) and add repeat open/click counters to `sends` (A4/D-11), apply them via a BLOCKING migration, then wire a single shared `recordSubscriptionStatusChange` helper into all four existing status-mutation call sites and add open_count/click_count increments to the webhook worker.

Purpose: Durably record every subscription-status transition and repeat engagement so the contact timeline and send log can display them; without this write path, status changes and «×N» repeat opens/clicks are simply not recorded anywhere.
Output: New table + columns + migration applied to the dev DB, plus write wiring at four call sites, all covered by integration tests.
</objective>
