# Phase 1: Workspace Foundation & Team Access - Context

**Gathered:** 2026-07-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Маркетолог может создать воркспейс, привести команду с правильными правами и подключить свой SendGrid-аккаунт — при полной изоляции данных каждого воркспейса с первого дня. Покрывает: регистрацию/вход, воркспейсы и членство, роли Owner/Admin/Member, приглашения, подключение и хранение SendGrid-ключа, мульти-тенантную изоляцию (RLS, request-scoped tenant context), системные письма платформы. Требования: TENANT-01…05.

</domain>

<decisions>
## Implementation Decisions

### Аутентификация
- **D-01:** Вход по email/паролю. Без OAuth и magic link в v1.
- **D-02:** Мягкая верификация email: пользоваться платформой можно сразу (баннер «подтвердите email»), но подтверждение ОБЯЗАТЕЛЬНО для критичных действий — как минимум для подключения SendGrid-ключа.
- **D-03:** Сброс пароля через email входит в эту фазу.
- **D-04:** Cookie-сессии (HttpOnly, серверные), долгие ~30 дней со sliding expiration.
- **D-05:** Auth на готовой библиотеке, кандидат — better-auth; финальный выбор подтверждает ресёрчер фазы (критерии: cookie-сессии, verification/reset flows, Fastify-совместимость).
- **D-06:** 2FA не в v1 (deferred).

### Системные письма платформы
- **D-07:** Платформа шлёт собственные письма (верификация, сброс пароля, инвайты) через ОТДЕЛЬНЫЙ платформенный SendGrid-аккаунт/ключ — не через тенантские ключи.
- **D-08:** Шаблоны системных писем живут в коде репозитория (простые HTML), НЕ в SendGrid Dynamic Templates.
- **D-09:** From-адрес: общий noreply@ домен платформы с SPF/DKIM.
- **D-10:** Приглашение: письмо + копируемая ссылка в UI как fallback.
- **D-11:** Инвайт истекает через 7 дней; Owner/Admin может отозвать pending-инвайт и переотправить.
- **D-12:** Приглашённый без аккаунта регистрируется прямо из инвайта (имя + пароль; email зафиксирован инвайтом) и сразу попадает в воркспейс.

### Модель воркспейсов
- **D-13:** Аккаунт пользователя отделён от воркспейса; пользователь может состоять в нескольких воркспейсах, в UI — переключатель воркспейсов.
- **D-14:** Создание воркспейса — отдельный шаг онбординга после регистрации (имя компании); пришедшие по инвайту этот шаг пропускают.
- **D-15:** Лимита на количество создаваемых воркспейсов нет (лимиты появятся с биллингом в v2).
- **D-16:** Воркспейс присутствует в URL слагом: `/w/{workspace-slug}/...` — ссылки шерятся между коллегами и однозначно указывают воркспейс.

### Права ролей
- **D-17:** Member: полный доступ к контактам/сегментам, создаёт и редактирует черновики кампаний/цепочек, но НЕ может запускать/публиковать.
- **D-18:** Owner и Admin управляют командой (приглашение, смена ролей, удаление участников); только Owner назначает/снимает Admin'ов и передаёт владение.
- **D-19:** Запуск кампаний/цепочек и смена SendGrid-ключа — только Owner/Admin (из TENANT-03).
- **D-20:** Удаление воркспейса в v1: Owner-only, подтверждение вводом имени воркспейса, soft delete с отложенной физической очисткой.

### SendGrid-ключ (UX подключения)
- **D-21:** При подключении валидируем: работоспособность ключа, наличие mail.send scope, и показываем список верифицированных отправителей/доменов из аккаунта тенанта.
- **D-22:** Подключённый ключ показывается маской (первые символы + последние 4), с бейджем статуса (активен/ошибка), кнопкой «проверить сейчас»; при ошибках отправки статус помечается автоматически.

### Онбординг и профиль
- **D-23:** Пустой воркспейс встречает чеклистом первых шагов: подключите SendGrid → пригласите команду (пункты про контакты/кампании добавятся в следующих фазах — чеклист проектировать расширяемым).
- **D-24:** Профиль пользователя v1: отображаемое имя + смена пароля. Смена email и аватар — v2.

### Claude's Discretion
- Точный выбор auth-библиотеки (better-auth как кандидат) — за ресёрчером/планировщиком фазы.
- Технические детали RLS-политик, схемы таблиц, структуры сессий, механики envelope-шифрования ключа (KMS) — по ресёрчу (STACK.md/ARCHITECTURE.md/PITFALLS.md).
- Формат slug'а воркспейса, коллизии имён — стандартные подходы.

</decisions>

## Existing Code Insights

### Reusable Assets
- Нет — greenfield, кода в репозитории ещё нет. Эта фаза закладывает фундамент.

### Established Patterns
- Паттерны задаёт ресёрч: Fastify-плагины по доменным границам, Drizzle + RLS, request-scoped tenant context (AsyncLocalStorage).

### Integration Points
- Всё последующее (контакты, события, кампании) строится поверх tenant-контекста и auth этой фазы; platform-email отправка из этой фазы позже может быть переиспользована/заменена общим send pipeline (Phase 4) — проектировать как простой изолированный модуль, не преждевременно обобщать.

</code_context>

<specifics>
## Specific Ideas

- Онбординг-чеклист как «живая» карта готовности воркспейса (расширяется в следующих фазах).
- Статус SendGrid-ключа как first-class сущность в UI (маска, бейдж, re-check) — согласуется с Core Value «надёжность видна пользователю».

</specifics>
