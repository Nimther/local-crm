<objective>
Deliver the send-side markers and the pure, DB-free delivery decision logic that the 05-03 worker will consume. Two independent, unit-testable concerns:

1. Extend the already-shipped Phase 4 `buildMailSendRequest` so every message forces `open_tracking`/`click_tracking` on (D-04, closes Pitfall 3 — otherwise opened/clicked events never fire for tenants whose account-level tracking is off) and so `kind='test'` sends carry a `test='true'` custom_arg (D-15, closes Pitfall 2 — otherwise a bounced test address is indistinguishable from a real orphaned send and could suppress a real contact).
2. Add three pure delivery-logic modules — `event-normalize.ts` (WBHK-02 event-type normalization incl. hard vs soft bounce), `suppression-rules.ts` (SUBS-02 / D-10/D-11/D-12 decision table), and `send-status.ts` (D-06 current-status priority) — each fully testable without a database.

Phase Goal (user story): **As a** marketer, **I want to** see accurate, deduplicated delivery outcomes for my sent emails and have bounces/spam-complaints/unsubscribes automatically suppress contacts, **so that** my stats are trustworthy and I stop mailing dead or opted-out addresses.

Purpose: Centralize the event→status decision in one pure place (Pattern 5 — prevents suppression logic drifting across code paths, PITFALLS #7) and force per-send tracking so the events actually arrive.
Output: One extended file + three new pure modules + their unit tests; no schema, no DB, no route.
</objective>
