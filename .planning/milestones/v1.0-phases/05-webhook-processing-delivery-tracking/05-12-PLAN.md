<objective>
Close both round-4 UAT gaps (Test 1 major, Test 2 blocker), which share ONE root cause: the SendGrid Event Webhook callback URL is built verbatim from boot-time `env.PUBLIC_APP_URL` with no https enforcement in any layer. During the live run PUBLIC_APP_URL was http://, SendGrid rejected webhook creation with `400 "webhook url must use https"`, and `errorForStatus` maps only 401/403 to typed reasons — so the 400 collapsed into the generic non-actionable "failed" warning and the webhook was silently absent.

This plan adds a pre-flight https short-circuit (mirroring the 05-09 missing_scope pattern) so the doomed call is never made, a new typed `insecure_url` reason with actionable Russian copy pointing at PUBLIC_APP_URL / docs/webhook-live-uat.md, health-card recognition of that reason, and two defense-in-depth env guards (predev http:// warning + production boot https requirement).

Purpose: Turn a silent, non-recoverable http-URL failure into an immediate, self-explanatory, operator-fixable warning — and catch the misconfiguration before it ever reaches SendGrid.
Output: A `insecure_url` typed reason end-to-end (provisioning result → persisted reason → connect/recheck/reconnect warning → health card), plus a predev warning and a production boot guard.
</objective>

## Root cause (from .planning/debug/webhook-url-must-use-https.md)

Single root cause behind UAT Tests 1 and 2:
- `callbackUrl` is `${env.PUBLIC_APP_URL}/webhooks/sendgrid/${pathToken}` at both call sites (sendgrid-key.ts:63 connect/recheck, webhook-settings.routes.ts:113 reconnect). `env.PUBLIC_APP_URL` is read once at boot and was http:// during the live run, so SendGrid returned `400 "webhook url must use https"`.
- No layer enforces https: `env.ts` accepts any `z.string().url()`; `check-env.mjs` warns only on localhost about reachability; `provisionEventWebhook` makes the create/patch POST unconditionally.
- `errorForStatus` maps only 401/403 → `missing_scope`; the 400 fell into the generic `failed` bucket → `WEBHOOK_PROVISION_FAILED_WARNING` ("Попробуйте переподключить ключ позже"), which never mentions the URL/scheme and advises a retry that can never succeed while PUBLIC_APP_URL stays http.
- Test 2's scope-limited scenario was never actually exercised — a 400 (body validation, not 401/403) proves the run's key HAD the webhook scope; both gaps are this one https root cause.

Note the fix lives in `provisionEventWebhook` (the single chokepoint every path routes through) rather than duplicated at each call site, so connect, recheck, and reconnect are all covered by one guard. Both existing call sites already persist `result.error` via `upsertWebhookEndpoint` and surface it via `webhookWarningFor`, so a new typed reason flows through them unchanged.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| env/config → provisioning | PUBLIC_APP_URL (untrusted operator config) determines the outbound webhook callback URL sent to SendGrid |
| API → browser | The insecure_url reason copy is returned to the client (connect/recheck warning + health card) |
| tenant BYO key → SendGrid | The pre-flight guard decides whether an outbound authenticated call is made at all |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-12-01 | Information Disclosure | insecure_url warning copy (API response + health card) | medium | mitigate | The copy is a fixed curated Russian string with no interpolation of the URL, key, or SendGrid body; it names only the env var and the runbook path. webhookWarningFor maps a typed enum, never raw input. |
| T-05-12-02 | Denial of Service | provisionEventWebhook outbound call | low | mitigate | The pre-flight https guard short-circuits before any fetch, so a misconfigured http URL can no longer drive a doomed authenticated POST/PATCH to SendGrid on every connect/recheck/reconnect. |
