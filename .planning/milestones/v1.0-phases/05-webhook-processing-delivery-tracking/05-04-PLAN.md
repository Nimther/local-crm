<objective>
Make delivery tracking self-configuring (the Klaviyo model, D-01/D-02): when a tenant connects or rechecks their SendGrid key, the platform uses that key to create/patch its OWN independently-named Event Webhook, enables signed verification (fetching the public key), and persists the webhook id + public key + a random per-tenant pathToken into `workspace_webhook_endpoints` — never touching the tenant's pre-existing manual webhooks (D-05). Provisioning is best-effort: a scope/plan-cap failure produces a clear message but never fails the key connect (D-01 fallback). Tenants can see webhook health and reconnect (D-03).

Phase Goal (user story): **As a** marketer, **I want to** see accurate, deduplicated delivery outcomes for my sent emails and have bounces/spam-complaints/unsubscribes automatically suppress contacts, **so that** my stats are trustworthy and I stop mailing dead or opted-out addresses.

Purpose: Deliver the WBHK-01 provisioning side — the per-tenant URL and public key that 05-01's receiver verifies against — with one button instead of an 8-step manual setup.
Output: The provisioning service, the sendgrid-key extension, the endpoint repository writer, and the authenticated health/reconnect routes.

Note (open technical question A3): the exact SendGrid CREATE path is not fully confirmed (`POST /v3/user/webhooks/event/settings` vs `.../settings/all`). Implement the documented path and a fallback, and defer the live confirmation to the phase-UAT human-check (below) — consistent with the Phase 1 precedent of deferring live-SendGrid checks to phase UAT (human_verify_mode: end-of-phase). Do NOT introduce a mid-phase blocking checkpoint.
</objective>

Export `provisionEventWebhook(apiKey: string, callbackUrl: string, existingWebhookId?: string): Promise<{ id: string; publicKey: string } | { error: "missing_scope" | "cap_reached" | "failed" }>`:

- If `existingWebhookId` is provided → PATCH `https://api.sendgrid.com/v3/user/webhooks/event/settings/{id}` to update url + friendly_name + the event flags; else CREATE a new webhook. For CREATE, attempt the documented path `POST /v3/user/webhooks/event/settings` with body `{ enabled:true, url:callbackUrl, friendly_name:"Mega CRM Delivery Tracking", delivered:true, bounce:true, dropped:true, open:true, click:true, unsubscribe:true, group_unsubscribe:true, spam_report:true }`; if that returns 404/405, retry against `.../settings/all` (A3 fallback) before giving up. group_unsubscribe:true is required for D-11.
- Then enable signed verification: PATCH `https://api.sendgrid.com/v3/user/webhooks/event/settings/signed/{id}` with `{ enabled:true }`, which returns `{ id, public_key }` in the same response (confirmed against official docs). Return `{ id, publicKey: public_key }`.
- Before CREATE, optionally GET `.../settings/all` to detect the account's `max_allowed` cap and an already-present platform webhook (Pitfall 4 reconnect guard); map an insufficient-scope (401/403) response to `{ error:"missing_scope" }` and a cap-exhaustion to `{ error:"cap_reached" }`; any other non-ok → `{ error:"failed" }`. Never throw for these expected failures (D-01 graceful fallback). Redact the apiKey from any thrown/logged error (mirror send-mail.ts's redactApiKey approach).

Use the raw-fetch-with-`Authorization: Bearer ${apiKey}` convention and typed response interfaces exactly like sendgrid-client.ts; never `@sendgrid/mail`.
