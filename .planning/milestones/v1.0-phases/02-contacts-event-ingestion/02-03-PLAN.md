<objective>
Introduce workspace-scoped API keys — the project's first non-session authentication mechanism — so a tenant's backend can authenticate to the Event and Contacts integration APIs (built in 02-04/02-06) without a browser session. This plan delivers the key model, the crypto (generate/hash/mask), the Owner/Admin-gated management routes and UI, and the runtime `apiKeyAuth` onRequest hook that resolves the workspace from the key itself.

## Phase Goal

**As a** marketer, **I want to** build and maintain my contact base through the UI, CSV import, and a server-side API — while my product backend streams freeform behavioral events — **so that** my contacts are created and enriched in real time and every contact carries an accurate subscription status.

This slice delivers a real capability: an Owner/Admin can create an API key so their backend can call the integration API — the credential every server-to-server call in 02-04 and 02-06 will present.

Purpose: The `apiKeyAuth` hook here is the auth template for the Contacts API (CONT-03) and Event API (EVNT-01); the same key model extends (via its reserved scopes column) to any future integration surface.
Output: workspace_api_keys table + RLS migration + shared schemas + crypto + management routes/UI + the runtime auth hook, all green under Vitest.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant backend → /v1 API (future) | Presents a Bearer API key; the key alone determines the workspace — no session, no slug |
| browser (session, Owner/Admin) → management API | Creates/revokes keys; the full secret crosses the wire once |
| API → Postgres | api-key lookup is by unique id outside the tenant transaction; all tenant-scoped management reads run under RLS |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03-01 | Spoofing | api-key brute-force / credential stuffing | high | mitigate | High-entropy (256-bit) secrets + SHA-256 hash storage + crypto.timingSafeEqual; @fastify/rate-limit applied on the /v1 routes in 02-04/02-06 |
| T-02-03-02 | Information Disclosure | key enumeration via timing/error differences | medium | mitigate | Uniform 401 body + constant-time compare; unknown-prefix and wrong-secret are indistinguishable (asserted in Task 1) |
| T-02-03-03 | Information Disclosure | plaintext secret at rest / in logs | high | mitigate | Only SHA-256 hash + mask persisted; secret returned once at creation and never logged (D-22) |
| T-02-03-04 | Elevation of Privilege | Member creating/revoking keys | high | mitigate | requirePermission('apiKeys',...) gates create/revoke to Owner/Admin (D-21) |
| T-02-03-05 | Information Disclosure | workspace_api_keys cross-tenant read | high | mitigate | ENABLE + FORCE RLS + workspace_isolation on workspace_api_keys; management reads run inside withTenantTransaction |
</threat_model>
