<objective>
Deliver freeform server-side event ingestion (EVNT-01/02/03): a fast API-key-authed /v1/events endpoint that validates only the envelope and enqueues, an idempotent BullMQ worker that upserts the contact (reusing 02-04's upsertContactByIdentity) and writes the event to a partition-ready table, and the partitioned `events` schema itself. This closes the phase's async pipeline and gives tenants the immediate "events are arriving" feedback the contact-card feed surfaces.

## Phase Goal

**As a** marketer, **I want to** build and maintain my contact base through the UI, CSV import, and a server-side API — while my product backend streams freeform behavioral events — **so that** my contacts are created and enriched in real time and every contact carries an accurate subscription status.

This slice makes the "backend streams events that create/enrich contacts in real time" half of the phase goal real: a tenant backend can now fire events and watch contacts appear/enrich — a capability that did not exist before.

Purpose: The partitioned events table + idempotent worker are the input to behavioral segmentation (Phase 3 SEGM-02) and the contact timeline (Phase 7 ANLT-03); the queue/worker pattern is reused by the send pipeline (Phase 4).
Output: partitioned events schema + migration, /v1/events route + producer, event worker, and idempotency/chaos tests.

## Decisions surfaced (honored here, not silently dropped)
- RESEARCH Open Question 2: this plan accepts an OPTIONAL client-supplied event_id per item (falling back to a server-generated UUID) so a tenant's own retried HTTP POSTs are also deduplicated — cheap because the id is already the idempotency key. The id (whether client- or server-supplied) is the BullMQ jobId AND the events primary-key component.
- Idempotency on a partitioned table: the events primary key is (id, occurred_at); occurred_at is resolved ONCE at ingestion time (client-supplied occurredAt, else the ingestion timestamp) and carried in job.data, so it is deterministic across redeliveries — making ON CONFLICT (id, occurred_at) DO NOTHING a correct DB-level safety net (a bare now() in the worker would differ on redelivery and defeat dedup).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant backend → /v1/events | Untrusted, high-volume, API-key-authed server-to-server input; can be a batch of ~1000 |
| queue → worker | Job payload is the sole context the worker trusts; workspaceId re-derived from it |
| worker → Postgres (partitioned events) | RLS-scoped writes to the partitioned events table |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06-01 | Denial of Service | unbounded event payload / batch size | high | mitigate | Fastify body-limit on /v1/events + eventBatchSchema .max(1000) + @fastify/rate-limit on the scope; apiKeyAuth on onRequest before body parse (Pitfall 3) |
| T-02-06-02 | Tampering | duplicate/double-counted events on retry | high | mitigate | Deterministic id + occurredAt used as jobId and events PK with ON CONFLICT DO NOTHING (Pitfall 1) |
| T-02-06-03 | Tampering | reserved-key mass assignment via event properties | high | mitigate | upsertContactByIdentity strips reserved keys before the JSONB merge (reused from 02-04); test asserts subscription_status cannot be flipped (Pitfall 4) |
| T-02-06-04 | Information Disclosure / Elevation of Privilege | cross-tenant event write from the worker | high | mitigate | Worker re-derives workspaceId from job.data and runs inside withTenant + withTenantTransaction (RLS on parent events table) |
| T-02-06-05 | Repudiation | client mistakes 202 "accepted" for "processed" | low | accept | Per-item status is explicitly "accepted" (queued), documented in the API contract (D-24); not "processed" |
</threat_model>
