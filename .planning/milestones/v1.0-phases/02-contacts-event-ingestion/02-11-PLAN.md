## Phase Goal

**As a** tenant integrator whose backend fires concurrent events and contact upserts under load, **I want to** the shared upsert to survive an insert race and honor a subscription-status change on an existing contact — and the connection pool to never hand out a dead client — **so that** a burst never turns into a 500 or a silently-ignored status change.

<objective>
Close the triage-severity robustness gaps on the shared ingestion plumbing that all three write paths (Contacts API, events:ingest worker, imports:csv worker) depend on. These HARDEN already-satisfied requirements — they are not re-claiming them (gap-contract rule 5), so `requirements` is intentionally empty:

- CR-02 (rare-path correctness): the unique-violation retry in `upsertContactByIdentity` runs inside the caller's already-aborted transaction, so its first statement throws `25P02` — the documented concurrent-insert defense is dead code. Fix: wrap the INSERT in a SAVEPOINT and ROLLBACK TO SAVEPOINT before retrying, so the transaction survives the conflict.
- WR-06: `upsertContactApiSchema` accepts `subscriptionStatus` on every item but the update branch never applies it — an integrator gets a 200 with no state change. Fix: apply valid subscribed<->unsubscribed transitions on the update branch mirroring `updateContact`'s D-12 rules (never set suppressed, never un-suppress).
- WR-09: `withTenantTransaction` and `lookupApiKeyById` release a connection that may have died mid-transaction back into the pool without the destroy flag, so the next checkout fails. Fix: pass the error to `client.release(err)` when ROLLBACK itself failed.

Purpose: make the shared upsert and tenant-context plumbing correct under concurrency and connection failure — the exact scenarios the idempotency/redelivery machinery assumes.
Output: a working race retry, status-on-update, dead-connection destruction, and tests for the first two.
</objective>
