## Phase Goal

**As a** tenant integrator streaming behavioral events, **I want to** get a 202 that actually means my event will be stored — isolated to my workspace and durable regardless of its timestamp — **so that** another tenant's eventId can never silently drop mine and a backfill or a post-September event is never accepted-then-lost.

<objective>
Close the two blocking event-ingestion gaps on Success Criterion #3 (EVNT-01, EVNT-03):

- CR-01 (tenant isolation, HIGH — this is itself a multi-tenancy vulnerability): the client-supplied `eventId` is used unscoped as both the BullMQ `jobId` (global per queue) and the `events` dedupe key (`PRIMARY KEY (id, occurred_at)` + `ON CONFLICT (id, occurred_at)`). A tenant can squat another tenant's UUID and silently suppress their event while the API still returns 202. Fix: scope the jobId to `${workspaceId}:${eventId}` and the DB key to `(workspace_id, id, occurred_at)`.
- CR-03 (durability, + WR-01): `occurredAt` is accepted unbounded but only `events_2026_07`/`events_2026_08` partitions exist with no DEFAULT partition, and neither queue configures retries — any out-of-window event fails the INSERT and dies with zero retries after a 202. Fix: a DEFAULT partition catch-all so no valid job can fail on partition routing, plus `defaultJobOptions` (attempts+backoff) on both queues.

Vertical slice: failing regression tests first (cross-tenant + out-of-window + retry-config), then the DB scoping (new hand-authored migration + worker ON CONFLICT, applied via a [BLOCKING] migrate), then the app-layer jobId scoping + queue durability.

Purpose: workspace isolation is the platform's hard day-one constraint on its highest-volume write path; an accepted event must not be silently lost.
Output: per-tenant idempotency at queue and DB layers, a durable default partition, retry-configured queues, and tests that would have caught CR-01/CR-03/WR-01.
</objective>
