<objective>
Deliver CSV contact import (CONT-02): a streamed upload with column mapping, a full-file dry-run preview, a background apply job that reuses the phase's upsert identity rules, and a completion report with a downloadable error CSV — scaled for 100k+ row files. This is the third contact-ingestion path (alongside the UI and the API), and it reuses the queue/worker foundation from 02-05 and the upsert from 02-04.

## Phase Goal

**As a** marketer, **I want to** build and maintain my contact base through the UI, CSV import, and a server-side API — while my product backend streams freeform behavioral events — **so that** my contacts are created and enriched in real time and every contact carries an accurate subscription status.

This slice adds bulk import: after it a marketer can bring an entire contact base in from a CSV with a safe preview and an error report — a capability that did not exist before. (The wizard UI is 02-08; this plan proves the pipeline end-to-end via tests.)

Purpose: CSV is how tenants seed their base; reusing upsertContactByIdentity keeps identity/suppression semantics identical across all three ingestion paths.
Output: csv_imports + csv_import_rows schema, upload/mapping/dry-run/status/report routes, the apply worker, and idempotency tests.

## Decision surfaced (honored here, not silently dropped)
RESEARCH Open Question 3: this project has no object storage and the worker is a separate process, so a shared filesystem cannot be assumed. This plan STREAMS the uploaded CSV into a `csv_import_rows` staging table on the upload request (row-by-row via csv-parse), and the apply worker reads already-persisted staging rows — so the import survives the marketer navigating away (D-16) without relying on shared storage.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (session) → upload route | Large untrusted file crosses into a streamed parse + staging write |
| queue → CSV worker | Job payload is the sole trusted context; workspaceId re-derived from it |
| worker → Postgres | RLS-scoped upserts + staging reads/writes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07-01 | Denial of Service | oversized / malicious CSV upload | high | mitigate | @fastify/multipart fileSize limit + true streaming (never full-buffer); csv-parse streamed into staging; route-scoped multipart (Pitfall 3) |
| T-02-07-02 | Tampering | double-applied rows on job retry | high | mitigate | UNIQUE (csv_import_id, row_number) staging key makes redelivered chunks no-ops (Pitfall 1) |
| T-02-07-03 | Tampering | reserved-key mass assignment via CSV columns | high | mitigate | Rows flow through upsertContactByIdentity, which strips reserved keys before the JSONB merge (reused from 02-04) |
| T-02-07-04 | Information Disclosure / Elevation of Privilege | cross-tenant write from the CSV worker | high | mitigate | Worker re-derives workspaceId from job.data; withTenant + withTenantTransaction + RLS on csv_import_rows / contacts |
| T-02-07-05 | Tampering | multipart breaking the global JSON body parser | medium | mitigate | @fastify/multipart registered route-scoped only, never at the root (Pitfall 3) |
</threat_model>
