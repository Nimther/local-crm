## Interface context for the executor

- `withTenantTransaction<T>(fn)` (packages/tenant-context/src/index.ts, re-exported via `apps/api/src/middleware/tenant-context.js`): requires an active tenant context (throws "No tenant context set" otherwise), checks out a client from the package's shared `pool`, runs `BEGIN` + `SELECT set_config('app.current_workspace_id', $1, true)`, then `fn(client)`. On error it runs `ROLLBACK` inside a try/catch; if the ROLLBACK throws it records `releaseWithError`; the `finally` calls `client.release(releaseWithError)` — passing a truthy error tells node-postgres to DESTROY the client. That destroy branch (lines 80-94) is the WR-09 behavior under test.
- The `pool` that `withTenantTransaction` checks out from is the singleton exported by `@mega-crm/tenant-context` — import `pool` from there (NOT from `apps/api/src/db.js`, which is a different pool instance) so the test operates on the exact pool the helper uses. That package already registers a `pool.on("error", ...)` handler (CR-03), so a killed idle client will not crash the process; add a defensive no-op `pool.on("error", () => {})` in `beforeAll` anyway, matching the sibling chaos test.
- Test harness (apps/api/src/test/db-fixture.ts): `ensureTestDbMigrated()`, `getTestDatabaseUrl()`, and `createTestPool()` (a fresh Pool at the non-superuser TEST_DATABASE_URL). `vitest.config.ts` already sets `DATABASE_URL` from `TEST_DATABASE_URL` via `test.env`, so the package `pool` is already pointed at the isolated test DB. Each vitest test FILE runs in its own worker process, so ending the shared pool in `afterAll` is safe.
- Same-role `pg_terminate_backend` is permitted for the non-superuser test role against its OWN backends and is already precedented by `rls-pooling-chaos.test.ts` (line 98). The killed backend and the terminator both use the same TEST_DATABASE_URL role.

    Create an integration test proving `withTenantTransaction`'s release-with-error (destroy) branch runs and the pool self-heals. Model the structure on the sibling `rls-pooling-chaos.test.ts`, but the KEY difference is: `withTenantTransaction` must OWN the client that gets killed (so its internal catch → ROLLBACK → release(err) runs), rather than the test releasing a client manually.

    Imports: vitest (`afterAll, beforeAll, describe, expect, it`), `randomUUID` from node:crypto, `{ ensureTestDbMigrated, getTestDatabaseUrl, createTestPool }` from `../../test/db-fixture.js`, `{ withTenant, withTenantTransaction }` from `../../middleware/tenant-context.js`, and `{ pool }` from `@mega-crm/tenant-context`.

    beforeAll: `await ensureTestDbMigrated()`; `process.env.DATABASE_URL = getTestDatabaseUrl()`; attach a defensive `pool.on("error", () => {})` (comment it as: expected — this test intentionally terminates a pooled connection).
    afterAll: `await pool.end()`.

    The transaction bodies only run session/util queries (`SELECT pg_backend_pid()`, `SELECT 1`) and never touch any RLS-scoped table, so a `randomUUID()` workspace id is a valid tenant context — no seeded organization/contact rows are required.

    Single `it(...)` — "a connection killed mid-transaction is destroyed on release and the pool recovers (WR-09)":
    - Create an admin terminator pool: `const admin = createTestPool()`. Wrap the rest in try/finally that ends `admin` at the end.
    - Capture `let doomedPid: number | undefined;`.
    - Assert the faulted transaction REJECTS. Run `await expect(withTenant(randomUUID(), () => withTenantTransaction(async (client) => { ... }))).rejects.toThrow();` where the fn body:
        1. `const { rows: [{ pid }] } = await client.query("SELECT pg_backend_pid() as pid"); doomedPid = pid;`
        2. Kill this exact backend from the admin pool: `await admin.query("SELECT pg_terminate_backend($1)", [pid]);`
        3. Wait for the server-initiated termination to land as a socket event on this client: `await new Promise((r) => setTimeout(r, 100));`
        4. Issue another query on the now-dead client to force the failure: `await client.query("SELECT 1");` — this rejects (connection terminated), the error propagates out of fn, and withTenantTransaction's catch then runs ROLLBACK (which also throws on the dead socket) → releaseWithError is set → `finally` destroys the client via `client.release(err)`.
    - After the rejection, assert `doomedPid` is defined.
    - Prove the backend was genuinely destroyed (not just marked): from the admin pool, `const { rows } = await admin.query("SELECT 1 FROM pg_stat_activity WHERE pid = $1", [doomedPid]); expect(rows).toHaveLength(0);`
    - Prove the pool recovers AND never re-serves the destroyed connection: run several (e.g. 6) sequential recovery transactions, each `const p = await withTenant(randomUUID(), () => withTenantTransaction(async (c) => { const { rows: [{ pid }] } = await c.query("SELECT pg_backend_pid() as pid"); return pid as number; }));` — assert each resolves to a number and that NONE equals `doomedPid` (a destroyed connection can never come back; had the helper wrongly returned the poisoned client to the pool, one of these checkouts would receive it and fail on BEGIN/SET). Collect the pids and assert `expect(pids).not.toContain(doomedPid)`.
    - finally: `await admin.end();`

    Keep the test to this single `it`. Do NOT modify any production file — the WR-09 fix already exists; this test only exercises it.
