<objective>
Create the durable storage spine for triggered flows: five new tables plus the send-ledger, contact-timezone, and workspace-quiet-hours column extensions, with correct RLS from the first migration, then apply the migrations to the live database.

This plan directly implements the FLOW-06/FLOW-07 storage guarantee (immutable published versions; in-flight runs pinned to their entry version) and the FLOW-01 definition-storage requirement. It is the shared foundation every later slice builds on.

Purpose: Everything downstream (send extension, API, engine, triggers, UI) resolves flow state against these tables. The partial unique index on sends is a hard prerequisite for flow-send idempotency (RESEARCH Pitfall 2).
Output: Live tables + applied migrations verified against the running Postgres.
</objective>

## Phase Goal (MVP user story)

**As a** marketer, **I want to** visually build, publish, and run automated triggered chains that send the right email at the right time, **so that** the right contacts receive the right emails automatically — reusing the proven send pipeline, suppression, and frequency cap.

> Vertical-slice note: this phase runs on a mature codebase (Phase 6 of 7). This plan is the unavoidable shared data spine and is itself the FLOW-06/FLOW-07 deliverable (versioned, immutable storage). User-observable slices begin once the engine (06-05) and trigger evaluator (06-06) land; the canvas UI track (06-10/06-11) proceeds in parallel from Wave 3.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker/API → Postgres | Every flow-table read/write crosses the RLS boundary; a missing/misapplied policy leaks or crashes cross-tenant |
| pooled connection reuse | A reused pooled connection can carry a stale/empty app.current_workspace_id GUC into the next query |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
