<objective>
Close blocking gap CR-02 (06-VERIFICATION.md 2026-07-10, roadmap success criterion 2 / FLOW-02): when a marketer publishes a segment-triggered flow choosing «Опубликовать только для новых» (enrollExisting=false), the ONLY thing preventing every current segment member from being enrolled is a "seed the snapshot as seen" step — and today that step runs in a SEPARATE BullMQ job AFTER publishFlow commits. The flow becomes live/sweepable/event-checkable the instant publishFlow commits, so a sweep tick in the race window (or a lost/failed seed job) diffs the full membership against an EMPTY snapshot and mass-enrolls the whole segment — potentially 100k+ unsolicited flow emails against the marketer's explicit choice. For an email-marketing platform whose CLAUDE.md names suppression/compliance as a core constraint, this is a compliance/reputation-grade failure.

Repair the complete observable behavior as one vertical slice using the SAFE atomic fix from CR-02: make the enrollExisting=false snapshot seed a single bounded INSERT...SELECT that runs INSIDE publishFlow's own transaction (so the snapshot is committed atomically with status='live' — no window exists where the flow is live but the snapshot is empty), and have the publish route stop enqueuing the async job for that branch. First a failing repository-level regression test proving the seed is synchronous/atomic (snapshot fully populated, zero runs, immediately after publishFlow returns), then the repository + route fix.

Purpose: A marketer's explicit "only new entrants" choice must be honored with zero race window — the wrong contacts can never enter the flow.
Output: an atomic enrollExisting=false seed inside publishFlow, a route that only enqueues the async job for enrollExisting=true, and a regression test that fails under the current async-seed code.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Web publish action -> API publishFlow | An Owner/Admin publishes a segment-triggered flow with an explicit "only new entrants" (enrollExisting=false) choice; the API must guarantee that choice is honored with no window in which existing members can be enrolled. |
| API publish transaction -> Postgres | The instant the flows row commits with status='live', the flow is discoverable by the cross-tenant segment sweep and by every event-driven segment re-check; the do-not-enroll snapshot must be committed in the SAME transaction, not after. |
| Async BullMQ enroll job -> worker | An async seed job can be delayed (race), lost (retries exhausted), or run after a sweep tick — any of which defeats the marketer's choice. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-18-01 | Tampering (of the marketer's explicit "only new entrants" choice) / Compliance | publishFlow + publish route enroll seed | high | mitigate | Seed the do-not-enroll snapshot atomically inside publishFlow's own transaction so the flow can never be live with an empty snapshot; drop the async job for that branch. Regression test proves snapshot fully seeded + zero runs synchronously. |
| T-06-18-02 | Denial of Service / mass unsolicited send (reputation) | flow-segment-sweep enrolling against an empty snapshot | high | mitigate | Removing the post-commit window means no sweep tick can ever observe a live-but-unseeded flow; the sweep's full-membership diff always sees the seeded rows. |
| T-06-18-03 | Elevation of behavior (bounded resource use) | publishFlow in-transaction INSERT...SELECT | low | accept | The seed is a single bounded (statement_timeout 60s) INSERT...SELECT holding the flows FOR UPDATE lock for its duration; acceptable for a publish action and matches the worker's existing bounded-seed discipline. |

No new runtime dependencies are added (no npm/pip/cargo installs) — supply-chain threat T-06-18-SC is not applicable to this plan. No migration is added.
