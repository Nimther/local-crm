<objective>
Extend — do not fork — the existing send pipeline so a flow send-node can dispatch through the SAME email-triggered queue, per-tenant token bucket, and pre-send gate as campaigns, with its own durable idempotency guarantee (the sends_flow_run_node_unique partial index from 06-01). This is the single most important structural decision in the phase (RESEARCH Pattern 1): a forked flow-only dispatcher would silently reintroduce the "two rate limiters" bug the project already avoided.

Purpose: Deliver FLOW-01's send node reliably and idempotently (FLOW-07 — a redelivered wake can never re-send). Frequency-cap disposition for flow sends is LOCKED here as skip (reuse evaluatePreSendGate unmodified), matching campaign behavior; deferral is explicitly out of scope for v1 (CONTEXT open discretion resolved).
Output: claimFlowSend/recordFlowStepResult + processSendJob kind:'flow' branch, proven by a redelivery idempotency test.
</objective>

> MVP user story (phase): **As a** marketer, **I want to** run automated triggered chains that send the right email at the right time, **so that** contacts reliably receive flow emails. This slice makes the pipeline flow-aware; TDD because idempotency has a crisp redelivery→single-send assertion.

  <behavior>
    - First dispatch of (workspace, flowRun, node, contact) inserts a sends row kind='flow' and sends one email.
    - A second (redelivered) dispatch for the same (workspace, flow_run_id, node_id) hits ON CONFLICT DO NOTHING → no second SendGrid call, no second row.
    - A contact failing the pre-send gate (suppressed/unsubscribed/frequency-capped) → recordExcluded (kind='flow') and outcome "excluded", no SendGrid call.
    - A 429/5xx from SendGrid → claim released, outcome "rate_limited" (retry re-claims); a 4xx → recordFlowStepResult failed, no false 'sent'.
  </behavior>
  <implementation>claimFlowSend uses ON CONFLICT (workspace_id, flow_run_id, node_id) DO NOTHING against sends_flow_run_node_unique. recordFlowStepResult marks the sends row terminal AND (same transaction) is callable to append the flow_run_steps row / advance the run — the run-advance worker (06-05) supplies the advance callback; here recordFlowStepResult just owns the sends-terminal write so the send path stays self-contained.</implementation>
</feature>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BullMQ redelivery → dispatch | At-least-once delivery means the same send job can arrive twice; the DB claim is the only durable dedupe |
| worker → SendGrid | Tenant BYO key; per-tenant RPS must be enforced in one place |

| T-06-03-02 | Denial of Service | a second flow-only rate limiter bypasses per-tenant RPS | high | mitigate | reuse the single consumeTenantToken limiter instance for every kind (RESEARCH Don't Hand-Roll); no new limiter constructed |
