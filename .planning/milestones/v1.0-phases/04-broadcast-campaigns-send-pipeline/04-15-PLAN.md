<objective>
Close the UAT Test 3 blocker: the campaign builder cannot select a segment audience because the segment picker requests the segment list with a page size the shared Zod query schema rejects, so Fastify returns 400 before the handler runs.

Root cause (see debug session): three Phase-4 UI call sites request list endpoints with a page size of two-hundred, while `segmentListQuerySchema` (packages/shared-schemas/src/segment.ts:152) and `campaignListQuerySchema` (packages/shared-schemas/src/campaign.ts:37) cap `pageSize` at `max(100)`. One call site is the visible blocker (segment picker), two fail silently (blank segment names on the campaigns list; the D-03 scheduled-campaign warning never renders — a latent UAT Test 12 failure).

Fix: introduce a single shared exported constant `EXHAUSTIVE_LOOKUP_PAGE_SIZE = 200` in shared-schemas, raise both list-query schema `max` bounds to reference it, and repoint all three client call sites to import that same constant. This preserves the authored intent (fetch up to two-hundred rows for a small, bounded, client-side exhaustive lookup) instead of shrinking the lookup ceiling, and makes the client/server bound a single source of truth so the mismatch cannot recur. A regression test asserts both list schemas accept the exact constant the client uses.

Purpose: A marketer can create a campaign again (pick a segment audience), campaign rows show real segment names, and the segment editor warns before editing a scheduled campaign's audience (CAMP-01, CAMP-02, D-03).
Output: One shared pagination constant, two widened list schemas, a contract regression test, and three call sites wired to the constant.
</objective>
