## Phase Goal

**As a** marketer, **I want to** trust that a broadcast never double-sends on a retry and never reports a rejected email as delivered, **so that** my send counts and my recipients' inboxes are both correct.

<objective>
Close CR-03 and CR-04 (verification truth #4, SEND-06/SEND-07). Today `processSendJob` wraps the dispatch claim INSERT, the external SendGrid HTTP call, AND `recordSendResult` in ONE `withTenantTransaction` (send-dispatch.ts:133-273): a crash after SendGrid accepts but before COMMIT rolls back the 'dispatching' claim, so the redelivered job re-sends — a genuine duplicate (CR-04). Separately, the response handler has only two branches — 429/5xx → rate_limited, everything else → recordSendResult('sent') — so SendGrid 400/401/403/413 rejections are recorded and displayed as delivered, and status='failed' is dead code (CR-03).

This plan (1) splits dispatch into three units — commit the 'dispatching' claim in its own transaction, call SendGrid outside any transaction, record the terminal result in a second transaction; (2) makes a redelivered job that finds an already-committed 'dispatching' claim record it as failed rather than re-calling SendGrid (closing the duplicate window; at-most-once wins over duplicate for marketing mail); (3) releases the claim on 429/5xx so a clean retry re-attempts; and (4) adds the missing `status >= 400` → failed branch.

Purpose: make "no duplicate emails on retry" and "no rejected send recorded as sent" actually true.
Output: restructured `processSendJob`, an `interrupted` result + `releaseDispatchClaim` in the ledger, and durability tests exercising crash/4xx/429 paths.
</objective>
