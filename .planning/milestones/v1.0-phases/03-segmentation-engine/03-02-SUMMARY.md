# Phase 3 Plan 2: Segmentation Engine Live over HTTP Summary

**The `segments` table (RLS-scoped) plus a `segment.repository.ts` evaluation engine (count/listMembers/isMember, one compiled WHERE from `@mega-crm/segments-core`, three tails) and a registered Fastify `segments` module -- CRUD, a statement-timeout-guarded `preview-count`, a paginated member list, and a loose-index-scan event-name picker -- proven by 16 new integration tests (126/126 green across `apps/api`).**

## Accomplishments
- `segments` table live in Postgres: `id`, `workspace_id` (FK, cascade), `name`, `definition` (jsonb), `created_by_user_id`, nullable `member_count`/`member_count_at` (D-11), timestamps -- `FORCE ROW LEVEL SECURITY` + `workspace_isolation` policy (0012), `idx_contacts_tags_gin` added for GIN-accelerated `has_tag`/`not_has_tag` containment queries.
- `segment.repository.ts` implements the unified evaluation contract from 03-RESEARCH.md Pattern 2: `countSegmentMembers`, `listSegmentMembers`, `isContactInSegment` all compile the SAME `SegmentDefinition` through `compileSegmentDefinition` and differ only in their SQL tail -- proven identical by `unified-engine-contract.test.ts`. Full CRUD (`createSegment`/`listSegments`/`getSegment`/`updateSegment`/`deleteSegment`) recomputes `member_count`/`member_count_at` on create and on any definition-changing update (D-11/D-13). `SegmentConflictError` is scaffolded (unused this phase) for Phase 4/6's future restrict-when-referenced (D-14).
- `event-names.repository.ts`'s `listObservedEventNames` uses the loose-index-scan recursive CTE from 03-RESEARCH.md Pattern 3 -- not a naive `SELECT DISTINCT`, which the phase's own benchmark measured at ~1900x slower at scale.
- `segments.routes.ts` registers the full HTTP surface: `GET/POST/PATCH/DELETE /api/workspaces/:slug/segments`, `GET /segments/:id`, `GET /segments/:id/members` (contacts-shaped pagination), `POST /segments/preview-count` (2000ms `SET LOCAL statement_timeout`, Postgres `57014` mapped to `200 { degraded: true }`), `GET /segments/event-names` -- all behind the established `resolveWorkspaceMember` 404-not-409 auth pattern, all Zod `safeParse` -> 400 on invalid input.
- 16 new integration tests across 4 files (attribute conditions, behavioral conditions, unified engine contract, preview-count + CRUD + event-names + auth-oracle + timeout-mechanism) -- all green; full `apps/api` suite (126 tests) green; `npm run build` clean across the entire workspace.

## Decisions Made
- Renamed drizzle-kit's auto-generated migration filename (`0011_dapper_nick_fury.sql`) to `0011_segments.sql` per the plan's explicit naming requirement, updating `meta/_journal.json`'s tag to match (drizzle-kit `migrate` resolves the SQL file by journal tag, so filename and tag must agree, or `migrate` fails to find the file).
- `createSegment`/`updateSegment` pass the `definition` object directly as a jsonb bind parameter (no `JSON.stringify`) -- matches `contact.repository.ts`'s existing convention for the `properties` jsonb column; node-postgres serializes plain JS objects to JSON automatically for jsonb columns.
- The preview-count degraded-path test proves the `SET LOCAL statement_timeout` -> Postgres `57014` mechanism directly (a raw `pg_sleep` inside `withTenantTransaction`), rather than forcing an HTTP request past 2000ms -- a segment definition has no way to request an artificial delay, so this is the closest faithful simulation of D-08's fallback path without weakening the production timeout value.
